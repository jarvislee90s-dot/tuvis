## 1. 目标、范围与权威关系

### 1.1 用户目标

小白安装 Tuvis 后，可以直接尝试向 Codex Desktop 会话发送消息，不需要理解版本白名单或预先开启实验发送；能够发现“自动适配”，遇到问题能从发送现场查看状态、排障并主动报告。

任何一次失败都应解释其含义，不能把超时当成未送达，不能自动重发。界面结束等待后，原动作仍须有可查询的记录和恢复出口。

### 1.2 两个相互衔接的范围

1. **Codex Desktop 自动适配与发送恢复**：默认开启、状态入口、审批硬门、30 秒前台预算、迟到结果与 Unknown 恢复、复用主分支的打断能力。
2. **全工具适配问题反馈**：本地结构化诊断、用户预览、公开 GitHub Issue、故障指纹与 GitHub Actions 去重。诊断入口覆盖 Tuvis 所支持的全部 harness；本稿不因此扩大其他工具的自动写入能力。

不自建接收 API、报告数据库或维护者管理软件。GitHub 是报告的公开提交、编号和处理入口。

### 1.3 已确认的产品决定

| 主题 | 决定 |
| --- | --- |
| 默认行为 | 自动适配默认开启，首次使用一次轻提示；发送区提供可点击状态入口 |
| 生命周期 | 同指纹、同能力成功取证后跨重启复用；暂时失败允许再次尝试，不因网络抖动永久关闭通道 |
| 路由 | Desktop 归属会话始终使用 Desktop IPC，不自动转 headless |
| 审批 | 待审批时新普通消息保留草稿，不自动入队；审批卡处理，或先打断再发送意见 |
| 打断后队列 | 原有未投递队列保留但暂停，由用户明确恢复 |
| 等待上限 | 一次发送的前台总等待最多 30 秒；Unknown 不自动重发 |
| 人工继续 | 只读核对仍无结论时，可明确选择“仍要重新发送（可能重复）”；旧动作继续保留待确认 |
| 报告 | 本地自动记录、用户主动提交公开 Issue；不自动上传 |
| 去重 | 完整故障指纹相同，最终只保留一个开放 Issue；原 Issue 关闭后允许再次提报 |
| 自动化与保留 | 使用 GitHub Actions 收敛重复；公开 Issue 保留历史；本地诊断滚动保留 7 天 |

“发错窗口”曾指讨论误发到官网聊天，不是新增的 Tuvis 错会话投递实测故障，不能作为本设计的事故依据。

### 1.4 与旧文档、主分支的衔接

项目宪法仍是 `docs/MASTER-PLAN.md`。本稿落实其安全递进、能力差异显式化、版本门控＋探针＋降级要求。

本轮用户裁决替代以下下层旧口径，实施时必须同步修订旧规格与文案，不能同时保留互斥契约：

| 旧口径 | 本稿口径 |

| 明确 NotSent 可自动转 headless，包括已验证 build 的例外 | Desktop 会话不自动转 headless；无头原生会话按自身路由处理 |

## 2. 架构与事实源

| 单元 | 单一职责与可复用基础 |
| --- | --- |
| 适配协调器 | 解析版本身份、复用能力证据、安排探测、输出适配状态；复用 adapter/probe 与现有账本 |
| Desktop 发送编排 | 校验目标、设备、审批、队列和预算；管理单次动作，不承担报告上传 |
| 动作与确认记录 | 持久化逻辑发送、投递阶段、关联键、Unknown 和人工解除记录；复用 codex_actions |
| 只读确认器 | 查询原动作、关联迟到回执和目标线程正式消息；绝不发送测试消息或重新投递原消息 |
| 通用诊断生成器 | 接收白名单结构化故障事件，输出安全诊断摘要和故障指纹 |
| 报告界面 | 用户预览、补充描述、查找已有 Issue、打开 GitHub、复制报告 |
| GitHub 去重工作流 | 重算报告指纹，关联并关闭重复开放工单；不决定工具能力 |

能力证据、连接健康和单次动作结果是三种不同事实。终端类交互遵守既有屏读权威及动态核验纪律；Desktop 原生交互依据 IPC 回执与新鲜目标快照，不能以本地发送记忆代替。

## 3. 自动适配状态流

### 3.1 能力证据的复用键

Codex 使用 `platform | desktop_build | bundled_cli_id | probe_epoch`，再按能力区分 state、send、command/file 决策证据等。“同 build”不能忽略随包 CLI；连接 epoch 用于隔离在途结果，不作为跨重启复用键。

其他 harness 的报告使用各自能获得的版本指纹，不强造 Desktop build 字段。

### 3.2 成功证据与失败观测分离

- 一次成功取证建立可持久复用的证据，不因重启或后续超时、断链被失败行覆盖。
- 运行失败更新连接健康、最后失败阶段和单次动作结果，不把历史成功改成“该版本没有能力”。
- 新指纹或探测规则版本变化时，重新取证；旧指纹证据留作历史，不跨身份使用。
- 没有成功证据时，暂时失败按既有 30 秒→2 分钟→10 分钟退避，在下一次用户触发时重试，无持续后台重探定时器。
- 明确协议拒绝须区分“本次不支持”和“暂时不可达”，不得继续强发。即使保留历史成功证据，当次操作仍可以不可用；证据不是绕过实时守卫的许可证。
- 账本应能同时表达最后成功证据和最近失败观测，不能继续以一个可覆盖状态字段承担二者全部语义。涉及存量开发库时需幂等兼容，并保留最近几轮代际隔离守卫。
- 成功证据须保存复用所需的安全数据及其规则版本。例如 schema 只存一个文件指纹不能重建决策词，需持久保存经过校验的决策词证据；仍在每个 pending 上求交集，不能因缓存直接批准。

### 3.3 触发与关闭

| 情景 | 行为 |
| --- | --- |
| 首次打开未知版本会话详情 | 按需安排只读探测；成功即缓存，不重复做完整兼容探测 |
| 首次发送 | 缺失的必要取证纳入同一次 30 秒预算；发送本身提供真实写证据，不另发测试消息 |
| 已有成功证据再次打开或重启 | 复用能力证据；重建实际连接和核对目标仍是必要操作，不算重复兼容探测 |
| 首次遇到 command/file 审批 | 缺少可复用 schema 决策证据时只读取证；每个 pending 仍需核对本身的决策词和上下文 |
| 关闭自动适配 | 阻止新的未知 build 自动探测和普通发送；已验证 build 按已验证能力运行 |
| 关闭时有在途/待确认动作 | 不撤回已投递消息、不抹除动作；允许原动作的有限收尾和明确的只读结果核对 |
| 再次开启 | 恢复按需工作，复用有效成功证据；不自动发送任何草稿或暂停队列 |

“不重复探测”不包含跳过每次操作的设备权限、目标身份、owner 代际、pending 和实时状态检查。

### 3.4 用户界面

首次接触此功能时出现一次可关闭的轻提示：“已开启自动适配；新版本会按实际能力尝试连接，遇到问题可在发送区查看详情。”记录用户已阅读，不随每个 build 重复弹出。

发送区状态入口统一使用“自动适配”，可呈现“检查中”“已适配”“连接异常”“已关闭”等状态，点击展开详情。首次提示和详情不能宣称已解锁全部能力。

详情包含版本与指纹摘要、已取证能力、当前连接状态、最近失败、关闭/开启、手动重新检查和排障入口。手动重新检查是只读取证，不包含测试发送或审批。

开启后允许尝试发送时，横幅不得同时宣称“暂不能远程发送”。底层 read_only 只代表已取证能力，须与当前可尝试的产品操作区分。

schema 证据安装、失效或连接代际变化后，必须重新计算并发布已跟随线程的审批策略。GET、SSE 首快照、后续推送及提交守卫同源，不能出现“第一次进入禁用，重新进入才解锁”。旧代际异步结果不得安装到新连接、解锁新卡或污染新指纹账本。

## 4. Desktop 发送、审批与队列边界

### 4.1 路由硬规则

Desktop 归属会话只走目标线程的 Desktop IPC。初始化失败、方法不支持、无 owner、明确 NotSent 或超时均不自动转 headless。发送现场不再将“开启无头注入”作为 Desktop 发送失败的解决办法。

无法唯一确定目标会话，或无法确认当前可安全发送的状态时，零投递，保留草稿并给出可理解原因。不得猜 owner、猜线程、广播写入或把普通文本改成审批决策。

### 4.2 服务端守卫

普通发送在入队判断和真正写出前都须核验：设备仍有效、目标一致、连接/owner 代际有效、无待处理原生请求、队列未被人为暂停、无禁止发送的未知结果屏障。

任何未处理的原生请求，包括不支持的审批/权限/问答，不得仅因 runtime_status 为 idle 而放行普通消息。无法确定 pending 状态时按未确认处理，不能借空本地缓存证明没有审批。

前端禁用按钮只是展示，服务端应对直接 HTTP 请求及后台队列 flush 同样执行硬门。

### 4.3 各种情景

| 情景 | 新普通消息 | 已在队列中的普通消息 |
| --- | --- | --- |
| 正常运行中，无 pending | 保留既有忙态 FIFO 排队行为，返回明确“已排队” | 按正常规则派发 |
| 等待审批/其他原生请求 | 拒绝进入发送队列，保留输入草稿，提示“先处理审批，或打断后发送” | 冻结派发，不被 idle 假象穿透 |
| 审批正常处理后 | 新鲜状态确认 pending 解除后恢复发送入口 | 未发生打断/Unknown 时，按原 FIFO 和可输入态规则接力 |
| 用户选择打断 | 等待既有打断闭环，不把受理当完成 | 保留但暂停，不在打断后突然自动发送 |
| 打断已确认、pending 已解除 | 用户可再次点击发送其意见 | 只有用户明确“继续发送”才恢复 |
| 打断结果未知 | 不宣称已结束；提供核对和排障 | 继续暂停 |

新意见不得悄悄越过先前队列。打断后用户发送新意见时，若旧队列仍有内容，明确选择“先恢复队列”或“保留旧队列暂停，本条先发送”；后者须是用户的显式选择，动作记录保留该选择。

command/file 决策继续使用当前策略与 pending 决策词的交集。对象形式的权限扩大决策不自动开放，权限/模式等未取证能力不因自动适配开启。处理不了的卡复用主分支打断能力，不另造终端二元按键兜底。

## 5. 30 秒前台等待与动作生命周期

### 5.1 一次逻辑发送

用户点击发送时生成并保存稳定的 actionId 与 clientUserMessageId；同一次网络重试、刷新页面后的核对沿用原 actionId。另建逻辑消息必须显式建立新动作。原有正文冻结、签名与幂等规则保留。

正文及本地关联信息仅进入既有本地动作/队列存储，不进入公开诊断摘要。

30 秒从点击发送开始计时，包含连接、必要探测、owner/审批复核、提交回执和必要确认；即使网络无响应，前端也必须在该窗口结束转圈。后端从接收请求起设不超过 30 秒的编排预算，并在能取得可靠剩余预算时进一步缩短；子步骤只能使用剩余预算，不能逐层重新获得 30 秒。

移动设备与服务端使用各自单调时钟，不假设两端时钟同步。前台到期不证明后端已经停止；网络延迟、部分写入或无法确认取消生效时必须呈现待确认，而不是承诺“30 秒后绝不可能送达”。

### 5.2 前台结果

| 结果 | 判据与界面 |
| --- | --- |
| 已排队 | 本地持久队列明确接受；立即结束等待，显示位置，可撤回；不等整轮运行结束 |
| 明确未送达 | 可证明零写入或明确拒绝；保留草稿，提供“重试”和“报告问题” |
| 已受理 | 对端明确受理；显示“已受理/正在执行”，不宣称本轮已完成 |
| 已确认送达 | 原消息的正式回显或等价的强关联证据；发送与任务执行完成分别展示 |
| 发送结果待确认 | 已可能写出但未取得足够证据；结束转圈，保留可见消息和原动作，提供“检查是否送达”“报告问题” |

确定未投递前的排队/校验等待到期，可取消尚未写出的本次提交。已经开始或不能排除写入后，前台取消等待不得删除账本、丢弃关联关系或使动作自动回队重发。

明确返回“已排队”后，这次前台等待已结束。正常队列允许在当前 Turn 结束后再派发，不被用户最初点击后第 30 秒清掉；队首真正开始派发时建立独立的有界后台派发预算，结果通过动作状态更新，不能重新让前台无限转圈。

### 5.3 有界后台收尾

前台等待者与派发动作解耦。等待到期后不自动发起新的尝试或补发；已在处理的原尝试按服务端预算有界收尾，可能已写出时继续等待回执或只读核对，不能虚构取消成功。首版主动收尾窗口上限为自实际派发编排开始起 120 秒（排队驻留时间不占这个窗口）。主动收尾结束后仍保留持久动作，用户可再次发起有界只读核对；不永久占用 RPC、线程锁或无限后台轮询。

不能继续用“RPC 15 秒超时就删除全部 pending 关联”实现此契约：普通调用超时后，已可能投递的 mutation 须保留可关联的迟到结果槽位或等价记录。记录绑定原 envelope、连接代际、目标和 actionId，限量、到期清理，连接退出和等待者丢失均安全收尾。超出容量应在投递前明确拒绝，不能投递后因没有核对槽位而失去跟踪。

迟到证据只更新对应原动作，不注入当前新卡；同一证据只能使该动作收敛一次。旧连接的真实回执可作为原动作证据，但不得被当成新连接上的 owner、审批或能力证据。

前台 30 秒、后台收尾 120 秒是本设计的首版工程预算；不是等待任务执行完成的时限。长任务正常运行可以超过这些时间。

## 6. Unknown 的核对、屏障与人工继续

### 6.1 自动或用户触发的只读核对

核对只针对原目标线程和动作，顺序是：读取持久动作已有结论 → 收敛有效迟到回执 → 从新鲜目标状态读取原消息的正式回显。首版单次用户核对窗口上限 10 秒，可提前返回。

优先使用 clientUserMessageId、明确绑定的 turnId 和正式 userMessage 关联；禁止用“出现相同文字”“消息数增加”“任意 revision 前进”或“线程现在 idle”判定原消息送达。开场临时 input 投影、别的 Turn 或另一个会话的内容不算证据。

| 核对结果 | 原动作与屏障 |
| --- | --- |
| 有明确零投递证明 | 原动作收敛为未送达，解除对应投递不确定屏障 |
| 找到原消息或有效受理回执 | 收敛为送达/已受理；普通运行顺序限制仍依据绑定 Turn 的实时状态，不立即 flush 下一条 |
| 无证据、快照缺失/过期、查不到原消息 | 继续待确认，保留屏障；“没找到”不等于“没发送” |
| 找到绑定 Turn 的完成/中断证据 | 按新鲜目标状态解除对应运行限制；pending 和人为暂停仍单独检查 |

无 turnId 时不得无限依赖“某个 Turn 完成”来清 Unknown；应继续使用原消息关联，或进入下述人工出口。

### 6.2 明确人工继续

只读核对仍无结论时，展示“仍要重新发送（可能重复）”。用户须看到：原消息仍可能迟到；再次发送会产生一条新消息；本操作不是证明原消息未送达。

服务端记录原 actionId、人工解除时间与原因、新 actionId 的关联；只允许原设备或仍具操作权限的设备显式操作。原动作保持 Unknown，不能改写成 NotSent/Cancelled。相同人工继续请求幂等，只建立一个新动作；刷新、代理重试不得多次建立新消息。

新动作仍须通过目标、pending、打断、忙态和队列守卫。人工继续不允许强行穿透审批或开启无头。旧动作迟到后可补记真实结果，但不得重新取得新动作的派发权、复活旧的自动重发或撤销用户的队列暂停选择。

这一出口接受用户明确知情后的重复风险，不承诺 exactly-once，也不假设 Desktop 会按 clientUserMessageId 去重。

## 7. 全工具本地诊断与预览

### 7.1 入口及职责

发送错误、待确认提示、适配详情提供“报告问题”；设置“帮助与诊断”提供同一入口并可选择受影响工具。普通用户不需要定位日志文件。所有受管工具可以生成基础报告，自动填写其已知结构化字段；无法取得的字段标记未知，不猜版本或根因。

上报成功与否不得影响当前发送、审批或只读核对的结果。

### 7.2 公开摘要白名单

| 字段 | 规则 |
| --- | --- |
| 报告格式、故障指纹算法版本 | 固定版本，用于解析和兼容 |
| 本地报告编号 | 随机编号，仅标识这份报告；不含设备/会话身份 |
| Tuvis 版本/开发提交号 | 正式版号；开发版附提交号，避免多个开发实现混成同一问题 |
| harness 标识、运行形态、版本指纹 | 从 adapter 的已知字段提取；Codex 包含 Desktop build 和随包 CLI |
| 系统信息 | 平台、系统主要版本、架构；不含机器名、用户名、网络地址 |
| 操作与失败阶段 | 受控枚举，如读取/发送/命令审批、握手/目标发现/状态解析/等待回执 |
| 错误码、细分特征码 | 从受控词表/结构分类产生；不抄原始自由错误文本 |
| 探测状态、证据来源、最近结果 | 区分历史成功、当前连接失败和从未取证；不能伪称 verified |
| 耗时、投递确认状态 | 数值与枚举；无消息内容和本地动作关联键 |
| 可选协议结构特征 | 仅经过定义的形态码，例如必要字段缺失类别；不包含原始帧或其正文 hash |

严禁自动附带消息正文、命令、文件/项目/安装路径、threadId、owner/client/envelopeId、设备名、cookie、访问密码、token、认证文件、环境变量、完整日志或数据库。用于本地核对的正文 hash、路径和动作上下文不得被报告生成器顺手序列化。

版本字符串须由各工具解析器提取并有长度/字符约束；不把异常原始输出当版本上传。通用日志没有统一脱敏器，本设计不把“读取整个日志后试着清洗”当成安全方案。

用户可补充问题描述。预览页明确报告公开、需 GitHub 账号提交，并提示不要填写正文、命令、路径或凭据；对可识别的敏感模式给出阻止提交/编辑提示。不得承诺能够从任意自然语言识别全部敏感信息，用户仍需确认实际公开内容。

### 7.3 本地记录与失败处理

独立诊断记录滚动保留 7 天，并同时设总容量上限（首版 1000 条或 10 MiB，先达到者触发清理）。报告预览冻结当前安全摘要，避免后来事件覆盖用户正在确认的内容；未提交草稿同样最多保留 7 天。

这套保留策略只管理新诊断存储，不删已有业务账本、未解决动作屏障或各 harness 的原始会话。诊断生成/落盘失败不得阻塞业务操作。

网络/GitHub 查询失败时保留本地报告，显示“未提交/查重暂不可用”，提供手动重试和复制摘要；不后台自动上传。超过本地保留期后如实提示原诊断已过期，不补造历史事实。

## 8. 故障指纹：防止完全相同问题重复开放

### 8.1 归并维度

规范化元组为：

```text
指纹算法版本
+ harness 标识 + 运行形态
+ harness 版本指纹
+ Tuvis 版本（开发版含提交号）
+ 平台 + 系统主要版本 + 架构
+ 操作类型 + 失败阶段
+ 标准错误码 + 已定义细分特征码
+ 投递确认类别 + 已知的协议形态码
```

对稳定排序后的规范化对象计算 SHA-256，得到 issue_fingerprint。版本规范化只移除 adapter 已确认的格式差异，不能丢失 alpha/beta 等实际版本段。缺省字段的表达和枚举映射在客户端及工作流中一致，维护固定测试向量。

时间、用户描述、具体耗时、网络地址、机器/会话/动作 ID 及原始错误文本不进入指纹；报告编号也不进入指纹。这样同类用户的不同描述不会制造新故障类。

“完整特征相同”是已采集结构化特征相同，不等于系统已证明根因相同。关键版本、错误细分或操作特征缺失，无法可靠区分时，报告标记“待分类”，不凭一个宽泛 unknown/timeout 自动吞并其他问题。维护者可修正结构分类后重新归并。

### 8.2 示例

| 情况 | 是否合并开放报告 |
| --- | --- |
| 相同工具版本、Tuvis、平台、发送阶段和同一细分错误；用户描述不同 | 是 |
| 同版本组合，一个读取解析失败，一个命令审批不支持 | 否 |
| 同版本组合，同为发送错误，但一个明确未投递、一个结果未知 | 否 |
| 不同 harness，或同 harness 的 Desktop 与 CLI | 否 |
| 相同完整指纹，原工单已经关闭 | 可以新建，记录为复发并关联历史 |
| 信息不足，只有相同工具名和 timeout | 不自动归并，进入待分类 |

诊断报告、用户上传和重复次数均不能自动提升能力证据；从报告升级 shipped/verified 仍需维护者单独核验。

## 9. 公开 GitHub 提交与自动去重

### 9.1 用户提交流程

首版目标仓库为当前公开项目 `jarvislee90s-dot/tuvis`，新增专用适配报告模板。用户主动点击“报告问题”后：

1. 本地生成并预览安全摘要，说明公开范围，允许补充描述。
2. 用户选择“继续到 GitHub”后，以公开指纹查询相同指纹的开放工单；外发查询前已经告知公开摘要，不携带敏感本地信息。
3. 找到同指纹开放工单：显示编号和“查看已有问题并补充”，不引导新建；由用户登录后在原工单评论。
4. 没有开放工单：打开预填标题、专用模板及安全正文的 GitHub 新建页面，由用户确认提交。
5. GitHub 实际提交后展示的 `#编号` 才是反馈编号。Tuvis 打开网页时仅显示“已打开提交页面”，不能谎称已上传成功或自动知道用户是否提交。

本地报告编号仅用于草稿和复制，不能冒充 GitHub Issue 编号。首版不收集用户 GitHub 凭据，不在 App 内置维护者 token，也不要求用户授予仓库写权限。

查重使用公开仓库能力，无需用户 PAT；遇到限流、离线或查询不确定时不能显示“确认不存在”。允许用户在明确告知查重不可用后继续到模板页面，由仓库端最终去重。

预填内容必须控制长度，并始终提供“复制报告＋打开模板”的备用方式，处理 URL 过长、浏览器拦截或预填失败。机器字段用可解析的版本化结构段携带，用户自然语言描述与机器段分开。

### 9.2 不承诺提交前的严格唯一

客户端查询不是原子锁。两位用户同时查询、GitHub 搜索索引延迟、绕过客户端手动提交，都可能暂时产生多个开放 Issue。用户已接受：**自动化处理完成后，每个可识别完整指纹只保留一个开放工单**。

Actions 被禁用、平台故障或权限不足时可能暂时无法收敛，不能宣称所有时刻都严格唯一；恢复后补扫处理。普通反馈不受诊断指纹强制限制，缺失机器段的手工 Issue 保留给人工分类。

### 9.3 GitHub Actions 去重规则

工作流在默认分支部署，监听报告的 opened、reopened、edited 及必要的分类标签变化，并提供定期补扫和维护者手动补扫。

- 不信任用户粘贴的指纹值：校验有界机器字段，按相同规范重新计算。
- 只处理专用适配报告或维护者明确归类的工单；工作流自行补上分类标签，不依赖普通用户有加标签权限。
- 同指纹有多个开放工单时，编号最小的保留为主工单；其余关联主工单并以重复问题关闭，不删除正文或评论。
- 如相同指纹只有已关闭历史，允许当前新工单开放，添加复发关联，不自动重开旧工单。
- 主工单被重开、报告被编辑改变分类时也重新收敛；关闭前重读目标状态与字段，避免按过期分类处理。
- 使用串行化归并流程，避免两个任务互相关闭主工单。每次有效运行都扫描当前相关开放报告并分页处理，不只处理触发的一个编号；即使并发队列合并事件，遗漏报告也会被本轮或定期补扫覆盖。
- 重跑须幂等：相同关联评论不重复刷屏，重复标签不抖动。自动化不可用时保留用户报告，不影响 Tuvis 业务链路。

工作流仅授予所需的 issues 写权限和必要读取权限，使用 GitHub 提供的受限工作流凭据，不引入用户端秘密。Issue 标题、正文、字段都是不可信数据，不得拼接进 shell 命令、执行代码、安装依赖或按用户提供的任意 URL 取资源。

### 9.4 公开历史保留与既有工作流

公开 Issue 及其关闭历史保留，不按 30 天自动删除。关闭只是处理状态，不代表数据删除；预览页须说明这个公开保留边界。

当前 `.github/workflows/stale.yml` 会在闲置后自动关闭 Issue。适配报告须从这一自动关闭流程中豁免，避免未解决问题被自动关掉后，用户再提交而失去主工单。维护者仍可按实际处理结果关闭工单。

## 10. 与代码基线的差距及接口责任

以下是设计所要求的变化范围，不是逐步执行计划：

| 基础 | 现状与本稿要求 |
| --- | --- |
| adapter/probe 与探测 DAO | 已有指纹、单飞、代际隔离；需把持久成功证据与最后失败观测分离，避免重启后重复成功探测 |
| remote/codex_ipc 与控制 router | 已有动作幂等、队列、兜底；需对 Desktop 全面禁 headless fallback，建立服务端 pending 硬门和打断后暂停规则 |
| connection pending 与动作账本 | 已有 3 秒初始化、15 秒 RPC 超时；需纳入统一截止时间并支持有界迟到关联，避免等待者丢失导致结果不可恢复 |
| 主分支打断能力 | 复用并核对原有回执，区分受理与打断完成；不能因本分支暂未合并而重新实现 |
| 移动端与设置页 | 统一自动适配状态、首次轻提示、详情、关闭/恢复、待确认与人工继续、报告入口 |
| 通用日志/审计 | 只能复用结构化事实，不能直接上传原日志；新增白名单诊断快照 |
| GitHub 模板/工作流 | 增加专用报告、规范化指纹与自动去重，调整 stale 豁免；工作流需在默认分支启用后才具备实际效果 |

对外至少提供这些职责：读取适配状态、切换适配、查询原动作、只读检查送达、显式人工继续、读取/生成诊断预览、查找已有公开报告。准确 IPC/HTTP 名称、存储迁移和任务拆分在设计稿获批后的执行计划中确定。

## 11. 验收要求

### 11.1 自动适配与真实界面

- 未知 build 无需开启实验开关即可按守卫尝试发送；身份无法确定时零投递并保留草稿。
- 同指纹成功取证后再次进入及重启不重跑该能力的完整探测；暂时失败可重试，历史成功不被覆盖。
- 关闭、重开不自动发送草稿；已验证 build 正常能力不受连带影响。
- schema 比首快照迟到时，原生审批卡原地自动更新，不需刷新或重新进入；换代和关闭时旧结果不解锁新卡。
- 所有新增中文文案同步英文；未知状态不显示 raw i18n 键，不把“已受理”写成“已完成”。

### 11.2 路由、审批与队列

- 对已验证和未知 Desktop build，NotSent 均不触发 headless；原 headless 归属会话维持其功能。
- pending＋idle、unsupported pending、直接 HTTP 绕过前端、后台 flush 均不能投递普通消息。
- 处理审批正常解除后接力正常队列；打断成功后队列仍暂停，只有用户明确选择才继续。
- 打断回执受理但快照未确认时，不假装已经解除审批。

### 11.3 截止时间与恢复

- 连接、探测、RPC 串联仍在 30 秒内结束前台等待；后台收尾不延长转圈。
- 确定零投递可以重试；可能写入、代理超时或页面关闭不自动重投。
- 迟到回执、无 turnId、有/无正式 userMessage、只有临时 input、跨 owner 换代均有定序回归。
- “未找到”和泛 idle 不解除 Unknown；人工继续保留旧 Unknown 并幂等建立一个新动作，不能穿透 pending。
- 超时/取消、重启、迟到结果与人工解除交错时，不死锁、不泄漏无限任务、不复活已撤销派发权。

### 11.4 全工具报告与 GitHub

- 所有工具都能从设置进入报告；有结构化错误的现场入口自动带入对应工具及操作。
- 测试报告生成器不会包含正文、命令、路径、凭据或本地业务 ID；任意原始日志不得流入报告。
- 同版本组合但不同操作/特征允许不同工单；相同完整指纹最终只有一个开放工单；旧工单关闭后允许复发。
- 覆盖并发新建、重新打开、编辑改指纹、索引延迟、分页、工作流重跑/补扫和限流，不靠单次客户端搜索保证唯一。
- 缺少关键字段不错误合并；不可信正文不能执行代码或越权。
- 本地过期清理不删业务动作；Issue 保留历史且不被 stale 自动关闭；用户未提交或 GitHub 失败时不显示提交成功。

### 11.5 最小真机补验

在当前未知 macOS build 上，用修复后的新构建验证：首次进入 pending 卡自动解锁、一次允许打印闭环、Tuvis 重启后一次终止闭环、关闭/恢复适配、超时后的只读核对与人工继续界面。通过已授权的隔离测试会话操作，不重启承载工作会话的 Desktop。

Windows 与其他工具的基础报告字段按平台补验；无法安排时明确保留未验项，不把合成输入当成真实 wire 兼容证据。GitHub 去重先在受控测试仓库验证，不用真实用户工单做破坏性演练。
