## 2. 必须修复的问题

以下行号均对应被审查的 HEAD，修复后以函数定位为准。

### R1 [P1] Windows 构建引用不存在的函数

位置：`src-tauri/src/services/tps/install.rs:625`、`:1241`、`:1326`。

`write_config_atomic_private` 仅在 `#[cfg(unix)]` 下定义，OpenCode 安装和恢复却无条件调用。Windows 目标会报找不到函数，影响整个应用构建，不只是该来源不可用。

修复与验收：提供正确的平台实现或成对的平台分支；Windows 编译通过。Mac 当前修复不得继续保留可静态确定的编译错误；Windows 真机运行验收仍可独立记录未运行。

### R2 [P1] 重复安装丢失首次所有权记录

位置：`install.rs:953`、`:994`、`:1238`、`:1263`。

Claude 每次 apply 都重新把当前配置记作 old_value 并覆盖原 receipt。首次转交原 OTLP 目标、再次安装、再卸载，将不能恢复原目标；首次新增键也会被错误当作原有键保留。OpenCode 二次安装把 replaced_user_content 变为 false 并覆盖原备份；随后卸载直接删除文件，首次被替换的用户插件无法恢复。

OpenCode 的 UI 可触发此路径：已安装但尚无事实仍分类为 unconfigured，继续显示安装按钮。

修复与验收：重复安装/升级必须保留首次接管前的 oldExists/oldValue，不能用自有安装值重置所有权。覆盖首次新增及首次 transfer 两类，连续 preview/apply 两次后 uninstall；原目标逐键/原插件逐字恢复，自有新增项删除，用户后改仍保留。

### R3 [P1] 活跃文件每次追加都会重读全部历史

位置：`sources/kimi.rs:247`、`sources/workbuddy.rs:265`、`sources/dsh.rs:296`、`sources/dsh.rs:728`；调用方 `collector.rs:334` 起持全局 DB 锁执行读取。

三个来源都先 std::fs::read 全文件，再按已消费 offset 切片；DSH 还从完整压缩字节重新扫描帧。已消费 1GB 的日志追加一行，前台每 5 秒仍会读取和分配 1GB。200 条观察上限不限制读取字节或预先解码量；持全局数据库锁还会阻塞其他查询。

修复与验收：从持久字节/帧边界 seek 读取，限制每批字节、行和解码量，未消费部分下轮续读；源 IO 不长期占用全局 DB 锁。用已消费大前缀加少量追加的隔离夹具验证实际读取量与历史长度无关，不仅断言输出行数。

### R4 [P1] WorkBuddy 已有真实日志无法通过时间解析

位置：`sources/workbuddy.rs:350`、`:475`。

真实五条 qua.end 的时间前缀为 `[MM/DD/YYYY, h:mm:ss PM.SSS]`；当前实现只尝试 RFC3339，全部缺 ended_at 而跳过。现有测试使用 RFC3339 前缀，无法证明报告所称 Mac 5.8.3 路线可用。

证据：现有 `~/.workbuddy/logs/*/*.log` 的前缀白名单核对，以及 `/Users/jarvis/Documents/tuvis-verify-logs/tps-probe-macos-supplement-20261024T133002+0800/runtime-probe-macos-supplement.md` §11.2。

修复与验收：支持实际日志日期格式，明确无偏移时间的本地时区处理，不拿 mtime 冒充事件时间；将真实前缀连同脱敏数值载荷重放至观察、采样点和查询。格式错误须诊断且不推进到永久丢样本。

### R5 [P1] Kimi 请求事件层级错误，丢模型身份和重试证据

位置：`sources/kimi.rs:317`、`:326`、`:429`。

代码先排除所有非 context.append_loop_event 行，却只在嵌套 event 内寻找 llm.request。已有 83 份 wire 中 815 条 llm.request 全在顶层，均有 model/turnStep；嵌套数量为零。真实请求因此全部丢失模型归属，进入 unknown；未匹配请求又按 aligned=true 处理，已可见重试无法排除。测试人为把请求嵌入循环事件，掩盖了问题。

证据：`docs/superpowers/evidence/2026-10-24-model-speed/dsh-kimi.md:106` 及既有 wire 白名单结构统计。

修复与验收：分别归一顶层请求和嵌套结算，按真实 turnStep 关联。测试顶层请求 + 嵌套 step.end 的正常模型归属，以及同 turnStep 两次请求的速度排除。行级 time 的 12,328 条现有记录均为整数，无需为此重新探测。

### R6 [P1] 最近一轮按裸回合号分组，跨会话串值

位置：`policy.rs:363`—`:369`。

same_turn 只比较 turn_key，未比较 session_key 和 host_instance。DSH 把会话内数字回合号直接保存为字符串；同模型/渠道的两个会话都存在回合 "1" 时，会合并成同一最近回合的 TPS、用时和计数。

修复与验收：使用来源/宿主/会话/回合的可靠联合身份；缺必要身份时保守降级。增加两个会话复用同一回合号但 TPS 明显不同的用例，最近一轮只能包含最新调用所属的那一轮。

### R7 [P2] ZCode 冷启动从最旧记录追赶，近期调用可能永远错过采样窗

位置：`sources/zcode.rs:92`、`:199`—`:204`。

空游标从 rowid=0 开始，ORDER BY rowid LIMIT 200 取的是最早 200 条，而非近期尾部。已有至少数千条历史记录的数据库首次启用时，要经过多轮才能读到新调用；后台每轮相隔 600 秒，新调用到达读取器时早已超出 120 秒采样窗。已有游标长期停机积压也可能复现。

修复与验收：优先恢复近期已完成调用与必要的运行中边界，旧历史不能阻塞近期抽样；不牺牲原地 UPDATE 收尾行的重读。以超过 200 条旧行和最后一条近期完成行为夹具，启动即可给近期调用出点；恢复积压同测。

### R8 [P2] DSH 沿用了被新设计取代的单一 profile 禁用规则

位置：`sources/dsh.rs:535`—`:539`，`replay_profile_matches`。

即使同消息输出与多时刻非空流完整，只要不是 pi-ai/2/openai-completions 就不给 generation_ms。当前设计 §4 已明确不是只认旧稿的单一 replay profile；实现采用了历史补证文档的更窄准入条件。

修复与验收：按当前设计恢复有依据的 provider-reported 路径，对输出包含关系如实标记，不将未知思考计数强行标成已包含；仍排除无可靠生成窗的调用。覆盖无该旧 profile 但同调用时间/输出完整的有效例，以及真正计时缺失的反例。不得为让测试通过直接无条件认定所有 profile 语义相同。

### R9 [P2] TTFT 分母仍绑定 TPS 有效样本池

位置：`policy.rs:110`—`:119`。

首 token 平均值仅从最近 20 条 TPS 有效调用中取得。有可靠 S/F 的成功调用，如果缺输出计数或生成窗，则首点仍被丢弃，与设计规定的独立首点分母不符。

修复与验收：在同一候选范围内单独选择成功且首点可对齐的样本计算 TTFT，不由 TPS 分子/分母是否完整决定。覆盖成功、有首点、无输出数的调用以及 TPS 与 TTFT 样本数不同的聚合。

### R10 [P2] 来源生效后重新进入页面丢失卸载入口

位置：`src/components/usage/tps/TpsSourceStates.tsx:137`。

按钮仅依赖本组件临时 receipt 或 await-restart 状态。来源收到有效样本变 active 后，关闭重开页面或重启 Tuvis 会失去 receipt，卸载按钮消失；安装后 read-failed 等状态同样受影响。

修复与验收：返回持久安装事实，安装/卸载入口不依赖短期采样状态。已有安装且 active/read-failed 的组件首次挂载仍能卸载；卸载后正确刷新状态。

### R11 [P2] 缺失计划点仍被连成连续实测线

位置：`src/lib/usage/tpsSeries.ts:63`。

仅当相邻点超过 1,320 秒才断线。同 run 的可见期点 0/120000ms（缺中间 60 秒点）和后台点 0/1200000ms（缺中间 600 秒点）都返回一个连续段。无法履行设计明确的缺计划点断线要求。

修复与验收：携带足够的计划节奏或显式中断信息，区分合法后台稀疏点与遗漏计划点；不得只调一个通用阈值猜测模式。覆盖上述两例，以及合法后台 600 秒连续点、manual 点、gap、切换模式和 runId 更换。
