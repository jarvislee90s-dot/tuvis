# TPS采集路线重新评估

日期：2026-10-24。用户指出原计划六源TPS禁用，没有实现跨工具TPS核心目标；旧spec、计划、提示词已暂停。本文是问题重定位，不是新接入路线定案，不授权安装插件或更改配置。

## 问题与成功标准

目标是每个目标工具实际能观测同一请求的首个有效输出、输出完成及对应总生成Token，而不是只完成统一空值界面。每条拟采用路线必须先以一条真实调用或同协议隔离样机证明上述三者能关联，说明模型/重试/思考计数覆盖，再更新支持矩阵与实施计划。

## 三项基本事实

- A1：吞吐是同批Token除以对应时间窗；缺分母不能靠UI或统计库恢复，因为比值必须具有两项输入。
- A2：首输出时间必须在运行时被记录或可靠观测；历史只有最终消息不能唯一还原此前到达序列，因为多个不同序列可产生同一最终消息。
- A3：插件、SDK、遥测或依赖只有实际暴露所需事件才有用；名称本身不保证观测能力，必须检查接口数据。

## 假设审查

| 旧假设                          | 基本事实与判断                 | 新结论                               |
| ------------------------------- | ------------------------------ | ------------------------------------ |
| 数据库没有就永久禁用            | A2仅限制历史，未限制未来运行时 | 撤销；研究未来采集入口               |
| 允许横杠就代表目标完成          | A1与用户跨工具比较目标         | 撤销；横杠是必要降级，不是核心交付   |
| 加统计依赖能补足缺失时间        | A1/A2缺输入不能计算            | 撤销；先确定数据入口                 |
| 插件必然很重                    | A3看实际扩展形式               | 修改；本地小插件可能足够             |
| Hook或插件一定能见首Token       | A3要有事件与请求关联           | 撤销；生命周期Hook与流式事件分别检查 |
| 官方app-server能旁观所有已开CLI | A2/A3需同一实例/会话关联       | 未证实，不作承诺                     |

## 当前可验证入口与限制

OpenCode官方文档确认本地插件目录可直接加载JS/TS文件，支持消息事件；SDK支持event.subscribe。这证明有运行时扩展/订阅入口，不证明统一TPS生命周期已完成关联。

- https://opencode.ai/docs/plugins/
- https://opencode.ai/docs/sdk/

Codex app-server文档确认它驱动的turn提供delta与用量事件。这不等于任意用户自行启动的已有CLI可由另一个app-server旁观，逐请求用量和隐藏推理窗口也仍须对齐。

- https://learn.chatgpt.com/docs/app-server

Claude已有原生遥测，但本机已查明其message_start/content_block_start不是首非空delta；不能因允许安装插件就宣称常规Hook插件能补齐。需继续评估原生更细事件或受管启动流式输出。

ZCode/WorkBuddy等封闭工具须先查公开扩展、运行时事件或诊断入口；不能承诺装一个通用插件即可全覆盖。无入口时涉及上游配合、受管启动或更深接入，须单独决定。

## 推导与压力测试

由A1/A2：保持原统计公式，新增运行时观测能力；由A3：按工具选择原生事件→轻量扩展→受管协议流，而非先选监控依赖再找数据。仍不把API key改走统一网关当成既定方案。

反向压力测试：如果完成代码后六个核心TPS仍为空，即使持久化、UI、工具时间全部正确，仍未达到用户主要目标。新设计必须先证明拟支持工具的采集样机，不能把原来的禁用表直接迁入新计划。

自查：结论均对应A1—A3；三项事实均有方案动作；未将接口存在写成端到端已验证，当前仍需用户确认插件/启动方式等新边界。
