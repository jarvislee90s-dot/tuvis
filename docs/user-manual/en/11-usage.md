# Usage Statistics

One ledger shows at a glance how many tokens each tool burns — collected automatically, read locally, zero telemetry.

## The usage ledger

Tuvis keeps one ledger for seven tools — Claude Code / Codex / Kimi Code / OpenCode / ZCode / WorkBuddy / dsh (OpenClaw is not collected yet). It only reads and aggregates each tool's own session records on this machine and reports no telemetry of any kind; the ledger lives in four tables in `~/.tuvis/tuvis.db` (hourly-bucket details, permanently kept daily aggregates, collection cursors, and a session dimension), hourly-bucket details are kept for 90 days by default with a 90-day maximum (configurable), and only daily aggregates remain after that.

Collection cadence: one automatic catch-up shortly after app launch, then on the configured interval (single-flight mutex plus a default 10-minute minimum-interval floor — collection runs on its own on-demand path and never rides on the 3-second session polling; the frontend can also trigger a collection on demand via `usage_collect`). **Settings → Usage statistics** offers "collect now" at any time plus a master switch — when off, nothing is collected or written to the ledger (retention cleanup is skipped as well, and dashboard / record queries return the off-state early; settings and export keep working, and the export covers the existing ledger — export not being gated by the master switch is a registered decision pending review). Numeric settings (mini-bar tool rows / detail retention / collection interval) keep a draft while typing and clamp/save only on blur or Enter, so values do not change mid-keystroke.

## Opening the big board

The usage dashboard is one of the main window's four top-level tabs (Messages / Resources / Usage / Output Speed) — click the tab to get there; the usage button in the title bar remains and now opens the Usage tab directly, and legacy entry points such as the pet minibar's "Details »" still wake the main window and select the Usage tab.

- **Usage trend** (always expanded): a line + gradient area chart whose x-axis granularity follows the time range — peak marked top-right, hover for exact values. Here "channel" means the provider alias (the provider display name, unedited = raw name; an explicit billing binding wins; tools are not a channel dimension; when no alias is configured, non-empty providers aggregate by their raw string; "unassigned channel" and "channel may be mixed" are not filter options);
- **Usage distribution** (expanded by default, collapsible): share bars across **By channel / By tool / By project / By model**, Top 5 by default with "show more"; each row shows name · tokens · cache hit rate · relative bar, with no dollar column. The same display name merges across tools, and identically named models no longer produce indistinguishable duplicate rows; when an empty provider has no assignment, the channel view merges it into one "unassigned channel" row and the model view splits by tool; the channel view also has a "channel may be mixed" row for log identities that may mix multiple accounts and cannot be split; an empty model shows "unknown model";

- **Work activity** (collapsed by default): the card header shows sessions and tool-call counts; expanding reveals turns, the three error layers, user interrupts and the top tool, while p50 / longest turn / tool duration live in the advanced stats section;
- **Export**: copy as text / export image (a share image including the pet's portrait) / export CSV (UTF-8 BOM, Excel-friendly, structured ledger columns only) / **Cost CSV** (all channel / model cost rows for the current window, no totals, no extra BOM added by the frontend; seven columns — channel key / channel kind / display name / normalized model / catalog release date / override flag / price-rule kind — are appended after the existing 17 columns; the single-value `observed_provider` column is left empty when a row merges multiple raw providers or includes an unlabeled source, with the full evidence available in the UI tooltip). Shared summaries no longer contain "user input (est.)" and now include cache-miss input. **Export settings → Image modules** chooses which sections the share image contains: the overview + trend chart are mandatory and cannot be turned off; group distribution is a multi-select over tool / project / provider / model, with one Top-6 section per selected dimension; "API equivalent cost" (estimated total + top rows) and "Work summary + pet speech bubble" toggle independently. Choices are saved on this device (browser localStorage) as soon as checked, affect the exported image only, and leave the "Copy text" summary unchanged.

Five time ranges are switchable, with custom spans up to 31 days. The "Records" tab in the same window shows one card per tool, one row per "provider / model" spend, groupable by tool / project, with measured / inferred / unknown markers; **row names prefer the provider alias** ("alias / raw model", falling back to the raw "provider / model" when no alias exists), while the raw identity stays in the title and the row data; **the channel / model dimensions of "Usage distribution" and the "API-equivalent costs" row tooltips** show raw provider evidence — when multiple raw providers merge, the complete list is shown, and groups that contain a non-empty provider together with an unlabeled source are marked "includes unlabeled source" (the tool / project dimensions show no provider evidence); ordinary rows no longer show "Assign channel / Edit assignment"; only ambiguous rows offer "Bind billing attribution", and the legacy billing attribution / reference rules live behind the footer's "Advanced" entry, each row keeping a lightweight "User assigned / Observed / Ambiguous" marker; every row also has a "Provider display name" entry (shown as "Edit" when an alias exists), and the dialog previews the rule's matching tools, models and total tokens for the last 30 days before saving. **Settings → Usage statistics → Display & pricing config** and "Custom price rules" now live in **one shared dialog** (the cost card's "Manage config" opens the same dialog): the settings page and the D card share it, with provider/model entries in the upper part and a collapsible custom price rules section in the lower part (collapsed by default). Settings and the D card are separate WebViews; changes in Settings do not guarantee an immediate refresh of an already-open usage dashboard, and the in-dashboard config is the primary path. Entries default to the top 10 by usage in the last 7 days, sortable by usage / raw provider / raw model (click the same key to reverse), with "show all" and search at the bottom; each entry has three rows — raw identity (read-only), provider name + model name (both editable: a provider name applies globally to the same raw provider, and empty-provider entries write a toolModel alias; model names apply per (display provider, raw model)), and the pricing identity (dropdown / search selection only). The advanced area's "Custom price rules" supports fixed and time-of-day pricing (USD/CNY denominated); legacy billing attribution / reference rules moved to the usage dashboard Records page's footer "Advanced" entry. ## Provider display names (aliases) and automatic pricing

- **Channel display names**: a channel is the provider alias. A non-empty provider maps exactly from its raw string to an alias — unedited = raw name; different raw strings can map to the same display name and merge across tools; an explicit billing binding has the highest priority; aliases only affect display and grouping — they never rewrite the ledger or change the token basis. **When no alias is configured, a non-empty provider aggregates by its raw string.** Records-page row names prefer the provider alias (the raw "provider / model" stays in the title and row data); aliases also appear in the "Usage trend" filter options, "Usage distribution" / "API-equivalent costs", the config dialog and the alias dialog; the channel / model dimensions of "Usage distribution" and the "API-equivalent costs" row tooltips show raw provider evidence — when multiple raw providers merge, the complete list is shown, and groups that contain a non-empty provider together with an unlabeled source are marked "includes unlabeled source" (the tool / project dimensions show no provider evidence).
- **Empty providers**: no automatic rule — set aliases individually for "tool + raw model" entries, and the change applies retroactively once saved; without an assignment the channel view shows one merged "unassigned channel" row and the model view splits by tool; an empty model shows "unknown model".
- **Provider and custom model names**: the provider / model entries section of the config dialog edits both names. A provider name applies globally to the same raw provider (empty-provider entries write a toolModel alias; unnamed = unassigned channel); a model name supports one-click copy of the raw name and clear-to-raw, with the display key (display provider, raw model) renaming all raw sources under it; the custom model name applies only to D-card row names ("Usage distribution" and the records page keep the raw model name; the records page shows the provider alias).
- **Pricing identity**: each model entry can be explicitly pointed at a catalog provider / model — dropdown / search selection only, no free-form input, so illegal keys are impossible; the curated auto-match result is shown by default and can be overridden or cleared; its priority sits below custom price rules and reference price rules, above auto-matching.
- **Known limitation**: when two subscriptions log the exact same raw provider string, aliases cannot split them and the channels stay merged; only the ambiguous row's "Bind billing attribution" or the footer's "Advanced" entry (explicit billing binding) can help, and tokens are never split proportionally.
- **Automatic matching (curated sources)**: only the public models.dev catalog is used (no built-in seed prices), with curated sources ranked **direct official providers (including China-site variants) > OpenRouter**, skipping all-zero quotes; model IDs are mechanically normalized then matched exactly, and within a tier the latest `release_date` wins with one price per currency; when exact matching misses, prefix fallback is used only when the candidate is unique, or when multiple candidates match but all share exactly the same price; cross-family substitution requires an explicitly chosen reference model. Conditional quotes (multimodal input, context tiers, etc.) are estimated at base text rates with a caveat; missing prices still render `—`, never 0. Models missing from the curated set stay unpriced by default — pick a catalog entry explicitly via the pricing identity (the catalog search is curated-only by default, with a "show all N sources" switch).
- **Cost granularity**: costs for the last 7 days / 30 days / custom spans (≤31 days) are computed from hourly details aggregated per day, so dsh is fully priced across input / cache hit / output; when a time-of-day rule exists, hourly buckets are classified as peak/off-peak before aggregation and the row unit price is a weighted average; when a lowered detail retention or cleanup leaves days without details, the whole span falls back to daily aggregation (dsh stays output-only; time-of-day rules are estimated at off-peak rates and disclosed in the accuracy caveats); the last 5 hours / today and the billing-channel preview are unchanged.
- **Refresh and verification**: refreshed daily by default and manually on demand (the D-card "Sync prices" button force-refreshes models.dev + native RMB sources + the daily FX rate); on failure the last valid snapshot is kept and the data source plus snapshot date remain visible; the D-card expanded footnote shows the normalized model and the snapshot fetch time. **A model release date is not a price date** — the catalog entry's release date only drives same-name dedup, while pricing always uses the rates as of the snapshot fetch time.
- **Custom price rules (fixed / time-of-day)**: inside the config dialog's "Custom price rules" you can set prices by **normalized model name**. A fixed rule overrides the input / cache read / cache write / output rates (USD / CNY, stored in that currency; the other display currency is converted at the daily rate and dashed-underlined). A time-of-day rule uses peak rates inside multiple Monday–Friday peak windows (whole hours, cross-midnight allowed) and off-peak rates elsewhere, including weekends; a blank off-peak component falls back to the catalog rate. The time zone can be China Standard Time, UTC or system local and only affects API billing peak/off-peak calculation; a "peak × %" helper fills the off-peak rates. **No provider is needed**; custom display names do not participate; once saved, all channels sharing the same normalized model use the price; it is not selected in pricing identities or reference rules. The list shows the catalog source, release date and snapshot date; later catalog syncs never overwrite user values. When only daily aggregation is available, the whole span is estimated at off-peak rates and the caveat is disclosed.

## Recent TPS (short-window sampling)

> 📌 **Shape update**: the standalone "Recent TPS" block described here has been replaced by the main window's fourth tab, **Output Speed** (dual-metric ranges plus collection management in one page — see the next section). The principles kept in this section — sampling is not full coverage, gaps are never drawn as 0, no benchmark requests, one-click setup with a natural restart — carry over to the Output Speed page; the concrete value rules there follow the new design.

The big board gains a standalone "Recent TPS" block: a sampled-throughput curve of recently **completed** calls (last 2 min / 10 min / 1 h / today, 1 h by default), two sample-metric panels ("Latest completed call" and "Latest turn" — sample model time / sample tool-call time / sample avg first token / sample TPS), and the per-source states. It is **short-window sampling, not a full-coverage statistic** — read it with these rules in mind:

- **Sampling, not full coverage**: each sample point takes only valid calls **completed** within the 120 seconds before that point (at most the latest 20 per curve), with point TPS = 1000 × Σ output tokens ÷ Σ generation ms. The x-axis is the actual sampling time — hours when Tuvis was not looking have no sample points; the curve is never interpolated and gaps are never joined into a continuous measured line; **no multi-day TPS** is offered, and facts and sample points are kept for the last 24 hours only;
- **Not a server benchmark**: every number comes from on-device sampling (the tools' own records or local events) and **no benchmark requests are ever sent**; "Refresh" only reads facts that already exist — new samples appear only when you actually use the tools. Precise instantaneous speed during generation is not promised in this version;
- **Reported reasoning only**: the token basis follows each source's native reporting — when the vendor's output already includes reasoning it is never added again; when no separate reasoning count exists the card shows "reasoning count not declared separately", never estimates hidden reasoning from characters, and never claims a separately measured hidden-reasoning speed;
- **Timing methods stay in families**: stream-observed (per-delta observation) / client-native (the host's own native timing fields) / native-event-approx (carries an "approx" badge — first token approximated by the first content block). Different methods are never merged into one continuous precise curve; tooltips show the method;
- **Gaps and freshness**: spans with no valid sample are kept as gaps — **never drawn as 0** and never faked from an old speed; "Sample ended" is the latest sample's end time and "N minutes ago" is its age; beyond 10 minutes it stops being shown as current ("No recent sample"), while historical points stay viewable; each Tuvis launch starts a new sampling run, and there are no live points while the app is closed;
- **Sources and one-click setup**: ZCode / dsh / Kimi are native read-only (automatic with the usage master switch); Claude and OpenCode need a **one-click install** inside the "Recent TPS" block (statistics config / observer plugin) — preview, confirm, then a "takes effect on next launch" hint; **Tuvis never restarts your Harness for you**; installs never touch API, auth or provider configuration, sensitive telemetry headers show masked values only, and uninstalling handles only Tuvis's own entries — anything you edited afterwards is kept and reported as a conflict;
- **Codex gap (declared honestly)**: Codex's metrics pipeline works, but there is currently no reliable per-call generation window, so **this version provides no TPS for Codex** (explicitly marked in the source states); its existing token/cost statistics are unaffected;
- **Current limits**: the WorkBuddy Windows route produces no TPS for now (insufficient evidence; the Mac normal route is supported); the OpenCode observer plugin produces samples after install and a natural restart; TPS acceptance on Windows is deferred to the final platform acceptance.

## Output speed (dual-metric ranges)

![Output speed board](img/output-speed-board.png)

The main window's fourth tab, **Output Speed**, provides **two independent on-device speed metrics**: a combined "tool · model · channel" list on the left (filterable by tool; click the column headers — name / speed / session count — to sort ascending or descending) and a large chart plus four metric tiles on the right (current-mode speed / avg first-token wait / total time / total tool time). The series name at the top of the detail pane is itself a **dropdown** for switching the selected series. Four ranges are switchable (15 min / 1 h / 5 h / 24 h — 5 h by default); hover the curve for that bucket's reading, click to pin it, and Esc or "Back to range summary" releases the pin. Hovering a list row reveals the **full series name instantly** (handy when the narrow column truncates it). It is a **range statistic over the collected valid subset, not full-coverage monitoring**, and it never sends benchmark requests — read it with these rules in mind:

- **Two speed metrics**: "Stream output speed / TPS" = 1000 × Σ streamed valid output tokens ÷ Σ generation ms (excludes the wait before the first token); "Response throughput (incl. waiting) / tokens per second" = 1000 × Σ response valid output tokens ÷ Σ response ms including waiting (the denominator includes the first-token wait plus preparation/queueing overhead inside that source's boundary, and excludes tool execution after the response ends). Both metrics judge validity independently and count samples independently; aggregation is always Σ/Σ — per-request speeds are never averaged. For one 100-token record with a 1-second wait and 4 seconds of generation, stream reads 25 TPS and response 20 tokens/s — both are true, the denominators differ;
- **Source capabilities are labeled honestly**: the six native sources (DSH / ZCode / Kimi / WorkBuddy Mac / Claude / OpenCode) each cover a valid subset of both metrics — "supported" means a computation path exists, not that every record is complete. **Codex provides response throughput only**: aligned by native response IDs over log input/generation boundaries (prominently labeled "incl. waiting · log-approx"); selecting Codex temporarily switches the view to the response metric and explains the gap. Its stream generation window is unavailable, and per-response first-token latency is unavailable too — the "avg first-token wait" tile shows "—", and the turn-level figure never stands in for it;
- **Total tool time is currently "—"**: only tool durations that can be reliably attributed to the current model call are accumulated, and today's sources generally provide no such attribution (hover the tile for this note); the usage page's original work-activity statistics (all-tools basis) are unaffected.
- **Sampling, not full coverage; empty buckets stay empty**: ranges and time buckets aggregate only the collected valid calls — a bucket with no valid sample stays empty (never drawn as 0, never estimated); where the measured line breaks, a gray dashed segment is a **visual connector only** (legend: "dashed connects only, no samples", with a strict-break style available); failures, cancellations and unalignable retries enter no speed, but timeable failures/cancellations do count into "total time" and the detail counters (candidate / failed / cancelled) — the speed n and the total time therefore need not agree;
- **A 24-hour fact window**: ranges aggregate raw numeric facts from the last 24 hours (attributed to buckets by completion time), with no early down-sampling and no older history; an empty range is a data empty state, not automatically a collection fault (check "Collection management" for source states);
- **Same-window entry**: Output Speed sits beside Messages / Resources / Usage as a main-window top-level tab; switching pages never stops session monitoring or notifications, and each page keeps its own range and selection; the speed page defaults to 5 h, fully independent of the usage page's time range; collection slows down while the app is in the background (about a 5-second cadence while visible, about 600 s in the background) — the displayed bucket width is not the collection interval;
- **Collection management and natural restarts**: "Collection management" at the speed page's top right and **Settings → Usage statistics** share the same component — sources are listed by their real state (Ready / Unconfigured / Await restart / Needs check; Codex shows "Ready · response only"); installing Claude or OpenCode goes through preview & confirm (sensitive telemetry headers show masked values only) with a "**takes effect on next launch**" hint — **Tuvis never restarts your Harness for you**; installs never touch API, auth or provider configuration, and uninstalling handles only Tuvis's own entries;
- **WorkBuddy compatibility and recovery**: WorkBuddy 5.8.3 Mac records whose numbers are string-shaped are now accepted (older versions skipped the whole source); after upgrading, recent records (last 24 hours) that an old cursor had skipped are recovered automatically within bounds and deduplicated — only speed facts are recovered; the token/cost ledger and other sources are untouched.

## Collection criteria at a glance

- **Four buckets** = uncached input / cache read / cache write / output; hit rate derives from cache semantics (mutually exclusive / inclusive / totals-only). Sources disagree on semantics, and records of the same tool can differ too — Codex decides per record by arithmetic on `total_tokens` (measured on this machine: 92.69% with the correct rule, while treating everything as "inclusive" yields absurd values above 100%). When in doubt it assumes mutually exclusive: better an under-reported hit rate than silent over-counting;
- **Total processed tokens = new input + output**; **cache-miss input = new input − cache read** (same formula for current and previous windows; "new input" is the ledger's request total — the basis is unchanged, only the on-screen wording is unified);
- **Sub-agents included**: token totals include sub-agent usage; session and turn counts are layered by parent/child (one conversation is not counted as several); turns are never summed across tools (each source's rule is not comparable), and the longest single turn is reported per tool as p50 + max — it includes idle time (idle is not excluded);
- **The sub-agent flag is only meaningful in the hourly tier**: `isSubagent` is `true` / `false` for hourly grouped rows, and is the empty state `null` in the daily tier and for record-page card rows (neither tier has a session dimension, so it cannot be computed) — `null` must **not** be read as `false` ("no sub-agents");
- **Errors are split into three layers, plus a separate "user interrupted" column** (the three layers are mutually exclusive; adding them up is meaningless);
- **Unavailable shows `—`, not 0**: some metrics exist for some tools only — WorkBuddy has no turn concept, no duration field and no provider; OpenCode has no tool-level errors; kimi has no user-interrupt rule; dsh errors and longest turns can only come from raw session logs, and only a subset of sessions still have raw logs, so no ratio is hard-coded (coverage varies with the machine and cleanup policy; the earlier "19/99" figure is obsolete). V2 removes "user input (est.)" from the dashboard and shared summaries (it is not API tokens); the ledger field and raw Token CSV column remain for compatibility;
- **"By project" follows record ownership**: one session file can span several projects (only the cwd inside a given record counts as its project); project names come from the same source as the dashboard session cards (`projectName`); on Windows the same directory may split into two groups because path casing differs between sources; records without a cwd fall into `Unknown`;
- **Privacy**: the UI and the CSV contain structured numbers plus tool / model / project / session titles only — no raw prompts, no code content; session titles and raw paths never enter the CSV.

> 💡 A `—` in a column is not a malfunction — the true value is unobtainable under that criterion; when a hit rate defies common sense it is usually a cache-semantics misjudgment, so attach the tool version when reporting it.
