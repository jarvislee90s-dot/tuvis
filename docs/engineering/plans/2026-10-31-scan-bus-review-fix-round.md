# 1. 本轮整改目标

本轮不是重构 Scan Bus，而是修复上一轮代码审查发现的功能缺口。

必须遵守以下原则：

1. 保留现有 Scan Bus 单一扫描总线架构。
2. 保留 Active / Idle / Away 三档自适应扫描机制。
3. 不恢复已经删除的前端高频轮询。
4. 不增加无意义的扫描次数。
5. 不允许因为修复事件唤醒而引入第二个并行扫描线程。
6. 不改变现有移动端 REST API 契约，除非有充分理由。
7. 优先复用现有函数、状态和测试设施。
8. 每个问题都必须有对应的回归测试，不能只修改代码。

本轮分为三个必须处理的任务组和两个建议处理的任务组。

# 2. 第一组：修复 F6 事件唤醒机制

优先级：P1  
涉及文件：

- `src-tauri/src/adapter/wakeup.rs`
- `src-tauri/src/adapter/scan_bus.rs`
- `src-tauri/src/adapter/mod.rs`

## 2.1 修复每个会话事件文件只监控前 8 个的问题

当前问题：

`wakeup.rs` 中的 `signature()` 使用：

`session_ids.iter().take(8)`

这会导致排在第 9 位以后的会话，即使其事件文件发生变化，也可能无法触发扫描。

而且当前监控对象是全部会话，不是设计要求中的活跃会话。

修改要求：

1. 移除固定 `take(8)` 限制。
2. 从当前 Scan Bus 快照中获取所有需要事件监控的活跃会话。
3. 活跃会话定义必须与 Cadence 的活动状态判断保持一致。
4. 事件文件必须监控 mtime，而不是只监控父目录 mtime。
5. 会话结束或不再活跃后，及时从监控集合移除。
6. 监控集合变化不能本身触发无意义的无限扫描。

建议修改：

- `monitored_ids()`
- `signature()`
- `spawn_runtime()`

注意性能：

不能因为监控全部会话，就引入每秒对所有历史会话文件进行大量 IO。

应该只对活跃会话执行必要的 stat 操作，并尽量复用已有快照。

## 2.2 处理 dsh 和 openclaw 的事件覆盖缺口

当前问题：

- Claude / Codex / Kimi 有 hook 事件。
- OpenCode 有数据库和 WAL 等低成本文件信号。
- DSH 和 OpenClaw 没有可靠的事件唤醒覆盖。

但是 Away 档仍然可能进入 30 秒扫描周期。

这不符合 F6 的设计要求：

没有可靠事件唤醒能力时，不能无条件进入 30 秒盲区。

修改要求：

先研究现有 adapter 对各工具的数据源和活跃会话文件的访问方式。

优先寻找已有文件的 mtime 或轻量级状态信号，不要引入新的重型扫描。

如果暂时无法实现某个工具的事件信号：

- 应增加事件覆盖能力标记。
- 根据当前活跃工具判断是否允许进入 Away 30s。
- 未覆盖工具存在需要监控的活跃会话时，使用有界兜底间隔。
- 不允许将一个没有事件覆盖的工具当作已经满足 F6。

注意：不要简单地将所有工具统一改成 2 秒扫描，这会破坏本次优化的核心目标。

## 2.3 事件合并与清理

保留现有 500ms 合并节流机制。

验证：

- 同一批事件不会触发多次扫描。
- 不同时间到达的独立事件不会被错误吞掉。
- 陈旧 hook 事件文件超过 5 分钟后能够清理。
- 清理操作不会误删仍然有效的事件。

## 2.4 新增测试

至少增加：

1. 第 9 个活跃会话事件文件发生变化，必须触发扫描。
2. 活跃会话事件文件原地写入，必须触发扫描。
3. 非活跃历史会话文件变化，不应该产生不必要扫描。
4. 会话退出后，监控集合能够移除对应 ID。
5. dsh/openclaw 没有事件覆盖时，不允许无条件进入 Away 30s。
6. 500ms 内多个事件合并为一次扫描。
7. 30 分钟连续运行模拟中，事件不能因为轮询间隔过长而丢失。

# 3. 第二组：修复 F4/F6 快照更新通知

优先级：P1  
涉及文件：

- `src-tauri/src/adapter/scan_bus.rs`
- `src-tauri/src/commands/session.rs`
- `src/lib/query/queries/scanBus.ts`
- `src/lib/query/queries/sessions.ts`

## 3.1 当前问题

目前桌面端主要监听 `scan-bus-mode`。

但是这个事件只有扫描档位变化时才会发送。

存在以下情况：

1. 当前处于 Away。
2. Hook 事件触发 Event 扫描。
3. Scan Bus 成功发布新快照。
4. Active / Idle / Away 没有发生变化。
5. `scan-bus-mode` 不会发送。
6. 前端仍然展示旧快照，直到下一次周期轮询。

这导致后端已经完成事件唤醒，但 UI 并没有同步更新。

## 3.2 修改方案

新增独立的快照发布通知。

建议事件名：

`scan-bus-snapshot`

建议携带：

- version
- reason
- scannedAt
- 必要的快照状态信息

通知必须由后端统一发布，不允许在每个 adapter 中分别 emit。

修改位置：

在 Scan Bus 的统一快照发布位置增加事件通知。

需要覆盖：

- ColdStart
- Periodic
- Event
- Action
- 其他实际会发布快照的路径

注意：

不要仅仅在档位变化的位置增加通知。

## 3.3 前端接入

修改 `scanBus.ts`：

1. 监听 `scan-bus-snapshot`。
2. 对新版本进行判断。
3. 当版本更新时，更新或 invalidate 会话 Query。
4. 多个窗口收到相同事件时，不应该产生重复刷新。
5. 避免事件触发后又额外执行无意义的轮询。

建议优先考虑将快照数据直接同步到 Query Cache，避免事件到达后再次执行不必要的 IPC。

如果采用 invalidate 方式，必须验证查询结果不会回退到旧版本。

## 3.4 窗口重新聚焦

当前 `set_user_watching()` 主要判断的是全局观察状态。

存在一个问题：

桌宠已经展开时，主窗口重新获得焦点，全局观察状态可能没有发生变化，因此不会触发主窗口需要的即时刷新。

修改要求：

1. 区分不同 WebView / 窗口的观察状态。
2. 每个窗口独立记录 visible / focused 状态。
3. 单个窗口从不可见变成可见时，允许触发一次即时刷新。
4. 全局仍然只有一套 Scan Bus。
5. 多窗口同时恢复可见时，必须通过单飞机制合并扫描。

不要为每个窗口创建独立扫描器。

## 3.5 新增测试

- Away 档下 Event 扫描完成，即使档位不变，也通知前端。
- 快照版本增加后，前端缓存更新。
- 相同版本重复事件不会重复刷新。
- 主窗口重新聚焦时能够及时刷新。
- 桌宠已经展开时，主窗口重新聚焦仍然能够刷新。
- 多窗口同时恢复可见，不产生并行扫描。

# 4. 第三组：修复 F5 卡片生命周期

优先级：P1/P2  
涉及文件：

- `src/lib/query/optimisticSessions.ts`
- `src/components/sessions/SessionCard.tsx`
- `src/pages/home.tsx`
- `src-tauri/src/commands/session.rs`
- `src-tauri/src/adapter/scan_bus.rs`

这是本轮需要特别仔细处理的部分。

## 4.1 统一单卡和批量清除的生命周期规则

当前：

单卡关闭逻辑已经区分普通未读卡和其他卡片。

但批量清除时，`hideSessionsOptimistically()` 对所有卡片一律执行整卡隐藏。

这与后端 `apply_dismissals()` 的处理方式不一致。

必须统一规则：

| 卡片类型 | 预期操作 | 用户看到的效果 |
|---|---|---|
| 普通未读卡 | 标记已读 | 卡片保留，未读态消失 |
| 数据驱动聚合绿卡 | 标记已读 | 整卡消失 |
| 普通已读卡 | dismiss | 整卡消失 |
| 其他需要归档的卡片 | dismiss | 整卡消失 |

注意：

不要仅根据 `status` 判断卡片类型。

应该复用现有的卡片类型判定逻辑，尤其是 `green_card_is_data_driven` 对应的业务规则。

## 4.2 重构乐观更新函数

当前：

`hideSessionsOptimistically(queryClient, targets)`

建议调整为接收完整 Session 对象，或者增加统一的生命周期分类函数。

建议抽象：

- `getSessionDismissBehavior(session)`
- `applyOptimisticSessionMutation(session)`
- `clearPendingSessions()`

具体命名可以根据项目现有风格调整。

关键要求：

单卡关闭和批量清除必须调用同一套规则。

不要维护两套容易逐渐产生差异的判断逻辑。

## 4.3 修复 applied=false 时的卡片复活

当前问题：

后端补扫等待超时会返回：

`applied=false`

但前端仍然在 finally 中 invalidate 后无条件清除 pending。

如果这次 invalidate 取回的仍然是旧快照，卡片可能重新出现。

修改要求：

1. `applied=true`：正常等待权威快照确认后清除 pending。
2. `applied=false`：不能直接清除 pending。
3. 应等待后续扫描发布的新快照。
4. 新快照必须能够证明本次操作已经反映。
5. 在此之前，旧快照不能让卡片复活。
6. 命令执行失败时，仍然需要允许正常回滚。

建议利用本轮新增的 `scan-bus-snapshot` 事件和 version 机制。

注意：

目前 `MutationOutcome.version` 不能简单理解为操作一定已经应用的版本。

需要明确区分：

- 命令返回时的快照版本；
- 操作实际反映到权威快照的版本。

如果需要，可以增加明确的 mutation 状态字段。

不要通过无限期保留 pending 来掩盖问题。

必须提供有界等待、超时恢复和失败回滚策略。

## 4.4 新增测试

至少包括：

1. 单卡普通未读：点击后卡面保留，未读消失。
2. 单卡数据驱动绿卡：点击后整卡消失。
3. 批量清除混合卡片：不同类型执行正确的乐观操作。
4. 批量清除过程中旧快照回写，不允许卡片复活。
5. `applied=false` 后第一次 invalidate 返回旧快照，不允许卡片复活。
6. 后续新快照发布后，正确解除 pending。
7. 命令失败时，卡片能够回滚。
8. 多张卡片批量处理只触发一次补扫。

# 5. 第四组：完善 F7 用量采集时机

优先级：P2  
涉及文件：

- `src/lib/query/queries/usage.ts`
- `src/components/settings/UsageStatusSection.tsx`
- `src/components/settings/UsageSection.tsx`
- `src-tauri/src/commands/usage.rs`
- `src-tauri/src/services/usage/collect.rs`
- `src-tauri/src/services/usage/ticker.rs`

## 5.1 设置页打开时立即采集

当前 `UsageStatusSection` 挂载时只执行 `loadToday()`。

需要补充：

设置页对应内容实际可见时，触发 `useUsageCollect()`。

要求：

- 设置页未打开时不采集。
- 打开用量设置分区时触发。
- 切换其他设置分区不应该反复采集。
- 60 秒内重复触发应去抖。

## 5.2 统一跨 WebView 的采集去抖

当前 `lastForcedCollectAt` 是模块作用域变量。

它只在单个 WebView 内共享。

不同 WebView 有各自的时间戳，可能在短时间内重复执行强制采集。

建议：

在后端采集入口增加统一的单飞 / 去抖协调。

要求：

- 所有 WebView 共用同一个采集执行状态。
- 同时到达的采集请求合并。
- 不允许同一批来源重复执行重型采集。
- 手动采集和可见性采集的优先级要明确。
- 不要让一次失败的采集永久锁住后续采集。

## 5.3 统一采集成功事件

当前后端 ticker 有 `usage-collected` 事件，但其他采集入口没有统一广播。

建议将事件发送统一放到后端采集完成路径。

要求：

- 无论从可见性触发、手动触发还是 ticker 触发，都使用统一事件。
- 成功完成后通知所有 WebView。
- 前端统一 invalidate 用量相关 Query。
- 不要只在 `new_records > 0` 时通知。
- 事件应明确表示采集完成，不应与是否新增记录混为一谈。

建议事件携带：

- collectedAt
- success
- newRecords
- 必要的来源统计

## 5.4 新增测试

- 设置页打开触发采集。
- 设置页其他分区不触发采集。
- 桌宠与主窗口同时可见，只执行一次采集。
- 手动采集后所有 WebView 刷新。
- 没有新增记录但采集成功时，事件仍然正确发送。
- ticker 正常运行。
- 开发构建不启动新增的后台 ticker。
- 启动时既有的一次初始采集行为不受影响。

# 6. 第五组：完善 F1/F2 稳定性

优先级：P2

涉及：

- `src-tauri/src/adapter/scan_bus.rs`
- `src-tauri/src/adapter/cadence.rs`

## 6.1 扫描线程自愈

当前扫描循环可以通过 `catch_unwind` 捕获单轮扫描 panic。

但扫描线程本身异常退出后，没有完整的 supervisor 恢复机制。

需要区分：

- 单轮扫描失败；
- 扫描线程退出；
- 扫描线程卡死。

修改要求：

1. 保留单轮 panic 隔离。
2. 增加扫描线程生命周期管理。
3. 能够识别线程异常退出。
4. 线程退出后能够重新启动。
5. 恢复时重新建立有效的扫描发送通道。
6. 严格保证同一时间最多存在一个有效扫描工作线程。
7. 不允许为了恢复而强行清除正在执行的扫描锁，导致第二个扫描线程进入。

可以参考项目已有的 `remote/watcher.rs` 线程管理方式，但不要直接复制而忽略 Scan Bus 的单飞约束。

对于超过 120 秒的 hang：

继续保留 degraded 诊断。

不能因为 watchdog 认为线程超时，就直接启动第二个扫描器。

## 6.2 修复 Away 恢复时间 30.5s

当前 panic 恢复路径：

500ms sleep + Away 30s 等待。

最坏恢复时间为 30.5 秒。

需要满足 F1 的 ≤30s 要求。

建议：

恢复线程后立即执行一次有界恢复扫描，或重新计算剩余周期，避免完整周期叠加固定延迟。

不能简单删除所有 backoff，导致持续 panic 时 CPU 飙升。

## 6.3 使用单调时钟

Cadence 中用于持续时间计算的时间源应采用单调时钟。

不要使用系统墙上时间直接判断：

- Active 降档；
- Idle 降档；
- Away TTL；
- WATCH_UNTIL；
- 超时窗口。

建议使用 `Instant` 或基于 `Instant` 的单调 elapsed 时间。

墙上时间只用于日志和 UI 显示。

新增测试：

- 系统时间向前调整不会提前降档。
- 系统时间向后调整不会延长降档。
- 连续 Active / Idle / Away 转换结果正确。
- TTL 边界正确。
- panic 恢复不超过 30 秒。

# 11. Agent 工作方式

本轮建议采用 Superpowers 的局部 Debug / TDD 思路，但不要求机械地执行完整 TDD。

每个 Task：

1. 先读取相关设计文档和现有实现。
2. 明确当前问题的根因。
3. 找出真实调用链，不能只修改表面函数。
4. 先添加能复现问题的回归测试。
5. 修改最少量代码。
6. 运行对应测试。
7. 检查是否影响其他扫描路径。
8. 更新设计实现状态和验收证据。

每完成一个 Task，必须提交一份简短报告：

- 修改了哪些文件；
- 修改了哪些函数；
- 根因是什么；
- 如何解决；
- 新增了哪些测试；
- 测试运行结果；
- 是否仍有未完成事项。

不要在没有测试证明的情况下，把设计文档中的功能标记为完成。

**最终交付：**

1. 完成上述整改的代码提交。
2. 对应回归测试。
3. 更新 `2026-10-29-scan-bus-and-adaptive-cadence-plan.md` 的任务状态。
4. 更新 evidence 文档，区分代码验证、模拟测试、真实运行测试。
5. 给出新的 F1–F10 完成度表。

最终目标是让 PR #191 不仅拥有正确的扫描架构，而且让事件唤醒、卡片生命周期、多窗口同步和用量采集在真实使用过程中也符合原始设计要求。
