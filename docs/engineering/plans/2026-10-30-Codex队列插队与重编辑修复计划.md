# Codex 队列插队与重编辑修复计划

> 执行方式：按 TDD 实现，前后端分文件并行；最后集中审查和验证。不提交其他任务文件，不推送、合并或发版。

目标：完成用户最新明确要求的四项修复；批量合并发送已取得用户明确的宪法例外授权。

## 已授权行为

- 删除队列区的“待发队列／原生回合未确认完成……”常驻长提示及独立停止按钮，停止仅由 composer 主按钮／紧凑入口承担；未知投递的必要核对入口保留。
- 插队 = 显式停止当前目标回合，确认终态后发送所选 queued 消息，保留原 action、正文和幂等，不只停不发；其余旧队列暂停。
- 行文案固定为“第 N 位　插队　重新编辑　撤回”，后三项是按钮。
- 重新编辑先由服务端 CAS 确认撤回，再将原正文回填 composer；已派发／撤回失败不回填，切会话迟到不回灌。现有新草稿不被静默覆盖。

## 任务

- [ ] 验证多设备／重放／取消／过预算／停止 Unknown 仍无重复派发。

## 第 4 项：批量发送的宪法裁决

用户要求自然空闲时将多条普通排队消息按顺序以空行合成一条。原 `docs/MASTER-PLAN.md:140` 明确“逐条 flush”，已先按项目指令取得以下例外授权。

**2026-10-30 用户已明确同意此处例外：**“仅这条是合并发送，因为如果这里是逐条发送的话，第一条发出去就会导致会话变成运行状态，然后就变成第二条进入排队了。”已仅修订宪法 F2.2 队列说明对应 Codex 例外，其他工具不变，允许实现下列批次任务。

若获准：只合并同线程连续普通 queued 动作，先原子取得全部成员派发权，保持各动作审计／回执归属，未知不重发、撤回不能落在合并后仍重复发送。两条以上一次 wire，按 seq 用 `\n\n` 分隔；单条与显式插队单条不变，暂停队列仍只经明确恢复。不跨线程或把审批／问答动作拼入正文。具体实现与反例在获准后补入本计划。

- [ ] 先写回归：普通空闲接力 Q1/Q2/Q3 单次 start-turn、正文严格 seq 顺序且相隔空行；插队只发指定一条；暂停不自动合并派发。
- [ ] 原子预留成员，真实撤回/编辑赢者不进入 wire；注册新消息不改变已冻结批次。
- [ ] 保留每个成员明确的批次关系与一致回执、重启/Unknown/迟到回执不二次发送；不能通过假标 cancelled 丢弃原动作投递去向。
- [ ] 设备许可、pending、写边界和消息大小预算在批次上仍有效；单条沿用原逻辑，失败/Unknown 如实呈现。
- [ ] 对原子领取、取消竞态、已合并动作重放与完整派发/恢复执行定序回归；必要迁移幂等且旧库可升级。

实现补充：为保留设备归属，仅合并同设备连续普通消息，不混合不同设备的待发稿。单批上限64KiB，超限后缀保留队列；合并结果未知时可核对整批，不允许旧单条人工继续接口拆条重发。
