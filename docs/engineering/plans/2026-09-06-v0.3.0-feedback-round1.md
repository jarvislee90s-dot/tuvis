## Task 1: #6 Codex 第二轮状态不更新——APP 类通用状态推导核（最重，优先做）

**现象：** Codex APP 同一会话窗口，首轮提问全程可见（黄→绿未读卡）；第二轮提问后看板卡片与宠物头顶卡片均不更新（运行中不可见），且第一轮卡片被点掉后永不重现。

**根因（两层叠加，均已用真实数据锤实）：**

1. **解析层**：`src-tauri/src/monitor/codex_parser.rs:272-374`（`parse_codex_jsonl`）只认 `response_item` 中**带 role** 的条目判状态；Codex 的工具调用条目（function_call / function_call_output / reasoning）**不带 role，全被跳过**。第二轮从第一条 assistant message 落盘起，"最后带 role 的条目"恒为 assistant 纯文本 → `determine_status` 判 Idle（绿），之后几十秒的工具执行完全不可见。
2. **绿卡剔除层**：`src-tauri/src/adapter/mod.rs:250-272`（P1-3）在"上一轮状态缓存已绿 && 未读池无行（用户已点掉 = mark_session_read 删行）"时把绿卡从扫描结果整体剔除。其隐含假设"变绿 = 回合真结束"被第 1 层击穿 → 第二轮第 3 秒起每轮扫描都判绿、每轮都剔。

**关键实测事实**（fixture 依据）：Codex APP 同一会话的第二轮**追加写入同一个 rollout 文件、session_id 不变**（样本：`~/.codex/sessions/2026/09/06/rollout-2026-09-06T13-40-16-01a0753b-*.jsonl`，内含两轮：05:40:24-53 与 05:41:19-43，尾部序列 user → reasoning → assistant message → function_call* → … → task_complete）。`~/.codex/hooks.json` 存在但 hook 事件未产生（`~/.mam/events` 无当日记录）→ 状态纯靠 JSONL 推导。

**目标架构（用户已确认）：**

```
              monitor/app_status.rs（新模块，APP 类状态推导唯一事实源）
              - AppEntryKind 枚举（归一化条目）
              - derive_app_status()  判定核（纯函数）
              - APP_STATUS_STALE_MS + overlay_stale()（自 workbuddy_parser 迁入）
                    ↑ 两个工具各写一个"格式翻译"适配器
   workbuddy_parser（平铺 JSONL → 枚举，行为不变）   codex_parser（解包 response_item/event_msg 外壳 → 枚举，修 bug 处）
```

**归一化条目与映射表：**

| AppEntryKind | WorkBuddy 来源 | Codex 来源 | 判定 |
|---|---|---|---|
| UserMessage | message + role=user | payload.message + role=user | Thinking |
| AssistantMessage | message + role=assistant | 同左 | Idle |
| ToolCall | function_call / function_call_result | function_call / function_call_output | Processing |
| TurnStart | （无，未来演进用） | event_msg task_started | Processing |
| TurnEnd | （无，未来演进用） | event_msg task_complete | Idle |
| Other | （不产生） | reasoning、token_count、item_completed、world_state、turn_context、thread_settings_applied 等记账条目 | 跳过（不参与判定） |

**判定核规则：**
- 从尾部 500 行倒扫，跳过 Other，取第一条有语义条目定状态（这是 WorkBuddy"最后一条说了什么就是什么"的推广；Codex 修复点=工具调用不再被无视）；
- 无任何语义条目时返回"无判定"（None），兜底留给各工具：Codex 保持现状（文件新鲜 → Processing，停更 → Waiting），WorkBuddy 保持现状（→ Waiting）——**两边边界行为都不变**；
- 叠加 300s 规则：Processing 且 JSONL mtime 停更 ≥300s → Waiting（`workbuddy_parser.rs:174-179` 的 `overlay_mtime_stale` 迁入共享核，语义不变）。

**改动范围：**
- 新增 `src-tauri/src/monitor/app_status.rs`（枚举 + 判定核 + 常量 + 单测）；`monitor/mod.rs` 注册；
- `codex_parser.rs`：`parse_codex_jsonl` 状态推导段替换为适配器 + 调核；mtime 从布尔（`file_recently_modified`，CLI 60s/APP 300s 两套）改为向共享核传文件年龄；`aggregate_app_sessions`/Phase1/Phase2 结构不动；
- `workbuddy_parser.rs`：`derive_status_from_tail` 改为翻译适配器（对外函数签名不变），`overlay_mtime_stale`/`APP_STATUS_STALE_MS` 从共享核 re-export 保持兼容；
- **不动**：`monitor/status.rs` 的 `determine_status`（CLI 工具消息模型，本次不统一）、green-drop 剔除逻辑、未读池、sync_unread——第 1 层修好后"绿=真结束"假设重新成立，第 2 层自然恢复正确语义。

**行为保证与测试（TDD）：**
- 先写判定核单测（枚举序列 → 状态；None 兜底；stale 叠加）；
- **Codex 用真实 rollout 的脱敏片段固化 fixture**，锁定四个关键判定：function_call 在尾 → Processing；task_complete / assistant message 在尾 → Idle；user message 在尾 → Thinking；记账条目（token_count/item_completed）在尾不改变判定；两轮同文件场景（模拟用户实测）第二轮运行期为 Processing；
- WorkBuddy 既有全部测试（`workbuddy_parser.rs` tests 模块）原样保留跑通，证明零行为变化。已知一处**顺带改善**需在提交信息注明：回合结束后文件尾若再出现纯记账条目，旧实现误显"运行中"（300s 后才降级 Waiting），新核下正确显示 Idle；
- 现有 `phase2_app_form_tests`（meta-only 夹具等）按新签名迁移，语义对齐（无 role 条目的兜底分侧保持）。

**验收：** `cargo test` 全绿；手工——Codex APP 第二轮显示运行中（黄），结束后转绿并以未读卡重现；看板与宠物头顶一致；第一轮点掉 X 后第二轮结束时未读卡正常出现（green-drop 语义恢复）。

## Task 2: #1 编辑激活中宠物——闪切回环修复（用户选路径 c）

**现象：** 编辑激活中的宠物（增删音频/保存/重命名）时宠物自动切回内置 foxbell（用户称"玲娜贝尔"），且经常切不回来。

**根因：** 闪切本身是设计（`src/components/pet/manage/PetManageDialog.tsx:113-121` `ensureNotActive`，EP5 冻结保护：宠物窗口持有音频内存快照，直改文件会背离）。**真正要修的是 3 个"切不回"漏洞**：
1. 增/删音频（onAdd :310 / onRemove :320）触发闪切后，不点"保存"直接关对话框 → 指针停在 foxbell；
2. 增/删音频后关闭再重开管理对话框（`openPanel:78` 重置 `frozeActive` state）再保存 → `wasActive` 判 false（:129/:165），保存后不切回；
3. `doSave`/`doRename` 抛错走 catch（:154/:204），指针不恢复。

**方案（保留闪切，让它真的只是"闪"）：**
- 闪切标记从组件 state 升级为**可跨对话框重开的持久标记**（localStorage 键，如 `mam-pet-flash-switched` = 被闪切的原宠物 id；保存成功/重命名成功/对话框关闭三个出口统一消费并清除）；
- `doSave`/`doRename` 的 catch 路径：若 wasActive → 恢复原宠物指针 + `emit("pet-active-changed")`；
- 对话框 `onOpenChange(false)` 关闭时：若持久标记在场 → 自动切回原宠物（复用 `saveActiveId` + 事件广播，与现有"保存完成自动切回" :196-200 同语义）；
- 编辑目标始终是原宠物（`selected` 不变），本次不改为"临时副本"模式（那是未采纳的路径 b）。

**验收（手工）：** 激活宠物 X → 增音频（切 foxbell）→ 直接关对话框 → X 自动切回；增音频 → 关对话框 → 重开管理 → 保存 → X 切回；改展示名后保存失败（可断网/构造错误）→ X 仍切回。

## Task 3: #2 "日常闲聊"音频时长"无法读取时长"

**现象：** 修改面板给"日常闲聊"组添加音频显示"无法读取时长"徽标；同文件加到其他组正常；保存重开后显示正常。

**根因：** 四个分组全链路同构（渲染 `VoiceGroupEditor.tsx:45-94`、写盘 `copy_audio_into` import.rs:378-426、探测 `useVoiceDurationProbe.ts` 均无分组分支），差异不在分组。真正缺陷：探测 hook 的失败**永久不重试**（`useVoiceDurationProbe.ts:27` `attemptedRef` 记账，P1-3 防死循环设计）——首次探测瞬时失败（WebView2 媒体引擎冷启动/文件刚落盘）即永久卡徽标；"日常闲聊"通常是用户当次会话添加的第一组，恰好踩中首次探测。

**方案：**
- 探测失败延迟重试 1-2 次（固定 500ms 间隔即可），仍失败才停留 null；重试不 reintroduce 死循环（总次数封顶）；
- "无法读取时长"徽标改为**可点击重测**（点击清除该行的 attempted 记账并重新探测）；
- 顺带修同名覆盖：`src-tauri/src/services/pet/import.rs:417` `fs::copy` 直接覆盖同组同名文件，且前端以 `r.file` 作 React key（`VoiceGroupEditor.tsx:66`）会产生重复行——`copy_audio_into` 目标已存在时自动序号去重（如 `name-2.ext`），返回实际落盘 rel。

**测试：** Rust 同名去重单测（tempdir，参考 import.rs 现有测试风格）；前端 hook 重试逻辑单测（现有 jsdom 体系，mock probeAudioDurationMs 首败后成）。

**验收：** 手工——连续添加同组同名音频不覆盖不重复；添加音频后徽标最多短暂出现（重试成功自动消失）或可点击重测。

## Task 4: #3 设置窗口不跟随暗色模式 + 导入对话框两按钮"未选中"观感

**现象（用户截图为准）：** 主窗口切暗色/浅色，**设置窗口（独立 Tauri 子窗口）恒为浅色**（含外观 tab、导入宠物对话框）；导入对话框"本地导入"分支下"选择文件夹""选择压缩包"两个动作按钮呈实心黑色主色，视觉上像被选中（用户实测的主诉）。

**已确认事实：**
- 设置窗口由前端创建：`src/components/common/main-title-bar.tsx:58` `createWindow("settings", { url: "/settings", transparent: true, decorations: false, ... })`，加载同一 SPA；
- 主题应用：`src/components/common/theme-provider.tsx`（d765439，已含于 v0.3.0）在**模块加载时**读 localStorage `tauri-ui-theme` 并把 `.dark`/`.light` 类挂到 documentElement；跨窗口同步依赖 storage 事件；
- `WindowFrame`（`src/components/common/window-frame.tsx`）与设置页均用主题 token（bg-background 等），无硬编码浅色；
- 静态排查未能锁死"子窗口为何没拿到 .dark 类"——**执行本任务时先现场定位**：运行应用，在设置窗口 devtools 检查 `documentElement.classList`、`localStorage.getItem("tauri-ui-theme")`、窗口创建参数，确认根因（候选假设按序：子窗口 storage 读取/同步失效；`theme:"system"` 分支在子窗口的 matchMedia 差异；模块加载时序）。

**修复方向（架构级，与具体根因无关地根治所有子窗口）：** 主题事实源上移——
- 以 DB settings KV（`get_setting`/`set_setting`，`src-tauri/src/commands/settings.rs:7-13` 已有）作为主题 SSOT；
- 各窗口挂载时 invoke 拉取当前主题应用类，并订阅 Tauri 全局事件（如 `mam-theme-changed`）实时跟随；`setTheme` 写 DB + emit 广播（localStorage 降级为首帧缓存，消除闪白）；
- 窗口创建时可按当前主题传 Tauri `theme` 选项，保证原生边框/标题栏一致。

**4b（独立小改）：** `PetImportDialog.tsx` 本地导入分支的两个按钮（"选择文件夹" :247-261、"选择压缩包" :262-278）由默认实心主色改为未选中观感（outline 或 secondary variant），仅样式，不动逻辑。

**验收：** 暗色主题下设置窗口整体（外观 tab、导入宠物对话框）呈暗色；主窗口切换主题设置窗口实时跟随；两个导入按钮呈明显未选中观感。

## Task 6: #5a APP 类卡片头部重排（全工具统一，不只 WorkBuddy）

**现象：** APP 类会话卡片（WorkBuddy、Codex APP 等）第一行元素顺序错乱：关闭 X 出现在"项目总结"左侧；未读绿点与状态灯同时亮绿（双绿点）。

**根因：** `src/components/sessions/SessionCard.tsx:89-131` 头部行顺序为 [工具标签][项目名][**未读点+关闭X**（:101-118）][总结/hash][分支] | [状态灯 :130]——X 与未读点插在项目名与总结之间。该组件为**全工具共用**，改一处所有 APP 卡生效。

**方案：** 重排为 [工具标签][项目目录名][项目总结/8位hash][git分支] | [状态指示区] | [关闭 X 最右]。约束：
- 未读语义必须保留、双绿点必须消除：未读指示与状态灯**合并为单一指示**（未读时以状态灯形态/徽章表达，不再渲染独立小绿点），实现方式由执行 Agent 定，但看板/宠物卡的未读→已读闭环（mark_session_read / dismiss_session_card 分流，:37-55）行为不变；
- X 仍 stopPropagation，不触发卡片跳转；
- 仅动 SessionCard 一个文件（及必要的状态映射辅助）。

**验收：** WorkBuddy 与 Codex APP 卡第一行顺序符合"标签→目录名→总结→状态点→X 最右"；未读卡仍可一键标记已读；普通 CLI 卡不回归。

## Task 7: #5b 通知历史双清理按钮

**验收：** 两按钮分别生效且持久化（重启后已清空不回显）；未读角标计数同步正确。
