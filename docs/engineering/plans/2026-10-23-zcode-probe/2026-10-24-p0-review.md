## 2. 接受与修正

### 2.1 读取根因：接受，可安排独立修复

两平台真实活动主会话均包含 session_＋32 hex；Tuvis v0.6.1 仅接受 sess_＋严格 UUID，造成全漏或部分漏。旧形态仍可能活跃，必须双形态兼容，保留原始 ID，不重命名／转写数据库。

这证明读取入口缺陷，不证明门放开后每张卡的状态、正文和附件都正确。后者属于修复的回归与产品验收，不必再重复一次 P0 调查来证明同一 ID 断点。ID 来源及时间切换原因暂不阻塞双形态兼容，也不能凭时间相关性认定某次升级是唯一触因。

Mac 报告把正文／附件列 GO_WITH_LIMITS，本复核收窄为“源码读取路径存在，运行闭环 NEEDS_EVIDENCE”；当前无消息端点的安装版端到端读取证据。

正确结论：

- prompt 面无可交互审批客户端的限制，不能推导为整个 ZCode 都没有审批／问答。
- Tuvis 当前没有接入 ZCode 决策通道是事实；上游源码已有交互实现也是事实。
- 协议服务自持回合的审批／问答与“附着现有 APP 回合”是不同能力。后者仍 NEEDS_EVIDENCE，而非“已证明不存在”。
- 需要继续追 APP host／source-server／RPC 到持有会话的协议实例；不能因为查不到第一套方法名就判 NO_GO。
- 早期文档 session/cancel 的表述保留历史含义；本次已找到 session/stop 实现。v4 具体 stop 命令与测试仍须一起核对，不按文档名称直接发包。

### 2.3 Windows provider 环境“最终代码未处理”：不采纳

Windows C-04 使用旧合流点 d5cc28b1 的 gate 实现。对 #117 最终 head 289b20db 的核对结果：

- gate.rs:130–137，provider_config_env 在 Mac 无条件返回，在 Windows 推导路径存在时返回。
- gate.rs:141–147，probe_env 调用该函数注入环境变量。
- 同文件 provider_config_env_is_set_on_windows_only_when_present 有正反例测试。

因此“#117 最终 Windows 完全未注入 provider env”不是有效结论。当前安装包环境需求仍需后续实测，但应按最终版参数构造做验证，不为旧分支已经解决的问题重复设计修复。

真实 hi 模型回合作为自动版本探针仍与当前 #174 原则不符，不能因旧实现有此设计就移植。
