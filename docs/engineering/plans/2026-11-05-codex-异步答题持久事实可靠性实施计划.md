## 4. T1：定义版本、结果与缓存状态

先新增纯内存状态机测试，再实现 `hint_state.rs`。类型使用设计 §3；对外 HTTP/SSE 不增加字段。

### 4.1 接口定案

`InteractionHintStore` 保留 `load` 的当前 None 降级语义；删除无结果的旧写入入口，全部实现同时改为：

```rust
fn begin_epoch(&self) -> Result<i64, HintStoreError>;
fn write_batch(
    &self,
    epoch: i64,
    hints: &[VersionedHint],
    at_ms: i64,
    permit: &HintCommitPermit,
) -> Result<BatchWriteReport, HintStoreError>;
```

`BatchWriteReport` 按事实键返回 `Applied`、`AlreadyCurrent` 或 `Superseded` 及当前实际行。`HintStoreError` 至少区别 Storage、VersionCollision、Fenced、VersionExhausted；日志只输出类别/阶段，底层错误不直接拼入业务正文。

v2.2 的 `HintCommitPermit` 定义在新增 `hint_commit.rs`，由实际 lease/mirror 生命周期签发，生产接口必须传入，不能提供默认放行实现。owner/scope Fenced 是旧上下文终态，不作为暂时存储失败重试；writer epoch Fenced 仍按原写入运行处理。现有 T1 纯状态机不依赖栅栏 I/O，T3/T4 接续接口并补提交边界。

`StoredInteractionHint` 增加可空 `observation_epoch`、`observation_seq`。DAO 只依赖自有数据库类型；生产 store 将业务版本/报告显式转换，不让 DAO 依赖 services。

内部侧载结构同步在 `hint_state.rs` 定义；`OwnerLease`/`ThreadKey` 使用现有类型。mirror 重建序号通过只读内部 accessor 取得，不序列化到远程协议：

```rust
#[derive(Clone, Debug)]
pub struct HintObservation {
    pub key: super::types::ThreadKey,
    pub owner: super::types::OwnerLease,
    pub mirror_generation: u64,
    pub hints: Vec<VersionedHint>,
}
```

adapter 在同次镜像观察中将其与原 permit 包装，不回改已实现的纯状态机职责：

```rust
pub struct AuthorizedHintObservation {
    pub observation: HintObservation,
    pub permit: super::hint_commit::HintCommitPermit,
}
```

permit 内部 authority/scope 字段不可由远程输入构造；capture 后不按 thread id 重新取得当前 permit 给旧观察。

### 4.2 状态机接口与不变量

提供 `observe`、`prepare_batch`、`apply_report`、`record_failure` 四个内部操作：

- `observe` 在镜像临界区内更新 latest；内容无变化且已有本运行观察时复用其版本，dirty 不清除。
- `prepare_batch` 按最新版本筛掉旧输入；复制工作后释放 std 锁，I/O 不持 std 锁。
- `apply_report` 核对逐项版本；只推进确认的 durable，不用旧 ACK 清掉新 dirty。
- `record_failure` 保留最新 dirty，不提前推进 durable；后续相同事实可再次 prepare。

内容规范化沿用现行三态：Answered→answered，Unknown→unknown，其余交互态→pending。B1.1 不把版本号变成强历史证据。

| 测试                                          | 受控输入                        | 预期                                                    |
| --------------------------------------------- | ------------------------------- | ------------------------------------------------------- |
| `b1_same_fact_reuses_observation_version`     | 同一题连续观察 pending          | 版本不无谓增长，未确认的 dirty 仍在                     |
| `b1_reverted_value_still_advances_version`    | pending→answered→pending        | 三次有效变化次序递增，第三次不能按 durable 内容相同去重 |
| `b1_late_ack_cannot_clear_newer_dirty_fact`   | v1 prepare 后观察 v2，再完成 v1 | latest=v2、dirty=v2；durable 至多确认 v1                |
| `b1_failure_does_not_advance_durable`         | prepare 后失败                  | durable 不进，dirty 保留                                |
| `b1_old_observation_is_filtered_before_write` | latest=v2，送入侧载 v1          | 不将 v1 派给 store                                      |
| `b1_sequence_never_resets_with_owner`         | owner 换代后继续 observe        | sequence 不回零；旧身份侧载不准写                       |

### 5.2 epoch 分配内核

DAO 的函数签名选为 `next_hint_epoch_conn(&Connection) -> rusqlite::Result<i64>`，适配当前 `DeviceStore::with` 的不可变连接引用。沿用仓库已有 `unchecked_transaction`，原子更新是本事务的首次业务操作，不先在事务外读旧值。

```rust
pub fn next_hint_epoch_conn(conn: &Connection) -> rusqlite::Result<i64> {
    let tx = conn.unchecked_transaction()?;
    let epoch = tx.query_row(
        "UPDATE codex_hint_writer_state SET epoch = epoch + 1
         WHERE singleton = 1 AND epoch < 9223372036854775807
         RETURNING epoch",
        [],
        |row| row.get::<_, i64>(0),
    )?;
    tx.commit()?;
    Ok(epoch)
}
```

无初始化行、溢出、busy、commit 失败均返回错误，由 store 转换类别；不能给默认 0。`begin_epoch` 在调用分配内核前还须核对基础 hints、两个版本列和 writer 单行状态均存在且合法；结构不全返回不可用，不能在这里执行 CREATE/ALTER。两个不同连接分配应取得不同 epoch，busy 属可重试失败，不能产生两个“成功但相同”的 epoch。

## 6. T3：事务批写、CAS 与逐项报告

### 6.1 SQL 更新门

在事务内验证 `codex_hint_writer_state.epoch == incoming_epoch`，否则整批 Fenced。每个输入都须具有本运行 epoch、正 sequence、合法事实状态与完整事实键。

版本更新条件如下；参数绑定按实际 DAO 类型完成，禁止插值外来输入：

```sql
INSERT INTO codex_interaction_hints (
    thread_id, source_turn_id, source_item_id, question_index,
    last_fact, updated_at, observation_epoch, observation_seq
) VALUES (?1, ?2, ?3, ?4, ?5, ?6, ?7, ?8)
ON CONFLICT(thread_id, source_turn_id, source_item_id, question_index)
DO UPDATE SET
    last_fact = excluded.last_fact,
    updated_at = excluded.updated_at,
    observation_epoch = excluded.observation_epoch,
    observation_seq = excluded.observation_seq
WHERE
    (codex_interaction_hints.observation_epoch IS NULL
     AND codex_interaction_hints.observation_seq IS NULL)
    OR excluded.observation_epoch > codex_interaction_hints.observation_epoch
    OR (excluded.observation_epoch = codex_interaction_hints.observation_epoch
        AND excluded.observation_seq > codex_interaction_hints.observation_seq);
```

同版本需读取并比较内容，相同为 AlreadyCurrent，不同为 VersionCollision。库内更新版本返回 Superseded 当前行。半空/非法旧版本按明确错误或保守隔离处理，不能被 SQL NULL 比较静默当成普通成功。整批成功报告只在 commit 成功后返回。

**v2.2 提交入口：** DAO 提供内部 prepared batch，持有尚未提交的事务和 report；生产 Store 在原 permit 的 gate guard 内调用 prepared batch 的真实 commit。不得让 DAO 在无 permit 的生产路径里提前 commit，不能用 `before_commit() -> bool` 后放锁代替。隔离 DAO 测试可以保留便利提交 wrapper，生产 Store 必须用受保护入口。SQL 准备、等待 DB 均不持 gate；一个 batch 只含同一 authority/scope。

### 6.2 直接 DAO 测试样例

在 `codex_interactions.rs` 既有 tests 模块新增。`hint`、`mem` 是现有 helper；新 DAO 函数由本任务定义为 `upsert_versioned_hints_conn(&Connection, i64, &[StoredInteractionHint])`，内部按上文事务规则返回报告。

```rust
#[test]
fn b1_dao_older_observation_cannot_replace_new_fact() {
    let conn = mem();
    let epoch = next_hint_epoch_conn(&conn).unwrap();
    let mut newer = hint("answered", 20);
    newer.observation_epoch = Some(epoch);
    newer.observation_seq = Some(2);
    upsert_versioned_hints_conn(&conn, epoch, &[newer]).unwrap();
    let mut older = hint("pending", 30);
    older.observation_epoch = Some(epoch);
    older.observation_seq = Some(1);
    upsert_versioned_hints_conn(&conn, epoch, &[older]).unwrap();
    let rows = get_interaction_hints_conn(&conn, "thread-1").unwrap();
    assert_eq!(rows[0].last_fact, "answered");
    assert_eq!(rows[0].observation_seq, Some(2));
}
```

同步现有 `hint` helper：为两个版本字段赋 `None`。新增 StoredInteractionHint 字段后用 `rg` 检查全部构造点，机械同步测试和生产转换，不能漏改集成测试。

## 7. T4：把版本绑定实际镜像观察

### 7.1 捕获位置

在 `project_mirror` 的调用方持有镜像锁且获得同次观察的题目列表时，立即构造内部侧载，再释放锁。可用局部 tuple 携带，无需改公共投影 DTO：

```rust
let (projection, hint_observation) = {
    let mut mirrors = self.inner.mirrors.lock().await;
    let mirror = mirrors.get_mut(key);
    // 在这里沿用现有投影与序号盖章，并同步捕获本次 hints 观察。
    // 无镜像/运行 epoch 初始化失败时侧载为 None，不假造可持久版本。
    self.project_with_hint_observation(key, mirror)
};
```

`project_with_hint_observation` 是本任务提取的内部 helper，返回现有 `ThreadProjection` 与可选内部 `HintObservation`。其中新增的观察捕获与 authority 状态更新只操作已加载内存，不执行 DB/I/O/await；原投影既有的同步 DB 读取仍属于 B1.3 待迁出项，本阶段不得在持 gate 时执行这些读取。实际 caps、policy、local_seq 与原投影同临界区读取，不能因提取 helper 破坏已有发布协议。

若保留原 `project_mirror` 签名，也可紧接其返回在同一临界区捕获；不得只在 persist 函数里给旧投影发新序号。

### 7.2 覆盖所有入口

- [ ] `projection()`：GET/轮询观察、无镜像分支、发布后的测试会合点均保持语义。
- [ ] `fresh_projection()`：已有镜像快路径也捕获最新观察，不能遗漏。
- [ ] `handle_state_changed`：owner 复核、A1 首帧 hints 加载、正常分支写穿仍有效。
- [ ] `publish_projection`、`republish_all_projections`、`handle_client_status_changed`、`mark_all_mirrors_stale`：按是否真的产生新事实捕获；stale 不是 Answered。
- [ ] `HintObservation` 与原 permit 同次捕获 owner/镜像身份。写前预检查可保留但不是提交边界，最终经原 authority 的单一 gate 核对并跨真实 COMMIT 持 guard，不用当前身份重标旧侧载。

- [ ] 不用 local_seq、revision 或墙钟直接代替 hints sequence；它们负责不同的事实顺序。

### 7.3 失败与 ACK

写穿入口接收已捕获的授权侧载。取得原 hints I/O 闸后先筛旧输入，复制待写项，再调用带原 permit 的 Result 批接口。Store 准备 SQL 后才取得提交 gate，持 guard 核验 owner/scope 并执行实际 COMMIT。撤销先胜则 rollback/Fenced；COMMIT 先胜则允许先提交，撤销等待后完成。gate/DB 锁外才核对每项报告与当前 scope/version；旧 ACK 不清新 dirty、不恢复资格，已提交事实不谎称零写入。

B1.1 接受同步撤销等待 COMMIT 的限制，不能称为短锁或慢库隔离通过；B1.3 另行实现异步 transition。完整细则及锁反向边见 owner 裁决。

### T9：单 worker、有界分批与自动重试

- [ ] 新增 `hint_writer.rs`，先使用一个 worker；不改全局 journal_mode，不宣称并行 SQLite 写。
- [ ] 128 线程、256 键每批、4 MiB 待写预算均可注入；这是待验证初值，256 不是历史总题数上限。

### T10：停止监督、热交接与最终验收

- [ ] owner/mirror 撤销使用 TransitionPending/Revoking→后台等待 gate→ticket 复核完成换代；pending 立即关闭该线程新动作/观察准入，但不是撤销已完成。forwarder 不 await 等待；恢复后复用既有 owner 恢复流程取得 fresh snapshot。
- [ ] 覆盖并发 reset/rebind/stop；旧 transition ticket 不得撤销/发布新 lease。新增 `b1_revocation_during_slow_commit_does_not_stall_other_threads`：阻塞持 gate 的 COMMIT，再送失效帧与其他线程超过 256 条广播，证明其他线程仍消费且无 lag。B1.1 同步栅栏测试不能替代本项。
