## 一、结论先行

- **走通了**：用户**卸载 Tailscale 后从零**走完 MAM 向导的 Windows 流程——用户报告覆盖
  `detect` → `download` → `install` → `login` → `shields_up` → `funnel` → `verify` 七步，
  **全程正常**，没有卡在某一步、没有需要手敲命令或查文档（第 8 步 `autostart` 是 MAM
  自身行为，不构成一次用户动作，用户未特别报告）。
- **据此改了一个验证位**：实测覆盖起点由第 6 步（`shields_up`）**前移到第 1 步**
  （`detect`）⇒ 未验清单为空 ⇒ `windowsVerified = true` ⇒ 前端那条
  「Windows 只实测了后半段」的黄标撤下（提交 `be71de3`）。
- **证据强度 = 口述（当事人陈述）**——既不是 A 级（本机实测产物），也不是可复算的取证。
  故本记录**逐条标注**：哪些是"用户报告正常"、哪些是"设计行为/代码常量"、哪些**尚未复核**。

## 三、走了哪几步（用户报告的流程）

> 下表按步骤表顺序列出**用户报告的经过**。其中"MAM 自动完成"的步骤，其**内部细节**
> （下载校验、写后回读、可达性探测等）写的是**设计行为**，用户只报告了"全程正常、没卡住"
> ——**不要**把这张表读成逐步取证（也没有任何产物，见"产物"列）。

| #   | 步骤 id      | 谁做                      | 用户报告的实际经过                                                                                                           | 产物 |
| --- | ------------ | ------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ---- |
| 1   | `detect`     | MAM                       | 卸载后向导判「未安装」，给出下载入口（**设计行为**：用户报告的是"从零开始走通了"）                                           | 无   |
| 2   | `download`   | MAM                       | 从官方源下载 MSI 并校验完整性（**设计行为**）                                                                                | 无   |
| 3   | `install`    | MAM 触发 + **用户点 UAC** | `msiexec /i`（**刻意不加 `/qn`**）：**用户自己选了安装路径**，并过了 UAC 授权——这两点由用户明确报告                          | 无   |
| 4   | `login`      | 用户在浏览器              | 完成 Tailscale 登录（本次走的是 MAM 主动取链接**之前**的构建，见 §七）                                                       | 无   |
| 5   | `shields_up` | MAM                       | 自动关闭「阻止传入连接」（**设计行为**：写后回读）                                                                           | 无   |

## 七、未覆盖 / 待真机复核（登记在案）

这几条是**本次之后**才进代码、且**尚未在 Windows 真机复核**的面——不得因为"用户走通了向导"
就当成已验：

1. **`tailscale login` 主动取链接**（提交 `673031a` 起）：新装机器 `NeedsLogin ∧ AuthURL=""`
   时由 MAM 后台 `spawn tailscale login --timeout 15s` + 有界轮询（≤9.5s）取回授权链接。
   用户本次走的是**这条链路进代码之前**的构建（据提交顺序：撤黄标的 `be71de3` 为
   2026-10-08 00:32，取链接的 `673031a` 为 00:43；当时登录步还是"无可点之物"的形态，
   见 `673031a` 的说明），故这条链路**没有真机样本**——本次走通向导**不**等于它被验过。
2. **`--timeout 15s` 的实际行为**：`login` 的 `--timeout` 默认 0s = 一直等；15s 有界参数
   在 Windows 真机上的退出形态（退出码 / 是否留 AuthURL）**未复核**。
3. **kill 等待者对 `AuthURL` 的影响**：轮询窗尽时 MAM 会 kill + wait 那个等待者——杀掉它
   会不会让**已经生成**的 `AuthURL` 失效？本机（macOS）无法验证 Windows 行为，当前取保守
   口径（拿到链接一律不杀）。**两条真机复核项**：① `--timeout 15s` 超时退出后
   `status --json` 的 `AuthURL` 是否仍在；② kill 掉等待者后 `AuthURL` 是否仍在。
   任一为"失效"⇒ 需要重新设计（例如把登录等待者交给 GUI 客户端）。
4. **恢复窗口内的"假待做"**：开机后后端重连期间，登录步可能呈现「待做」+「获取登录链接」
   按钮，而机器其实已登录（判据只看 `BackendState == "Running"`）。危害有界（点下去只是一次
   有界等待、不改配置），但**待裁决**：给登录步补一道 W-A 初始化门，或把该窗口内的登录步
   呈现成 amber「恢复中」（已登记进设计说明书 §C3 要求 7 的六处写表）。
5. **MSI 路径选择 + 服务登记兜底**（`278f77f` 的 CLI 非默认路径发现）：本次用户**走过了 MSI 的
   路径选择界面**（§三 第 3 步），但**最终装到默认路径还是自选路径没有登记**——故 CLI 发现链
   第二来源（读服务登记 `ImagePath` 推同目录 CLI）**在本次是否有真机样本无从判断**；
   该来源的真机形态**未逐字段复核**（本机为 macOS，只有注入测试可跑）。
