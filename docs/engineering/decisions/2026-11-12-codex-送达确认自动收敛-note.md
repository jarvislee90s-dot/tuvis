## 二、消息队列与派发

### 2.1 合并两个已认可方案

沿用 [Codex 队列占位收敛与强制插队设计](../specs/2026-11-11-codex-队列占位收敛与强制插队设计.md) 的历史 book 修复、持久核销和独立接管，补入本 note 原有的送达确认自动收敛。

| 判定对象     | 证据与结果                                                                        | 权衡                                                          |
| ------------ | --------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| 消息已送达   | 本动作正式用户消息证据成立：Unknown → Accepted，补绑对应 turn，更新远程待确认提示 | 不必等模型结束；同时保持运行占位，避免把送达确认误当串行放行  |
| 回合已结束   | 对应 turn 的明确终态及既有新鲜度、运行态条件成立：核销该动作 DB fence 与内存 book | 增加跨层一致性处理，避免只清 DB 后后继仍卡死                  |
| 用户强制插队 | 对选定 queued action 的既有显式确认形成独立接管，只优先发送本条                   | 不依赖历史完成证明或自动清理成功，但不把旧 Unknown 伪记为完成 |

### 2.2 后到送达证据

- 优先按正式 `userMessage.clientId` 等本次消息身份匹配，并核对线程、actionId、attempt 与 turn 归属。
- 正文 hash 仅作补充：必须限定本动作的派发关联、候选 turn 和唯一正式 `userMessage`；全历史任意同文不能证明本次成功。
- 请求参数回显、显示气泡、重复同文或缺失关联均不能单独落 Accepted；证据不足继续 Unknown，不自动重发。
- 复用既有手动“检查是否送达”的身份核对、回执收敛和回合补绑能力，接入后台后到证据消费；后台与手动核对共用幂等入口。
- 先成功持久化对应回执与 turn 关联，再同步该动作的内存关联并通知远程视图；不得只更新提示而账本仍 Unknown。
- 回合仍 active 时保留对应运行限制；不能只删除 `settle_turn_evidence` 的终态条件，否则会提前释放运行屏障。
- 权衡：投递状态和运行状态分别收敛，增加一条证据消费路径，换取及时纠正而不破坏普通队列顺序。

### 2.3 完成核销与新旧动作归属

- 统一完成核销入口，按 `ThreadKey + actionId` 清理；同一动作有多次尝试时同时比对 attempt，绑定的 turn 也必须一致。
- `verified_complete` 与该源动作 DB fence 的清理同事务提交；成功后才条件清其内存 book，不执行整线程无条件 `clear_active`。
- 旧 A 的完成证据、回执或迟到回调不得清掉新 B 的 book、claim 或真实运行限制；重复证据无额外效果。
- 沿用前述设计的持久核销记录及 `explicit_takeover` 作用域；自动完成核销与本条接管不得互相冒用，也不冒写人工解除时间。
- DB 失败保留限制并可幂等重试；DB 已提交但内存未清时，由对账按记录补清；迟到结果不得复活已核销限制。
- DB fence 为空、runtime idle 或时间经过均不能单独证明旧动作完成；已有孤儿 book 可精确对账，不能猜测送达或重发。
- 权衡：保留最小持久语义与迁移成本，换取重启、竞争和迟到结果下可恢复的一致性。

### 2.4 强制插队独立接管

- idle 且无真实 writer：选定单条直接取得下一次合格派发优先权；旧 book 或无完成证据的 Unknown 不能永久挡住本条。
- active：沿既有 `confirm` / `expectedTurnId` 确认与停止流程，确认目标回合终态后再发送；上下文改变或停止未知时不得发送。
- 接管不依赖自动清历史成功，不拼接其他旧条、不顺带 flush 整队、不解除队列暂停，也不修改旧 Unknown 的投递事实。
- 争锁前登记有界优先意图，获锁后复核当前 runtime、目标仍 queued 及授权；reserve、grant attempt 的 CAS 消费与接管记录原子提交。
- 保留真实 writer 串行锁、派发任务/RPC 与 claim 生命周期；已在写的任务不能被抢锁，前台超时不撤销真实在途责任。
- 撤回、离队、取消、超时、能力拒绝或存储失败须收尾意图；只绕过历史顺序占位，仍返回真实在途、停止未知等具体原因。
- 权衡：为历史残留提供独立故障出口，代价是额外调度状态；幂等和单条作用域避免授权扩散及重复写入。

## 三、取消文件预览目录限制

v0.6.6 已是全盘可读、仅在主目录内另设敏感黑名单，并有产物子路径豁免；并非仍只允许项目目录。
`AppData` 整段拒绝覆盖了用户临时目录，导致 Temp 产物被挡；本次选择取消目录黑名单，**作为默认行为**，不增设可选“全盘模式”，也不只添加 Temp 豁免。

- 移除 `read_file_safe` 等文件预览链的目录黑白名单准入拒绝，包括敏感目录拒绝、home 不可用时的凭据段拒绝及仅为绕过这些拒绝设置的子路径豁免。
- 用户临时目录、主目录下原敏感目录及其他目录中的普通文件，只要 OS 允许 Tuvis 进程读取，均可沿现有预览入口读取；不追加逐文件确认。
- 保留合法路径解析、相对路径按会话 cwd 解析、canonicalize、普通文件检查及只读语义；保留 OS ACL 的真实拒绝、缺失和 IO 错误，不再伪报目录策略拒绝。
- 读取权限变化不扩大写入能力；附件落盘位置、文件名消毒和目标工具自身权限保持原契约。
- 沿用现有远程端点总闸门、设备认证与凭据有效性检查；文件面板及产物图片使用同一读取入口，不留第二套目录准入规则。
- HTML iframe 保留 `sandbox="allow-scripts"` 且不加 `allow-same-origin`；保留现有 CSP、nosniff 与私有内容缓存约束，文件脚本不能继承本人凭据。
- `remote/files.rs::SENSITIVE_DIRS` 仍被 `inject/create_path.rs` 引用，**不能整表删除**；本次只解除预览链引用，保留创建会话的原表值与判定。
- D21 的创建路径黑名单、ASCII、本地卷等约束不变；预览文件类型识别、产物展示类型范围也不因目录开放而扩大。
- 权衡：去掉持续补豁免的维护成本，让认证后的本人按 OS 权限读取；代价是原敏感目录内容也可被读取，信任边界统一回到已授权总闸门，渲染隔离继续保留。

## 四、增大预览与文本/图片上传容量

### 4.1 基线与建议值

以下以文件净字节计，**1 MiB = 1024 × 1024 字节**；建议值尚非用户逐项确认，不新增设置 UI。

| 能力                | v0.6.6 已知限制                                        | 本稿建议上限              | 取舍                                               |
| ------------------- | ------------------------------------------------------ | ------------------------- | -------------------------------------------------- |
| 文本完整预览        | `remote/files.rs::MAX_TEXT_BYTES` = 500 KiB            | 10 MiB（10,485,760 字节） | 读取范围显著增大，但避免把大文本全部交给高成本渲染 |
| 图片预览            | `remote/files.rs::MAX_IMAGE_BYTES` = 5 MiB             | 50 MiB（52,428,800 字节） | 支持较大原图，需保留懒加载、并发限制和资源回收     |
| 文本/图片单文件上传 | `remote/attachments.rs::MAX_ATTACHMENT_BYTES` = 20 MiB | 50 MiB（52,428,800 字节） | 上传和完整预览分别定额，保持服务端有界接收         |

### 4.2 预览与传输契约

- 文件大小等于上限应成功，超过上限应明确拒绝；读取前检查及实际读取均须有界，避免 stat 后文件增长突破内存预算。
- 首版建议：文本超过 10 MiB 返回明确 `too_large`，显示实际大小和完整预览上限，提示在本机分割成较小文件后查看；不得返回空内容冒充成功。
- 本稿不宣称已有分块/分页 API；若采用截断或分页，须另行补齐读取范围、总大小、未显示内容提示和接口契约，不能静默截断。
- ≤10 MiB 可完整读取不等于必须全量语法高亮或 Markdown/HTML 自动渲染；大文本优先有界纯文本呈现，渲染预算须验证，未显示部分不得冒充空内容。
- 上传 50 MiB 文本可以成功而完整预览超限；上传成功提示与预览超限提示分别表达，不把 10 MiB 预览阈值误用为上传限制。
- 已核实移动端 `api.uploadAttachment` 通过 XHR 向 `/m/api/v1/session-attachment` 发送单个 File 原始字节；当前不是 multipart 或 base64 上传，不为扩容另造批量 API。
- 多选沿现有逐文件请求，每文件分别校验 50 MiB，不以整批合计替代单文件阈值；上传调度须有界，进度、取消与逐文件失败状态继续有效。
- 当前原始字节请求的 body limit 应容纳完整 50 MiB；后端文件限额、路由 `DefaultBodyLimit`、前端校验和错误文案统一采用相同净字节口径。
- 如链路涉及 multipart 或 base64，HTTP 总请求体应计入封装开销：base64 长度为 `4 × ceil(n/3)`，另计 JSON/字段；不得以 50 MiB 编码体预算误拦 50 MiB 文件。
- 多文件若未来合并请求，总体预算须另行有限定义为文件净字节总和加封装开销；本次不改变现有一文件一请求接口。
- 文本预览 JSON 转义、图片解码、传输副本均可能放大内存；保留图片懒加载、最多两个读取在途及 object URL 回收，不设无限读取/并发预算。
- 超限响应须让前端稳定识别，包括 HTTP body limit 在 handler 之前拒绝的路径；中英文提示应展示正确阈值，OS 错误不得被容量文案掩盖。
- 权衡：先扩现有接口与有限阈值，避免设置 UI 和新传输协议成本；高亮、图片解码、弱网上传的性能边界仍需实测。

## 五、会话消息列表与控件归属（2026-11-13 补充）

### 5.1 现象、已确认结构与证据边界

- 用户新增反馈为“会话已显示最新，下面仍有展开/加载按钮”，本期处理其可见列表与控件归属。
- 截图可见“总结模式”“展开全部”“加载更多消息”；当前源码分别提供“加载更早消息”（`zh.json:3006`）、“展开全部”（3012），另有“跳到最新消息”（2992）滚动按钮，没有“展开最新”字面。仅记录截图与源码的文案差异，不将截图右下滚动条的灰色三角认定为该应用按钮。
- 源码核对表明：`SessionDetail.tsx:646–650` 定义 `codexProjectionActive`，1901 起渲染 Codex 投影 `loadedMessages`；通用 `<ul>`（2093）已有 `!codexProjectionActive` 门控。
- 通用 summary-banner（2000）仅判 `isSummary && toggleableMessages.length > 0`，loadMore（2075）仅判 `hasLoadMore`，两者缺上述门控，故 App 投影显示后仍能挂出通用控件。
- `expandAll`（1466）只改变隐藏通用 `messages` 的折叠状态；loadMore 点击（2085）只 `setLimit`，触发通用 fetch（843–862），均不能直接控制可见投影。App 双消息源切换的结构缺陷与截图相符；CLI、ZCode 等通用分支的控件则绑定可见通用列表。此结论依据渲染与 handler 接线，尚未现场点击复现，跨工具真机表现待验。
- v0.6.6 与当前源码此处同构；当前进程为 debug，版本字段 0.6.5，尚未 GUI 复现，不能把截图认定为正式 v0.6.6 现场，也不能据此认定 stale。

### 5.2 本期最小设计与交互契约

- 按当前实际可见消息源绑定控件：App 投影激活时，通用 summary-banner 和 loadMore 均加 `!codexProjectionActive`，与通用 `<ul>` 对齐；不能只按工具名称或 idle/finished 状态隐藏。
- 通用分支继续使用自身历史和折叠状态；“展开全部”必须改变可见内容。工具、会话或消息源切换后，控件只反映新可见列表，不残留上一分支的操作入口。
- 通用 `hasLoadMore`（1489）为 `(messages.length >= limit || truncated) && limit < 1000`，每次增加 200，后端读取尾窗；因此“最新已可见，同时还有更早历史可加载”合法，不能删除其他工具的正常历史按钮。
- 通用按钮明确为“加载更早消息”，置于对应可见列表顶部；扩展尾窗后将新增更早记录前插并保留原阅读锚点，不能跳到另一处或把历史加载解释为获取最新。
- 右下“跳到最新消息”仅滚动当前可见列表；距底部大于 240px 时显示，到底隐藏，点击不请求历史。该条定义验收行为，不据截图指控现有阈值有 bug。
- 权衡：首选补齐已有源门控，以最小改动消除无效入口，并保留正常通用历史；统一重构双消息源成本更高，本批不扩展为投影折叠功能或新的分页系统。

### 5.3 Codex 历史与能力边界

- 真正保留或新增 Codex 正文历史入口，须接 `useCodexThread.loadEarlier`、`historyToken`、`beforeId` 与 `MessagesPage.status`（`ready/end/loading/unavailable/cursor_invalid`），分别表达可继续、结束、加载中、不可用和游标失效。
- 当前仅文件定位链 `useArtifactJump`（`SessionDetail.tsx:744–751`）接入该分页能力，没有独立正文分页按钮；通用 `setLimit` 不等于投影翻页，本批不强行补建上述入口。
- 保留投影 `partial/truncated` 提示、健康状态和文件定位分页能力；隐藏无效通用控件不表示历史完整，也不能改用通用消息补齐投影。
- 权衡：保留现有可用能力并如实呈现边界，代价是本期不新增独立 Codex 历史按钮；若后续需要该入口，必须完整接入现有状态契约，不能用一个无效按钮占位。

## 七、验收标准 / 测试要点

以下全部待验；设计落盘不代表实现完成、自动化通过或真机验证通过。证据仅保留版本、场景类别、脱敏状态、结果和次数，不含私人线程 ID、正文或原始帧路径。

| 待验场景                             | 完成判据                                                                                                                                |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| 真实 router → Unknown → 后到送达证据 | 由实际派发建立 book，回合仍 active 时自动改为 Accepted、补绑 turn、远程提示同步；运行占位保留，实际写入仅一次                           |
| 对应回合完成                         | 终态证明成立后先提交 DB，再精确清同动作占位，后继按原规则接力；同进程无需重启                                                           |
| 弱证据与缺失关联                     | 旧消息同文、多义 hash、仅参数回显或无动作关联时保持 Unknown，不误绑、不重发                                                             |
| 强制插队故障兜底                     | DB fence 已空/book 残留或历史 Unknown 无完成证据时，idle 且无 writer 可只发选定单条，不等待自动清理、不拼旧条、不解除暂停               |
| active 与真实 writer                 | 确认 expectedTurnId 停止且终态成立才发送；停止未知不写出，writer 最大并发为 1，优先意图异常可收尾                                       |
| 旧 A / 新 B、重复操作                | 旧 A 完成或迟到不清新 B；重复核对/点击幂等，CAS 只消费一次，任一 Accepted/Unknown 不再派发                                              |
| DB 失败与恢复                        | 回滚不清内存、不半消费；提交后中断可按持久记录恢复，迟到不复活已核销限制                                                                |
| Temp PNG 与原黑名单普通文件          | 使用临时隔离样本，预览面板及产物图片均可读取；home 缺失、别名路径也不重新引入目录拒绝                                                   |
| OS 拒绝、缺失与非普通文件            | 实际权限拒绝仍失败且原因准确，缺失/目录/IO 不伪报敏感或空成功；预览不产生文件写入                                                       |
| 文本、图片与上传容量                 | 分别覆盖旧阈值以上至新阈值、恰好新阈值及多 1 字节；单位一致，50 MiB 文本上传成功但预览超限有可操作提示                                  |
| 多文件、请求体及编码                 | 多个合法文件逐个成功，超限文件独立失败；真实路由 body limit 与前端均不提前拦边界；涉及 multipart/base64 时计入开销，不伪称新 API 已存在 |
| 大文件性能与内容隔离                 | 文本无假空/静默截断，图片在途及资源回收有效；HTML sandbox/CSP/nosniff 继续隔离脚本与本人凭据                                            |
| 共享创建策略回归                     | `inject/create_path.rs` 的黑名单及 D21 约束保持，不能因移除预览引用或误删共享表而放宽新建会话                                           |
| App 投影与通用缓存                   | 投影开启且通用缓存超过 200 条、存在可折叠消息时，均不出现通用总结/展开及历史加载控件；idle、finished 同样成立，控件不能操作隐藏消息     |
| 工具、会话与消息源切换               | App、CLI、ZCode 及其他工具之间切换不残留上一来源控件；通用分支原有历史和折叠正常，点击展开确实改变当前可见内容                          |
| 最新与更早历史共存                   | 通用尾窗已含最新消息且仍可读更早历史时，顶部保留“加载更早消息”；其请求增加更早记录，不能将按钮存在判为 stale 或无历史                   |
| 历史置顶与加载保锚                   | 历史入口位于对应可见列表顶部；加载成功后原阅读消息及视口位置稳定，新记录前插，不跳到最新或错误消息源                                    |
| 回最新箭头                           | 只滚动当前可见列表；距底大于 240px 显示、到底隐藏，点击不发起通用或投影历史请求                                                         |
| 投影健康、截断与文件定位             | `partial/truncated` 和健康提示继续如实显示，文件定位仍可沿既有游标加载；不回退为通用消息、不把隐藏按钮解释为历史完整                    |

## 八、风险清单与本次不动项
