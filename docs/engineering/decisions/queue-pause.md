# 队列暂停裁决

## 2026-10-28 · 暂停是保护闩，不在 GET 中自动删除

- 背景：按“无 queued/无屏障”自动删除暂停行会误删并发新建的 token，且 30 秒无法证明在途任务结束。
- 决定：读取路径不删除持久暂停；无旧队列时仅隐藏暂停条；保留显式“恢复队列”和“本条先发送”。
- 后果：空暂停不再产生无意义黄条；暂停行仍可能阻止后续已入队消息自动接力。
- 状态：active。

## 2026-10-28 · 入队后必须显示“恢复后发送”

- 背景：空暂停隐藏后，新消息遇忙入队不会自动接力，用户容易误以为空闲后会自动发送。
- 决定：保留“入队后仍需用户恢复”的产品取舍；`codex_queued` 后立即重拉 send-info，显示暂停提示和恢复/先发入口。
- 后果：不自动清闩、不全局放宽旧队列；恢复后按原 FIFO 继续。
- 状态：active（提示位置由下一条收窄到队列区）。

## 2026-10-30 · 暂停是派发保护闩，不是入队否决

- 背景：队列展示收纳把“暂停说明/恢复/本条先发送”全部收进队列区后，用户确认的链路变成
  “先入队，再到队列区对某一条点『先处理这条』”。但后端旧策略在“已暂停且有更早排队条目”时
  对新普通消息直接 `finish_not_sent(queue_paused)` 终态拒绝——消息根本不在队列里，也就无从
  “先处理这条”（2026-10-30 收纳复审 Q01）。前一轮把它当成“纯展示改动”是漏判了这道后端口。
- 决定：暂停只冻结**派发**。旧队列在场时，新普通消息与 `queue_only` 同样返回真实
  `codex_queued`：持久在账、零 start-turn 帧、旧暂停与旧队列原样保留；用户的处置出口是队列区
  的“恢复队列”（按 FIFO 接力）或对单条“先处理这条”（一次性越队授权）。
  显式 `bypassPausedQueue` 路径语义不变（async 题卡“仅本题先发”仍走它）。
- 后果：`queue_paused` 不再是普通发送的终态理由码，仅存于越队授权消费失败等既有一致性
  拒绝面；前端 `reasonQueuePaused` 文案改为指向队列区的两个出口。设备、原生 pending、
  未知投递、writer 等安全门全部原样保留——入队不等于放行。
- 状态：active。

## 2026-10-30 · 折叠摘要按阻塞原因分档，不按屏障清单长度

- 背景：摘要曾以 `blockedActionIds` 非空判为“待人工核对”。该清单包含“已受理并绑定回合”的
  正常屏障（`native_turn_pending`），回合终态会自动释放——正常发送也会被标成待核对，展开后
  却找不到可解除的东西（2026-10-30 收纳复审 Q02）。
- 决定：摘要状态词由 `blockedReasonCode` 分档：`native_delivery_unknown` / `compat_outstanding`
  → “待人工核对”（并优先于普通暂停）；`native_turn_pending` / `native_turn_active` →
  “等待回合完成”；其余按暂停/排队/无待发。清单读取降级为空不影响该判断（阻塞码独立派生），
  即“空清单”不被当成“无需核对”的证据。
- 后果：正常运行不再闪现人工核对提示；真 Unknown 折叠态仍可见并可进入处理。
- 状态：active。


## 2026-10-30 · 停止类暂停随回合终态自动解除，队列自然接力（推翻 2026-10-28 第二条）

- 背景：用户指出远端排队应与 Codex 自身一致——「主会话停止了之后，排队的会话会自然进到
  主会话；或者直接按插队，它会先终止主会话，然后把队列里的消息打到主会话里」。
  此前「打断后必须手动点『恢复队列』」的取舍让用户在桌面回合已停的情况下仍卡在暂停里
  （本次实机反馈：点了插队、进程确实停了，但队列没有任何一条发出去）。
- 决定（用户 2026-10-30 明示，以最新判断为准）：
  1. **停止类暂停只在「停止在途 / 结果未知」期间作为派发闸存在**。该线程绑定的回合一旦
     拿到终态证据（沿用既有证据门：投影非 stale + 绑定 turnId + 该 Turn 实体以
     completed/failed/interrupted 在场 + runtime idle/failed），`settle_thread` 自动清除
     该线程的**停止类**暂停行，队列按 FIFO 自然接力——不需要用户再点「恢复队列」。
  2. 回合未拿到终态（打断未生效 / 仍在跑）→ 暂停保持，不放行（「停止未生效不要放行」不变）。
  3. 插队仍是「先终止目标回合、确认终态、再把那条打进去」，且旧队列其余条目保持暂停。
  4. 只自动清 `interrupt_pending` / `interrupt_accepted` / `interrupt_uncertain` /
     `cancel_pending` 这类由停止/取消写入的档；其他来源的暂停行不受影响，且清除后若仍有
     其他暂停行，该线程仍视为暂停。
- 实现：`codex_queue_pause` 增 `pause_turn_id`（旧行 NULL = 未绑定，保守保留仅显式 resume）；
  `settle_thread` 在 fence 核对之后、flush 之前调用 `auto_release_stop_pauses`。
  `POST /codex/queue/resume` 端点保留（无暂停行时幂等回执，手动清非停止类暂停仍可用）。
- 状态：active（取代本文件 2026-10-28「入队后必须显示恢复后发送」中的「不自动清闩」部分）。

## 2026-10-30 · 投递身份校验补弱证据；证据不足的 Unknown 屏障不得永久堵死插队

- 背景（实机）：发了 `sleep 300秒`，正文已出现在会话里（确实投递成功），界面却报
  「原生投递结果未知」。真实账本对应行 reasonCode = `client_message_unverified`：
  Desktop 回了 success + turnId，但 2 秒窗口内镜像里没出现 `userMessage.clientId == 本次
  cmid`（桌面侧以自有消息 id 回显）→ 降级 Unknown，且该行屏障无 turnId、无核对证据字段，
  于是既不能靠回合终态释放、也不能靠 reconcile 清掉，队列被永久冻住。
- 决定：
  1. **clientId 强证据保持第一优先**；窗口内若该 Turn 出现**唯一**一条正文 hash 与本次
     wire 一致的 userMessage，同样判 Accepted。只在已 ack 的同一 turnId 内匹配、多义
     （≥2 条同 hash）不采纳、跨 Turn 不采纳、窗口不延长。
  2. 原生 Unknown 屏障落账时补 `compat_wire_hash`（只补空、幂等、不伪造 rollout 证据）；
     settle 路径对 native Unknown 也做一次镜像只读核对，核对通过才清——「到点了 / idle 了」
     仍然不算证据。
  3. 对**确实无任何可用证据**的 Unknown 残留：自动接力仍被屏障冻结（保守面不变），但
     **显式用户插队**（对具体行的知情动作）允许仍可尝试——「未知 ≠ 已知失败」，证据不足
     的保守屏障不得永久堵死插队。屏障本体保留到核对通过或人工解除。
- 后果（如实申报）：旧数据里的 Unknown 行（wire_hash 为空、queued_text 已清）无法被核对
  自动解除，出口是插队 / 人工解除 / 保持冻结；弱证据不支持镜像尾窗外的唯一性证明。
- 状态：active。

## 2026-10-31 · 陈旧停顿记录不得让空闲会话变成「全部排队」

- 背景（用户实机）：会话明明空闲（桌面没有运行中的回合），所有普通消息却一律
  进队列。用户明确重申排队前置条件：「只有在窗口正在运行时才该排队/打断」。
- 根因（两条叠加，均已用真实账本核实）：
  1. **迁移前的停止类暂停行** `pause_turn_id` 为空（本机 6 行 `interrupt_pending`）。
     上一条裁决的 P3 自动解除对这种形态 `continue`（无绑定回合 → 证据无从核对），
     于是永不解除；叠加历史 queued 行后 `send_inner` 的暂停门恒真。
  2. **陈旧 Unknown 屏障**（`compat_outstanding=1`、无 turnId、无核对证据，例如
     本机 `fd273390` 那条 `client_message_unverified`）。`send_inner` 的
     `has_compat_fence` 门对每条新消息生效，与线程是否在跑无关。
- 决定：
  1. `send_inner` 判定暂停前先清理**无回合绑定 + 无在飞回合**的停止类暂停行——
     这类行携带不了任何在途证据，保留等于让一次早已结束的过去操作永久冻结普通
     发送。真实停止保护一律带绑定（P3 起写入即绑定），清理不误伤。
  2. 屏障门对**全部为未绑定回合的 Unknown 残留**放行新普通消息（屏障本体保留，
     待核对或人工解除）；绑定回合的屏障、accepted 屏障、有在飞回合时维持冻结。
- 后果：空闲会话的普通发送恢复直发；「运行中才排队」的语义重新成立。停止在途
  （有绑定、回合未终态）仍然冻结——不会为了"直发"牺牲停止保护。
- 状态：active。

## 2026-10-31 补记 · 漏改 flush_thread：队列必须能排空

- 背景：上一条裁决只改了 `send_inner`（新消息入口），**没改 `flush_thread`**
  （队列接力出口）。结果是：陈旧暂停行/屏障清不掉时，队列里的遗留消息永远发不出去，
  新消息也就一直排在它后面——用户第二次实机看到「全部排队」，正是这个组合。
- 补充决定（与上一条同源，落点补齐）：
  1. `flush_thread` 接力前同样先清「无回合绑定 + 无在飞回合」的陈旧停止暂停行。
  2. `flush_thread` 的**屏障门保持无条件冻结**——崩溃恢复行（reserved→unknown）
     可能已写出，自动重发即双投；这条「Unknown 不是完成」的裁决在接力路径最硬，
     不因上一条的放行而放宽。放行的只是 `send_inner` 的新消息（有实时门核对）。
- 后果：遗留队列可被清空；崩溃恢复场景仍然不自动重发。
- 状态：active。

## 2026-10-31 · 插队不依赖「队列已暂停」（推翻 R04 的越队前置）

- 背景（用户第三次实机）：排了两条消息后点「插队」，进程被终结但**这条消息没发出去**，
  界面只回一句「桌面正忙或仍有未完成的派发」。用户裁决原文：「插队的行为就是需要在
  停止进程了之后，直接把这个消息打出去」。
- 根因（死结，两条规则互斥）：
  1. `prioritize_queued` 内部（`router.rs` 的 R04 接缝）要求「空闲**且队列已暂停**」才
     允许越队，否则返回 `queue_not_paused`；
  2. 上一条裁决引入的「陈旧停止暂停行自动清理」会把暂停行清掉 → 队列变「未暂停」；
  于是暂停被清 ⇒ 插队恒被拒，而同一时刻屏障又挡住自动接力 ⇒ 插队永久不可用、队列也
  发不出去。前端另有一处同源假设（`confirmInterrupt = queuePaused !== true`）会在空闲
  时错误地要求「停止确认」。
- 决定：**插队不要求队列处于暂停态**。它是用户对具体一条的显式意图：桌面在跑就
  先停止该回合、确认终态、再把这条打出去；桌面空闲就直接打出去。FIFO 与全部安全门
  原样保留——授权 CAS 保证恰好一次写出、在飞派发由线程锁挡、未解屏障由
  `barrier_outstanding` 判定、原生 pending 由端点前置臂挡、停止未知由
  `stop_attempt_state` 状态机挡。前端停止确认改按**真实运行态**判定（有共享控制器用
  `turnRunning`，否则取 false），不再以暂停状态作代理。
- 移除：`queue_not_paused` 作为插队拒绝码（常量与其文案保留给其他用途；对应的旧反例
  `t06_prioritize_clear_with_unpaused_queue_stays_fifo` 按新契约改写为
  `..._sends_selected_only`，仍断言 Q1/Q2 原样留队、位次不变、未被借道派发）。
- 状态：active。

## 2026-10-31 · 插队的停止确认必须等终态，不能查一次就判

- 背景（用户第四次实机）：第一次点插队 → 进程被打断但消息没发出去；等远端进程
  结束后**再点一次**才成功。用户判断「打断后桌面有延迟，立刻检查会误判为还没断」。
- 根因（代码确认）：`POST /codex/queue/prioritize` 在 Desktop 回
  `interruptedTurnId: null` 的分支里**只做一次** `fresh_send_gate` 就决定拒绝
  （`stop_not_effective`）。Desktop 回 null 有两种含义——真换代/无可打断回合，或
  **停止已受理但状态帧还在路上**（真机常态延迟）。旧实现一律按前者处理，于是第二次
  点击（此时帧已到、门变 Clear）才成功。
- 决定：该分支给一个**专属终态等待窗口**（`STOP_SETTLE_WINDOW_MS = 3_000`），在窗口内
  轮询到 Clear 就继续派发；窗口耗尽仍不转才判真换代并如实拒绝。窗口取前台预算与此
  常量的较小者（S3「子步骤共用预算、不重置」纪律不变）。
  - 取 3 秒而非用户建议的 5–10 秒：真机被打断的回合通常 1–2 秒内转终态，3 秒已留足
    余量；更长会让真换代场景的插队按钮长时间无响应。
- 后果：第一次点插队即可完成「停止 → 等终态 → 发出去」；真换代场景仍在有界时间内
  如实拒绝（既有反例 `t06_prioritize_stale_target_never_dispatches_and_keeps_foreign_pause`
  保持通过，未被削弱）。
- 状态：active。

## 2026-10-31 · 已受理屏障不得拦住对另一条消息的插队；终态释放须清全部

- 背景（用户第五次实机）：插队成功一次后，**下一次**插队又被拒（「桌面正忙」）。
- 根因（两条叠加，均已用真实账本 + 代码确认）：
  1. `barriers_all_unknown_residue` 要求该线程屏障**全部**是 `unknown` 才放行。
     成功插队会留下一条 `accepted` + 绑定 turnId 的屏障（本机 `250b36a8`），
     于是「成功一次 → 锁死下一次」。
  2. `active_turns` 每线程只存一条（后写覆盖先写），`release_turn_if_complete`
     因此只清**最后一条**的持久屏障——前面那些已终态的 accepted 屏障再无清理路径，
     在账本里越积越多（本机就同时躺着 accepted 与 unknown 两条）。
- 决定：
  1. `barriers_all_unknown_residue` 改为逐条判定：`unknown` 放行；`accepted` **且
     绑定 turnId**（等该回合终态自然收敛的正常在途记录）放行；`accepted` **未绑定
     turnId**（保守屏障）仍冻结。
  2. `release_turn_if_complete` 遍历该线程**全部**在册屏障，逐条按同一证据门
     （绑定 turnId 的 Turn 实体在镜像中以终态在场）清理；证据不足的原样保留。
- 后果：插队不再「成功一次锁一次」；历史残留屏障会在对应回合终态后自然清空。
  「Unknown 不是完成」「未绑定不得自动放行」两条安全口径不变。
- 状态：active。
