# v0.6.3 Codex 异步答题识别缺陷

日期：2026-10-28。结论：已确认当前正式版对新版 Codex 异步问答存在过严的识别条件；本次仅调查，未修改实现。

## 现场

- 用户截图：蓝色“待作答（异步）”卡，已填写“允许”，按钮禁用，显示 `operation_no_evidence`；底部另有普通消息“已进入桌面队列，第 1 位”。
- 运行程序为 `/Applications/Tuvis.app/Contents/MacOS/tuvis`，安装版本 0.6.3。
- 本地 main 与 tag v0.6.3 同为 `5a53b9a7`。
- 当前官方 Codex Desktop：`26.1023.51421`（bundle version 22530），随包 CLI 指纹 `0.165.0-alpha.1.2`。此前验收环境为 `26.1021.31345`，不能把旧版通过直接当作此次新版通过。
- 日志 `~/.tuvis/logs/mam.log` 在 2026-10-28 19:34:59（UTC+8）记录该包匹配 Send、CommandApproval、FileChangeApproval、BlockingInput、Interrupt，**没有 AsyncAnswerIdle**。

## 已确认原因

`src-tauri/src/services/codex_desktop_ipc/probe/desktop_contract.rs` 的 AsyncAnswerIdle 规则要求同时出现固定片段，包括：

- `question:r.P(),answer:r.P()`
- `startsWith(uxe)`
- `endsWith(dxe)`

本次只读解析当前安装包的 ASAR，按源码同样去空白／统一反引号后检查：

- 正式问答开闭标记、questionItemId、紧凑题目标识合成、min(1)、slice(34,-35)、startTurn 分支仍可找到。
- 上述三个固定片段未找到。
- 当前包的开闭标记实际绑定名为 `_Se`／`vSe`，不再是 `uxe`／`dxe`。

其中压缩器生成的局部变量名被当成了稳定契约。仅变量重命名就足以让对应规则失败，造成当前操作无匹配证据。整个包读取成功并识别其他五项，所以不是“完全读不到 Codex 包”。

策略层在没有该项 shipped／contract／observed 证据时给出 operation_no_evidence，前端据此禁用按钮。因此本图属于提交前能力识别拒绝；不能据截图说答案已被 Desktop 受理或正在等待审批。

## 影响与边界

- 这张卡是模型征询用户意见的异步 Question，题干里出现“是否允许”不会把它变为原生命令／权限审批。
- 普通发送、命令／文件审批、阻塞答题和打断已分别识别，不应因修异步问答而连带放开或关闭。
- 普通消息的入队回执与本卡提交是两条路径；不能把入队等同于原卡已答。
- `reasonText` 没有为 operation_no_evidence 提供就近中文说明，截图因此裸露机器码。这是独立的用户提示缺口。
- 本次没有发送真实答题帧，也没有执行题干涉及的 DSH 局域网、配对或控制操作；未声称新版完整清卡行为已验。

## 修复要求与验收

1. 异步识别器按信封结构、数据字段、字符串常量及引用关系核验，允许等价局部标识符重命名；不能仅把旧变量名换成新变量名，也不能删掉全部契约检查或强行置可用。
2. 保留字段类型、题目标识精确合成、方法版本、当前包身份及目标／状态保护；结构实际改变时仍应拒绝。
3. 用当前包最小脱敏片段验证识别，再补“只改变量名仍匹配”和“改变字段／方法版本／信封语义仍拒绝”的正反例。
4. 修复缺证据提示，明确区分尚在识别、识别规则未匹配和当前操作暂时受阻；保留草稿，不把该错误显示为已提交。
5. 在当前 build 的独立会话发送异步题，卡片允许正式提交，确认 Desktop 原卡撤下；普通发送和原生审批对照不回退。
