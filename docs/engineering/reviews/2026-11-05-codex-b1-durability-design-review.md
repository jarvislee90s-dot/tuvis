## 1. 原六项问题的核实结果

| 用户问题                   | 当前证据                                                                                                                             | 相对 B1 目标的缺口                                                                  |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| ① 写失败后可能不再重试     | 最新实际 ensure/load/persist 方法的局部受控验证：连续提交相同 answered，store 只被调用一次，DB 仍 pending，缓存已 answered           | 缺结果接口、待重试记录、成功后才推进的 durable 水位                                 |
| ② 写入顺序不等于观察顺序   | 在旧观察生成后用通道暂停，新 answered 先写，再释放旧 pending；最终 DB 回 pending                                                     | 缺观察时定序及数据库、内存缓存两端的版本比较；A1 异步闸仅解决串行访问               |
| ③ 答复缺失时已答回翻       | 实际 projector/history_view 的局部验证：answered hint 在场，当前信封消失且当前覆盖允许时，Answered → Pending，actionable=true        | 行为已复现，但是否误判取决于历史是否真的裁剪或已回滚；不能把所有这种 Pending 都判错 |
| ④ 旧 answered 不能永久信任 | 实际 patch 应用方法接受连续 revision 的 `/turnHistory/history` 替换；无缺口、无需新 snapshot。世系不变不能仅由传输顺序推出           | 缺可执行的历史变更分类和强事实失效规则                                              |
| ⑤ 慢存储拖慢广播           | 实际 persist 加容量 256 的 Tokio broadcast 受控组合：阻塞写入时发送 257 条，下一次接收 `Lagged(1)`；生产共享数据库锁路径另已源码确认 | 缺生产读写锁隔离；该局部验证不等于完整 production forwarder 压测                    |
| ⑥ 旧行不能迁移成强证据     | 用户未提交迁移测试已编译运行，正确失败于 `missing observation_epoch`                                                                 | 有有效红测；尚缺迁移成功、幂等、事务回滚和 legacy 不增强的通过证据                  |

这六项不是六个新增生产缺陷：①②是当前实现的持久化缺口；③是需结合历史语义裁决的派生行为；④是新方案必须防住的错误复用；⑤是受控可触发的容量风险，尚未测量现场发生率；⑥是新增数据模型的兼容义务。

## 2. 需要先修订的五处方案

### R1 / P2：明确生产数据库锁的隔离，不能用 worker 数量代替

对应设计 §5 第 35—37 行、计划任务 4 第 46—48 行（以本轮受审版本为准）。

生产调用链：

```text
StoreInteractionHints.upsert
  → DeviceStore::with → 全局 Connection 的 std::Mutex

forward_events → handle_state_changed → project_mirror
  → queue_paused_of → queue_pause_source
  → 同一 DeviceStore::with

compute_operations → auto_adapt_enabled
  → auto_adapt_gate → 同一 DeviceStore::with
```

把 hints 事务搬到后台后，该事务仍可持有这把锁；下一帧投影会在同步查询处等待。四个 worker 不会创建四份独立数据库连接，也不会自动使 SQLite 并行写入。

**必须补进计划：**

- 明确提示写入连接、投影读取连接和共享应用连接的关系。若使用独立连接，需要验证实际 SQLite 事务模式、busy 超时、读写并发与关闭行为；不能只改成另一把 Rust 锁。
- 或让投影消费已装载的设置/暂停事实，并明确更新来源、更新时定序和写入口复核；不能用可能过时的设置快照扩大写权限。
- 枚举仍同步访问数据库的投影调用，不仅移走 `persist` 的 await。冷加载提示仍在 `handle_state_changed` 内等待，也须明确是否属于首次订阅允许的等待。
- 区分“广播接收任务不等待提示事务”和“多个线程的提示事务可以并行”。B1 首先需要前者，后者不是必须承诺。
- `slow_store_does_not_drop_broadcasts` 至少一条用例装配共享 `DeviceStore` 与实际暂停/适配门；独立假 store 的测试不能证明生产隔离。

源码依据：[DeviceStore](../../../src-tauri/src/remote/pairing.rs)、[生产装配](../../../src-tauri/src/remote/codex_ipc.rs)、[投影与事件处理](../../../src-tauri/src/services/codex_desktop_ipc/adapter.rs)。

### R2 / P2：把传输连续性与历史有效性分开，缩小完整前缀证明

对应设计 §4 第 27—30 行、计划任务 3 第 38—40 行。

同 owner、连续 revision、未重建 snapshot 只证明接收顺序；合法 JSON patch 仍可删除答案、替换 turn 或整份历史。设计写了“无替换/无不一致”，但尚未定义从哪些字段或变更识别它们，也未说明如何区分裁剪与回滚。

**必须先定义变更表：**

| 当前变更                                              | 已确认答案是否可沿用             | 当前状态的处理                                                  |
| ----------------------------------------------------- | -------------------------------- | --------------------------------------------------------------- |
| 明确追加到答复之后，或与题目/答复依赖无关的元数据变化 | 可在同一有效观察范围内沿用       | 保持 Answered；不复活旧 token                                   |
| 当前直接重新读到同线程、同题、唯一合法答复            | 可重新取得强事实                 | 当前强证据优先                                                  |
| 能通过已取证标记证明只是窗口淘汰，且未出现反证        | 仅在该证明的适用范围内沿用       | 记录证明来源与有效范围                                          |
| 删除/替换答复依赖，整段历史替换，无法分类的移除       | 不能仅凭 owner/revision 沿用     | 标记当前证据失效；是否 Pending 还需当前新历史完整且可证明无答复 |
| revision 缺口、owner 换代、重连/重启但没有当前证明    | 不沿用旧运行的强资格             | Unknown，保留旧证据用于核对                                     |
| 新线程 fork                                           | 原线程事实不自动复制为新线程事实 | 新线程重新按其当前历史派生                                      |

如果上游没有足够字段区分“窗口淘汰”和“语义删除”，两种历史可能给出相同可见数据；此时无法同时承诺永不回翻和永不误清。B1 必须诚实进入 Unknown，B2 再补证。这是证据不足的边界，不能靠换一种 hash 解决。

**完整前缀分支的修订：**

- 当前提议要求从明确起点、完整读取原题及答复，再匹配前缀。该条件下通常已经可以直接核验信封，需先说明前缀分支新增了什么可用场景。
- 推荐首个 B1 版本暂缓跨重启完整前缀复用；直接重见答复则重新确认，无证明则 Unknown。文档明确这是首版范围，不把“可持久化证据”宣称成“重启后自动证明仍有效”。
- 若保留前缀，必须确定版本、稳定编码、字段集合、起点判据、终点及预算。终点应精确到对应答复条目，不能把其后仍变化的 assistant 输出含入稳定证明。
- 生成证明前严格检查原始 canonical 引用：悬空、重复、非唯一条目、未加载 items、缺页均拒绝。`HistoryView::turns()` 的跳过与去重是读取便利行为，不是证明校验。
- 不用仅包含可见消息呈递的 `historyToken` 或 UI 文字摘要充当持久历史世系；不在每次 GET 全量散列无界历史。

源码依据：[mirror 的 patch 应用](../../../src-tauri/src/services/codex_desktop_ipc/mirror.rs)、[HistoryView](../../../src-tauri/src/services/codex_desktop_ipc/history_view.rs)、[异步题派生](../../../src-tauri/src/services/codex_desktop_ipc/async_question.rs)。

### R3 / P2：队列合并必须保留更新的失效事实

对应设计 §5 第 35 行、计划任务 4 第 46 行。

最小反例：

```text
观察 v10：Answered，尚未落库
观察 v11：历史发生改写，必须失效为 Unknown
错误合并：“不能用弱状态覆盖强答复” → 丢弃 v11
结果：只落库 Answered(v10)，数据库 CAS 无法恢复被丢掉的 v11
```

**修订要求：** “保强答复”仅限已证明有效的同一历史范围。把当前事实/失效状态与历史答复证据分开表示：旧证据可以留存，但不能阻挡新失效，也不能继续解锁或自动清卡。

| 排队/在飞状态         | 新观察                           | 合并与落库要求                                    |
| --------------------- | -------------------------------- | ------------------------------------------------- |
| pending(v10)          | 同范围 Answered(v11)             | 用 v11 取代尚未开始的 v10                         |
| Answered(v10)         | 同范围仅展示缺窗，连续性仍可证明 | 保留有效答复证据，推进最新观察位置                |
| Answered(v10)         | 历史失效 Unknown(v11)            | 必须保留 v11；v10 可留审计，当前状态为失效        |
| v10 已在写            | v11 进入待写                     | v10 完成不能把 v11 从内存待写集合删除；随后写 v11 |
| 旧 v10 晚入队或晚回执 | v11 已生效                       | 数据库、内存 durable 水位、待写清理均不回退       |

数据库 `ON CONFLICT` 的版本比较只保护数据库，不能代替入队合并、内存状态和 ACK 清理的版本检查。实现应明确每种“成功”的结果：实际应用、相同版本幂等、因已有更新版本而跳过；不能把事务无异常就当作本批内容已经成为当前事实。

启动 epoch 可用于本地写入排序，但不是历史世系，也不是跨进程真实观察时间。项目已装配单实例插件；首版应明确单个有效写入器的前提，序号不能随 mirror/owner 重建归零，旧写入器的迟到任务需要 fencing。

### R4 / P2：补足空闲重试与 3 秒关闭的最终语义

对应设计 §5 第 36—37 行、计划任务 4 第 46、49 行。

三次失败后仅等“下次观察或显式重新核对”，可能使已完成、无新消息的线程永远不再落库；重新核对入口属于 B2，不能作为 B1 的必要恢复依赖。

**修订要求：**

- 确定错误分类：暂时失败可采用封顶间隔的后台重试，或明确声明本批只在新观察时重试而不保证空闲收敛；要完成原可靠性目标，推荐前者。
- 永久错误如磁盘满、库损坏须保留未完成状态并可诊断，不能无限紧循环，也不能宣称 durable。
- 重试用本地持久化幂等键，只重做本地事务，不发送 Desktop mutation。
- 3 秒只限制停止等待的时长；已启动的 `spawn_blocking` 不能靠 timeout/abort 保证终止。明确仍在飞任务的句柄、连接与所有权由谁保留。
- 热停止后重新启动写入器时，不得让旧任务晚提交覆盖新运行，也不得让旧 ACK 认领新队列。可用数据库事务内的有效写入器标识与版本校验，或明确单写入器完成交接后才能启动替代者。
- 分别描述正常关闭、等待超时、进程崩溃：内存队列未提交时可能丢失；重启不能假称已落库，只能按当前证据恢复。
- UI 仍可先发布观察事实；所有旧的“收到 Answered 帧时 DB 已写完”断言、源码位置锁与验收文案必须一并更新，不只改一条测试。

本轮已核对本机 Tokio 1.53.1 的 `src/task/blocking.rs` 对已启动阻塞任务不可中止的说明；它不构成应用已实现关闭控制的证据。

### R5 / P2：明确容量满后的退路，消除 B1/B2 循环依赖

对应设计 §5 第 36 行、§7 第 48 行；计划任务 4 第 47 行。

“容量不足后安排有界只读恢复”若包括拉新快照或补读历史，就是 B2；如果只从现有 mirror 重算，应明确写为本地重算。

每线程 256 题的硬上限还缺出口：当前 mirror 若有 257 个相关键，重算相同 257 个键会再次溢出，不能通过循环重建恢复。

**修订要求：**

- 初期将 128 线程、256 题和 4 worker 标为待容量验证的参数，不把任意数字当作已验证保证。
- 区分排队容量与需保存的有效证据容量。入队失败必须返回显式结果，由调用方保留 dirty/失效标记，不允许静默丢失最新否定事实。
- 定义每线程字节预算、单批大小、分批排空与公平调度；仅用题目数量不能证明内存上界。
- B1 若仅从现有 mirror 分批重算，要有进度水位与终止条件；超过阈值不反复重置同一整批。
- 无法本地恢复则 Unknown/受影响答题资格关闭；不牵连无关审批或其他线程能力。主动重新取证进入 B2 单独任务。

## 4. 必须补入实施计划的验收用例

| 用例                                             | 受控安排                                              | 核心断言                                                           |
| ------------------------------------------------ | ----------------------------------------------------- | ------------------------------------------------------------------ |
| `hint_write_failure_retries`                     | 第一次事务失败，保留同一事实；推进测试时钟使重试      | 未成功前 durable 不进；成功后仅记录对应版本                        |
| `older_observation_cannot_replace_new_fact`      | 镜像观察旧内容后停住，新观察先落库，再放旧观察        | 数据库和缓存均保留新版本                                           |
| `answered_survives_temporary_window_loss`        | 直接看到答复，再施加已证明的窗口裁剪                  | 仅在证据仍有效时保持 Answered；未知裁剪不假称有效                  |
| `history_lineage_change_invalidates_answer_fact` | 同 owner、连续 revision，合法 patch 替换/删除答复依赖 | 不能因传输连续而保留旧强事实；按新历史完整性判 Unknown/Pending     |
| `slow_store_does_not_drop_broadcasts`            | 暂停生产装配共享 store 的写入，持续投递受控事件       | 提示写不阻塞广播消费；其他同步 DB 读取的等待边界也经过验证         |
| `newer_invalidation_survives_queue_coalescing`   | answered(v10) 未提交，失效(v11) 后到                  | 最新失效不被“保强”策略丢弃                                         |
| `late_ack_cannot_clear_newer_dirty_fact`         | v10 写入挂起，v11 入队，再完成 v10                    | v11 仍待写，durable 不冒认 v11                                     |
| `idle_thread_retries_without_new_observation`    | 已完成线程不再产生事件，暂时存储错误恢复              | 按已选择的保证自动收敛，或明确暴露未完成而非伪通过                 |
| `writer_stop_timeout_rejects_late_commit_or_ack` | 写入越过停止等待时限，启动替代者后释放旧任务          | 旧提交/回执按设计被隔离，或启动替代者被严格阻止直到交接完成        |
| `overflow_rebuild_makes_progress`                | 单线程相关键多于一批容量，多个线程争用                | 分批有进度、有终止，不循环重建同一超限集合                         |
| `legacy_answered_is_not_strong_evidence`         | 旧 answered 行升级后重启，当前无信封                  | 不凭旧状态补证据；字段为空/legacy，当前 Unknown                    |
| `proof_rejects_dangling_or_duplicate_references` | 仅在保留前缀方案时执行                                | 原始引用非法、多义、内容变更均拒绝；不是对过滤后的视图做哈希就通过 |

`tokio::time::pause/advance`、oneshot/通道/屏障用于控制具体时序；超时只能作为测试挂死保护，不能靠随机 sleep 声称覆盖竞争窗。
