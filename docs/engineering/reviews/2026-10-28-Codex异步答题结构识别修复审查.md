## 1. S01 · P2：标记守卫和解析输入没有形成同一条引用链

位置：[desktop_contract.rs:711](/Users/jarvis/Documents/tuvis/src-tauri/src/services/codex_desktop_ipc/probe/desktop_contract.rs:711)、[desktop_contract.rs:777](/Users/jarvis/Documents/tuvis/src-tauri/src/services/codex_desktop_ipc/probe/desktop_contract.rs:777)、[desktop_contract.rs:824](/Users/jarvis/Documents/tuvis/src-tauri/src/services/codex_desktop_ipc/probe/desktop_contract.rs:824)。

`guard_references` 只查 `.startsWith(open)` 后 64 字节内存在 `.endsWith(close)`，不比接收者；`parse_link_present` 只要求任意标识符 `.slice(34,-35)` 被 safeParse 使用，不核它是否正是被守卫检查的输入。二者结果在全体候选文本上分别求存在。

**实跑反例：**

- 原 `!r.startsWith(_Se)||!r.endsWith(vSe)`，仅把后半改成 `!other.endsWith(vSe)`，仍通过。
- 保留原守卫，把 `JSON.parse(r.slice(34,-35))` 改成 `JSON.parse(other.slice(34,-35))`，仍通过。

这不是变量一致改名：被验证与被解析的内容已经不同，仍会登记 AsyncAnswerIdle。单纯“标记存在＋附近调用存在”不能等同于同一解析链。

**修改：** 在同一个可识别的解析函数／作用域中，关联开闭标记绑定、同一接收者、拒绝守卫与裁切解析的输入。允许这些标识符一致改名；输入脱钩、守卫引用其他输入时拒绝。不能靠扩大字节窗口修复。

**验收：** 原包／全套一致改名正例通过；两个已复现反例、跨函数无关守卫与解析拼接负例均拒绝，其他五项对照仍匹配。

## 2. S02 · P2：题目标识只核“两个标识符”，没有核参数顺序和身份

位置：[desktop_contract.rs:794](/Users/jarvis/Documents/tuvis/src-tauri/src/services/codex_desktop_ipc/probe/desktop_contract.rs:794)。

`question_id_synthesis_present` 只看 tag 后跟两个标识符以及 `])`，没有把它们与生成函数的形参关联。

**实跑反例：** 真实夹具函数 `bSe(e,t)` 的返回由 `[tag,e,t]` 改成 `[tag,t,e]`，仍通过；独立审阅也运行了 `[tag,e,e]`，仍通过。这会改变 Desktop 原题的精确 questionItemId，而 Tuvis 仍按原顺序构造，导致正式答案不能关联原题。

**修改：** 识别生成函数的参数与数组位置关系，确认第二元素来自原 item 参数、第三元素来自 index 参数；一致改名保持同样引用关系。未知变体不能仅凭 tag 和两个变量共现放行。

**验收：** 函数和形参一致改名通过；交换、重复、用其他变量替代任一元素必须拒绝。补完整 read() 黑盒用例，不只校验 tag 改变。

## 3. S03 · P2：schema 构造／转换只认外形，不能支撑所申报的类型和结果语义

位置：[desktop_contract.rs:724](/Users/jarvis/Documents/tuvis/src-tauri/src/services/codex_desktop_ipc/probe/desktop_contract.rs:724)、[desktop_contract.rs:754](/Users/jarvis/Documents/tuvis/src-tauri/src/services/codex_desktop_ipc/probe/desktop_contract.rs:754)。

三字段使用相同空参调用，只证明调用相等，不证明结果是字符串 schema；数组／联合构造也仅接受任意成员链外形。`envelope_schema_bindings` 检查到 `.transform(` 为止，没有核回调是否把原条目包成唯一元素数组。

**实跑反例：**

- 三字段全部由 `r.L()` 改成 `z.number()`，仍通过；现有“类型漂移”只改一个字段，因此仅验证了一致性。
- `ey.transform(e=>[e])` 改成 `ey.transform(e=>[])`，仍通过；独立审阅的 `e=>e` 变体也通过。
- 独立审阅另确认联合／数组 callee 替成不同角色的构造调用仍可通过。

当前 Tuvis 发送的是数组，单条 transform 改变不必然使其数组分支失效，因此不据此单独断言当前包写入失败；但实现不能声称已证明“字段类型”和“单条包数组”语义，进而将相应真漂移都判断为同一契约。

**修改：** 限定并证明所采纳的 schema 构造角色／字符串类型来源，按包内绑定或其他一手 schema 证据解析引用；回调必须核验入参到唯一数组元素的关系。不要求做通用 JS 解释器，也不能再把压缩访问器字面写死。对无法证明的形态保持不匹配，明确证据覆盖范围。

**验收：** 三字段统一改为非字符串类型必须拒绝；单条转换为空数组、标量或别的变量必须拒绝；字符串 factory／局部名一致改名正例保持通过。验收文档与 semantic_rule 对类型和转换的描述必须与实际检查一致。
