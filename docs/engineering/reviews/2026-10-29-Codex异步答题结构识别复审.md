## 1. S01 残留 · P2：同接收者不等于同一有效解析路径

位置：`src-tauri/src/services/codex_desktop_ipc/probe/desktop_contract.rs:746`、`:760`、`:778`。

`guarded_parse_schemas` 已拒绝不同接收者及退出外层函数后的拼接，但只检查守卫表达式形状和花括号深度不为负，没有检查守卫的分支作用，也没有排除进入新的函数作用域。

根审阅按当前真实片段制作两条单点变体，直接调用原样提取的生产结构核验函数，两条均被接受：

1. 将 `if(!r.startsWith(_Se)||!r.endsWith(vSe))return null;` 改为 `if(r.startsWith(_Se)&&r.endsWith(vSe))return null;`。合法信封会被立即拒绝，识别器却把这条肯定表达式认成匹配。
2. 把原 `try/safeParse` 放进守卫之后声明、从不调用的内层 `function dead(r){...}`，外层直接 `return null`。花括号只增加不回退到负数，因此仍匹配；实际入口不会执行解析。它与已登记的“同作用域重新声明接收者”不同：这里是另一个函数中的同名形参。

**修改要求：** 先只支持有真实证据的“负向检查失败即返回，随后解析”分支；没有需要保留的肯定形证据时可直接撤回该额外分支。解析必须位于同一函数的有效后续路径，不能以“没有退出外层花括号”代替函数边界检查。无需实现通用 JS 求值器或扩大扫描窗口。

**验收：** 两条反例拒绝；当前真实包、已有不同接收者／兄弟函数反例和一致改名正例保持原结果。若保留肯定形，必须证明解析位于其成功分支，并补反向返回的拒绝测试。

## 2. S02 残留 · P2：index 已绑定，但 itemId 来源仍未绑定

位置：`src-tauri/src/services/codex_desktop_ipc/probe/desktop_contract.rs:919`，尤其 `:935–941`。

`callsite_passes_index` 确认了第二实参是 map index，却只要求第一实参是“不是 index 的成员链”。当前真实调用为 `(e.questions??[]).map((t,n)=>bSe(e.id,n))`，将 `e.id` 改成 `e.type`，核验仍返回 true。独立审阅也确认 `t.id`／`e.turnId` 形态可通过。

这些不是局部名一致改名：题目标识由原条目 ID 变成类型、题目子项 ID 或回合 ID，Tuvis 仍按原条目 ID 构造信封时，双方无法定位同一道题。原 S02 的形参顺序、重复参数和 index 反例均已修复，但尚不能据此认定 itemId 来源已证明。

**修改要求：** 把 `questions` 集合的原条目接收者与第一实参的 `.id` 关联，允许该接收者一致改名；不接受任意别的成员链。对尚无证据的调用形态保持不匹配。

**验收：** 原条目 `.id` 正例及一致改名通过；原条目 `.type`／`.turnId`、map 子项 `.id` 和其他对象 `.id` 拒绝；已有交换／重复参数和缺调用点反例保持通过。
