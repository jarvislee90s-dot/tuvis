## 3. 哪些只是缺前端，哪些需要后端

本矩阵没有把任何新增主需求判成“后端已完整完成，只画按钮即可”。

- **已有前后端、但关闭**：官方队列删除/重排/恢复；引导入口存在但禁用。它们不是 R04/R05 的实现。
- **可复用底层、需要增加编排**：Tuvis 待发队列、指定一条停止后发送、暂停/恢复、原子撤回及回填。
- **前后端都需要扩展**：跨供应商选择、权限模式选择。
- **已有核心能力、还涉及分发工程和系统验收**：钥匙串记住信任。保存 JWT 已完成，不需要改成浏览器 Cookie 或明文文件。

## 4. 最新范围与旧文档的关系

1. 用户已明确指定 Codex 式“先由 Tuvis 暂存，插队时停止后只派一条”。本设计据此调整此前“新消息直接进入官方队列、不建 Tuvis 队列”的下位设计约束；不是开启旧 QueueNow 按钮。
2. 已进入 ZCode 官方队列的历史项目保持独立来源；不自动搬入 Tuvis 待发队列或复制重发。
3. 跨供应商功能从旧 O1 的“仅设计”提升为本设计主线目标；不再仅以存在 NO-GO 文档就无限搁置。代码可先完成，真实切换验收单列。
4. 新截图已确认提示请求方与开发 Keychain 条目；旧 O3 中“尚无截图，来源未知”的前提不再完整。签名变化是否导致本次重复提示，仍不能仅靠截图判定。
5. 2026-11-01 用户追加将 R10 纳入本批。受阻须给具体证据与缺失链路，不能作为“可选”跳过；已有审批卡的受限应答不改成常驻授权。依据见 [模式静态核对](../reviews/2026-11-01-zcode-mode-static-evidence.md)。
6. 本批不做上下文百分比圆环、不改官方原生附件上传协议、不增加第二条 relay 连接、不重写 OAuth/保险箱。

## 5. 交付顺序与完成口径

1. **核心交付**：R03–R07；保留 R01/R08 及既有问答、审批、正文、附件能力。
2. **主线增强**：R09；R02 的应用身份收敛可独立进行，签名材料不影响队列核心编码。
3. **同批控制增强**：R10，与 R09 共用选择状态基础。某模式确有协议阻断时仅单项收口并给证据，整批不得将 R10 标完成；队列核心可独立交付。

每个 ID 分开记录：代码已接通、自动化通过、实机通过、剩余条件。默认关闭只说明风险被隔离，不说明用户功能已经交付。R02 的系统条件与 R10 的实际支持范围尤其要明确，不能以“全部测试绿”宣称全部需求完成。
