# Codex 题卡状态与发送区修正要求

日期：2026-10-29。状态：用户已认可本轮四项修复设计；本文固化行为和验收边界。最高依据为 `docs/MASTER-PLAN.md`，不修改宪法。

## 1. 范围与证据

基于 `e772b1f4` 的只读调查，本轮处理：正式答复未被识别导致历史题积压、题卡占屏、能力标签闪动、运行中发送区提示和操作入口。

- 指定会话日志有 7 次异步提问和 7 条键匹配的正式答复，闭标签后均有换行。当前 `parse_answer_envelope` 直接剥离闭标签，拒绝尾部换行。实时 IPC canonical 是否保留同一换行仍需补一份只读样本，不能把 JSONL 当作真实投影。
- 卡片停靠区允许占 55vh；异步卡题干默认字号大于旧 CLI 卡，另有常驻自由输入和空提示占位。当前顶部字号档位只覆盖消息和预览，不覆盖题卡。
- `allowed` 混合证据、设置、连接及运行条件，却被展示为适配能力。停止能力本身不受 idle/active 门控，其闪动需记录实际翻转原因，不能预设为回合状态变化。
- 空队列也可能因为 `native_turn_active` 展开长说明；composer 没有停止按钮。已有暂停、定向打断、一次性越队能力必须复用。

前置文档：`2026-10-26-Codex-F01-F08阶段需求与设计.md`、`2026-10-27-Codex兼容可用性与分组答题修正要求.md`；本轮交互变化以本文及用户本轮裁决为准。计划见 `../plans/2026-10-29-Codex题卡状态与发送区修复计划.md`。

## 2. 已答题收敛

1. 正式信封允许外部首尾空白，尤其 LF、CRLF；不改答案内部空白、内容和题目标识。
2. 继续只认可用户消息里的合法正式信封；助手消息中的引用、代码围栏、普通正文答案、错误标签、无效 JSON、超限内容、信封后非空正文都不能冒充正式回答。保留既有合法来源前缀，不新增按自然语言猜引用的规则。
3. 正式答复准确关联原题后，当前卡和其他组入口均消失，旧核对锚退休；刷新和重启不复活。
4. 历史提示表必须允许被当前强证据纠偏，不能继续用旧 pending 覆盖 answered。普通正文回答不强行写成已正式答题。
5. 无真实答复的题不按时间直接标已答，也不向 Desktop 自动发取消或答案。

## 3. 紧凑题卡

1. 保留同组逐题、内存存稿、最后一次提交；只展开一组。
2. 其他有效组统一收进一个“另有 N 组”入口，展开后可切组；不常驻 N 行。已答组不计数。
3. 题干和选项文字跟随顶部字号设置；按钮、工具栏、页头维持稳定操作尺寸。此为对旧“只有消息和预览缩放”的局部调整，仅扩展至题卡内容。
4. 100% 时题干采用旧 CLI 卡的紧凑字号基准（14px），缩小段间距；没有回执不留空行。
5. 自由填写默认收起，点“其他答案”展开；已有自由稿自动展开。选择与文本继续互斥，收起、切题和切组不丢稿。
6. 常态停靠区最多 35dvh；长题干默认最多三行并可展开，长组选项可内部滚动，题号和提交操作保持可达。可提供明确的展开大面板入口。虚拟键盘出现时按可视高度适配。
7. 360/390 CSS px、中英文、深浅色、75%/100%/125% 检查，100% 且可视高度至少 640px 时消息区至少保留 40%。不通过缩小点击面积换空间。

## 4. 稳定能力与当前动作资格

1. 服务端独立输出“版本能力支持状态”与现有“当前允许执行”。能力标签根据支持状态保留位置；暂时运行中、暂停或连接恢复不画成该版本失去支持。
2. 关闭自动适配仍立即禁用相应新动作；详情区分别显示“已支持”和“适配已关闭”。稳定展示不参与实际授权。
3. 同一目标短暂断链可保留上次识别结果用于展示，同时标“连接恢复中”；切换目标、包 SHA 或规则版本后不能沿用旧支持结果。
4. 工具栏与详情使用同一版能力事实；详情可独立读取版本、设置和诊断，但不以另一时刻的临时资格替代页面当前事实。
5. 为 GET、SSE、手动刷新统一建立版本落地守卫。当前 Rust 的 owner 与 local_seq 是 `serde(skip)`，不能假设前端已收到它们；需增量下发排序信息，并处理宿主重启和 revision 重置。
6. “停止本轮”闪动先记录脱敏的证据、原因、连接／投影版本及来源，再用定序测试确认；没有实际证据时不得申报其现场触发原因已经查明。

## 5. 发送与停止

| 状态                                     | composer 主按钮    | 结果                               |
| ---------------------------------------- | ------------------ | ---------------------------------- |
| 运行中、无文字且无附件、有可确认停止目标 | 停止               | 用户点击才调用既有定向打断         |
| 运行中、有文字或附件                     | 发送               | 沿用既有提交规则；合法消息遇忙入队 |
| 空闲、有合法内容                         | 发送               | 正常提交                           |
| 空闲、无内容                             | 禁用的发送         | 无动作                             |
| 断链、目标不明或停止能力不足             | 不提供可执行的停止 | 就近显示短状态                     |

附件单独发送是否允许沿用既有规则；有附件时不能因为文字为空误触停止。Enter 仍只用于既有发送操作，不将空 Enter 映射成打断。已有草稿时另在紧凑菜单保留停止入口。

1. 停止操作绑定用户点击时看到的线程和 turnId，保留设备许可、预算、写边界校验及未知结果处理；不把“停止 HTTP 等待”冒充停止模型回合。
2. 没有排队消息、没有真实未知投递屏障时，不因正在运行就展开整段队列提醒。
3. 入队后显示紧凑的“排队第 N 位”，可展开撤回和“先处理这条”；旧队列暂停时保留恢复入口。
4. “先处理这条”不是一般 FIFO 调序：运行中须经用户明确确认停止当前回合；确认停止后只允许该消息一次性越过暂停的旧队列，旧队列仍暂停。有原生审批／未知投递屏障时不借此绕过。
5. 优先处理必须关联已入队的同一动作，不能复制正文创建第二条消息而让原条仍排队。停止结果不确定时不继续派发、不自动重试。
6. 同一暂停原因只解释一次。真正需要人工核对的 Unknown 不因界面收纳而隐藏处理入口。
