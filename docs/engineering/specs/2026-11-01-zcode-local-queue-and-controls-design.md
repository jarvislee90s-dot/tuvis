## 1. 目标、选择与范围

用户需要在手机中立即看到尚未投递的消息，能编辑、撤回、选一条插队；模型可按供应商选择，授权尽量复用。保留已有官方连接、协议适配、动作账本和读取能力。

### 1.1 路线比较与选择

| 路线                                          | 能解决什么                                                  | 代价/局限                                                       | 裁决                                         |
| --------------------------------------------- | ----------------------------------------------------------- | --------------------------------------------------------------- | -------------------------------------------- |
| 继续完全交由 ZCode 官方队列                   | 能观察官方队列；取证后可操作官方项                          | 入队已经向 ZCode 投递；编辑因果、暂停恢复和“引导”语义受官方限制 | 保留只读观察，不承担新待发主线               |
| Tuvis 持久队列 + 已有 ZCode 官方发送/停止端口 | 入队立即可见；未投递项可原子撤回/回填；支持指定项停止后发送 | 需要本地调度、重启恢复和跨层状态收敛                            | **用户指定采用**，借鉴 Codex main 的业务规则 |
| 手机浏览器内存暂存，点按钮再提交正文          | UI 改动少                                                   | 刷新丢失、不同页面不同步，不能可靠证明是否投递                  | 不采用                                       |

“本地”指运行 Tuvis 的电脑后端，不是仅存在手机内存。它保存业务待发记录，不另建 ZCode 会话/连接。普通发送忙时留队、不自动停止；明确点击某条插队才进入停止编排，保持宪法 R2.3/F2.2 的普通消息规则。

### 1.2 首版范围

- 必做：矩阵 R03–R07、R09；R01/R08 及问答、审批、附件、阅读功能维持并回归。
- R02：保留原生凭据复用，增加应用身份收敛和分场景验收。证书及系统条件不能冒充软件逻辑已解决。
- R10：纳入本批编码和验收。具体模式证据不足可单项受阻，不能以“可选”为由不施工；受阻不要求回退已完成的队列核心。
- 不做：通用跨工具队列框架、任意 shell/杀进程、DOM 点击、浏览器凭据提取、上下文占用圆环、重写 relay、官方原生附件协议。

## 2. 复用边界与数据流

```text
手机输入/既有附件上传
  → 配对保护的 ZCode 待发 API
  → ZcodeQueueService（新：持久记录、队列版本、单会话串行）
      ├─ 忙/暂停：只保存，零上游消息帧
      ├─ 空闲且可派发：取队首 → 现有绑定/能力/发送端口
      └─ 指定项插队：定向停止 → 等终态 → 仅派发此项
  → 现有 Auth / Hub / CommandSender / Bridge / 官方 relay

本地队列变更 → REST + SSE local_queue → 手机列表
官方状态 → 现有 SessionView/REST/SSE → 正文、卡片、运行态和官方队列观察
```

- `AuthService`、`CredentialStore`、`BridgeManager`、目标绑定和 `CommandSender` 继续承担原职责。
- 参考 Codex 的队列事务、定向停止、有界终态观察、单条派发和 Unknown 收口；不复制其 Desktop IPC transport，不复用带 Codex 身份的表或请求类型。
- 当前 `zcode_actions` 是命令幂等/回执账本，不把它直接扩成持久全文队列。新增业务队列表，实际派发仍引用既有命令动作 ID。
- 队列服务拥有“何时派发”的职责；低层发送器不回调队列服务，避免入队/派发递归和重复加锁。

## 3. Tuvis 待发队列合同（R03–R07）

### 3.1 最小存储与身份

新增本机 SQLite 业务表 `zcode_send_queue` 和会话队列状态；须版本化迁移，保留现有动作记录。

| 记录面     | 必需内容                                                                                                     |
| ---------- | ------------------------------------------------------------------------------------------------------------ |
| 队列项     | 随机 itemId、服务端派生的设备身份、Tuvis sessionId、可重新核验的原工作区身份、递增 seq、行 version、创建时间 |
| 可编辑材料 | 原草稿正文、已就绪附件引用；入队时冻结的最终发送正文和来源标记设置；不靠预览或反向拆 markup 取回全文         |
| 派发关系   | 持久 dispatchActionId、实际派发代际、回执/宿主 admission；一次编排的 stopActionId 与已认领/未知状态          |
| 会话状态   | autoDrain、暂停原因、queueVersion；本地版本与官方 revision 是不同计数，不能混用                              |

全文是待发业务数据，只存在本机库，不能进入日志、审计摘要、证据报告或 Git。JWT/token/官方链接不进队列表。条目派发明确受理或普通撤回后清理可重发正文，保留必要的 ID、hash、回执元数据；Unknown 保留核对材料，不提供盲目重发。“再编辑”有独立的结果快照清理规则（§3.3），不能在撤回 CAS 成功时立即丢掉全文。

正文只组装一次：入队时调用现有 `compose_official_text` 冻结来源标记及附件正文；内部派发端口须显式接收已组装材料，不再按当时设置追加一次签名。再编辑返回原始草稿/附件，再次入队才生成新材料，不能把旧尾签名当用户正文重新拼接。

首版沿用 Codex 的设备归属隔离：用户可管理本设备入队项；FIFO 位次按会话全局队列计算。其他设备条目的内容和操作不因知道 itemId 而越权开放。跨设备代管不是本批默认扩权。

连接重建后用原 Tuvis 会话及工作区重新绑定，逐次取得新鲜代际；不能把上次的连接代际当作长期身份。链接/工作区改变且不能证明仍是原目标时暂停，不把旧消息自动投向新目标。

### 3.2 入队与自动发送

1. 上传沿用 `/session-attachment`，就绪附件落在项目 `.tuvis-attachments/<session>/`；保留 `?` 说明、进度、取消和失败 chip。
2. 只接受就绪附件。入队校验复用服务端解析的项目/绑定工作区、现有大小限制和正文 `MAX_TEXT_BYTES`；附件清理后失效的引用必须拒发并说明，不静默丢附件。
3. 入队事务成功便返回 **“已加入 Tuvis 待发”**、itemId、队位及 queueVersion，手机立即展示；这不等于宿主已受理。失败时保留草稿和附件。
4. 入队成功清除本次提交的草稿/附件，继续输入的新草稿与新附件保留；网络未知时按同一提交 ID 查询/重放入队结果，不换 ID 自动再登记一份。
5. 忙态只入队；空闲、未暂停、无审批/问答或未解 Unknown，且目标及发送能力就绪时，调度队首一条。该条正式进入运行态后等待宿主回合终态，再接力下一条，不把 ACK 当成回合结束。
6. 远程关闭、断线、设备撤销、目标不能精确绑定时不派发。可证明属于原会话的纯待发项保留；离线入队不强行打开 OAuth 或新连接。
7. 所有 ZCode 手机普通发送接入同一调度。旧 `/zcode/actions` 的 Send 请求不得绕过已有待发/暂停/在途保护；保持既有回执查询，旧页面无法表达新入队回执时应明确要求刷新，不能伪造 Accepted。

自动接力必须建立**本次派发的回合屏障**：Accepted 之后先确认该输入关联的宿主执行/终态，不能把 ACK 刚回来、尚未出现新 activeWorks 的空窗当成“回合已结束”。复用并补足输入/执行关联的最小投影；关联证据缺失时保守暂停并允许用户核对后显式继续后续队列，不能用固定等待或“看到任意执行消失”代替。此时继续的是后续消息，不是重发结果未知的原消息。

2026-11-01 本机安装包的只读形状依据：`out/main/chunk-XYX2CJ3H.js` 中，`activeWorks` 元素含可选 `sourceCommandId` 与 `foregroundExecutionId`（相关定义偏移 637968）；`turn.started` 含 `inputId/foregroundExecutionId`（定义偏移 700934），`turn.completed` 含 `inputId/resultType`（定义偏移 702253）。当前 Tuvis 尚未完整投影这些关联字段。实施时先核对它们在实际订阅帧中的承载位置，只投影关联所需的 ID/终态，不下发其中的原始 input/response；字段可选，缺席仍走屏障而非猜测。这是 PACKAGE 静态证据，不是实时帧或关联成功实测。

### 3.3 编辑、撤回与列表

- 列表默认显示待发行，采用 Codex 紧凑布局：`第 N 条 | 正文摘要 | 插队 | 再编辑 | 撤回`。超 20 个字素省略；全文有可访问提示；不把三行消息隐藏在难发现的数量按钮后。
- “插队”只表示本设计的单条优先处理；不叫“引导”，不绑定官方 `sendQueuedNow`，也不只是把列表行挪到最前。
- 撤回/再编辑只对 **尚未取得派发权的 queued** 项有效，SQL CAS 与派发认领竞争。CAS 输家刷新实际状态，禁止假报已撤回。
- 再编辑先解决已有草稿的“合并/替换/取消”，默认取消；CAS 成功后返回完整草稿和附件引用。等待期间草稿变化需再次确认，不覆盖续写；保留附件引用，无需重新上传，不自动发送。
- 编辑撤回 CAS 与**编辑结果快照**在同一事务持久化，绑定 editRequestId、设备、会话、原 item/version 和完整草稿/附件。响应丢失后，同一请求可重新查询/重放结果；旧项虽已取消，也必须返回既有编辑结果，不再次撤回或登记新消息。CAS 输给派发的一方不能创建成功编辑快照。
- 作者建议编辑快照保留到关联的新入队成功或用户明确放弃，最长 24 小时；超期按本机清理任务删除。它不是可派发队列项，查询仍受原设备/会话授权。前端先收敛该编辑请求再允许再次创建编辑操作，不能把断网误当“原文不存在”。普通撤回不需要编辑快照，成功发送的正文清理不影响尚未取回的编辑结果。
- 再编辑后的发送登记为新待发项，旧项已撤回；不偷偷越过其他待发项。只有明确点击“插队”才获得指定项优先处理语义。
- HTTP 入队回执负责立即上屏；后续 SSE `local_queue` 和 GET 统一纠偏。本地 queueVersion 单调，旧 GET 不覆盖新事件。不要用官方 revision 排序本地列表，也不把官方队列项 ID 当本地 itemId。

### 3.4 停止、单条插队与恢复

```text
选择 C 插队
  → 核对属主、目标、行 version、queued 状态，认领本次编排
  → 运行中？
      是：明确确认 → 持久认领 stopActionId → 发送定向 stop 一次
                    → 有界等待该执行结束 + 新鲜状态允许发送
      否：核对新鲜可发送态，不要求队列此前已暂停
  → 认领 C 的派发权 → 发 C 一次 → 保存正式回执
  → 其他待发项保持暂停；用户点“继续队列”才按原顺序接力
```

- 停的是原 `foregroundExecutionId` 对应的回合，保留 ZCode APP/host/relay；不执行 kill、退出 APP 或重启 app-server。
- 若出现新的运行目标、待处理卡、连接换代或预算到期，停止本次编排，C 留待核对，不自动停新回合。
- 停止 ACK 不等于停止完成：复用既有守卫清除/终态观察，动态等待判据，不使用固定睡眠后盲发。
- 首次可能写出停止前即持久记录尝试；浏览器断开、超时或 Tuvis 重启后，同一次编排不得重新发一轮停止。停止 Unknown 时零消息帧，UI 说明“停止结果待确认，本条未发送”。
- 运行中普通发送绝不自动停止。主动停止或选条插队应在本地持久暂停其他待发项，防止停止后自动 flush 抢先派发 B。
- 空闲时明确选择 C 也能只派 C；不能依赖“队列必须已暂停”的旧门形成死结。
- 每会话只有一个调度/停止派发编排；DB 锁不跨 await。现有手机同步写锁同时覆盖新的本地队列 API 和既有命令提交，不能让新入口再次绕过共享锁；后端线程锁、CAS 才是多手机与自动调度的最终保护。
- “继续队列”只改变本地 autoDrain，随后正常 FIFO；停止/单条插队不隐式调用官方 `setAutoDrain(true)`，不恢复整份官方队列。

### 3.5 回执、异常与重启

业务项至少区分 `queued / dispatching / accepted / unknown / failed / cancelled`；停止尝试状态单独记录，不把“停止未知”误写成“消息已发送”。

| 情况                                      | 必须行为                                                                                       |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 入队事务成功、尚未写出                    | 可显示待发与编辑/撤回；不冒称官方受理                                                          |
| 官方完整 inputAccepted，delivery=startNow | 记录已受理并离开可编辑队列；等待官方运行/结束事实后再自动接力                                  |
| 竞争窗口下官方实际 delivery=queue/guide   | 记录真实 admission，告知已交官方处理；不留作仍可本地发送项、不自动补发，不让本地下一项盲目接力 |
| 明确写前拒绝或确定零投递                  | 留队或返回可理解的失败，由用户再次操作；不自动连发多次试错                                     |
| 消息 ACK 未知/超时、崩溃时已认领派发      | 保守 Unknown，暂停本会话自动派发；只读核对原动作，不能当成 queued 自动重投                     |
| 纯 queued 项重启                          | 恢复原 seq/正文/附件及暂停标记；重新绑定原目标，按原 autoDrain 策略处理                        |

**本批必须补 admission 的持久透传**：目前 `_delivery` 被丢弃，在旧方案中允许；新方案需要区分“仍由 Tuvis 持有”和“已被官方入队”，必须把 `sendAdmission{delivery,inputId}` 写入正式 ActionReceipt/动作回执存储，完成版本化迁移和重放。旧回执缺该字段视为未知，不按文字相似或队列增长猜归属。

### 3.6 已存在的官方队列

保留单独的“ZCode 官方队列”观察区；当前 W0 未验的官方修改/重排/恢复继续关闭。它与“Tuvis 待发”有不同来源标识和 ID 空间。

不把官方项复制到本地，不自动删除、清空或恢复官方队列。发现已有官方待处理项时，自动派发暂停并提示用户到官方端处理；明确选择本地单条优先处理仍须遵守官方 inputRouting/heldQueue CAS。若需官方的保留/清空选择，明确向用户询问，不能为了兑现“点一次就发”默认清空旧队列。此历史兼容不影响全新纯 Tuvis 队列的正常路径。

旧 W0 十二项中，官方 delete/reorder/setAutoDrain 的实跑不再是本地撤回/编辑/继续队列的实现前置；新链路仍须验证 stop→终态→单条 send。不能把所有新能力继续统称“W0 未验”而全部禁用。

## 4. 供应商、模型与思考强度（R08/R09）

- 复用 `model-selection.getView`、`switchModelConfig`、CAS、选择确认和现有模型控件。新增的是目标 provider 与目录分组，不重建连接或读取 API Key。
- 目录投影为当前选择三元组，以及官方当前会话/用户配置下的供应商分组。不能使用营销模型目录或手机自报目录；可用性按官方可信字段核实，未登录/不可用项明确禁用。
- 当前 `catalog_models` 丢弃非当前 provider、Selection 动作无目标 provider，均需改造；不是增加两个前端控件即可。
- UI 为“供应商”与“模型”两个联动单选下拉框，保留模型专属“思考强度”。先选供应商只更新待选组合，选定模型/合法档位后一次提交最终三元组，不先写 provider-only 中间态。
- 当前模型/档位在新供应商中不合法时选目录明确支持的值；没有明确合法档位则不给假值，不发送。不同模型的档位不做并集。
- 服务端在新鲜目录中验证目标三元组，将 provider 加入动作幂等指纹；发一次命令并带官方要求的 baseRevision。旧客户端缺 provider 时仅代表当前 provider，不能推断跨供应商目标。
- 确认目标 provider/model/thought 全部匹配新鲜官方配置才显示生效；缓存按 provider 失效，不把上家目录合给下家；被拒保留实际选择、显示原因，Unknown 不自动恢复或重发。
- 首版在空闲、无待处理交互时允许跨供应商写入；运行中可准备待选项，实际切换暂不强制中断回合。Tuvis 待发正文默认在实际派发时使用宿主当前已确认配置，不为每条队列消息新增模型快照功能。
- 正式开放前完成两个已配置可用供应商之间的切换/切回及上下文保留验证。可以先完成代码和忠实假宿主测试，不把此项永久停在“仅设计”。

## 5. 凭据复用与钥匙串提示（R01/R02）

继续使用方案 A：Tuvis 自己的 OAuth JWT 存系统凭据库，内存复用，每次连接现取 terminal token。沿用 `store_lock/epoch/purge_pending`、忘记删除、过期/401 清对应身份、自动连接与用户暂停语义。

已确认的证据：用户新截图对应 `com.jarvis.tuvis.dev.zcode`；当前 debug 二进制 `Signature=adhoc`、`TeamIdentifier=not set`。这足以确认条目来源和身份不稳定的嫌疑，不足以证明每次提示都由重编译造成。不得继续写“完全没有截图/来源未知”，也不得标“签名原因已实机闭环”。

| 场景                           | 设计与交付                                                                                                                                    |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 同一个构建普通退出/重启        | 引导用户选择系统“始终允许”；保持现有启动恢复一次、轮询只读内存。专用测试条目记录真实 load 次数，验 3 次冷启动不重复提示                       |
| 开发版反复重新编译             | 作者推荐提供可选的固定开发签名身份配置/构建入口，保持同一指定身份与路径；若尚无可用证书，明确工程输入未就绪，不用“同构建重启通过”冒充此项完成 |
| 正式版正常升级                 | 稳定 bundle ID、签名身份/Team 与发布路径，补对应构建验证。Tauri updater 签名与 Apple 代码签名分开处理                                         |
| 用户拒绝、钥匙串锁定、身份变更 | 正确报告存储问题，保留显式重试/忘记入口；不自动当成 JWT 失效再开 OAuth，不降级到明文文件                                                      |

不新增后台常驻钥匙串代理、不跳过原生存储、不改成浏览器登录态。固定开发签名是作者建议，尚不代表用户已同意安装/采购证书；本设计阶段不变更系统证书或 ACL。已有证书可通过配置接入，没有时保留明确交付条件，不阻塞队列编码。

承诺范围是同一用户、同一可信应用身份和正常系统策略下的常规复用；不承诺跨签名、换用户、任意重装/重编译后永久无系统提示。Windows/Linux 保持原生凭据库，不为解决 macOS 提示改它们的实现。

## 6. 本批权限模式（R10）

本机安装包及固定公开源码存在 `switchCollaborationMode{mode}`，值域为 `build/edit/plan/yolo/guarded`。新增核对确认实际 handler 及标签：`plan=计划模式`、`build=变更前确认`、`guarded=自主模式`、`yolo=完全访问`；`edit=自动编辑` 只读兼容。旧材料将 guarded 称为“变更前确认”的叫法不能用于新实现。依据见 [模式静态核对](../reviews/2026-11-01-zcode-mode-static-evidence.md)：这是可编码依据，真实效果尚未实跑。

- 本批实施独立的 Mode 动作、模式投影、能力槽、幂等指纹及状态确认。复用既有命令信封、baseRevision 和连接，不接受任意字符串或任意宿主 payload。
- 实施前从当前 build UI 与命令处理链核对“计划/变更前确认/自主/完全访问”的准确映射，只开放确认过的选项；未知项保留只读当前值。
- 仅用户主动操作时切换。完全访问等权限扩张需要明确确认，不能因换模型、重启、恢复队列而顺带切换；不自动恢复为更宽模式。
- 新鲜官方配置确认才显示生效；旧 revision、目标改变、Unknown 不补写。首版运行中/待审批时禁用模式写入，避免改变正在等待的请求。
- 既有审批卡的 allowOnce/deny 仍是独立通道，原 fullAccess/常驻选项硬闸不因新模式选择器而取消。
- 旧合同有 terminal-origin sendText 在 guarded 下也未弹审批的负证据。必须核验实际效果，不能把“模式切换成功”宣传成“手机每次发送均受审批保护”。此项未过不阻塞 R03–R09。

已知 build `3.16.2.8769` 的完整静态链路与新鲜模式形状齐备时，Mode 可按逐能力候选策略接受一次用户主动切换，通过有界配置确认升级；不能共用官方队列写的 W0 关闭槽。未知 build/缺模式形状则该能力关闭。权限扩大必须显式确认，后台恢复不写模式；模式配置效果和“手机发送是否触发审批”分开验收。

## 7. 模块与接口边界

下表是拟新增/修改的职责，不声称其中的新名称已在源码存在；执行计划须对当时 HEAD 再核定签名。

| 模块                                               | 变更/复用                                                                                                                                  |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 新 `services/zcode_control/local_queue/`           | 按 types/store/service 拆分 ZcodeQueueService：入队、暂停、FIFO、指定项优先处理、重启收口；不管理 JWT；替代初稿单文件 queue.rs 布局        |
| 新队列 DAO + `database/{schema,migration}`         | queued CAS、派发/停止认领、队列版本；正文与审计分离；ActionReceipt admission 迁移                                                          |
| `command.rs` / `action.rs`                         | 复用精确 stop/send/selection；补 admission 持久化；本地派发声明 startNow 意图，最后一跳仍核对新鲜运行态，宿主实际 queue 时如实交接而不重发 |
| `hub.rs` / `remote/zcode.rs`                       | 接入服务、配对/属主/目标守卫、单会话编排和队列事件；所有外部发送不绕调度                                                                   |
| `selection.rs` / `types.rs` / `bridge.rs`          | 分组目录、目标 provider、三元组确认与缓存失效；本批 mode 投影/动作                                                                         |
| `ZcodeControlPanel` / `ZcodeQueuePanel` / API/hook | 即时本地待发行、三按钮、回填冲突、队列版本纠偏、官方队列独立观察、两个联动选择器；保留主按钮、蓝色问答卡、审批及附件说明                   |
| `credential_store` / `auth` / 构建脚本             | 原生凭据与既有生命周期尽量不改；签名配置、提示说明和最小诊断，只在实证发现重复读取时再改恢复逻辑                                           |

拟议队列 API 统一位于既有配对 gate 下：GET `zcode/local-queue`，POST 同族 `enqueue / prioritize / edit / retract / resume`。入队携稳定提交 ID、Tuvis 会话与材料；按项操作只携 itemId/version 和必要确认，不接受正文副本来冒充“插队”。设备身份由 gate 派生；generation 只在真正官方写入前按新鲜绑定核验。

事件提供 queueVersion、会话、授权可见的本设备项及全局位次；重连 snapshot/resync 可用 GET 重建，不重放写动作。具体 DTO 字段、冻结原因码与迁移编号留执行计划按真实源码确定。

## 8. 必须闭合的验收链

| 场景                       | 自动化必须证明                                                                                      | 实机验收必须证明                                     |
| -------------------------- | --------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| A 运行，提交 B/C           | 真实 HTTP→队列事务→SSE/GET→手机立即两行；零 sendText，草稿续写不丢                                  | 当前回合结束前手机已可管理 B/C；官方尚未收到         |
| 选择 C 插队                | 先持久停止认领；仅停预期 A；确认终态才一帧 C；B 留队暂停；同帧/多端重复请求不双发                   | A 结束后 C 真正作为下一条执行；其余项不偷跑          |
| 空闲选择 C、手动停止后恢复 | 无旧“必须 paused”死门；普通停止暂停队列；resume 按 FIFO；既有卡片不误答                             | 点谁只处理谁；继续队列的行为和文案一致               |
| 停止未知、写入未知、重启   | 零盲发/重发；旧尝试可查询；纯 queued 恢复；失效设备不派发                                           | 断线/重启后状态能核对，结果未知不自动再发一次        |
| 编辑/撤回与派发竞争        | CAS 单赢家；原文/附件恢复；编辑响应丢失或重启后同请求可取回快照；已有和续写草稿不覆写；撤回零上游帧 | 附件仍可被目标工作区读取，编辑不重复上传或自动发送   |
| 官方旧队列/竞争 admission  | 来源分离；inputId/delivery 持久重放一致；不复制官方项、不默认清空                                   | 官方确实把某项入队时手机不谎称直接执行               |
| 跨供应商/模型/档位         | 真实目录形状、provider 指纹、模型专属档位、一次命令、旧帧不回退                                     | 两个已配置供应商切换/切回与上下文影响正确            |
| 钥匙串                     | 假体证明恢复不重开 OAuth、状态轮询不读 OS、失败不误删；构建身份检查可读                             | 同构建重启、稳定签名升级、开发重编译分别记录提示次数 |
| 模式与继承功能             | 模式值域与扩权确认；U1–U7、既有八能力、附件和身份守卫完整回归                                       | 模式真实效果单列；不能用切换 ACK 冒充权限保护        |

假宿主应按已核实 schema 校验身份与 payload，不能全部硬编码 true 掩盖真实路由；至少一组测试穿过生产 HTTP 路由。审核需核对“用户动作→持久状态→命令→官方事实→GET/SSE→手机”，不能只看新函数及测试总数。

## 9. 实施分段与设计裁决

1. **先交核心**：入队、立即列表、编辑/撤回、普通 FIFO、主动停止暂停、指定项优先处理、admission 与重启防双发一起闭合。不能先开放按钮、把停止确认/幂等留到加固期。
2. **再加主线控制**：跨供应商选择；应用签名/提示工程独立推进。复用现有核心，不顺带通用化所有 harness。
3. **同批完成模式，再做平台加固**：R10 已纳入，不静默跳过；macOS 真机后补 Windows/Linux 凭据与队列同口径验收。

用户已确定的是 Tuvis 暂存、指定项停止后发送、供应商/模型二级选择、凭据尽量记住；本次追加将 R10 纳入。作者补足的首版选择包括：默认展开本地待发、沿用 Codex 设备归属隔离、运行中暂不跨供应商写配置、待发消息采用派发时已确认模型、固定开发签名配置可选；这些应随本设计一起审阅，不写成用户此前已逐条批准。

本设计通过后再写逐 task 的执行计划。验收表继续按 R01–R10 区分代码、自动测试、实机与外部条件；不得把“普通构建关闭”标成“功能已完成”，也不因为一个可选系统条件未满足而停掉全部核心编码。
