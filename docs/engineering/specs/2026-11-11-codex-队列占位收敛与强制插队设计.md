## 二、适用范围与证据边界

- 最高依据为 `docs/MASTER-PLAN.md`：R2.3 普通注入不打断，F2.2 单会话串行；显式操作沿 R3.1 与既有 `docs/engineering/specs/2026-10-22-codex-remote-interrupt-design.md`。
- 普通发送仍按真实运行态遇忙排队；本设计不让普通发送自动停止 Desktop，不改变其既有队列规则。
- 插队是对某条 `queued` action 的独立授权：仅本条优先，不合并旧队列项、不顺带解除队列暂停；本次结束后其余条目按原规则处理。
- 历史 Unknown 可继续保留，不自动重发、不伪造 Accepted；显式接管不要求先证明它已经完成。
- 本次不含 B1.3、`questions:null` 旧题出卡、无答复关闭识别、最初 `client_message_unverified` 的触发原因、版本白名单扩张。
- 权衡：修复集中在现有队列、控制路由与账本边界，不扩大为协议层重构或新能力审批体系。

### 2.2 源码根因与历史遗漏

以下引用均指 `v0.6.6@707a11a5` 的符号，不以当前脏工作树行号定位。

1. `src-tauri/src/services/codex_control/router.rs` 的派发分支先 `book::mark`，初始 `turn_id=None`；Unknown 结算分支不补绑、不 forget。
2. 同文件 `converge_with_ledger` 对 Unknown 保留 book；`release_turn_if_complete` 依赖内存 turnId，遍历屏障时也跳过无 turnId 行。
3. `src-tauri/src/remote/codex_ipc.rs::settle_turn_evidence` 核对通过后仅调用 `clear_compat_fence`；DAO 的 `clear_compat_fence_conn` 保留 Unknown、清 DB fence，没有同步内存。
4. 于是 `flush_thread` 仍受 book 阻挡；`prioritize_queued` 的 `(has_fence || active_book)` 为真，而 `barriers_do_not_block` 要求 fences 非空，DB 已空时仍可能拒绝插队。
5. 原有释放归属缺口：`release_turn_if_complete` 在清任意旧 fence 后可能执行整线程 `clear_active`，误清新动作占位；现已在 Task1 控制层自动回归中取得对应业务 RED，修复后完成该批规格与质量验收。该证据不等于真实 Desktop 现场复现，具体结果见配套计划。
6. DAO `finish_late_result_conn` 对旧 Unknown 仍可能重置 `compat_outstanding=1`；仅人工解除标记防复活，自动核销缺少持久终局标记。

历史上，`d6d2d348`（2026-10-20）形成 Unknown 保留规则；`9d2a0a88`（2026-10-31，#192）加入后续核对清 DB 与队列规则时，没有把完成核对联动到内存占位。两处状态生命周期分散，局部规则各自成立却未闭环。

## 三、方案选择与关键不变量

| 方案                                           | 权衡与结论                                                              |
| ---------------------------------------------- | ----------------------------------------------------------------------- |
| 仅补自动清 book                                | 改动较小，但旧 Unknown 无证据时仍无法满足用户主动插队；不能作为完整方案 |
| 空 fences 或 runtime idle 就清整线程、全面放行 | 容易误清新动作、真实 writer 或其他队列限制，不能保持单会话串行；不采用  |
| 统一自动核销 + 独立显式接管                    | 增加持久语义与优先意图管理，但能分别表达完成事实和用户授权；采用        |

必须保持以下不变量。

- **事实与权限分开**：`verified_complete` 表示某旧动作已被精确证明完成；`explicit_takeover` 表示用户允许本条越过历史顺序限制，绝不表示旧消息已完成。
- **历史占位与真实写者分开**：book 不等于 writer。真实派发锁、仍在运行的派发任务 / RPC 及写入 claim 必须单独核实，不能仅查 book 或 DB fences。
- **按所有者清理**：释放必须比对 `ThreadKey + actionId`，重试涉及同一 action 时再比对 attempt；旧 A 的终态、核对或迟到回调不能清 B。
- **持久先于内存**：核销记录与相关 DB 变更先提交，成功后才条件清内存；失败保留限制并允许幂等重试，不宣称已解除。
- **授权仅本条**：grant 绑定目标 action 与 attempt，以 CAS 一次消费；不扩展为线程级开关，不给其他 queued 条目借用。
- **未知不重发**：Unknown 或 Accepted 均不能重新进入本次待派发集合；核销及接管不改写旧动作的投递事实。
- **串行不降级**：单个会话同一时刻最多一个实际 writer；前台超时、取消请求或旧消息状态未知都不能绕过仍持有的真实派发权。

## 四、关键流程

### 4.1 自动完成核销：`verified_complete`

1. 由既有终态结算、周期对账等入口取得未陈旧的投影与对应动作的精确完成证据；沿用现有核对纪律，不以 idle、时间经过或 fences 为空替代证明。
2. 将 `release_turn_if_complete` 与 `settle_turn_evidence` 的结果统一交给按 action 的核销入口，传递旧 action、已验证 turn 及核销原因。
3. DAO 在同一事务中幂等记录 `verified_complete` 并清对应持久 fence；原投递状态可以仍为 Unknown，人工解除时间不变。
4. 提交成功后，router 只在当前 book 仍属于该 action / attempt 时清理；可泛化 `force_clear_turn_limit` 的精确归属逻辑，名称不再暗示只能人工解除。
5. 后继通过原 `flush_thread` 规则接力；若真实 Desktop 仍忙、待审批或队列暂停，继续遵守对应门禁。

权衡：统一生命周期入口会增加少量 DAO / router 协作，但避免“只清 DB”与“整线程清内存”两类相反错误。

### 4.2 强制插队：`explicit_takeover`

1. 沿既有插队入口校验设备、权限、目标线程、载荷身份及 action 仍为 queued；重复请求关联同一进行中尝试，不新建第二个写者。
2. 在争锁前登记绑定目标 action / attempt 的优先意图。同线程同一时刻仅有一个有效接管意图；同目标重放幂等，其他目标收到明确的已有接管提示。
3. 后台 flush 及其他新派发在获锁后、写出前检查该意图并让位；已经开始的真实 writer 继续完成，不抢其锁、不清其 claim。
4. 用现有线程派发锁有界等待串行权，避免循环 try-lock 被后台 flush 反复抢走；预算耗尽返回 `dispatch_in_flight` 等具体原因。
5. 持锁后重新获取 fresh runtime，并核实真实派发任务 / RPC 是否已退出写阶段；仅“DB 无 fence”不能放行。
6. **Desktop idle**：对本次目标接管历史 book / 旧 Unknown 的顺序限制，不等待自动 cleanup 成功，也不要求旧消息完成证据。
7. **Desktop active**：沿既有忙态确认与能力门，绑定当前 `expectedTurnId` 请求停止；有界确认该回合终态后再优先发送本条。上下文变化则重新确认，不能无阀停止新回合。
8. Desktop 不可达、投影陈旧、待审批、权限不足、停止拒绝或结果未知时如实回执；未确认终态不得发送目标消息，不另建一套审批流程。
9. 最后复核 action 未撤回 / 未离队、设备有效及写前运行态；在事务中完成 reserve、grant 对应 attempt 的 CAS 消费与 `explicit_takeover` 记录。
10. 提交后按所有权接管历史顺序占位，交给唯一后台任务派发**本条**；禁止走普通批量拼接入口，不取消其他条目暂停，不顺带 flush 整队。
11. 回执如实表达本条 Accepted、Unknown、明确未送达或仍排队；其他条目后续仍由原队列规则决定。

权衡：显式接管独立于完成证据，提供用户要求的主动出口；代价是可能越过尚未核实的历史消息，因此保留旧 Unknown 及接管审计，真实写者与运行态门始终有效。

### 4.3 优先意图与真实在途的收尾

- 优先意图是短期调度权，不是另一份永久 book；绑定请求预算、action 和 attempt，不产生跨 action 的长期特权。
- 写前撤回、目标离开 queued、能力 / 权限拒绝、前台预算耗尽或请求取消，均撤销 / 失效该意图并唤醒正常调度；异常路径也有有界失效兜底。
- 写出后的串行责任移交唯一后台派发任务；前台断开只影响等待，不注销仍活跃的 writer，不重新铸造授权或重发。
- writer 身份由实际派发任务 / RPC 生命周期和 claim 共同描述；未确认退出写阶段时，宁可回具体在途原因，也不能把它当历史残留清掉。
- 停止结果未知继续沿既有停止状态机核对；优先意图失效不等于可以越过未确认停止的活动回合。

权衡：保留既有锁体系，仅补意图与在途生命周期，不另建并行锁；实现必须保证每条终止路径都能释放调度意图。

## 五、持久语义、孤儿修复与失败恢复

### 5.1 核销记录契约

新增最小持久核销记录，逻辑集合记为 `codex_barrier_resolutions`；它补充现有 action / grant，不代替投递账本。

| 字段 / 约束                              | 明确语义                                                                        |
| ---------------------------------------- | ------------------------------------------------------------------------------- |
| `host_id + thread_id + source_action_id` | 被核销或被本次越过的历史动作身份；写入前核对归属                                |
| `reason`                                 | 仅本设计两类：`verified_complete` 与 `explicit_takeover`，不能互相冒用          |
| `evidence_turn_id`                       | 自动核销必填且须已精确验证终态；显式接管不要求该证据，不虚构 turnId             |
| `target_action_id + grant_attempt`       | 显式接管必填，限定仅该目标的该次派发；自动核销为空，表示该源动作的全局完成核销  |
| `resolved_at` 与授权审计关联             | 记录实际提交时间及既有设备 / 操作审计关联；不保存正文、题干、答案或原始帧       |
| 幂等与唯一性                             | 自动核销按源动作唯一；显式接管按源动作、目标及 attempt 唯一，重复提交无额外效果 |

- `verified_complete` 与清源动作 fence 同事务提交；`explicit_takeover` 与目标 reserve / grant CAS 同事务提交，记录本次越过的历史所有者。
- 显式接管记录仅对目标 attempt 生效，旧动作的全局 fence 可以保留；不能用它全局豁免其他队列项，也不能解除旧队列暂停。
- 两类记录均单调保留，后续只补充真实结果；若旧动作后来获完成证明，可追加 `verified_complete`，不覆盖原接管理由。
- 旧数据库无记录一律表示“未记载解除”，迁移不得从 `compat_outstanding=0`、idle 或记录年龄回填“已完成”。
- `barrier_force_released_at` 只表示真正发生过的人工解除；自动核销不得冒写这个字段。

权衡：增加迁移与记录存储，换取重启、迟到和重复请求下可验证的语义；自动核销与单次接管作用域分开，防止授权扩散。

### 5.2 对账与错误路径

- **已有 DB 空 / book 残留**：对账从 book 取源 action 查询核销记录；已提交完成核销即可精确补清内存，无须 DB fence 仍存在。
- **旧数据没有核销记录**：只有精确完成证据成立才补记自动核销；证据不足保留 Unknown。用户显式插队另走接管路径，不因对账失败而永久等待。
- **DB 失败**：核销事务回滚则不清内存；接管事务失败则不写 Desktop、不消费部分授权；返回存储错误并保留可重试状态。
- **DB 已提交、内存更新失败或进程退出**：下一次对账 / 启动恢复读取记录完成条件清理，不重新推断完成、不复活已提交效果。
- **迟到结果**：`finish_late_result_conn` 及正常结算入口检查核销作用域。已 verified 的源动作不能重新置起完成屏障；已接管的目标 attempt 不能被迟到源结果重新阻断。
- **保留真实事实**：迟到 Accepted / Rejected 可以只补对应旧动作真实回执；不能因此清新动作 book、回滚接管审计或自动重发任一旧消息。
- **消费后明确零投递回队**：仍 queued 且证据证明零写入，才允许后续新的用户授权产生新 attempt；Unknown / Accepted 不得以重铸 grant 重试写出。

## 六、接口与前端结果契约

复用现有插队、停止及队列接口；保留能力、权限与忙态确认，不新增公共操作或审批入口。

| 结果类别                             | 后端 / UI 必须表达的含义                                                 |
| ------------------------------------ | ------------------------------------------------------------------------ |
| Accepted / Unknown                   | 本条已受理 / 投递结果未知；Unknown 不呈现成失败并诱导重新发送            |
| `dispatch_in_flight` / 接管已进行    | 真正派发尚未结束或已有有效接管意图，本条未新增写入；可以等待当前操作结果 |
| runtime active / 停止待确认          | 需要沿既有确认停止特定回合，不能用清历史占位代替停止                     |
| 不可达 / stale / 状态不可确认        | 无法取得 fresh 运行态，本条仍排队，不能笼统归类为“桌面忙”                |
| pending / capability / permission    | 审批未完成、能力不可用或权限不足；本次接管不穿透这些门                   |
| 停止拒绝 / 停止结果未知 / 上下文变化 | 分别如实说明，未确认目标回合终态时不发本条                               |
| 撤回 / 离队 / 重放 / 存储错误        | 返回目标实际账本状态及原因；不误报发送成功，不自动另建新消息             |

后端保留具体 `reasonCode` 与操作阶段，前端按类别显示中英文案及本条排队 / 投递状态；新增枚举命名随既有契约对齐，不能把不同原因统一改写成 busy。
权衡：前后端增加少量分支，换取可操作的失败信息；不把内部 book、SQL 等实现细节暴露为用户操作流程。

## 八、验收标准 / 测试要点

以下均为待实现后的验收要求，不表示本轮已运行或通过测试。

| 场景                             | 必须验证的结果                                                                                        |
| -------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 真实派发 → Unknown → 完成核对    | 经 router 实际建 book，不直接只种 DB；核销与 book 收敛后后继自动派发，实际写入一次                    |
| 首次接力后再次插队               | 同一 Tuvis 进程不重启；第二次选中动作可按其运行态完成接管，不被前次历史占位锁死                       |
| DB fence 已空、book 残留         | 可按持久核销记录或精确证据补清；也可在 idle 且无真实 writer 时显式接管，不依赖后台先清完              |
| 旧 Unknown 没有完成证据          | 自动路径不猜完成；用户显式插队可仅发选中条目，旧 Unknown 保留、不重发、不伪造 Accepted                |
| Desktop active                   | 普通发送仍排队；插队确认后仅停止 expectedTurnId，确认终态再发本条，不拼接其他 queued 消息，不解除暂停 |
| 旧 A 完成 / 迟到，新 B 仍 active | A 的 fence 可核销，B 的内存 book、claim 与真实运行限制必须保留                                        |
| 真 writer / RPC 未结束           | 插队有界等待或回明确在途原因；实际 writer 最大并发数为 1，不抢锁、不清真实 claim                      |
| flush 连续竞争与意图收尾         | 登记后的插队获得下一次合格派发优先权；撤回、取消、超时、离队、能力拒绝不会留下永久优先占位            |
| DB 核销 / 接管失败               | 回滚不半消费、不清错内存、不写 Desktop；重试提交后最终收敛                                            |
| 提交后重启与迟到结果             | verified 不复活；explicit 的目标作用域与消费结果保持，旧迟到不阻断已接管 attempt、不清新动作          |
| 重复点击、撤回、已有 Accepted    | CAS 仅一次消费；撤回赢则零写入；Accepted / Unknown 的重放不再次派发；明确零投递才允许新授权 attempt   |
| 前端 reason 分类                 | 不可达、状态未知、真实 writer、审批 / 权限、停止拒绝及停止未知分别呈现，双语一致                      |

既有覆盖的准确边界：`codex_ipc_remote.rs` 的 P2 用 `seed_unknown_barrier` 直接建立 DB 状态，确实验证后继 Accepted，但未经过真实 router 建立 book，不能覆盖本次完整生命周期。`codex_control_remote.rs` 的 P9b 令旧、新 turn 同时终态，未验证“旧 A 终态、新 B 仍活动时保留新占位”。

真机验收状态：**待验**。在保留同一 Tuvis 进程的条件下，由用户在 Desktop 执行所需确认和操作，验证空闲残留插队、active 停止后本条先发、再次插队及旧队列暂停保持；代理不代答题目或审批。
真机记录仅保留版本、动作类别、结构化结果、次数与脱敏状态，不收录私聊正文、题干、答案、原始帧或具体私人 threadId。

## 九、风险清单与完成边界

- fresh 状态取得后仍可能发生桌面侧变化：由 `expectedTurnId`、最后写前守卫及真实 writer 串行权约束；竞态需集成测试与真机复验。
- 旧数据没有核销记录：保持“未解除”的保守默认，自动修复需要精确证据；显式接管提供独立出口，不能靠迁移猜完成。
- 优先意图收尾遗漏可能形成新占位：写前所有终止路径须覆盖取消与预算耗尽，写后仅由唯一后台任务结算。
- 自动核销与显式接管混淆会扩大放行范围：持久记录分别表达理由与作用域，普通发送、暂停及单会话串行均按既有规则。
- 最初 `client_message_unverified` 的触发成因尚未定位，留作后续独立调查，不纳入本批根因修复。
- “清旧 fence 误清新 book”的归属检查缺口属于本批必须修复的范围；现已通过 Task1 新旧动作交错、代际与补绑回归及两阶段审查。该局部验收不代表整体实现、原有 B1.3 草稿或真机验收已通过。

完成标准是上述功能语义实现、定向回归通过，并取得列明的用户真机验收结果；本文档落盘只代表设计归档，不代表实现获授权、测试通过或问题已修复。
