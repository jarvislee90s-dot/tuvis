## 0. 结论先行

1. 有官方契约的协议（MCP / ACP / Codex app-server）都用同一套办法：**major 版本号只管破坏性变更，功能用 capability 位协商，未声明 = 不支持**。Codex app-server 更进一步，`initialize` 里根本没有 `protocolVersion`，只有 `clientInfo` + `capabilities.experimentalApi`。
2. 没有契约的私有 IPC（我们这类），同类项目没有一个能「推断」版本兼容性。它们的做法是：**精确 pin 一版做 verified，其余一律 best-effort；失败按单操作归因，不整体禁写**。
3. Happy 对 Codex 用的是官方 `codex app-server`，并且自己解析 `codex --version` 维护「能力 × 最低版本」表（app-server 0.153+、goal 操作 0.140+），未知版本该能力关闭。它**不碰** Desktop 私有管道。
4. 我们当前是「精确白名单 + 未知即全关」，属于最严的一档；安全上没错，产品上不可持续。
5. **用户裁决（2026-10-21）**：未知 build 在**首次触发相关能力时**才探测，单次最多 **15 秒**，然后反馈状态；探测结果**落本地账本**，下次同版本直接复用，不重复探测；`permissions` 本阶段不做。
6. **macOS 实机探测（2026-10-21）**：build = `CFBundleShortVersionString`（`26.1013.40934`）、socket 路径与 0700/0600/同 uid 全部成立；`initialize` 首帧 0.914 ms，`clientId` 在 `result.clientId`；唯一被推翻的是「CLI 哈希目录」——macOS 没有，改读 `codex-package.json` 的 `version`。

## 1. 现状与代价

`profile_for(platform, build)` 只匹配四个 build：

- Windows：`26.1013.3656.0`、`26.1013.4894.0`
- macOS：`26.1013.31256`、`26.1013.40934`

不命中 → `ProtocolProfile::closed()`，`CapabilitySet` 全 false。连带影响（已核对代码）：

| 位置 | 行为 |
| --- | --- |
| `mirror.rs:463 availability_of` | 只有 `send && state` 才 `Controllable`，否则 `CompatOnly` |
| `remote/codex_ipc.rs:277 ipc_available` | 要求 `caps.send && caps.state`，未知 build 恒 false → A 路不可用，退回 queue/exec |
| `pending.rs` | 已知方法但能力未验证 → `capability_unverified`；未知方法 → `capability_unavailable` |

也就是说：**只读投影被 `send` 绑死了**。即使探测证明 `state` 可用，只要 `send` 没开，界面仍然是 `CompatOnly`——这是实施时必须先拆开的一处耦合。

现状的代价：Desktop 自动升级 → build 变化 → 全部能力归零 → 用户看到「未解锁」→ 我们必须真机探测 + 发版才能恢复。

## 2. 外部怎么做的

### 2.1 有契约的协议：版本管破坏，能力管功能

| 协议 | 版本信号 | 未知/不匹配时 | 关键规则 |
| --- | --- | --- | --- |
| **MCP** | `initialize.params.protocolVersion`（日期串） | 服务端回自己支持的最新版；客户端不支持则断开 | 客户端发自己支持的最新版；双方**只能使用协商成功的 capability**；错误示例里带 `supported` 列表 |
| **ACP** | `protocolVersion`（整数 = **major**） | 服务端回「同版本」或「自己最新的较低版本」 | 只有破坏性变更才递增；**新增能力不算破坏性变更**；**未在 initialize 里声明的一律视为 UNSUPPORTED** |
| **Codex app-server** | **没有** `protocolVersion` | 不适用 | `initialize` 只有 `clientInfo` + `capabilities.experimentalApi`；上游明确写：`experimentalApi` opt-in **不能**标识 GUI 版本兼容 |

共同点：**能力发现优先于版本比较**。版本号只回答「我们说的是不是同一套语法」，功能问题交给 capability。

Codex app-server 是特例：连语法版本都不协商，靠「只增不改 + 未知字段忽略 + experimental 开关」。代价是上游自己也承认：**能力位不等于兼容性**。

### 2.2 私有 IPC 同类项目：pin + best-effort + 逐操作归因

**① `melompeel/codex-desktop-remote`（Android 远控，Kotlin + Node bridge）**

`desktop_bridge/src/ipc/adapter.ts`：

```ts
packageVersion: "26.901.1978.0",
cliVersion: "0.153.0-alpha.5",
methods: { "thread-stream-state-changed": 11, "thread-follower-start-turn": 2, ... }
```

- `verified` 判据是 **Desktop 包版本 + 随包 CLI 版本两者都精确相等**；
- 不相等 → `mode: "best-effort"`，`supported` 仍为 true；
- `API_CONTRACT.md` 原文：不匹配时「已知 IPC 操作继续可用、可解析的流继续同步、**单个操作被拒只报它自己的协议错误，不全局禁用写**」；
- 每个方法带版本号，未知方法抛 `unsupported-ipc-method:<m>`。

**② `gantrol/codex-control`（C#）**

- 自我定位「**显式版本化的 desktop 协议边界**」，声明不是稳定公开 API；
- 消费方 pin **同一个精确包版本**；
- 明确「**不做自动 fallback、不重放可能已发出的 mutation**」。

**③ 我们**：精确白名单，未知即全关——三家最严。

### 2.3 绕开协议的一类：PTY + hooks

Superset 的做法是「**不解析 agent 输出**，在真实 PTY 里跑，靠 hooks 观察生命周期」。版本无关，但只能做起停/看状态，做不到原生审批、结构化问答、历史线程接管。

**这就是我们不能只走 PTY 的原因。**

### 2.4 Happy 具体怎么做

- **Claude 侧**：官方 `@anthropic-ai/claude-agent-sdk`（`canUseTool`、`setPermissionMode`），依赖 caret 锁 `^0.3.x`；**兼容外包给官方 SDK**。
- **Codex 侧**：官方 `codex app-server`（stdio JSON-RPC）+ `execSync('codex --version')` → major/minor → 「能力 × 最低版本」表（app-server 0.153+、goal 0.140+），读不到版本 → 该能力 false。
- **从不碰** Desktop 私有管道。

**启示**：它有官方口可用，所以不需要探测；我们只有私有管道，只能自己造探测口。

### 2.5 手段汇总

| 手段 | 代表 | 前提 | 我们可用性 |
| --- | --- | --- | --- |
| 握手协商版本 | MCP / ACP | 对方配合 | ✗ 无 protocolVersion |

## 3. 我们手里有什么信号

| 信号 | 现状 | 能用吗 |
| --- | --- | --- |
| Desktop build | MSIX `AppxManifest.xml` / macOS bundle，唯一才取 | ✓ 归因、账本键 |
| 随包 CLI 版本 | 目前没读 | ✓ 可补，第二指纹（可选） |
| `initialize` 回包 | 只回 clientId，无版本 | ✗ 无协商口 |
| 方法 `version` 字段 | 我们发，对面不回「支持哪些」 | ✗ 只能用于发送 |
| 错误形态 | 版本不匹配会表现成 `no-client-found`，与「无 owner」歧义 | △ 只能当「不确定」 |
| 状态流 | `thread-stream-state-changed` 不来 = 漂移信号 | ✓ 静默即证据 |
| 回执/镜像 | 写后唯一事实来源 | ✓ 成功判据 |

**关键判断**：我们没有「问对面支持什么」的能力，能力只能来自**行为证据**。

## 4. 设计

### 4.1 核心改动：白名单 → 证据缓存

```text
profile_for(platform, build)
  ├─ 命中 shipped 表        → Verified（现有证据，不探测）
  └─ 未命中
       ├─ 账本命中（同期）  → 直接复用结论，不探测
       ├─ 账本未命中/过期   → 首次触发能力时惰性探测（≤15s）
       │                       ├─ 通过 → Probed，写账本
       │                       └─ 不定 → Inconclusive，写账本 + 退避
       └─ 明确失败          → Closed，写账本
```

`profile_for` 的返回值语义从「能不能用」变成「已知多少」。**能力开关不再由 build 决定，由证据决定；build 只决定「这份证据能不能复用」**。

### 4.2 三态（用户可见）+ 内部证据级别

| 状态 | 含义 | 读 | 发 | 审批/权限 |
| --- | --- | --- | --- | --- |
| **Verified** | 精确 build 有真机证据 | ✓ | ✓ | 按证据 |
| **Probed** | 未知 build，探测通过 | ✓ | 设置开关后 ✓ | ✗ |
| **Closed** | 探测明确失败 / 无 endpoint / 身份不明 | ✗ | ✗ | ✗ |

内部证据：

```rust
struct CapabilityEvidence {
    source: EvidenceSource, // Shipped | LedgerProbe | None
    build: Option<String>,
    probe_stage: Option<ProbeStage>,
    observed_at: i64,
}
```

`CapabilitySet` 的每个 true 都必须能回答「凭什么是 true」。

### 4.3 指纹与账本键

账本键（也是证据复用键）：

```text
probe_key = platform + build + cli_id + probe_epoch
```

**第二指纹 `cli_id`（2026-10-21 双平台实测）**：

| 平台 | build 指纹 | `cli_id` 取法 |
| --- | --- | --- |
| Windows | MSIX 清单 `Identity/@Version`（实测 `26.1013.4894.0`） | `codex.exe --version` → 归一化 `0.163.0-alpha.10.2`；失败用 `bin/<hash>` 目录名 |
| macOS | 主 bundle `CFBundleShortVersionString`（实测 `26.1013.40934`） | 读 `Contents/Resources/codex-cli/codex-package.json` 的 `version`（免执行）；或 `--version`；**没有哈希目录** |

macOS 实测细节（2026-10-21，Mac mini / arm64）：

- CLI 固定路径 `Contents/Resources/codex-cli/CodexCLI.app/Contents/MacOS/codex`（238 MiB），另有 328 B 的固定 shim `Contents/Resources/codex-cli/bin/codex`；路径不含版本、不含哈希，升级不变；
- `codex-package.json` 自带 `version` / `target`（`aarch64-apple-darwin`）/ `layoutVersion`，比目录名信息量更大，且**不用执行子进程**；
- 两平台 CLI 同版本（`0.163.0-alpha.10.2`），但 App 包 build 不同（40934 vs 4894）——`cli_id` 确实是与 build 独立的第二指纹；
- **身份必须锁主 bundle**：`Codex (Service)`/`(Renderer)` 是 `155.0.8059.80`（Chromium），`CodexCLI.app` 的 ShortVersion 为 null，`Codex Computer Use.app` 是 `26.1013.1001501`；只有 `CFBundleIdentifier == com.openai.codex` 的那份才是 build 真源；
- 现有 `unix.rs` 的 XML plist 解析已实测成立：本机 `Info.plist` 是 **XML 1.0 / ASCII**（`<?xml ve`），不是 `bplist00`；但只覆盖这个 build/这台机器，其他 build 仍可能改二进制 plist——`plutil` 兜底列为低优先，不阻塞 P1。

- **`probe_epoch`**：Tuvis 侧常量，**探测算法/方法表/解析期望**一变就 +1。
- 用 `probe_epoch` 而不是 Tuvis 版本号做键：patch 版本升级但探测逻辑没变时，不必重新探测；否则每次发版都要重探，那才是真冗余。
- **build 读不到**：允许只读探测，但写能力恒关——**无法归因的写操作不允许发生**。
- 不做跨重启之外的持久失效：同 build 同 epoch 的证据长期有效（同一个二进制，协议不会自己变）。

### 4.4 探测时机与预算（用户裁决）

**惰性触发**，不在 `initialize` 后就跑：

| 触发点 | 需要证明的能力 |
| --- | --- |
| 用户打开某个 Codex 线程详情 | `state`（只读链 P0–P3） |
| 用户点发送（且 `state` 已 Probed） | `send`（不单独探测，**发送本身就是探测**） |
| 出现 pending 卡片 | `command` / `blocking_input`：**不探测、不开放**，只如实提示到桌面处理 |

**15 秒总上限**（读链；Windows/macOS 均已有实测，预算按「上限」而非「预期」给）：

| 级 | 动作 | 上限 | 实测（Windows 4894，2026-10-21） |
| --- | --- | --- | --- |
| P0 | connect + `initialize` | 1s | connect 亚毫秒；initialize **200–440ms**（Mac 0.9ms） |
| P1 | `thread-owner-discovery` | 2s | 有 owner **11–13ms**；无 owner **~2s** 回 `no-client-found` |
| P2 | `following-changed` + `status-requested` | 3s | follow 后 **15–21ms** 收到 snapshot |
| P3 | 首个 snapshot 解析（核心字段门槛） | 3s | `change.type=snapshot`、`revision=5`、`conversationState` 45 键、9.2KB |

总预算 9s，留 6s 余量给冷启动/调度抖动，硬上限仍 15s。
超时 → 记 `inconclusive`（不是 `fail`），界面反馈「未确认，可重试」，按退避重试（30s → 2min → 10min），不无限重试。

**探测请求要镜像 Desktop 自己的 envelope**：`sourceClientId` + `timeoutMs` 一起带（`app.asar` 的 `sendRequest` 就是这么发的）；Windows 实测带这两个字段时 discovery 11ms 返回。生产代码目前不带也能工作，但探测实现按上游形态走，减少未知。

**单飞**：同一 `probe_key` 同时只跑一条探测，其他触发点 await 同一结果；否则多个入口各跑 15s，既慢又重复写账本。

**可取消**：用户切走/关页 → 取消探测，不写「失败」，下次重新来。

### 4.5 为什么只读探测能证明东西

| 级 | 证明了什么 | 失败处理 |
| --- | --- | --- |
| P0 | 传输/帧格式/envelope 没变 | Closed |
| P1 | 方法存在、owner 路由可用 | `no-client-found` → **不确定**，不判死 |
| P2 | following 语义、状态方法版本 | 静默 → `protocol_drift_suspected`，**不误判可用** |
| P3 | 字段结构可解析（turn 状态 / items / thread id 核心字段） | 解析失败 → Inconclusive（只读缓存/CompatOnly） |

**P3 的具体判据（Windows 4894 实测形态，2026-10-21）**：

```text
params.change.type == "snapshot"
params.change.revision 是数值
params.change.conversationState 是对象，且至少含：
  - turns: array
  - requests: array
  - turnHistory: object（history.entitiesByKey / islands 可为空）
```

实测样例：`change` 键 = `type/revision/conversationState`；`conversationState` 45 个键（`id/turns/requests/turnHistory/threadRuntimeStatus/latestCollaborationMode/...`）；`entitiesByKey=2`、`islands=1`、`requests=0`、整帧 9.2KB。

**空线程也算通过**：只要 `turns/requests/turnHistory` 三个容器存在且类型正确（entities 为 0 正常），就证明结构可解析；不要要求必须有内容。

四条必须守住：

1. **`no-client-found` 不能当死亡判决**（现有注释已写明版本不匹配就长这样）；
2. **P3 解析失败不等于协议不存在**，只能判「看不懂」，降级但不伪造；
3. **被动广播不是我方请求的证据**：macOS 实测 `initialize` 后约 1ms 就被拉进 following 广播组，并收到真实会话的 `thread-stream-following-changed{following:true}`——它只证明「方法/版本存在、链路活着」，不能证明「我方 follow 成功」。探测必须按 `requestId` 关联自己的响应与快照，未关联的帧只能记为「链路存活」；
4. **`clientId` 在 `result.clientId`（不是顶层），且每次握手都换新**：P0 的通过判据必须是「拿到本次 `result.clientId`」，不是「收到任意帧」。另外 `client-discovery-request`（内层 `ide-context`，带 `workspaceRoot`，5s 超时）会偶发出现，生产链路已回 `canHandle:false`；探测链路同样处理或忽略，**不能把它的超时算成协议失败**。

### 4.6 本地账本

**目的**：同版本不重探；同时沉淀「Codex build × Tuvis 能力」的匹配数据，后续可以据此把某个 build 提升进 shipped 表。

**存储**：SQLite `~/.tuvis/tuvis.db` 新表（`schema.rs` 里 `CREATE TABLE IF NOT EXISTS`，新表不需要 migration；与 `session_status_cache` 同类做法）。

```sql
CREATE TABLE IF NOT EXISTS codex_ipc_probe (
    probe_key      TEXT NOT NULL,   -- platform|build|probe_epoch
    capability     TEXT NOT NULL,   -- state|send|command|blocking_input|plan_implementation|collaboration_mode
    state          TEXT NOT NULL,   -- verified|probed|failed|inconclusive|unknown
    probe_stage    TEXT,            -- 最后通过的级 P0..P3
    error_code     TEXT,
    attempts       INTEGER NOT NULL DEFAULT 1,
    first_seen_at  TEXT NOT NULL,
    last_seen_at   TEXT NOT NULL,
    next_retry_at  TEXT,
    last_duration_ms INTEGER,
    PRIMARY KEY (probe_key, capability)
);
```

- **一行 = 一个 (版本, 能力)**，6–7 个能力 × 少量 build = 几十行，**不随会话/线程增长**；
- **upsert 不是 append**：`ON CONFLICT(probe_key, capability) DO UPDATE`，只累加 `attempts`、刷新时间；
- **不存正文、不存 threadId、不存原始帧**，只存 stage / 错误码 / 耗时（对齐现有审计隐私纪律）；
- 同一 build 不同账号策略可能不同（例如 permissions 请求在部分账号根本不出现）——所以审批类**本来就不靠探测开**，账本也不给它升级；
- 账本只对「非 shipped build」写入；shipped 表命中的 build 不重复记录（避免同一事实两处存）。

**复用规则**：

| 账本状态 | 下次行为 |
| --- | --- |
| `probed`（读/发） | 直接启用，**不再探测** |
| `failed`（明确协议错误） | 直接 Closed；换 build / `probe_epoch` 变更 / 用户点「重新探测」才重试 |
| `inconclusive` | 到 `next_retry_at` 再试；期间按 Closed 展示但文案是「未确认」 |
| `unknown` / 无行 | 触发一次惰性探测 |

**会不会冗余？** 不会，前提是三条：

1. 键是「build + probe_epoch + capability」，不是「会话 / 线程 / 每次连接」；
2. **upsert 覆盖**，不是每次探测插一行；`attempts` 只是计数；
3. 不按 Tuvis 应用版本号做键（否则每发一版全部重探，那才是真的冗余）。

### 4.7 发送：先拆耦，再开关

**先拆耦**：`availability_of` 现在要求 `send && state`。必须改成 `state` 独立决定「能不能看」，`send` 独立决定「能不能发」，`availability` 增加只读档。

**再开关**：发送默认关，设置页显式开「兼容发送（实验）」。

**成功判据**（沿用 S5 纪律）：

- 写前 `NotSent`（`UnsupportedMethod` / 连接失败 / 忙态拒绝）→ 允许 fallback 一次；
- `Accepted` 只代表「对面受理」；
- `Unknown`（超时/断链）→ **不重发、不 fallback**，账本记 `delivery_unknown`，界面提示「可能已发送，请到桌面确认」；
- `clientUserMessageId` 继续带，用于回显对位；**不假设对面会去重**。

### 4.8 审批 / Plan / permissions（本阶段范围）

| 能力 | 未知 build 策略 | 说明 |
| --- | --- | --- |
| `permissions` | **本阶段不做**（用户裁决），保持关闭 | 不探测、不推断、不开放 |
| `command` | 不探测；保持证据门 | 出现 pending 时如实提示「请到电脑处理」 |
| `blocking_input` | 不探测；保持证据门 | 同上 |
| `plan_implementation` / `collaboration_mode` | 不探测；保持证据门 | 属于模式切换，冻结 spec §5 之外 |

即：本阶段探测**只解决读与发**，审批相关的门一个都不动。这既是用户裁决，也是风险最小的切法。

### 4.9 用户可见

- 徽标：`已验证` / `兼容探测（实验）` / `未确认` / `未解锁`；
- 首次触发时显示「正在探测此 Desktop 版本（最多 15 秒）」，带取消；
- 失败必须带原因码：`desktop_build_unverified` / `probe_failed:P2` / `protocol_drift_suspected` / `probe_inconclusive`；
- 设置页：「Codex Desktop 兼容模式」三档——仅已验证 / 允许探测（默认）/ 关闭。

### 4.10 错误码

沿用现有拆分：

- `capability_unverified`：方法已知、能力未验证（现有语义复用）；
- `capability_unavailable`：方法未知/连接不可用（现有）；
- 新增 `reasonCode`（不改 error 主码）：`desktop_build_unverified`、`probe_failed:<stage>`、`protocol_drift_suspected`、`probe_inconclusive`、`delivery_unknown`。

审计只记 actionId / threadId / build / probeStage / 结果，不记正文。

### 4.11 观测

`probeReport { stage, ok, latencyMs, errorCode, build, cliId, probeEpoch }` 落**结构化日志**（`log::info!`），供排障与人工提升 shipped 表时检索。

**不做诊断页、不做导出**（2026-10-21 裁决）：账本是程序自用的缓存，不是用户功能；需要看时用 SQL 查 `~/.tuvis/tuvis.db` 即可，不增加产品面。

## 9. 已裁决（2026-10-21）

- 未知版本：首次触发能力时惰性探测；
- 单次探测上限 15 秒，超时反馈「未确认」；
- 探测结果落本地账本，同版本复用，不重复探测；
- `permissions` 本阶段不做；
- 账本键用 `probe_epoch`，不用 Tuvis 应用版本号；
- 补读随包 CLI 做第二指纹（Windows `--version` / 哈希目录兜底；macOS `codex-package.json`）；
- **desktop-owned 会话不得静默改走 headless**（发到 A 或诚实失败）；**裁决 B（2026-10-21）**：已验证 build 的 A 路 `NotSent` 保留 R8 headless 兜底，作为明确例外；

- 兼容模式**默认「允许探测」**。

## 10. 执行前还缺的设计（2026-10-21 二次评审）

以下是「政策已定、但写代码前必须钉死」的条目，按重要性排序：

1. **发送与回退语义（最重要，已确认；2026-10-21 裁决 B）**：桌面归属会话在**没有写能力证据**时只允许「发到 A 或诚实失败」，不得静默改走 headless。**例外（明确保留）**：已验证 build 的 A 路 `NotSent`（如 Desktop 瞬时断链）仍按 R8 契约兜底到 headless——这是产品裁决，不是实现遗漏。实现上用 `build_send_verified`（build 证据，与连接存活解耦）区分「未取证」与「已验证但断了」；`session-send-info` 必须与 `session-send` 同源，未知 build 返回 `injectable:false` + `capability_unverified`。
2. **探测跑在哪条连接**：复用 adapter 现有单连接（`ensure_connection`），不另开；P0 预算并入现有握手。探测的 follow 必须用临时引用并立即释放，**不得增加 `gate` 订阅计数**、不得干扰 mirror。
3. **P3 判据**：已由 Windows 实测钉死（见 §4.5）——`change.type=snapshot` + `revision` 数值 + `conversationState` 含 `turns/requests/turnHistory`。空线程只要三个容器在就算通过，不要求有内容。
4. **P1 选线程**：必须选 **Desktop 有 owner 的线程**；用户打开的线程无 owner → `inconclusive`，不判死；是否允许换一个最近 owner 线程重试一次（建议允许 1 次）。
5. **15 秒内的 UI**：详情页进入「探测中」骨架态，完成后再渲染；不得先渲染假空会话。
6. **发送结果 → 账本状态映射**：`accepted` → `send=probed`；写前 `NotSent` → `failed`；`Unknown` → `inconclusive` + `delivery_unknown`（不重发）；**`verified` 只来自 shipped 表，账本永不写 verified**。
7. **重试/取消驱动**：无后台定时器，只在下次触发时看 `next_retry_at`；用户切页**不取消**探测（15s 很短），仅停止等待——需确认。
8. **`PROBE_EPOCH` 常量纪律**：放 probe 模块，注释写明「方法表 / 解析期望 / 探测步骤变更即 +1」，并加测试断言 key 含 epoch。
9. **可执行性前置（测试）**：本机当前 build 就是已验证的 4894，跑不到未知分支 → 需 debug-only 强制开关（如 `TUVIS_CODEX_IPC_FORCE_UNVERIFIED=1`，仅 debug 生效），否则 P1 只能靠 `ScriptedPeer`。
10. **文案与文档**：移动端 i18n（探测中 / 未确认 / 未解锁 + 原因）、README 能力矩阵注记、`docs/capabilities.json` 说明，随发版同步。
11. **router 错误响应没有 `method` 字段（实测，必须修）**：`connection.rs:649` 要求 response 的 `method` 与 pending 一致，否则放回等待；但 Windows 实测 `no-client-found` 的响应是 `{"type":"response","requestId":…,"resultType":"error","error":"no-client-found"}`，**没有 `method`**。后果：owner discovery 失败会卡到 15s RPC 超时才返回，而不是 2s 拿到 `no-client-found`；#172 的探测也会把「无 owner」误判成超时。修法：`requestId` 命中且 `method` 缺省时，按该 pending 处理（method 存在但不一致才放回）。

**还需要哪些实机探测（2026-10-21 更新）**：

- **Windows 读链已完成**（W1–W4，见 §11.1）：成功路径 ~0.4s、失败路径 ~2s、P3 形态已钉死；
- Windows 只剩 W6（探测对 mirror 的干扰，需 P1 代码）与 W5（CLI 更新残留，等真实更新）；
- **macOS 主要项已完成**（M1–M9，见 §11.2）；剩余未取：`CODEX_HOME` 对 App 侧的影响、重启后 socket 重建——两者都需要重启 App，按约定不做；
- Windows 上「强制未验证」的探测时序仍建议在 P1 实现后用 debug 开关补一次，但设计不再依赖它。

- 握手后约 1 ms 就被拉进 following 广播组，收到两条真实会话的 `following:true`；

### 11.3 探测后的设计判定（已落地到本文）

- M1 成立 → macOS build 取法不变，但**必须按 bundle id 精确锁定主 bundle**，防止 helper 版本污染；
- M3/M5 → macOS `cli_id` 改读 `codex-package.json` 的 `version`，删掉「哈希目录」假设；Windows 仍用 `--version` / `bin/<hash>` 兜底；
- M6 成立 → `validate_socket` 的 0700/0600/同 uid 检查保持不变；
- M8 → P0 通过判据改为「拿到本次 `result.clientId`」；预算按 Windows 实测收紧为 1s/2s/3s/3s（总 9s，硬上限 15s）；
- M9 当前单实例 → 多义规则保留（`>1` 即 `None`），不因为「现在只有一个」而放松；
- M11 本机 XML → 现有解析路径成立；`plutil` 兜底列为低优先（其他 build 可能改二进制 plist）。
