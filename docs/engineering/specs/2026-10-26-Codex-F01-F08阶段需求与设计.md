## 1. 目标、范围和方案

### 1.1 本阶段解决什么

用户通过手机控制已经打开的 Codex Desktop 原会话。Desktop 更新后，Tuvis 能按实际能力继续提供答题、审批和打断，而不是因完整 build 未登记就一律只许发消息。原生请求应通过原生路径解决；不支持时仍能看见内容和真实处理出口。输入区恢复紧凑显示，不常驻堆叠不可用控件和重复解释。

本阶段必须交付 F01—F08。兼容不是全部能力保证，也不意味着能够修改上游权限。用户不需要为每次 Desktop 更新自行安装旧版本、手工采样或修改白名单。

### 1.2 方案选择及明确排除

| 方案                                    | 适配方式与代价                                                            | 本阶段选择                                         |
| --------------------------------------- | ------------------------------------------------------------------------- | -------------------------------------------------- |
| 原 Desktop IPC＋逐能力契约匹配          | 保留原会话和原窗口，复用既有连接、镜像与动作编排；逐项确认写入与解决语义  | **沿用用户已选路线**                               |
| 每个完整 build 手工登记后才允许全部操作 | 门控直接，但维护成本随 Desktop 更新增长，不能解决大部分用户长期受限的问题 | 不作为新增能力的唯一准入方式；已有真机证据继续有效 |
| Tuvis 托管独立 app-server／无头运行时   | 改变会话宿主，需要另一套进程和任务管理                                    | **明确不使用，也不作为失败回退**                   |

允许读取当前实际运行包的版本、方法及离线 schema；生成 schema 后退出不等于托管运行时。只读取证不得执行对话、批准请求、修改权限或自动发送测试消息。Happy 仅作交互和生命周期经验参考。

### 2.2 不能扩大推断的地方

- steer 的回执成功、同回合落点和本地配对成功，均不能推翻“桌面仍未答”的复核结果。未清卡的具体内部原因未定，不把客户端本地 store 假说写成根因。
- F03 自由回答通过的是“有选项的题＋非选项答案”。无 options 的真实题形未产生，可按已核验契约和夹具覆盖，不冒称有该形态的实机证据。
- `availableDecisions` 未提供的 `decline` 被一次真实请求接受，只证明该样本语义；不自动授权向其他请求发送未列词。
- `activeFlags` 是辅助事实，不代替请求集合、活动回合、镜像新鲜度和目标身份。
- 未见专用 resolved 广播，不等于上游永远没有；状态从正确应用 snapshot／连续 patches 后的镜像判断，不把 patch 缺少完整列表当作列表为空。
- Windows 未触发不等于不支持，也不等于已通过。平台能力必须与当前实际目标建立自己的契约匹配关系；不复制 Mac 的成功账本。

## 3. 共用产品与能力规则

### 3.1 逐能力，而非整会话总开关

后端按操作输出：Tuvis 是否已接入、当前能否操作、不可用原因、证据来源。消息、命令审批、文件审批、阻塞答题、异步空闲答题、请求级取消和回合打断分别判断。模式／权限未接入时如实列在详情，不因消息或审批成功而连带开放。

| 情况                                       | 用户可见含义                   | 按钮行为                     |
| ------------------------------------------ | ------------------------------ | ---------------------------- |
| 已实现且当前契约匹配                       | 自动适配可用；详情注明契约证据 | 当前目标和状态满足时可操作   |
| 有本机真实成功                             | 此操作已有成功记录             | 仍检查当前目标、请求和状态   |
| 未接入／契约不明／已确认不支持             | 该操作暂不可用，原因可查       | 不展示必然失败的常驻控件     |
| 临时断链、状态过期、正在运行或另有阻塞请求 | 当前暂不能执行                 | 相关卡保留输入，显示就近原因 |

UI 不读取一个总布尔值自行拼按钮，也不要求直接消费原始 `caps.*`。卡片合法动作、HTTP 写入口和前台按钮使用后端同一有效策略。既有 schema 审批可用时，不因静态 `caps.command=false` 错误关闭。

### 3.2 新版本如何继续可用

对未登记 build，放行某个非普通消息操作需同时满足：

1. 当前实际运行目标、完整指纹、owner 和线程可归因。
2. Tuvis 有已核验的契约分支；当前方法／版本和必要结构与该分支匹配。
3. 参数、响应、状态确认方式和作用域已知，当前请求能满足该操作约束。
4. 用户明确发起该操作，设备授权与运行状态允许，写出边界再次检查通过。

方法名存在、只有 CLI schema、相邻 build、其他平台或其他用户成功，不能单独满足以上条件。不在用户后台创建问题、审批或写消息“测试能力”。当前契约不匹配只关闭对应能力，保留其他功能。

成功证据按完整目标指纹、能力与契约规则版本持久复用。重连重新建立当前目标绑定，不把旧异步结果装入新身份；不因每次重启重复完整成功探测。暂时网络失败记录为运行观测，不抹掉历史成功；失败按既有退避／下一次显式触发重新检查。

关闭自动适配立即撤回未知版本的新适配动作；已发动作仍可只读核对和有界收尾。重开不自动批准、发送答案、重发草稿或恢复队列。已有精确证据档的设置语义保持既有设计。

### 3.3 身份、状态和预算

- 历史事实按原线程、原回合、原消息／题目定位；原生请求 ID 保持整数／字符串类型。连接 token 再绑定当前 owner、连接代际和内容版本，不以题干当身份。
- revision 仅同宿主／连接代际内比较。重启、同 build 重连、整数请求 ID 复用，均不能恢复旧写资格。历史响应的关联还必须带原回合／条目，不能只比数值 requestId。
- pending 阻塞、过期状态和权限门在服务端强制执行。前端隐藏控件不代替写出边界校验；旧页面／直接 API 也不能绕过。
- 复用已审动作编排：点击起前台总预算最多 30 秒，必要后台收尾最多 120 秒，用户只读核对最多 10 秒；子步骤不重置预算。到点结束转圈，未知不等于未送达。
- 普通消息保留既有知情人工继续机制；**审批／正式答题的未知结果不能套用普通消息的自动后继重发**。先只读核对或回原端处理，不提供重复批准的隐性出口。

## 4. F01 · 逐操作能力识别与放行

**用户得到什么：** 打开新版本 Desktop 会话，无需自行寻找实验开关；可用操作正常出现，不可用项能在适配详情解释。

**功能点：**

1. 进入会话时按需识别当前目标；首次遇到某类真实请求时，只补该能力缺少的只读信息。
2. 输出能力与临时状态两层事实。例如“阻塞问答已适配，但当前断链”，不能退回“此版本永久不支持”。
3. 卡片只显示合法决策；工具栏只显示已接入且有有效能力来源的入口。
4. 当前契约漂移时撤回对应动作，保留摘要、输入和诊断原因。
5. 成功证据复用与实时上下文检查分开，避免每个问题重探整个 build。

**验收条件：** 未知 build 的命令审批可用、阻塞问答未识别、权限未接入三种状态可同时正确呈现；旧连接迟到证据不能解锁新卡；关闭适配后未知版本写入口立即失效，重开不触发写动作；识别阶段没有测试性对话副作用。

## 5. F02 · 原生阻塞问答正式作答

**用户得到什么：** 手机显示原请求中的问题、选项和允许的自由输入；同一请求的多题在一个表单内正式提交，解决原 Desktop 请求。

**功能点：**

1. 来源是当前原生 `item/tool/requestUserInput` 等已核验请求，不与异步 Question 混用接口。
2. 按原 requestId 和题目 ID 构造响应。发送形状是 `answers[qid].answers[]`，已答投影可能是 `answers[qid]=[]`，分别解析。
3. 所有题目与合法答案在服务端校验；禁止未知题目、重复题目、遗漏契约要求的题目、非法选项和不允许的自由文本。自由文本逐题读取 `isOther` 等当前契约条件，不按整个请求一刀切。
4. 当前已核验的答案数组契约允许多值，提供明确的多值作答能力；有已核验数量限制的分支按限制呈现。**不靠题干自然语言猜单／多选，也不把一个数组字段当作所有未知契约都允许任意数量。** 当前分支的多值允许来自已核验契约与真机样本，不来自字段名猜测。
5. 一次提交覆盖同一原生请求需提交的题目；不拆成多条普通消息，不进普通消息忙态 FIFO。提交中抑制重复点击，输入保留到结果确认。
6. `isSecret` 等敏感输入按其语义隐藏展示，不写普通诊断日志；当前契约不能安全处理的变体降为回原端处理。

**确认方式：** 同目标新鲜镜像中的原请求响应条目 `userInputResponse`、准确关联的 answers 和 completed 优先作为已答证据；只有请求消失而原因不明时写“请求已结束”。

**验收条件：** 单题、多题、允许的多值和自由文本正式闭环；另一端先处理、请求换代、题目内容变化、回执丢失均不串答；同一 Tuvis 的多设备竞争最多产生一次有效派发，外部端已处理时准确收敛，不声称跨宿主绝对 exactly-once。

## 6. F03 · 异步 Question 正式作答

**用户得到什么：** 原生异步问题在手机可选答或自由回答；空闲时提交后，原 Desktop 卡得到正式处理。运行中仍可编辑答案，不发生“答进去了但卡还挂着”的已知分裂行为。

### 6.1 问题识别与回答

1. 来源是已核验的 `agentMessage.questions[]`，不要求它出现在 requests。记录来源消息、题目索引及来源回合；题干相同不合并。
2. 当前分支的题目标识按官方 `JSON.stringify(["request_user_input_async", itemId, questionIndex])` 等价构造，**字符串精确一致**。采用同一编码规则，禁止多余分隔空格；测试覆盖特殊字符／转义，不能仅凭语义相同判相等。
3. 选项与自由回答都转换为正式信封 `{questionItemId, question, answer}`；自由回答不套用 F02 的 isOther 条件。没有 options 的结构可展示自由输入，但标明其真实题形仍待产品验收。
4. 每题独立提交，其他题保留；多题按稳定顺序切换。本阶段不新增跨题批量自动提交。
5. “正式答题”是独立动作：后端从当前题目构造信封，不接受客户端提交任意原始信封／任意正文来借用此权限。

### 6.2 空闲、运行中与队列

| 当前状态                               | 行为                                                                                 |
| -------------------------------------- | ------------------------------------------------------------------------------------ |
| 新鲜确认空闲、没有阻塞请求、其余门通过 | 用户可正式提交，经已核验 start-turn 路径发送                                         |
| 运行中                                 | 可编辑／保存答案；显示“正在运行，空闲后可提交”；不派发、不进入普通消息 FIFO          |
| 恢复空闲                               | 更新按钮状态，提示可以提交；**不自动发送，须用户再次点击**                           |
| 另一张阻塞请求在场，包括 pending＋idle | 优先处理该请求；保留异步答案，不走 start-turn／steer 绕过                            |
| 队列处于暂停保护                       | 不凭答题动作自动清暂停；按既有明确恢复／本条先发选择处理，授权必须绑定该正式答题动作 |
| 断链、身份／历史状态不足或写前状态变化 | 保留答案，提示刷新或等待；不能确认安全则零派发                                       |

**本阶段不登记或调用 `thread-follower-steer-turn` 作为答题路径。** 其落点、清卡和目标安全边界留后续专项，不因方法存在就放开。

### 6.3 正式解决与历史

空闲 start-turn 分支的准确原线程正式答复记录，按已核验客户端规则关联原题，形成“已回答（由原会话答复关联）”的派生事实。它不是本机点击记忆，不只记在提交设备；重进页面或换设备可从原会话恢复。

RPC 成功、模型说收到、正文继续或单纯本地配对都不能替代已核验分支的完整判据。尤其外部已存在的 steering 答复不能仅因配对命中而假称原卡已解决；不能确定时保留状态待确认，不自动再答。

历史题仍可在身份和内容有效、状态可核对时正式回答；原回合 completed 本身不使异步题失效。收起只改变 Tuvis 本地显示，不同步成 Desktop 取消。

**验收条件：** 选项／非选项自由回答关联正确原题并清卡；普通正文不清卡的区别保留；运行中编辑→空闲只启用提交按钮，零自动写出；点击后状态变为 busy 则阻止派发并保稿；特殊字符、同名题、历史题、另一端先答、超时已落地均不重复提交或清除新输入。桌面和手机将信封呈现为“问题／答案”，不暴露内部标记。

## 7. F04 · 命令与文件审批

**用户得到什么：** 手机展示具体命令／变更摘要和真实可用决策，按钮清楚说明是否会结束回合；可用审批不受整个 build 未登记误伤。

### 7.1 决策与显示

| 决策                             | 含义                       | 展示要求                               |
| -------------------------------- | -------------------------- | -------------------------------------- |
| accept                           | 仅允许当前请求             | “批准一次”，不扩大到后续请求           |
| decline                          | 当前请求不执行，回合可继续 | “拒绝”；只在当前合法策略提供时显示     |
| cancel                           | 拒绝并终止当前回合         | 明示“拒绝并中止本轮”，不伪装成普通拒绝 |
| 会话级允许、策略修订、对象扩权词 | 改变后续权限或执行策略     | 本阶段不发送、不自动转换成单次允许     |

当前策略按请求种类与当前证据生成：

通过 cancel 终止回合与 F07 定向打断使用相同的前置持久暂停及归属收尾保障；暂停建立失败不派发 cancel。decline 只是拒绝当前请求，不因此自动暂停整个回合队列。

- 显式 availableDecisions 存在时，取安全字符串词与已实现策略的交集；显式空列表／仅扩权对象列表不回退开放。此规则不因旧证据档而被绕过。
- 字段缺失与显式空列表不同：缺失时仅使用**该请求种类已核验契约**的最小策略。文件审批的缺失字段不能套用命令词；未知契约不猜。
- 新样本证明未 offered 的 decline 可被接受，但本阶段**不据此自动增加显式列表外按钮**。可以识别桌面或其他端产生的 declined 终态；未来要扩大显式列表外的拒绝能力，另作准入设计，不在实现时顺手放开。

### 7.2 摘要与确认

命令摘要从真实请求提取；文件请求没有 changes 时，按原 thread／turn／item 关联权威 fileChange 条目。无法唯一关联或摘要不足以说明被批准内容时，写明“无法确认变更内容”，不猜 diff、不启用批准；已有可靠拒绝／中止出口仍保留。

Desktop 显示“请求权限”不代表协议种类就是 permissions。网络／执行策略申请仍可能是 command approval；按原 method 与已核验结构分类，不按标题放行。独立 permissions 请求和线程权限切换不在本阶段开放。

回执不确定时保留待确认；准确请求消失及操作终态参与收敛。`commandExecution.status=declined` 是已拒绝，不当作仍在运行或未知；原因不明仅显示“请求已结束”。

**验收条件：** 命令 accept／cancel、文件 accept／decline 按各自合法策略闭环；桌面 decline 后手机准确撤卡；空交集／对象词／旧 token／换 owner 零写出；摘要缺失无法盲目批准；同样显示成“权限”的不同协议请求不串接口、不自动扩权。

## 8. F05 · 生命周期与多端同步

**用户得到什么：** 活动区只保留仍需处理或需核对的交互；处理结果在手机和桌面收敛；旧卡不会因重连、分页或延迟回包重新取得写权限。

### 8.1 事实来源与状态

| 来源                         | 可采纳的事实                            | 不足以证明什么                           |
| ---------------------------- | --------------------------------------- | ---------------------------------------- |
| 原生 pending／对应响应与终态 | 该原请求仍在、已答、拒绝或结束          | 单靠请求消失不能猜具体决策               |
| 异步题＋原线程正式答复       | 按已核验分支派生已答                    | 本机发过、steer 接受或模型确认不等于清卡 |
| runtime／activeFlags         | 运行、等待批准或等待输入等辅助状态      | 不替代 pending、目标与历史完整性         |
| 同代连续镜像                 | snapshot＋合法连续 patches 后的当前状态 | 不连续增量、过期投影不能恢复操作         |

统一状态至少包括：待处理、暂不可提交、提交中、结果待确认、已回答、已拒绝、已取消、请求已结束、状态无法确认。操作资格与处理事实分开：stale 只撤回动作，不伪造终态。

原生阻塞请求结束后退出活动区；异步未答题不随原回合结束自动消失。多张卡以真实阻塞请求优先，其余按稳定顺序提供切换／折叠；保留待处理数量和入口，不把所有历史卡展开挤占正文。

### 8.2 重连、历史与多端

- 需要确认某个异步题未答时，必须覆盖“该题出现→当前”的完整答复范围（相关回合及其 items 连续、完整且新鲜）。仅更早历史存在 olderCursor 不自动关闭最新题目的操作；相关范围有缺页／缺条目时，“没看到”不是“已删除／已处理”，显示“待核对”、撤回写资格并保留输入。
- 用有界只读补取和既有镜像恢复纠偏，不持续全量扫描全部历史。目标题／答复证据无法在预算内恢复时，保持无法确认，不自动清卡或重发。
- 当前新鲜原生请求集合可用于 pending 收敛；异步题的历史配对不误套用这个消失规则。
- 两个手机的提交资格同源；原端或另一端处理后，前台通过服务端投影更新或只读刷新收敛，不要求原提交设备继续在线。
- 暂停／恢复、能力活门变化等本地状态也须进入当前投影，不能依赖 Desktop 偶然再发一帧。投影发布遵守内容版本与发布顺序协议，状态未变不反复发布，避免调度自激。
- 异步题没有可直接读取的 answered 位；其派生状态需可重建。旧代际的提交资格不持久复活。对同一线程内原生题和异步题去重时按来源身份，不按显示文本。
- `autoResolutionMs` 已 deprecated，不用作倒计时、自动清卡或自动打断依据。没有真实结束事实时不提供定时解决承诺。

**验收条件：** 原端处理／另一手机处理、请求 ID 重用、宿主重启 revision 回退、历史窗口缩小、增量断档、超时后实际已答均能纠偏；没有 UI 假成功、历史重放复活或广播循环。等待时用户编辑的新答案／正文／附件不被旧回执清掉。

## 9. F06 · 安全摘要与普通意见回退

**用户得到什么：** 即使当前交互不能正式操作，也能读懂在等待什么，知道可行的下一步。

1. 展示安全可解析的题干、选项、命令或计划／变更摘要，标明来源和当前待处理／待核对状态。只白名单提取可展示字段，不把原始对象、凭据或完整日志直接输出。
2. 真实 plan 请求可显示经过长度限制和敏感字段处理的摘要，但不提前接入 F10“允许实施”。无法安全提取时只说明请求类型和需回原端处理，不能让模型补猜内容。
3. 正式信封识别后以“问题／答案”呈现；未知条目给稳定、可折叠的未支持摘要，不把内部类型占位和重复错误当作多条聊天消息刷屏。
4. 普通消息只表达意见，不代替审批／正式答题。真正阻塞请求在场时拦普通消息并保留草稿，pending＋idle 也不例外。
5. 用户可先在卡片正式回应，或明确中止当前回合后再发送普通意见；中止成功也不代表用户原来的问题已回答。
6. 没有可靠远程动作时，提供回原 Desktop 处理指引和“刷新状态”。可折叠摘要但保留待处理入口，不伪造取消、不自动发无头消息或键盘注入。

**验收条件：** 未知 kind、计划实施卡、摘要不足、当前无打断能力均有准确出口；普通正文不审批；历史“等待审批”措辞不让已结束请求重新进入活动区；敏感输入和原始内部对象不进入摘要或诊断。

## 10. F07 · 请求取消与回合打断

**用户得到什么：** 有可靠能力时，能明确中止目标回合，解除无法处理的阻塞；清楚知道它不同于收起卡片或拒绝单个请求。

1. 首批必须把当前已核验 interrupt 契约接入逐能力策略；未知 build 不再只因未登记就关闭。绑定原线程、owner、代际与 expectedTurnId，缺安全阀零指令，不降到无目标版本。
2. 打断前建立持久队列暂停保护；暂停失败则不发打断。Accepted／Rejected／NotSent／Unknown 各自处理，未证实中止不能写成功。
3. 保留已审并发暂停归属、写出权、迟到结果和屏障机制；失败的另一条打断不能清掉已建立的暂停。
4. 打断后旧队列保持暂停，由用户明确恢复或一次性授权本条先发；不因回合结束、再发普通意见或适配重开自动续跑旧任务。
5. 单请求取消／跳过仅在存在已核验的对应动作时显示。本阶段没有通用 Question dismiss 接口，默认不显示“取消这张题”。file decline、command cancel、turn interrupt 不能统一成同一个“取消”。
6. 收起只是本地展示操作。用户在 Desktop 收起未答题，线上无结束事实时，Tuvis 不能声称它已取消。

**验收条件：** 定向中止原回合、无关回合不受影响；终态早于回执、双端竞争、数据库失败和超时均不放出旧队列；暂停／恢复无 Desktop 新帧也能推达，且静默期不刷帧；只有用户明确恢复后才按既有规则继续。

## 11. F08 · 一行工具栏与适配详情

**用户得到什么：** 无异常时输入区上方一行；可用项正常操作，不支持项不占常驻空间；真正待处理或发送不确定仍有醒目入口。

### 11.1 常态与按需展开

| 区域           | 规则                                                                                                          |
| -------------- | ------------------------------------------------------------------------------------------------------------- |
| 常驻工具栏     | 只放已接入且当前支持的模式／权限组及轻量“自动适配”入口；本阶段 Desktop 模式／权限未接入时整组隐藏，不占空容器 |
| 首次提示       | 轻提示一次，说明自动适配及详情位置；不反复出现版本警告                                                        |
| 适配详情       | 系统／Tuvis／Desktop 版本、逐能力状态、证据来源、临时限制、关闭适配和排障入口；不显示暗示全部已验证的总徽标   |
| 待处理／待确认 | 一条可展开入口，准确区分原生请求、异步题、队列暂停和发送结果；可在展开区处理，不隐藏真实阻塞                  |
| 问答／审批表单 | 用户展开时按需占用空间；“常态一行”不限制表单高度和必要操作说明                                                |
| 临时异常       | 就近显示，同一原因只解释一次；恢复后撤掉当前异常，历史记录不冒充当前状态                                      |

状态区分“自动适配可用”和“此操作已有成功记录”，不把“已验证”作为整个会话的全能力保证。状态文案面向用户，不显示 requestId、协议名、schema 词或权限实现细节。

### 11.2 通道互斥与一致性

- Desktop 原生卡与旧终端 `ApproveCard` 来源互斥：同一原生请求只展示一张卡，不再同时请求终端屏读并渲染一张永远读不到的降级卡。
- Desktop 不显示没有后端能力的旧 TUI 模式／权限 chip；直接 HTTP 写侧仍保留保护，不因前端隐藏而删除。
- 卡片、工具栏、队列、发送提示使用同一能力和状态事实。“暂无停止出口”时不能在另一处引导点击不存在的停止按钮。
- 暂时断链时显示读数过期，不沿用旧运行态假称队列仍因当前回合暂停；无新事实不能假称已空闲。
- 输入框按 Desktop／终端来源使用准确占位文案；连接错误作为状态提示收纳，不继续把同一组重连错误生成多条正文气泡。
- 窄屏优先收纳次要入口到“更多”，不缩小触控目标或横向撑破正文。前端文案中文／英文同步。

**验收条件：** 360／390 CSS px、中英文、正常／待处理／暂停／断链／Unknown 各态检查；常态一行、无必失败按钮、无双审批卡；多个真实原因可分别展开，同一原因不重复；输入与回复正文仍有可用空间，已处理请求不长期顶住输入区。
