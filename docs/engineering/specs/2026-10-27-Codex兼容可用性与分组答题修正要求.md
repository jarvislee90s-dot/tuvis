# Codex 兼容可用性与分组答题修正要求

日期：2026-10-27。

本文件明确现场问题的修改后行为与验收条件，不是执行计划，不规定代码结构。最高设计依据仍为 `docs/MASTER-PLAN.md`，本轮不修改宪法。

本轮用户已明确的交互要求：同一次发出的多道题只显示一张答题卡，逐题填写、内存暂存，最后一次提交到 Desktop。该要求调整原 F01—F08 阶段设计 §6.1 的“每题独立提交、不做跨题批量提交”：改为**同组多题一次提交，不跨组拼批**。不合并审批决策、不同原生请求或不同历史来源的问题。

本轮优先解决真实可用性和交互问题。既有复审中的其他恢复加固分开安排；没有修改或修复的事项不能因此标为已完成。

## B01：已匹配能力不能继续显示“未验证、不可用”

### 修改后的行为

- 自动适配开启、当前包的某项操作契约匹配、目标及实时条件满足时，该项即可使用。不要求每个新 build 都先有人手工成功使用一次。
- 消息发送、审批、文件审批、阻塞答题、异步答题和打断分别判断，互不批量扩权。
- 主工具栏、适配详情、答题卡和真实提交入口对同一操作给出一致结论。
- 如果临时不可用，显示实际原因，如正在运行、存在当前阻塞请求、连接已断开；不能用“版本未验证”笼统覆盖这些情况。
- 成功证据的自动提升若尚未达到归因要求，可暂缓写入；不把“没有历史成功记录”当作当前契约匹配能力的禁用理由。
- 目标不明、过期请求、重复提交、无法确认的审批决策仍受保护。Desktop 会话不转 headless。

### 验收

当前测试机同一会话中，普通发送、正式问答、实际可用的审批和定向打断分别跑通；契约匹配后无需重进页面才出现能力。不得出现“上面显示可发、输入框却因版本未验证禁用”的矛盾。重连后重新核对当前身份，再恢复相应能力。

## B02：可用操作一处展示，不可用项只放适配详情

### 修改后的行为

- 主区域只保留一行：可用操作标签＋一个“适配详情”入口。
- 移除主区域的“更多 N”“N 项不可用”和展开的不可用原因列表。
- 可用标签较多时保持单行，窄屏可横向查看；详情入口始终可找到。不用多行堆叠说明占聊天空间。
- 适配详情集中展示版本、自动适配开关、各项能力及不可用原因；不再嵌套第二套工具栏、更多入口或详情入口。
- 常态不显示无错误的诊断长文。真正影响当前操作的原因仍在当前卡片附近说明一次。

### 验收

360／390 宽度下，主操作区一行；打开详情后无第二套工具栏。可用操作不被“更多 N”隐藏，不可用能力不占聊天区。用户能区分“能力支持但当前忙”和“此能力尚未支持”。

## B03：历史问题不能统统计为当前待处理

### 修改后的行为

- 当前原生请求、当前问答组、历史问题、状态待核对分别呈现。
- Desktop 已正式回答的题，Tuvis 从准确关联的正式答复收敛，不再占当前待办；从手机或电脑作答都一样。
- 原生审批／阻塞问题已结束时，按原请求的实际证据退出当前区；不能因整数 ID 重用认错请求。
- Desktop 的异步题关闭／跳过若没有可读取的状态，不伪造“已答”或“已取消”。无法确认的历史题进入“历史待核对”，不继续作为当前未答题铺满界面。
- 历史区提供“在 Tuvis 中忽略／重新查看”。忽略仅改变 Tuvis 的收纳，不向 Desktop 发答案、取消或打断，也不算能力成功证据。
- 不按固定时间自动宣布题目解决；回合完成也不自动等同异步题已答。
- 待办按组显示，例如“待回答 1 组 · 共 5 题”；历史待核对另列。审批数量独立，不把它算成一道选择题。

### 验收

用当前现场旧题复现：能确认已答／已结束的均退出当前待办；不能确认的进入历史待核对，不再表现为六张当前活动卡。刷新或换设备后，正式答复的收敛仍成立。真正尚未处理的当前请求保持可见。

## B04：同组多题只有一张卡，逐题填写

### 修改后的行为

- 同一原生多题请求，或同一次异步发题所含的多道题，组成一个答题组。
- 一次只显示一张当前题卡，标题显示“第 1／5 题”等进度。
- 用户选择选项或填写自由答案；单选、多选、自由输入按该题真实规则显示，不要求有选项的题必须再填文本。
- 非最后一题显示“下一题”；允许“上一题”返回修改。翻题不向 Desktop 提交答案。
- 已填写答案保存在当前页面内存中，前后切题、收起展开都不丢。内存不是“已回答”的权威证明，不写成成功记录。
- 最后一题显示“提交全部答案”，也可返回前题修改。
- 可选题才能跳过；必答题不允许空答案走到提交。跳过不是自动选择“拒绝”或“取消”。
- 不同发题批次不拼成一张五题卡。正在填写时新到一组问题，不插进当前组、不改变当前题号和已填答案；完成当前组后再处理下一组。

### 验收

同组 5 题：始终只见一张题卡；第 1 题选好，前进再返回仍保留；第 5 题以前零答题写出。两组各 2 题保持两个独立批次，不变成一组 4 题。审批卡不进入问答组。

## B05：点一次提交，正式交付本组答案

### 修改后的行为

- 用户点一次“提交全部答案”，正式提交本组冻结后的答案，不需要每题再确认一次。
- 原生多题请求沿原请求一次提交所有合法答案；异步同组题沿正式答题信封提交本组答案。
- 不由前端逐题自动点旧接口、为每题分别开启回合；不能用五次独立发送冒充一次分组提交。
- 提交时仍核对组内每题是否属于当前有效来源。另一端已处理、题目改变或身份换代时，保留未解决题的草稿并清楚列出需复核项，不把旧答案套到新题。
- 受理不等于已回答；明确收敛后显示完成。结果未知时停止转圈、保留答案及原动作核对入口，不自动重发。
- 若只确认部分题已解决，分别展示已确认与待核对题，不虚报“全部成功”，也不把整组静默重发。
- 提交过程中另填的下一组草稿不受上一组迟到结果影响。

### 证据边界与验收

已有探测材料确认正式异步答复信封接受答案数组；原生多题一次提交已有真机证据。但不能据此把“同组 5 道异步题一次提交、桌面全部清卡”直接记为已验。

完成条件必须包含一轮隔离实机：5 题逐题填写→一次最终点击→同组正式答案一次交付→Desktop 对应原题全部收敛→Tuvis 显示本组完成。另测另一端先答其中一题、提交后丢回执、双击提交，均不重复答题、不误清其他组。

## B06：旧消息队列暂停不再要求第二个答题按钮

### 修改后的行为

- 已有消息队列因打断暂停时，用户仍按正常“提交全部答案”完成本组答题，不需要额外点“仅本题先发”。
- 这次点击只授权交付当前问答组；旧普通消息继续暂停，不恢复、不夹带、不重复发送。
- 卡片上不再同时摆一个黄色“本题先发”和一个灰色“提交答案”。只有一个明确的提交入口。
- 暂停提示统一显示一次：“此前的消息队列已暂停；不影响本次答题。”保留独立的“恢复旧消息队列”入口，恢复是另一个明确操作。
- 真正的原生阻塞请求在场，或当前 Desktop 仍运行而该异步答题路径不能安全提交时，仍显示具体原因；不能因点答题而绕过另一项审批、强行打断或偷偷排队自动发送。
- 出现选项题本身不创建消息队列暂停。暂停仍须能追溯到具体打断／取消流程，明确失败时正确撤回对应暂停。

### 验收

先排两条普通消息并打断暂停，再完成一组问答：只点一次提交，本组答案正式送达，旧两条仍暂停、零自动写出。随后显式恢复旧队列才按原顺序继续。两题卡不会各重复一段队列警告；无历史暂停时，单纯出现选项题不会显示暂停。

## 交付口径

先让当前 Mac 现场完成 B01—B06 的主路径验收，再补其余边界。Windows 未经本批验证的行为如实标待验，不平移 Mac 实测结论。

这份要求不承诺“隐藏 Tuvis 历史卡＝取消 Desktop 原卡”，不把异步答题与原生审批混为同一个请求，也不新增自动恢复队列或自动重发。实施者需要提交实际界面和桌面收敛证据，不能只以组件测试通过申报现场问题已解决。
