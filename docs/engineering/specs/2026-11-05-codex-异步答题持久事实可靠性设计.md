## 2. 前期问题快照与证据限制

以下是方案起点，不是当前缺陷清单：写入结果、次序及旧库版本问题已由 B1.1 验收，历史有效性已由 B1.2 验收，慢库隔离属于尚未实施的 B1.3。当前完成度以 §1 和验收记录为准。

1. 原 `upsert` 返回 `()`；当时写失败仍更新去重缓存，局部验证为 `writes=1 / DB=pending / cache=answered`。
2. A1 的异步闸只按取得闸的顺序串行；旧观察后到仍能覆盖新事实。必须在观察时定序。
3. 已有 answered hint 不参与可见题的强事实分支。合成状态中答复缺失时确实能回 Pending，但不能据此把真实历史回滚后的 Pending 判为错误。
4. 同 owner、连续 revision 仍允许合法 patch 删除答复或替换历史；它们不证明历史语义不变。
5. 提示存储、设置和暂停查询共用 `DeviceStore::Global` 同步连接锁；多个 worker 不会提供锁隔离。慢写与容量 256 的广播组合已能受控触发 Lagged，现场发生率尚未测量。
6. 现有迁移红测已编译运行，在缺少 `observation_epoch` 处失败；这不批准原先的全部拟议列，也不证明迁移已成功。

## 3. B1.1 数据与观察协议

### 3.1 三个不同概念

- **写入运行 epoch：** SQLite 事务分配的正整数，识别一个有效提示写入器。不是历史世系，也不是 Desktop owner epoch。
- **观察 sequence：** 本写入运行内单调递增的正整数；在镜像临界区观察事实时分配，不在异步等待后或发送前分配。不随 owner/mirror 重建归零。
- **历史有效范围：** B1.2 的证据状态；不能由上述两个数推导。

当前单实例应用只允许一个有效 hints 写入器。重建写入器时重新分配 epoch；旧写入器不再拥有写入资格。epoch/sequence 溢出是显式失败，不饱和复用、不归零。

epoch 每个有效写入器运行只分配一次，不按线程、GET、状态帧或普通连接重连重复分配。

### 3.2 事实键和内部侧载

事实键仍为 `(thread_id, source_turn_id, source_item_id, question_index)`；hint 不含题干、选项、答案、信封或 context token。

新增内部类型放在 `services/codex_desktop_ipc/hint_state.rs`，DAO 数据类型可以位于现有 `codex_interactions.rs`，通过显式转换避免数据库模块反向依赖业务模块。

```rust
#[derive(Clone, Copy, Debug, PartialEq, Eq, PartialOrd, Ord)]
pub struct HintVersion {
    pub epoch: i64,
    pub sequence: i64,
}

#[derive(Clone, Debug, PartialEq, Eq)]
pub struct VersionedHint {
    pub hint: super::async_question::InteractionHint,
    pub version: HintVersion,
}
```

内部 `HintObservation` 记录目标 ThreadKey、观察时的 owner/镜像身份和 `Vec<VersionedHint>`。通过局部 tuple/内部侧载从临界区带出，不给 HTTP/SSE DTO 增加仅供持久化的字段。

对同一题，状态和来源未变时复用最近观察的版本，避免每个流式帧都写库。只要最近观察变过，即使新值与旧 durable 值相同，也必须保留新版本：`pending(v1) → answered(v2) → pending(v3)` 中的 v3 不能被“DB 原本也是 pending”去重。

### 3.3 三份状态必须分开

| 状态            | 更新时机                 | 作用                                            |
| --------------- | ------------------------ | ----------------------------------------------- |
| latest observed | 镜像临界区内捕获观察     | 投影提示与新旧观察比较                          |
| durable         | 事务成功且逐项核对结果后 | 已落库去重水位；不扩大答题资格                  |
| dirty / retry   | 最新观察尚未确认持久化   | 后续同事实观察仍尝试写；旧 ACK 不能删除新 dirty |

A1 的“成功加载历史提示后才合并当前观察”继续保持。加载失败不能创建假已加载槽位；B1.1 继续允许同步等待 hints I/O，不宣称已完成 R1 的广播隔离。

即使当前 `async_questions` 为空，也要检查该线程已有的 dirty：answered 提示不再生成占位时，不能因空列表早退而吞掉先前写失败的重试。

### 3.4 存储接口与提交结果

写接口改为批次 `Result<BatchWriteReport, HintStoreError>`；错误包含阶段/类别，不携正文。Result 不只是“SQL 没报错”，还必须返回每个键的实际判定：

- `Applied`：应用新版本；
- `AlreadyCurrent`：相同版本且内容相同，幂等；
- `Superseded`：库内已有更新版本，返回该当前行供核对；
- 相同版本但内容不同：版本碰撞错误，整批回滚；
- epoch 不再有效：`Fenced`，整批不写。

数据库事务内复核运行 epoch，然后逐项比较更新；任一 SQL/版本碰撞错误整批回滚。不得逐行提交后把部分成功冒称整批成功。legacy 行仅在两个版本列均为空时按旧提示处理；半空或非法版本列不得被当成有效新事实。

adapter 在取得 I/O 闸后，先用 latest observed 丢弃已被更晚观察替代的输入；提交后再按逐项报告更新 durable。旧 ACK 不能将最新缓存回退，也不能清除更高版本的 dirty。

### 3.5 B1.1 迁移

本阶段只新增 `observation_epoch`、`observation_seq` 两个可空列，以及单行 `codex_hint_writer_state(singleton, epoch)`。旧 `last_fact` 保留，版本为 NULL，不补造答复凭证。

**结构归属裁决（v2.1）：** B1 新结构全部由 `migration::migrate` 中的同一局部迁移事务创建：writer 表、初始行、两列一起提交。`schema::init` 保持 hints 的基础旧形状，不提前创建 B1 表、初始行或版本列；新库也先建基础 schema，再走相同 B1 迁移，最终得到完整结构。无需把全库初始化和所有历史迁移合并为大事务。

回滚严格恢复该 B1 事务的前态：原先不存在的 writer 表应回滚；原先已经存在的表、列和 epoch 则保留，不补偿 DROP、不归零。局部事务失败后不得分配 writer epoch 或退回无版本写入。完整判据、故障注入点和启动顺序见[迁移原子性裁决](../decisions/2026-11-05-codex-b1-schema-migration-atomicity.md)。

旧初稿中的 `prefix_digest` 取消；`proof_version`、答复身份等证据字段由 B1.2 引入，不为使旧红测变绿而提前加空壳列。执行 agent 可把现有未提交迁移测试调整为本版两列契约，保留旧行与幂等断言。

世代分配在事务中原子自增：先检查初始化行和整型溢出，成功提交后才能启用新写入器。分配失败时，镜像正常只读，提示持久化不可用，不能假定 epoch=0；后续投影可再次尝试初始化。

`begin_epoch` 还须验证 B1 所需结构和单行状态完整，避免遗留 writer 表但缺列时错误启动。结构不全返回不可用，不在 DAO/加载/写入口偷偷建表或补列。直接使用 `schema::init` 的 B1 DAO 测试须补跑迁移，不能依靠 schema 提前建新结构来让测试通过。

### 3.6 B1.1 重试与发布保证

暂时失败保留最新 dirty；下一次相同事实投影或正常状态帧必须能重试。B1.1 不新增后台计时器，因此无新观察时不保证自动收敛，这个限制明确由 B1.3 关闭。

本阶段保留同步写穿路径：正常写成功再发布；写失败可以发布当前观察，但明确没有 durable 保证。“收到 Answered 必然 DB 已写完”从来不能覆盖失败情形，不得继续作为无条件承诺。成功路径的顺序保证到 B1.3 才统一改为异步发布。

### 3.7 owner / mirror scope 与真实 COMMIT（v2.2 裁决）

写前预检查、writer epoch 与 hint CAS 都不能单独阻止“预检查后换代、旧任务再提交”。每个 lease 新建一个可撤销提交 authority，其唯一同步 gate 同时保护 owner_valid 和 current_mirror_scope；内部 permit 在镜像观察时捕获。新 lease 不复活旧 authority，scope 旋转不复用旧标识。

DAO 先准备事务与 report，生产 Store 最后从原 permit 取得 gate，核验 owner/scope 并跨真实 COMMIT 持有 guard。失效先完成则整批回滚并返回 owner/scope Fenced；COMMIT 先取得 gate 则允许先提交，撤销等待其退出。原 `HintObservation` 保持纯内存，adapter 额外携带 `AuthorizedHintObservation` / `HintCommitPermit`，不向旧侧载重配当前身份。

所有 owner bind/失效/release/reset 与镜像 snapshot/clear/stale 必须在各自变更生效前，经同一 gate 条件撤销原 scope。worker 持 gate 不取 owners/mirrors/HintState、不 await、不通知；撤销路径持 gate 不查 DB、不做投影或回调。ACK 在 gate/DB 锁外应用，已过期 ACK 不清新 dirty，也不伪称已提交记录未落库。

**v2.3 测试观测例外：** 仅 `#[cfg(test)]`、实例级固定 Probe 可在指定检查点执行纯原子观测/控制与 yield；不运行可注入闭包、不发 channel/watch 等消息、不取其他应用锁、不改权限或提交路径，非测试构建完全移除。它只用于确定性证明生产 Store 的 SQL 后/permit 前窗口和真实 DB 锁竞争，不能把线程启动或主控 try_lock 失败当成 worker 已进入竞争的证据。标准 Mutex 不公开 OS parked 状态，验收以 worker 的同一公共获取路径实际得到 WouldBlock 为准。见[生产测试窗口裁决](../decisions/2026-11-05-codex-b1-test-checkpoints.md)。

B1.1 的同步撤销可能等待 COMMIT，不能称为有固定时限的短锁或广播非阻塞保证。B1.3 必须按 TransitionPending→后台撤销→带 ticket 完成换代处理，forwarder 不等待该后台任务。完整锁序、线性化语义及验收见[owner 提交栅栏裁决](../decisions/2026-11-05-codex-b1-owner-commit-fence.md)。本次不新增持久表/列，不用 owner 换代旋转全局 writer epoch。

## 4. B1.2 历史证据和失效

### 4.1 首版范围

暂缓完整前缀持久证明，不用 `historyToken`、共享 turn、build 或墙钟代替世系。重启/owner 换代后，直接重见同线程同题合法答复，且未命中本运行已知撤销/隔离时可重新确认；没有当前证明时，旧证据只供核对。

强答复必须来自原始 canonical 引用链，题目和答复身份唯一、关联精确。校验发生在去重/跳过非法引用之前；非法、多义、缺 ID、未知编码版本不能产出强证据。

B1.2 增加可空 `proof_version`、`answer_turn_id`、`answer_item_id`、`answer_digest`、`evidence_state`。digest v1 使用 SHA-256，按固定字段顺序和 UTF-8 字节长度前缀编码线程、题目标识、来源回合、答复回合、答复条目及解析后的 question/answer；字段只用于内存计算，不存正文、不记日志。摘要不证明历史仍有效。

同一题的“历史见过答案”与“当前仍可用的事实”分开存储。当前状态 Unknown 时可保留旧答复的身份摘要及 unverified/invalidated 标记，但不能据此自动清卡或赋予提交资格。

### 4.2 变更分类定案

| 变更                                                                     | 处理                                                                           |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| 当前直接看到唯一合法同题答复，未命中本运行已知撤销且未被 quarantine      | 重新取得 Answered 强事实                                                       |
| 答复后明确追加，或与依赖无关的 runtime/元数据变更                        | 保留当前有效证据                                                               |
| 移动呈递尾窗裁剪，原始 canonical 中答复仍在                              | 继续按原始 canonical 核验，不把 UI 窗口当历史边界                              |
| 原始 canonical 删除/替换题目、答复或其依赖；整段历史替换；无法分类的移除 | 失效旧强事实；不因 owner/revision 连续而沿用                                   |
| 缺口、镜像重建、重连、owner 换代、重启                                   | 旧范围失效；重新直接核验或进入 Unknown                                         |
| 上游明示淘汰且真实取证证明不代表历史改写                                 | 仅在该取证规则覆盖的范围内允许保留；首版没有这种证据时按未知处理，不按字段名猜 |
| fork 新线程                                                              | 不跨线程复制有效状态；新线程独立派生                                           |

对刚失效的题，只有当前原始历史的相关答复范围完整，且有明确的新历史/重建观察证明无答复，才可按策略恢复 Pending；缺页、多义和无法区分裁剪/删除时 Unknown。legacy answered 不确认已答，也不能永久压制当前明确完整新历史的正常派生。

`answered_survives_temporary_window_loss` 必须说明是哪种窗口：UI 窗口裁剪可确认；原始 canonical 缺失则需要真实淘汰证明，否则测试应断言 Unknown。不得用合成标记自行发明上游语义。

### 4.3 合并转换表

| 旧事实             | 新观察                 | 必须保留                     |
| ------------------ | ---------------------- | ---------------------------- |
| Pending(v10)       | Answered(v11)          | v11                          |
| 有效 Answered(v10) | 同有效范围内的展示缺窗 | 有效答复证据和最新观察位置   |
| Answered(v10)      | 历史失效 Unknown(v11)  | 当前 v11；旧答复仅作历史证据 |
| v10 正在写         | v11 入队               | v10 ACK 不清除 v11 dirty     |
| v11 已生效         | v10 晚到               | DB/缓存/队列均不回退         |

“保强”只能在同一已证明有效范围内使用，绝不能吞掉更高版本的失效事实。数据库 CAS 不能弥补入队前丢失的 v11。

### 4.4 多次失效与旧答复重放（v2.4）

单条最近撤销记录不足：W1 失效→W2 有效→W2 失效后，恢复 W1 不能因“不同于最近 W2”变成新答复。同 patch 改题并换答时也须退役全部旧来源。仅在整批历史变化成功采用后，合并受影响旧 witness 的撤销记录。

确定退役与 Unknown/unverified 不混淆：已证实的依赖改写、来源替换/历史删除才能新增退役；单纯缺页/未加载不是已知语义删除，不能凭 witness 暂未返回就永久拉黑。恢复一致的当前合法证据仍可重新核验；已经证实的退役则不能被恢复流程抹掉。

采用应用运行级共享的、有预算的 `AnswerValidityLedger`，按 ThreadKey、questionKey 累积稳定答复来源的撤销。新 W2/W3 不清旧记录；当前候选命中撤销或 quarantine 时 Unknown，无候选时仍按 §4.2 的完整性条件处理。已退役的 answer_item_id 改内容或移动位置，不能只因 digest/turn 改变就洗成新来源。

ledger 不随 snapshot、owner、mirror clear/删除重建、远程 stop/start 清空；它的所有者寿命覆盖这些操作。题级/全局预算耗尽时保守关闭受影响范围的追踪并进入 Unknown，不能 LRU 丢墓碑再默认放行，也不能生成无限 quarantine 标记。

本批不新增持久撤销 journal，继续 T6 五列。跨进程冷启动按 §4.1 重新直接取证，不承诺拒绝前次进程全部已撤销 witness；更强保证需要独立持久撤销信息，不能靠最新 witness 或集合总 hash 推出。完整身份、预算、生命周期与测试见[重放裁决](../decisions/2026-11-05-codex-b1-witness-replay.md)。

## 5. B1.3 生产隔离、重试和生命周期

### 5.1 选定的隔离方向

使用单个 hints 写入 worker，先不增加四个竞争同一 SQLite 锁的 worker。广播投影、策略计算及发布盖章只消费已装载的内存事实，不同步取数据库连接锁。

owner/mirror 撤销还须从 B1.1 的同步 gate 等待改为 §3.7 的异步 transition；仅移走 DB 查询仍不能声称 forwarder 不会因慢 COMMIT 停顿。

必须枚举并移出事件消费路径中的 `queue_pause_source`、`auto_adapt_gate`、成功证据源、probe ledger 缓存未命中和 hints 冷加载。设置/暂停等事实通过现有变更入口和版本化通知更新；缺少新鲜事实时保守禁用受影响写资格。实际 mutation 写入口继续按原资格闸核对当前权威状态，内存展示缓存不能单独授权。

生产 hints 事务可继续使用现有 DeviceStore；单独连接或 WAL 不是本版前提，不在本批擅改全局 SQLite 配置。该选择要求测试证明广播路径已不再依赖同一全局锁。其他数据库写事务仍可串行，不能宣传“多个 SQLite writer 并行”。

冷启动加载在工作任务中进行；初次尚未完成时显示 Loading/Unknown，不能先造 Pending。完成后按当前 owner/镜像重新观察、合并、重发布；旧加载回包不覆盖新观察。A1 的加载安全性不降低。

### 5.2 有界队列与容量退路

配置项 `max_threads=128`、`max_keys_per_thread_batch=256`、`max_pending_bytes=4 MiB` 为首版待测试预算；序列化元数据使用实际估算字节，不能仅按题数声称有界。活动线程本身还受既有 following 上限约束。

256 限制一批，不限制线程全部历史。线程被观察到的新事实保存在其现有镜像/最新观察状态中，后台按稳定顺序分批扫描，用处理水位保证 257 个键至少经两批推进；已处理后不能每次从头重新生成同一超限批。

排队接口返回 accepted/coalesced/deferred-stale/closed 的明确结果。队列满时保留线程级 dirty/失效标记，不允许旧 Answered 因新失效未入队而继续有效。超出可保留预算时，受影响范围 Unknown/不可答；dirty 标记仍受活动线程数约束。无法仅凭现有镜像恢复则等待 B2，不发主动重取请求，不循环本地重建。

调度使用线程轮转、每线程最多一个在飞批次，合并遵循 §4.3。观察与 durable 状态分开，失败及旧 ACK 不丢进度。

### 5.3 自动重试

暂时失败按首次失败后 1/4/16 秒重试，之后间隔封顶 60 秒，线程空闲也继续；可注入测试时钟。长期错误保持待处理、限频诊断与有限单次工作预算，不紧循环。明确配置/格式类不可重试错误进入持久化不可用状态，只有相关条件改变或新运行恢复，不能虚报成功。

这里只重做本地幂等事务，不重发任何 Desktop mutation。写入不确定时，重试前核对当前版本/运行 epoch。

### 5.4 停止与热重启

3 秒是等待上界，不是阻塞任务取消保证。停止接收新观察后，由监督者保留在飞 JoinHandle、连接及运行 token；超时后报告未排空并返回，监督者仍负责收尾。新写入器不能在旧在飞事务结束前接管同一连接；无需界面操控，监督者完成交接后自动启动替代运行并分配新 epoch。

事务开始和提交前复核该运行的有效 token；旧 ACK 还需比较运行 epoch 与逐键版本，不能清新 dirty。已经提交的旧版本可作为历史记录存在，但不能覆盖新运行的更高版本。退出进程可能丢未提交内存工作，不宣称已 durable；重启按当前历史重新核对。

### 5.5 发布保证的最终变化

B1.3 起，Answered 帧表示“当前观察证实”，不再表示“该观察已持久化”。dirty/writing/durable/failed/fenced 是可测试的内部诊断状态，不能拼成新的答题资格。同步更新旧源码位置锁、成功时序测试和验收文案。

## 6. 迁移、隐私和验收门

迁移在内存库/临时完整旧库上验证，幂等且失败原子回滚。旧行不造证明，版本非法不放行。真实账本迁移由正式应用升级承担，实施测试不打开用户真实数据库。

必须覆盖：失败重试、旧观察后到、相同事实再次变回旧值、同版本内容冲突、批次回滚、legacy、序号溢出、owner 换代、缺历史、最新失效合并、迟到 ACK、实际共享 DeviceStore 慢写、257 键分批、内存预算、空闲重试、停止超时和热重启交接。

用受控通道/屏障/测试时钟安排顺序；局部 harness、fake IPC 集成和真机分别声明结果。电脑操控继续保持停止，不恢复真实 UI、设备或当前会话代答。
