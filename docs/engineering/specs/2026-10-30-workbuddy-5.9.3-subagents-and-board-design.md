## 1. 边界与原则

1. **只读 WorkBuddy**：不写 `~/.workbuddy` 下任何文件/数据库；`workbuddy.db` 一律只读打开（`monitor/sqlite.rs::open_readonly_with_timeout`）。
2. **用量事实源 = jsonl**：`message.usage` 是唯一 token 事实源；`workbuddy.db` 只用于会话枚举、`cwd`、标题、`status`、活跃时间。
3. **看板事实源 = 心跳 ∪ DB 活性 ∪ 主 jsonl 尾部**：心跳负责身份/pid，DB 负责「还活着」，主 jsonl 尾部负责状态细节。
4. **不新增轮询重 I/O**：看板每 3 秒一轮，只允许做「心跳文件枚举 + 一条小 DB 查询 + 活跃会话的 jsonl 尾部摘要（已有 L2 缓存）」。
5. **不改 schema**：`usage_detail` / `usage_daily` / `usage_session` / `usage_cursor` 全部沿用；子代理只新增行，不新增列。
6. **不改 TPS、不改国际版、不改采集节奏**（用户裁决）。

## 2. 用量采集设计（R1）

### 2.1 数据布局（5.9.3 实测）

```
~/.workbuddy/
├── workbuddy.db                       # sessions(id, cwd, title, custom_title, status, ...)
└── projects/
    └── <mangled-cwd>/                 # 例：Users-jarvis-Documents-tuvis-worktree3
        ├── <parentSessionId>.jsonl    # 父会话（现有采集对象）
        └── <parentSessionId>/         # 同名目录
            ├── subagents/
            │   ├── agent-<agentId>.jsonl   # 子代理转写（本次新增采集）
            │   └── ...
            └── tool-results/          # 不采集
```

- 子代理行内身份：`sessionId`（子代理会话 UUID）、`providerData.isSubAgent: true`、`providerData.model`、`cwd`、`timestamp`
- 用量位置与父会话一致：`message.usage.{input_tokens, output_tokens, cache_read_input_tokens, cache_creation_input_tokens?, total_tokens?}`
- 文件名 `agent-<agentId>` 与行内 `sessionId` **不是同一个 UUID**；会话身份以行内 `sessionId` 为准
- 实测：32 个子代理文件 / 25.9 MB / 1,612 次带 usage 的请求；父会话文件 18 个 / 8.3 MB；父 jsonl 中 `isSubAgent=true` 的行数为 **0**（无双计风险）

### 2.2 枚举算法

在 `collect_with_home` 的父会话循环内，父 jsonl 定位成功后追加：

```
main_jsonl = find_session_jsonl(home, cwd, parent_id)   # 现有函数
if main_jsonl is None: continue                          # 保持现状
project_dir = main_jsonl.parent()
sub_dir     = project_dir / parent_id / "subagents"
for file in sorted(sub_dir/*.jsonl):
    collect_file(file, identity=resolve_subagent(file), is_subagent=true, parent=parent_id)
```

规则：

1. **只用父 jsonl 的实际父目录**推导 `subagents/`，不用 `mangle(cwd)` 重算——`find_session_jsonl` 可能走目录扫描兜底，实际项目目录名与 `mangle(cwd)` 不同。
2. `sub_dir` 不存在 / 不是目录 → 跳过（旧会话无子代理）。
3. `read_dir` 的 `NotFound` / `NotADirectory` → 跳过；`PermissionDenied` 等其他错误 → `UsageError("usage-source-io", ...)` 整源失败（W-06）。
4. 只枚举该目录**直接子文件**的 `*.jsonl`；不递归（嵌套子代理是未来形态，明确不在本轮）。
5. 文件名不限定 `agent-` 前缀：`*.jsonl` 全部纳入，防未来命名演进；`tool-results/` 等非 jsonl 不读。

### 2.3 子代理会话身份解析

新增 `resolve_subagent_session_id(path) -> (String, bool)`：

1. 读取文件**前 64 KiB 或前 200 行**（取先到者），逐行解析。
2. 优先取「`providerData.isSubAgent == true` 且 `sessionId` 通过 `is_strict_uuid_form`」的第一行。
3. 如果没有，取任何 `sessionId` 通过 `is_strict_uuid_form` 的第一行（子代理首条 user 行 `isSubAgent` 可能缺省）。
4. **防自指**：解析结果等于父会话 `parent_id` → 拒绝，退回文件名 stem（`agent-<agentId>`）并 warn；否则会把父会话误标成子代理（`MAX(is_subagent)` 不可逆）。
5. 完全没有 UUID → 退回文件名 stem（仍是稳定唯一键），并 warn（身份降级可见）。
6. 结果写入 `WbState.subagent_session_id`（`#[serde(default)]`），后续增量轮次直接复用；`rescan` 时清空重解析。

`is_strict_uuid_form` 直接复用 `monitor/workbuddy_parser.rs:91` 的公开函数，不新写判据。

### 2.4 游标、增量与回填

- **游标键**：`file_key_of(&root, file)`（相对 `~/.workbuddy` 的路径），与父 jsonl 同一规则；`usage_cursor.session_id` 列存的就是这个键（WorkBuddy 现有约定，W-17 断言）。
- **新文件**：`ctx.cursor_of(file_key) == None` → `read_incremental` 从字节 0 读取 → **自动回填全部历史**（用户 D1 裁决）。
- **父会话游标**：完全不动，避免重读父文件。
- **增量状态**：每个子代理文件独立 `WbState`（`tools` / `last_model` / `dropped_no_model` / 新增 `subagent_session_id`），互不串状态；工具调用配对（`callId`）按文件内配对。
- **截断/重写**：沿用 `read.rescan` 语义，重置该文件 `WbState`。
- **文件消失**：游标行不主动删除（现有行为；键有界，按会话/文件数增长）；文件再次出现时从 0 重读。**注意：`usage_detail` / `usage_daily` 是加法账本（`dao/usage.rs:164-169`、`:343-348`，测试 `daily_upsert_is_additive`），从 0 重读会双计；只有 `tps_observation` 按 `message_id` 幂等。** 文件被截断/重写时，必须按 §4 的回滚口径先清理该文件对应的明细与日聚合，或在验证中显式申报双计。
- **回填成本**：当前 32 文件 / 25.9 MB，一次性；后续只读追加字节。`read_incremental` 无单次字节上限（现有主会话回填即此语义），本轮不引入新预算。

### 2.5 处理流程重构（单一实现）

把 `collect_with_home` 中「单文件处理」整段抽成：

```rust
fn collect_file(
    ctx: &CollectContext<'_>,
    b: &mut DeltaBuilder,
    path: &Path,
    file_key: &str,
    session_id: &str,              // 父会话 id 或解析出的子代理 id
    cwd: &str,
    title: Option<String>,
    is_subagent: bool,
    parent_session_id: Option<String>,
) -> Result<bool, UsageError>      // Ok(true) = 本轮真读并处理了该文件
```

> 类型必须与 `b.session` 对齐（`collectors/mod.rs:236-244` 的 `title: Option<String>`、`parent: Option<String>`）。子代理身份解析应发生在 `collect_file` **加载游标/WbState 之后**：先读 `state.subagent_session_id`，为空再解析并写回；调用方不要提前算 id，否则每轮都会重读 64KiB 前缀。

职责：

1. 读游标、处理 `rescan`、加载/反序列化 `WbState`（现有逻辑逐字搬入）
2. 行循环：`process_line` + 模型未知缓存重放（现有逻辑）
3. **会话维度登记**：`b.session(session_id, Some(cwd), title, is_subagent, parent_session_id, None, ctx.now_ms)`——每文件只调一次（W-13）
4. `parsed_files += 1`、`new_records` 累加、写回游标（现有语义）
5. 返回是否真读（用于调用方计数）

调用点：

| 调用方 | session_id | title | is_subagent | parent |
| --- | --- | --- | --- | --- |
| 父会话 | DB `id` | DB title | false | None |
| 子代理 | 解析出的 UUID/stem | None | true | Some(parent_id) |

`process_line` 不改：它已按行取 `providerData.model`、`message.usage`、`cwd`、`callId`、`timestamp`，对子代理文件同样成立。模型继承 / 幽灵行防护 / 工具配对全部复用。

### 2.6 明细键与归属

- `DetailKey.session_id` = 本次文件的会话身份（父 id 或子代理 id）
- `project_key` = 行内 `cwd` 的 `project_key_of`（子代理行自带 `cwd`，实测与父一致；缺失时回退父 cwd）
- `model` / `provider` / `cache_semantics` / 四桶 / `requests` / 工具计数：与父会话同口径
- `usage_session`：
  - 父会话行：`is_subagent=0`、`parent_session_id=NULL`（不变）
  - 子代理行：`is_subagent=1`、`parent_session_id=<父 UUID>`、`title=NULL`
- 查询层零改动：D17 已保证 token 总量含子代理、会话数/turn 数不含子代理

### 2.7 错误、坏行与预算

| 场景 | 行为 |
| --- | --- |
| 子代理目录不存在 | 跳过（旧会话） |
| 子代理目录不可读（非 NotFound） | 整源 `usage-source-io`（不静默少算） |
| 单个子代理文件读失败 | 仅「文件已消失（轮转竞态）」跳过；其余整源失败（W-06） |
| 目录条目/`file_type()` 读取失败 | 仅 `NotFound`（枚举中消失/轮转）跳过；其余整源 `usage-source-io`（不得 `unwrap_or(false)` 静默漏文件） |
| 坏 JSON 行 | 单行丢弃，不影响同文件其余行（现有） |
| 整文件无模型 | 缓存重放/丢弃 + 计数（现有；绝不写 `model=""`） |
| 首条带模型的行是工具回执 | 先建立模型上下文、按原序重放 pending，再处理当前行；否则 finish 先于 start，`tool_ms` 少算 |
| 子代理身份解析失败 | 用文件 stem，warn，不丢用量 |

`caps` 不变：`turn=false`、`user_est=false` 等仍成立；本轮不新增 caps 字段。

### 2.8 采集触发与回填时点

- 采集仍由 `usage_collect` 触发（`src/lib/api/usage.ts:27`），**不改进采集节奏**（用户 P2 裁决）。

## 3. 看板设计（R2）

### 3.1 现状与硬约束

- 发现入口：`WorkBuddyAdapter::find_processes` → `discover_workbuddy_processes`（`adapter/workbuddy.rs:24`）
- 会话入口：`get_workbuddy_sessions(processes)`（`monitor/workbuddy_parser.rs:382`）
- 现有过滤：严格 UUID、`kind != prewarm`、pid 文件/内容一致、pid 存活、心跳 <90s（`workbuddy_parser.rs:402`）
- **硬约束**：`get_all_sessions_inner` 对空进程列表不调 `find_sessions`（`adapter/mod.rs:628`），且测试 `all_adapters_yield_no_sessions_without_processes`（`:2179`）锁死该契约 → 兜底必须发生在 `find_processes` 或为其保留「至少一个进程」信号
- 5.9.3 心跳写入一次（`register()`），30s 刷新方法 `startHeartbeat()` 在打包代码中无调用点 → `lastHeartbeat` 冻结
- DB 状态可靠：`sessions.status` 实测值为 `working` / `completed`；`updated_at` 随父会话写入刷新（**不是独立心跳**），`last_activity_at` 冻结。`updated_at` 只能用于 completed/DB-only 的 300s 兜底，不能用来覆盖 working 会话的静默期。
- 宿主判定已有：`monitor/host.rs::is_host_process` + `tool_host_alive_in`（`host.rs:8`、`:47`）
- 移动看板与桌面同源：`remote/server.rs:482` 复用 `adapter::get_all_sessions`，只修一处

### 3.2 活性模型（唯一判据）

```
runtime_present(session) =
    heartbeat_file_exists(session_id)
    && pid_alive(session_id)
    && heartbeat_content.sessionId == session_id
is_live(session) =
    db_status == "working"                       -- 按 id 查 DB，不受 300s 窗口限制
 || db_activity(MAX(last_activity_at, updated_at)) >= now - 300s
 || main_jsonl_mtime >= now - 300s
-- runtime_present 只用于候选身份/pid；completed + 残留心跳/pid 在 DB/jsonl 超窗后必须下板并可补偿
```

> **必须用 `MAX`，不能用 `COALESCE`。** 实测（2026-10-30 12:00 CST）：两个活跃会话的 `last_activity_at` 冻结在 10:40:23 / 10:52:36（与心跳文件 `updatedAt` 10:40:24 / 10:52:36 同刻），`updated_at` 为 11:57:26 / 11:57:45；`COALESCE(last_activity_at, updated_at) >= now-300s` 返回 **0 行**，`MAX(...)` 返回 **2 行**。`last_activity_at` 与心跳 `updatedAt` 同刻冻结，说明它由同一注册/更新路径写入；心跳不刷新它也不刷新。
>
> **mtime 不可得 = 未知，不是“刚刚活跃”。** 共享判据只在 `mtime_ms.is_some()` 时才把主 jsonl 计入 300s 窗口；completed + DB 超窗 + mtime 缺失 → 下板/可补偿，不能因 `map_or(0)` 无限续命。
>
> **`working` 是主判据，300s 只是 completed/DB-only 兜底。** `runtime_present` 不再单独构成在场：completed + 残留心跳/pid + DB/jsonl 超窗必须下板，否则补偿永远不触发。9 分钟探针（13:13:57–13:22:58，54 样本）实测：父 jsonl 出现 143s 空档时，`updated_at` 冻结在 13:15:29，直到父会话 13:17:44 再次写入才跳到 13:17:48；81/133/143/92/51s 的空档全部如此。`updated_at` 随父会话写入刷新，不是独立心跳。历史 08:05:49–08:15:53 父 jsonl 只有 `credit-usage` 行、同期子代理 `agent-6e1ce7ab` 写入 95 行——纯 300s 规则会在第 5 分钟把正在跑子代理的卡掉掉。因此：心跳文件存在且 pid 存活时，`working` 会话**不因静默而下板**；`completed` 或 DB-only 候选才用 300s 窗口。

- 300s 与 `APP_STATUS_STALE_MS` 对齐（`monitor/app_status.rs:37`）
- `heartbeat_fresh` 仍用 `HEARTBEAT_FRESH_MS = 90_000`（`workbuddy_parser.rs:41`）
- **场信号**：5.9.3 的 `lastHeartbeat` 不刷新，但心跳文件在 `onStop → unregister` 前一直存在，且 pid 可存活；因此「心跳文件存在 + 内容 pid 存活 + sessionId 匹配」是可靠的「会话运行时在场」信号（**不需要新鲜度**）。`completed` 后才按 300s 下板。
  - **实测反例（2026-10-30）**：主 jsonl 在会话仍运行时存在 10.1 分钟（08:05–08:15）、10.0 分钟（09:11–09:21）、8.0 分钟（10:55–11:03）、7.1/6.5/6.1/5.8/5.3/5.1/5.0 分钟的空档。若 DB 信号用错（COALESCE）或 `updated_at` 在这些空档里也冻结，卡片会直接掉线，修复无效。
  - **强制判据**：`心跳文件存在 + 内容 pid 存活`（`WorkerRegistryLifecycle.onStop → unregister` 已确证，见 evidence §3.2）作为主「会话运行时在场」信号；`status='working'` 决定 Processing 并保持卡片；`completed` / DB-only 候选才用 300s DB/mtime 窗口。300s 不再覆盖 working 会话。
  - **9 分钟探针（13:13:57–13:22:58，54 样本）**：81/133/143/92/51s 的父 jsonl 空档里，`updated_at` 均冻结（143s 空档：13:15:29 → 父 13:17:44 写入后才到 13:17:48），`last_activity_at` 全程冻结。`updated_at` 不是独立心跳。
  - **历史 10 分钟空档**：5d229cd1 的父 jsonl 在 08:05:49–08:15:53 只有 `credit-usage` 行，同期子代理 `agent-6e1ce7ab` 写入 95 行。按旧规则，DB/mtime 在 08:10:49 过期 → 卡片在子代理运行期掉线。故 `runtime_present` 是必需项，不是可选项。

### 3.3 `find_processes` 改造

```
recent = recent_db_sessions(home, now - 300s)          # 仅用于决定是否需要宿主哨兵
processes = []
for hb_file in ~/.workbuddy/sessions/<pid>.json:
    hb = parse(hb_file)
    if !strict_uuid(hb.sessionId) || hb.kind == "prewarm" || hb.pid != pid: continue
    if !process_alive(pid): continue
    processes.push(AgentProcess{pid, cwd, exe, form: App})   # 不看新鲜度
if processes.is_empty() && !recent.is_empty() && host_pid exists:
    processes.push(AgentProcess{pid: host_pid, cwd: None, exe: host_exe, form: App})
return processes
```

- **心跳不再要求新鲜**：心跳文件 + pid 存活只负责「候选/身份」，新鲜度与 DB/jsonl 活性统一在 `get_workbuddy_sessions` 判定
- 代价：空闲会话也会进入 `find_sessions`，但只做「路径查找 + stat」，不读尾部（design §3.4）
- **DB 兜底哨兵**：仅当没有可用心跳进程、但 DB 有近期会话且 WorkBuddy 宿主进程存在时返回一条宿主进程，用于通过 L1 门禁并让 `find_sessions` 查询 DB
- 无宿主、无有效心跳、且无近期 DB 会话 → 空列表 → 不调 `find_sessions`（L1 保持）
- 新增 `host::tool_host_pid(system, tool_id) -> Option<u32>`：把 `tool_host_alive_in` 的谓词抽成「找 pid」，`tool_host_alive_in = tool_host_pid(...).is_some()`；WorkBuddy 的 `codebuddy` 会话运行时排除逻辑逐字保留

### 3.4 `get_workbuddy_sessions` 改造

```
recent = recent_db_sessions(home, now - 300s)          # id -> {cwd,title,status,activity}
candidates = []
db_by_id = {row.id: row for row in recent}
for p in processes:
    hb = read heartbeat(p.pid)                          # 可为空（哨兵）
    if hb valid: candidates.push({sid: hb.sessionId, cwd: hb.cwd, pid: p.pid, hb,
                                  db: db_by_id.get(hb.sessionId)})   # ← 必须把 DB 行并入心跳候选
for row in recent:
    if row.id not in candidates: candidates.push({sid: row.id, cwd: row.cwd, pid: 0, db: row})

for c in candidates (按 sid 去重，心跳优先):
    jsonl = find_session_jsonl(home, c.cwd, c.sid)
    if jsonl is None: continue                          # 与现状一致
    mtime = jsonl.mtime
    runtime = c.hb != null && pid_alive(c.hb.pid) && c.hb.sessionId == c.sid
    if !(runtime && c.db?.status == "working") && db_age > 300s && mtime_age > 300s: continue
    digest = WORKBUDDY_SCAN.parse(jsonl, ...)           # 仅在判活后读尾部
    status = if c.db?.status == "working" { Processing }
             else { overlay_mtime_stale(apply_green_debounce(digest.status, digest.tail_kind, eff_age), eff_age) }
    eff_activity = max(jsonl_mtime, db.activity, hb.lastHeartbeat)
    ... Session { id: c.sid, pid: c.pid (DB-only = 0), last_activity_at: eff_activity, ... }
    if c.hb exists: LAST_SEEN_SESSIONS.insert(c.pid, ("workbuddy", c.sid))
```

关键点：

1. **先判活、后读尾部**：过期会话只 stat jsonl，不解析 500 行
2. **状态上拉**：DB `status='working'` → `Processing`（覆盖主 jsonl 尾部 Idle 的子代理运行期）；其余沿用现有尾部推导 + 10s 防抖 + 300s mtime 叠加
3. **mtime 叠加** = max(主 jsonl mtime, DB activity, 心跳时刻)，避免子代理干活时父卡被 `overlay_mtime_stale` 降成 Waiting
4. **DB-only 卡片 pid=0**：心跳文件缺失的兜底路径。跳转走 macOS `activate_agent_app` 的 bundle/枚举兜底；不进入 `LAST_SEEN`（因此该边缘路径没有 W4 完成补偿，见 3.6）
5. **去重**：同一 `sessionId` 只出一张卡；心跳候选优先（有真实 pid）
6. **已删会话**：DB-only 候选由 `recent_db_sessions` 过滤 `deleted_at > 0`；心跳候选的 by-id 查询**返回 deleted 标记**，`deleted=true` 直接跳过（心跳文件残留不得复活）；`NULL`/`-1` 视为未删。**删除状态贯穿补偿与未读池**：补偿按 LAST_SEEN 查 deleted 并移除观测/池行；未读池合并前过滤 deleted WorkBuddy 行；DB 不可读 → `None`/空集，不清除。
7. **标题**：DB `COALESCE(custom_title, title)` 优先，回退现有 `resolve_title`（首条 user 消息）
8. **排序/去重/未读合并**：全部沿用 `get_all_sessions_inner` 下游，不改
9. **必须删除 90s 过滤**：`get_workbuddy_sessions` 现有 `!heartbeat_is_alive(hb, now)`（`workbuddy_parser.rs:402-408`）必须删除，只保留 UUID/kind/pid；新鲜度统一由本层的 `is_live` 判定。否则 `find_processes` 放行、`get_workbuddy_sessions` 又挡回去，R2 完全无效。
10. **L1 early-return**：`get_workbuddy_sessions` 第一行 `if processes.is_empty() { return vec![] }`，必须在任何 `recent_db_sessions` 之前；否则 `all_adapters_yield_no_sessions_without_processes`（`adapter/mod.rs:2179`）会红，单测还会读真实 home。
11. **状态上拉的作用域**：`status = if c.db?.status == "working" { Processing }`——心跳候选也必须有 `db`（见上面的 merge），否则 AC9 在正常路径不成立。
12. **working 优先于活跃**：按 id 查到的 `status='working'` → 卡片保留，即使 DB/mtime 超过 300s；300s 只用于 `completed` / DB-only 候选。`completed` + 残留心跳/pid 在 DB/jsonl 超窗后下板，并进入补偿。
13. **DB-only completed 与未读池**：WorkBuddy 的 `pid=0`、Idle/Finished active 卡若池里已有同会话未读行，adapter 在合并前把卡标 `unread=true`（`build_unread_cards` 会跳过 active，否则未读行被普通卡吞掉）。
14. **已读生命周期**：DB-only completed（`pid=0`、Idle/Finished）若存在已读墓碑且 `last_activity_at <= read_at`，最终渲染前剔除；墓碑之后有新活动（`last_activity_at > read_at`）则保留。`last_activity_at` 取自**行内 timestamp/DB 活动**（不取 mtime），并保留毫秒；只 touch mtime 不复活、同秒新工作可恢复。测试 `read_completed_db_only_card_is_dropped_until_new_activity`、`db_only_completed_last_activity_ignores_mtime_touch`。

### 3.5 心跳补偿对齐（W4）

`compensate_vanished_heartbeats_in` 增加一个注入的 `is_live: &dyn Fn(&str) -> bool`：

```
vanished(pid) = heartbeat 缺失/过期 && !is_live(session_id)
```

- 删除状态：`deleted_workbuddy_session_ids` 返回 `None` = DB 不可读（不清理）；`Some(set)` = 确认删除 → 从 `LAST_SEEN`/未读池删除，补偿跳过。
- `is_live` 与看板同源（实现里 `session_is_live` 传入按 id 查询的 `by_id` 与心跳文件集合）：
  1. `working`（按 id 查 DB，不受 300s 窗口限制）→ 无条件在场；
  2. **心跳文件已被正常 unregister 删除**：`completed` → **立即**补未读；`working` → 仍视为在场；
  3. 文件存在：`completed` 用 `MAX(last_activity_at, updated_at)` / 主 jsonl mtime 的 300s 窗口；DB 不可读但心跳 pid 存活 → 保守在场，不误补。
- 仍在运行的 5.9.3 会话（心跳冻结但 DB 活跃/pid 存活）**不会被补成未读**——否则卡片修好后会被补偿逻辑立刻插入未读/通知
- 正常完成（心跳文件被 unregister 删除）→ 立即按尾部完成态补偿；异常（文件残留但过期）→ 300s 后才按尾部完成态补偿
- **观测消费时机**：只有“完成态已明确处理”（Idle 且通过状态缓存/已读墓碑护栏 → 产出补偿；或非 Idle → 无完成通知可发；或已绿/已读）后才从 `LAST_SEEN` 移除；**JSONL 暂缺时保留观测**，下一轮重试，避免本轮无产物 + 下轮失据的永久漏通知。
- `status_of` / `was_read` 两道既有护栏不变

### 3.6 性能与已知限制

- `workbuddy.db` 的 `sessions` 表本机 17 行；`MAX(last_activity_at, updated_at)` 查询 0.03ms；每 3 秒两查询可忽略
- 不扫描 `subagents/` 文件 mtime（文件数会随子代理增长）；子代理活动由 DB `updated_at` 代理
- 尾部摘要仍走 `WORKBUDDY_SCAN`（mtime+size 缓存），只有活跃会话才读
- **DB-only 卡片无 W4 补偿**：心跳文件缺失是边缘路径（5.9.3 实测文件持续存在）；正常路径有心跳文件，补偿可用
- **空闲 >5 分钟下板**：见 3.2 取舍；用户下一条输入即恢复
- **DB 打不开**：`open_readonly_with_timeout` 返回 None → DB 候选为空，回退心跳路径；不 panic、不报错
- **状态上拉只单向**：`working` → Processing；`completed` 不强制绿色（仍走尾部+防抖），避免误绿

## 4. 兼容性、迁移与回滚

- **schema**：无变更（`usage_session.is_subagent` / `parent_session_id` 已存在）
- **旧账本**：父会话行/明细不变；首次采集新增子代理行与子代理游标行
- **旧游标**：`WbState` 新增字段带 `#[serde(default)]`，旧 `state_json` 可反序列化
- **回填**：一次性读取 25.9 MB 子代理历史；历史日报会跳升（用户已批准）
- **回滚**：回退代码即可；已写入的子代理行是真实数据，保留不影响正确性。若必须撤销回填（需用户批准），删除 `usage_cursor` 中 `session_id LIKE '%:subagents:%'` 的游标与对应 `usage_detail` / 重新聚合 `usage_daily`——本设计不提供自动脚本
- **降级**：DB 打不开 → 看板回退心跳路径；心跳/DB 都失效 → 无卡（不误报）

## 5. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 主/子文件重复计入 | 实测父文件 0 行 `isSubAgent=true`；夹具断言父+子总量；identity 自指拒绝 |
| 子代理会话 id 冲突/自指父 id | 严格 UUID + 自指拒绝 + stem 兜底 + warn |
| 子代理目录不可读被静默吞 | 非 NotFound 整源 `usage-source-io`；测试锁 |
| 回填把真账本写脏 | 开发期用 `TUVIS_HOME` 影子账本 + `TUVIS_USAGE_FIXTURE_ROOT`（debug）；真实采集只在用户批准后做一次 |
| 看板误判活跃（DB updated_at 被 UI 操作刷新） | 300s 窗口 + 宿主存活 + 主 jsonl 存在；误判代价仅是卡片多留最多 5 分钟 |
| 补偿把运行中会话补成未读 | 补偿与活性判据同源（3.5）；测试锁 |
| 同 pid 多会话（DB-only） | DB-only 卡 pid=0，不进 LAST_SEEN，不参与补偿；正常路径每会话有独立心跳 pid |
| 心跳文件被上游清理 | DB 兜底出卡；无补偿（已知限制） |
| 采集耗时突增 | 一次性 25.9 MB 回填；之后增量；采集在 spawn_blocking 中执行，不阻塞 UI 线程 |
| 国际版/TPS 被误改 | 明确不在范围；验收 AC6 检查零变化 |
| `last_activity_at` 被当作活信号 | 已冻结；统一用 `MAX(last_activity_at, updated_at)`，测试锁「last_activity 旧、updated 新」夹具 |
| 父 descriptor.usage 被叠加 | 30/34 存在，29 精确、1 滞后、4 缺失；只做交叉核对，禁止入账 |
| rescan/文件重写双计 | `usage_detail`/`usage_daily` 是加法账本；截断前先清理对应明细或显式申报 |
| 5 分钟空档掉卡 | 实测主 jsonl 有 10.1/10.0/8.0 分钟空档；先验证 `updated_at` 在子代理期刷新，否则改用心跳文件+pid 或子代理 mtime |
| 自指/串号 | 解析结果必须不等于任何 DB 主会话 id，不只父 id |
