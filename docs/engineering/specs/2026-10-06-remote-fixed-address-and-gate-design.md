- 状态：待用户评审（带宽与可达性校验均已按 2026-10-06 实测回填）
- 权威链：`docs/MASTER-PLAN.md`（宪法）→ 一期设计说明书 §P6（配对）/ §P7（固定地址与通道）→ 本设计说明书

## 1. 目标与范围

### 1.1 要解决的空白

> **用户诉求**：「我想在移动端、在户外去连接家里的电脑……让没有技术背景的小白用户也能开箱即用——① 获得一个固定的链接；② 具备密码验证机制，然后就能直接进入远程连接。」

外网接入现有两条路，中间留了一个空白：

| 现有路径             | 地址                       | 代价                                 |
| -------------------- | -------------------------- | ------------------------------------ |
| 临时通道             | 每次重启就换，二维码得重扫 | 无——开箱即用                         |
| 固定网址（自有域名） | 永久                       | 用户得**自己有域名**并按指引配置隧道 |

> **空白：没有域名、也不想折腾的用户，拿不到一个永久地址。**

### 1.2 一句话方案

把宪法**已有的第 4 模式（Tailscale）从「文档指引」升为「内置通道」**，具体形态为 **固定网址 · 免域名**：由 Tailscale Funnel 提供 `https://<机器名>.<tailnet 名>.ts.net` 这个永久地址，MAM 负责**引导安装、调起、显示与配对**。

> **这不是新增第 5 模式，无需修宪。** 宪法 §0.1 与 F1.2 已把 Tailscale 列为四模式之一（直连域名 / named tunnel / quick tunnel / Tailscale），§3.(d) 的判定为「采用（模式之一，文档指引）」。本次只是把该模式的实现从"写在文档里、让用户自己配"升级为"MAM 内置调起"——**宪法条款一条不动**。

**但接入前的安全核查发现既有门禁存在一条 fail-open 的鉴权豁免路径**（详见第一部分），其安全性完全依赖第三方闭源边缘行为。**故本设计分两部分交付。**

### 1.4 明确不做

- **不自建公共中继**。宪法 §3.(d) 已记「自建 WSS 中继 → 三期后可选」，本次不动该结论。
- **不改既有三条通道的语义**（临时 / 固定网址 / 局域网各自行为与交付前一致）。
- **不引入账号体系**。Tailscale 账号是用户与 Tailscale 之间的事，MAM 不持有用户任何第三方凭据。
- **不改变默认通道**。宪法 D1「quick tunnel 为无公网用户默认」维持：新通道是"想要固定地址时的升级路径"，不是新的默认。
- **不打包、不再分发 Tailscale 安装包**（合规红线，见 §C2）。
- **不放宽任何既有限速语义**：连续失败上限与锁定时长维持不变——§G5 只修正"按什么分桶"，不放松强度。

## 2. 第一部分 · 门禁零豁免（前置）

### 2.0 为什么它是前置：现状与风险

**现有本机免密（M5 A3）的判定链**：

1. 来源为回环；**且**
2. 「连接归属实锤」未命中——反查系统连接表拿到持有该连接的进程，与 MAM 自己拉起的隧道进程对账；**且**
3. `Host` **不在**隧道域名名单 → **放行（免设备凭据）**

**风险一：第 3 步是黑名单，fail-open。** 任何不在名单里的 Host 都通过。

**风险二：macOS 上第 2 步恒不命中。** 归属实锤在 Windows / Linux 为一等实现，**macOS 无对应实现**（无 procfs，且本期不做 libproc FFI），判定恒回落到第 3 步。于是 macOS 上**只剩黑名单一道防线**。

**风险三：这道防线不是 MAM 挣来的。** 隧道流量的 TCP 对端恒为回环，故第 1 步对所有公网流量都成立；当前之所以安全，只因为 Cloudflare 边缘会拒绝伪造的 Host。**这是一个未被声明、未被测试锁定的第三方假设。**

**威胁模型（macOS）**：任何**原样透传客户端 Host** 的入站通道，攻击者只需发送一个不在名单里的 Host，即可免密获得**全看板读 + 全部写权限**（写操作含发消息、审批应答、切换模式）。2026-10-06 源码核对：Tailscale serve/funnel、ngrok、zrok **三家全部原样透传**（其中 Tailscale 在 TLS 下按 SNI 路由、不校验 Host，黑名单直接 fail-open）。根因是 Go 生态反向代理的**默认行为**，属系统性默认而非个别疏忽——**「换个隧道就安全」不成立**。

**附带发现（同根因）**：

- **「直连域名 + 同机反向代理」免密洞（已实测证实）**：用户的反代与 MAM 同机运行时，从回环转发公网流量，Host 是用户自有域名（不在隧道名单）→ 被判为"本机"→ 免密。实测三种域名形态**全部 200（免密）**。而"直连域名"正是一期设计说明书定的**用户主路径**。
- **每次请求的全量连接表扫描**：归属实锤需要遍历系统连接表，而它在**每个回环来源请求**上都会执行；隧道在跑时，每次请求（含实时流轮询、状态刷新）都付这个代价。Windows 的实现无此问题。

### G1 · 鉴权零豁免（第一部分的核心）

- **需求**：`/m/api/v1/*` 的鉴权只有一条规则——**携带有效设备凭据**；唯一例外是换取凭据的配对入口（访问密码即凭据）。判据只能来自**服务端自身状态**，不得来自请求携带的任何数据。
- **约束（不变量 G1）**：**任何请求头、来源地址、进程归属不得参与鉴权判定。** 三条推论：
  1. 请求头（含 Host 与各类转发头）**永不**影响放行；
  2. **新增任何入站通道不需要在门禁侧新增代码、配置或名单**——这是第一部分的主要收益，也是第二部分能低成本接入的前提；
  3. 展示字段（如配对的来源标注）与鉴权**彻底解耦**：允许不准确，**永不得**被安全逻辑消费。
- **输出与效果**：macOS 上的免密绕过面消失；「直连域名 + 同机反向代理」免密洞**结构性消失**（无需单独修）；三平台在鉴权上完全同构；后续接入任何通道**默认安全**，不必逐通道论证代理的 Host 行为。
- **边界**：403 响应体保持为空（不泄露"未配对 / 设备失效"的区分）；凭据有效性判定与活跃度续期仍在同一临界区完成（维持既有并发纪律）。

### G2 · 连接归属判据退役

- **需求**：§G1 生效后，连接归属判据（含其两套系统级实现与 macOS 的空实现）失去唯一的安全用途，**整块退役**。
- **输出与效果**：删除约 300 行代码与**两套系统级实现 + macOS 空实现**；**每次回环请求的全量连接表扫描开销一并消失**。
- **边界**：退役以编译告警为准逐项清理（不预判哪些符号还有消费者）；**macOS 无归属实锤这一历史落差随之失去意义**——这也是选「零豁免」而非「给 macOS 补一套归属实锤」的理由：后者只补齐一个平台，判据仍是 fail-open 的黑名单。

### G3 · 展示字段与鉴权解耦

- **需求**：配对的"来源"标注降级为**纯装饰字段**，只用于设备花名册展示，不再参与任何判定。
- **输出与效果**：来源标注由域名推断，取值为「临时隧道 / 自有域名 / 外部域名（免域名）/ 局域网」**四值**（与 §C4 四张卡片一致；第四值随第二部分接入 Tailscale 通道时加入，第一部分落地时为三值）；**「本机」不再是一个取值**（本机不是通道，见 §C4）。历史数据中已有的「本机」标注**保留可读**，不做数据迁移。
- **边界**：代码注释须显式写明「装饰用途，不得用于任何安全判定」。新增通道**可选择性**登记自有域名以使标注准确——纯装饰，**不构成鉴权配置项**。

### G5 · 配对限速的来源分桶修正（**2026-10-06 用户裁决并入本批**）

- **问题（已实证）**：配对入口的限速键取 **TCP 对端地址**，而隧道流量的对端**恒为同一个回环地址**——于是**所有经隧道的配对尝试共用一个计数桶**，任意一个陌生人反复输错几次，就能把这条入口锁住一段时间，且可无限重放。同一根因还让花名册与审计里的来源地址**失去区分度**（全部显示同一个值）。
- **危害定级（如实申报，勿夸大）**：这是**低危可用性问题，不是安全事故**。影响面仅限「**经隧道首次配对一台新设备**」；**已配对设备完全不受影响**（走设备凭据，根本不经过配对入口），本机 / 局域网路径与桌面端重置密码也都不受影响。
  > **为什么仍要修**：限速的设计意图写明是"按来源 IP"，而在隧道下它**事实上退化成了全局计数**——与本意不符；且来源地址的区分度是花名册与审计要用的。修法便宜，故一并做掉。
- **需求**：限速与来源记录必须**能区分公网来源**，且**不得引入新的伪造面**。
- **实测证据（2026-10-06，经 quick tunnel 回显全部请求头）**：

  | 伪造的头           | 边缘行为                                            | 可否采信                |
  | ------------------ | --------------------------------------------------- | ----------------------- |
  | `CF-Connecting-IP` | **Cloudflare 直接 403，整个请求被拒**               | ✅ **权威可信**         |
  | `X-Forwarded-For`  | 200，本地看到 `伪造值,真实值`——**真实值被追加在后** | ⚠️ 可污染，须取最后一段 |
  | `True-Client-IP`   | 200，**原样透传**（伪造值直达本地）                 | ❌ **不可用**           |
  | `X-Real-IP`        | 被边缘丢弃                                          | ❌ 不存在               |

  **结论：Cloudflare 通道的权威来源头 = `CF-Connecting-IP`**（伪造它会被边缘拒掉整个请求，比"覆盖"更强）。这与生态做法一致（信 `cf-connecting-ip`、不信 XFF）。

- **分桶规则（按来源"可证性"分档；不可证就 fail-closed）**：
  1. 来源地址**非回环** → 直接按来源地址分桶。**真实且不可伪造**，覆盖局域网与一切直连来源；
  2. 来源地址**是回环**（流量经本机连接器进来）→ 只有**同时**满足「请求 `Host` 命中该通道**已登记**的域名」**且**「该通道**声明的权威来源头**存在」时，才按该头分桶；两条件缺一即**回落全局桶**；
     - Host 那一条**对「真过 CF 边缘」的流量够用**（本次实测两次伪造 Host 均被边缘 403）；但**同机转发不受此保护**——同机反代或任何能触达回环端口的转发可**同时**伪造 `Host` 与 `CF-Connecting-IP`，从而**自选限速分桶**。影响**只限限速**（放行判定只看设备凭据，请求头进不了鉴权）。**详见 §8 已知限制第 11 条**（与 §7 证据台账「闭源边缘行为，不得作为设计依赖」口径一致）。
     - 权威头**按通道静态声明**（临时隧道 / 命名隧道 = `CF-Connecting-IP`）——**不得在运行时按请求内容推断"该信哪个头"**；
  3. 其余一切情况（含**直连域名 + 同机反代**、以及未来尚未验证入口行为的新通道）→ **回落全局桶**。宁可更严，**绝不**回落成"每请求一个新桶"（那等于取消限速）；
  4. **不采信 `True-Client-IP`，也不裸信 `X-Forwarded-For`**（前者可伪造、后者可污染）——**这条要写进代码注释**，防止后人"顺手支持一下"。
- **全局上限（滑动窗口，2026-10-07 用户裁决）**：保留一道全局上限（分布式爆破只能靠它挡），但它的语义**必须是时间窗口内的失败密度，而不是进程生命周期内的累计计数**——后者是"只进不出的水桶"：正常用户的零星失败会永久累积，且单个来源每锁定周期只贡献 5 次、约 **100 分钟**即可填满阈值，随后把所有人（含局域网/本机来源的合法配对）一起挡在门外。
  > **评审实测更正**：初稿写"阈值 50 即宽到单个来源填不满"——**该断言为假**（算术见上）。改为**滑动窗口衰减**：计数 = "最近一个锁定窗口内的失败次数"，窗口外的旧记录在判断前丢弃。正常使用几乎不可能触发，而密集爆破照样触发（防护不损）。
- **既有恢复路径（如实记录，本批不新增安全面）**：① 用**本机 / 局域网地址**配对（不同桶，不受影响）；② 等待锁定期结束；③ **桌面端重置访问密码**（走进程内通道，不经门禁、不受限速；代价是全部设备凭据失效、需重新配对）。**本批不新增"本人专用"配对通道**——用户 2026-10-06 裁决：危害有限，不为它扩大安全面。
- **输出与效果**：捣乱者只影响自己那一份计数；限速仍能挡住爆破；来源地址恢复区分度（花名册与审计可用）。
- **边界**：本项**不修改**连续失败上限、锁定时长与防预言机语义，只修正"按什么分桶"；§G1 的不变量**不因此放宽**（限速不是放行判定）。**已知代价**：「直连域名 + 同机反代」这一接线会落在全局桶，即其配对限速与今天等价——这是 fail-closed 的有意选择；若要精细化，需让用户声明"我的反代会设某个来源头"，**列为后续可选，不在本批**。

## 3. 第二部分 · 固定网址通道

### C1 · 通道本体：固定网址 · 免域名

- **需求**：没有域名、也不想折腾的用户，也能拿到一个**永不变化**的接入地址。
- **机制（为什么地址是固定的）**：
  - **地址不是 MAM 发的，是 Tailscale 发的**——它注册在 Tailscale 的 DNS 里，由账号与机器名共同决定，**不随进程重启、机器重启、断网恢复而变化**。与临时通道的本质差别：临时通道的域名**每次连接现铸**，本通道的域名**注册在 DNS 里**。
  - **证书也不用用户碰**——由 Tailscale 自动签发与续期。
  - **配对链接因此可长期有效**——二维码不再漂移，用户扫一次即可存为书签。
- **链路怎么走**：

  ```
  手机浏览器 → ① Tailscale 边缘（只按域名转发，不解密）
             → ② WireGuard 加密隧道
             → ③ 你机器上的 Tailscale 终止 TLS
             → ④ 转给 MAM 的服务器
             → ⑤ MAM 业务（看板 / 会话内容 / 注入）
  ```

  三点必须说清：① **中继拿不到明文**（TLS 在本机终止），这比临时通道更好（临时通道在 Cloudflare 边缘解密）；② **项目方不经手流量**——四条通道里 MAM 作者/项目方都没有服务器参与，本通道引入的是 Tailscale（第三方）；③ **中继不可信也不影响正确性**——信任永远来自配对门禁，不来自通道（宪法「通道只是入口不是信任边界」）。

- **输出与效果**：一个永久地址 + 二维码；重启后地址不变、已配对设备免重配。
- **边界**：定位是「**用一次性登录换永久地址**」，与临时通道「用地址漂移换零配置」互补，**不是替代**；Funnel 仍为 beta，文案不得承诺 SLA。

### C2 · 首次配置引导（一条龙）——一等需求

> **用户原话**：「我特别在意首次配置桌面客户端的易用性……我希望尽可能做到开箱即用、傻瓜式的一条龙默认配置，直接把服务唤起。这个需求的强度非常大。」

- **需求**：MAM 负责「检测 → 下载 → 拉起 → 引导 → 验证 → 自恢复」**全链路**；用户只在**物理上必须由人做**的地方点一次确认。
- **三条设计原则**：
  1. 用户**永远不需要**：打开终端、手敲命令、读文档、判断状态、去第三方网站找入口；
  2. **安全红线（不为体验让步）**：不打包分发第三方安装包；只从官方源下载并校验完整性；**不静默提权**；**不接触任何用户凭据**（登录一律由用户在浏览器完成）；
  3. 引导必须**自己判断进度**、**卡住时知道卡在哪**，否则就会变成"用户点了没反应"。
- **引导流程：macOS 九步 / Windows 八步**（Windows **没有"批准系统扩展"这一步**），其中**需要人的步骤：macOS 四步、Windows 三步**。**步骤表按平台分别定义**（见下条"平台数据"），不写死成一份。

  | #   | 步骤                     | 谁做                       | 用户动作                                                                                                                 |
  | --- | ------------------------ | -------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
  | 1   | 检测是否已安装           | MAM                        | 无（自动）                                                                                                               |
  | 2   | 从官方源下载并校验       | MAM                        | 无（自动）                                                                                                               |
  | 3   | 触发安装                 | MAM 触发，系统弹管理员确认 | **输一次系统密码 / 点 UAC**                                                                                              |
  | 4   | （仅 macOS）批准系统扩展 | 系统弹出，用户去系统设置   | **点一次「允许」**                                                                                                       |
  | 5   | 登录 Tailscale           | 用户在浏览器完成           | **可能点两次**：先点「获取登录链接」（MAM 主动向后端要一次链接），再去浏览器完成登录；MAM 把链接做成按钮，用户不用自己找 |
  | 6   | 关闭「阻止传入连接」     | MAM                        | 无（自动）                                                                                                               |
  | 7   | 开启 Funnel              | MAM 触发，浏览器弹一次批准 | **点一次「批准」**                                                                                                       |
  | 8   | 验证并显示固定地址       | MAM                        | 无（自动）                                                                                                               |
  | 9   | 此后每次开机             | MAM 自动恢复               | 零维护                                                                                                                   |

  > **步骤 5 的现状（2026-10-08 回写）**：**授权链接不是 `status` 自动吐出来的**——新装机器上是
  > `BackendState = NeedsLogin ∧ AuthURL = ""`，链接要**发起一次交互式登录**才由尾网生成
  > （与 Windows GUI 的「Log in」按钮同义）。故 MAM 在该步**后台 `spawn`
  > `tailscale login --timeout 15s`**（三条标准流给 null、句柄登记进单飞槽，绝不同步等待）
  > 并**有界轮询 ≤9.5s** 把 `AuthURL` 取回来做成按钮 ⇒ 用户**可能点两次**（先「获取登录链接」、
  > 再去浏览器完成）。**合规红线一字不让**：MAM **仍不代登录、不持有任何凭据**——那条 argv
  > **零旗标**（除有界的 `--timeout 15s` 外一个参数都不带），内容由守卫测试从**实际 argv** 上锁死；
  > 取不到链接就**如实回空串 + 成因**（前端给「去客户端点 Log in / 稍候重试」的兜底文案），**绝不无限等**。

  **用户的动作总和 = 输一次密码 + 点三次允许。全程不碰命令行、不查文档、不判断状态。**

- **MAM 怎么知道每一步做完了**：读 Tailscale 自身的状态——安装看标准安装位置；登录看其后端状态字段，处于"待登录"时**须先发起一次交互式登录**才有**授权链接**（MAM 主动发起、把链接做成按钮，见上条注）；「阻止传入连接」是**可程序化读写**的偏好项（故第 6 步全自动）；Funnel 与地址都从 Funnel 状态回读，不靠猜。
- **四步为什么不能自动化（如实申报）**：

  | 步骤                   | 原因                                                                                                      |
  | ---------------------- | --------------------------------------------------------------------------------------------------------- |
  | **装软件**             | 安装包需管理员权限。要自动化就得让 MAM 常驻管理员——**这正是安全上要避免的**。系统弹确认框是特性不是缺陷。 |
  | **macOS 批准系统扩展** | Apple 规定只有 MDM 能预批准，而 MDM 配置描述文件 Apple **又禁止用户自行安装**。平台级硬约束。             |
  | **登录**               | 需要用户的第三方身份。MAM 代持凭据正是本设计要避免的；只把登录链接递到用户面前。                          |
  | **首次开启 Funnel**    | Tailscale 有意插一次网页批准——它要改用户的 tailnet 策略并签发证书。上游设计，无法用技术绕开。             |

- **合规红线（§1.4 的依据）**：Tailscale 的**开源客户端源码是 BSD-3**（可分发），但 **macOS / Windows 的图形安装包是专有软件**——许可明确为「**不可转让**」并禁止复制、再现、转售。本机已核实官方安装包由 Tailscale 签名与公证、官方源提供校验值。
  > **MAM 的做法**：**代用户从官方源下载并运行**（有用户明确同意）——合规可辩护。
  > **MAM 不做**：把安装包塞进 MAM 的安装程序、内嵌或再分发——**未获授权**。
- **写路径（动作）的实机验证位（2026-10-07 评审补）**：与 Windows 步骤表同纪律——**macOS 的写路径**（`funnel --bg` / `funnel reset` / 批准链接抓取）同样是**零实机验证**（设计期只跑过只读命令），故与 `WINDOWS_VERIFIED` 并列一个 **`writePathVerified` 位**，两平台均标"未验证"，不得伪装成已验证。
- **Windows 行已实测回填（2026-10-07）**：真机探测（Windows 11 家庭版 / Tailscale 1.102.4 MSI）结论——
  **字段核对表 7/7 与 macOS 完全一致**（`BackendState` / `AuthURL` / `Self.DNSName` 带点 / `CertDomains` 不带点 /
  `funnel status --json` 未开通为 `{}` / `get --json` 键名 `shields-up`）；**三条写路径全部可用且无需管理员**。
  **人工确认数按实测登记：macOS 3 必需 + 1 可选 / Windows 2 必需 + 1 可选**（原按官方文档预填的"Windows 3 次"被实测推翻）。
  > ⚠️ **覆盖面（2026-10-08 更新，覆盖前述收窄）**：上面"从第 6 步开始"是 **2026-10-07 第一次探测**的范围。
  > **同日稍后用户卸载 Tailscale 后从零走完 MAM 向导全程**（检测 → 下载 → 安装（含 MSI 路径选择与 UAC）→ 登录 →
  > 关闭 shields-up → 开通 Funnel → 可达性校验，**全程正常**），故 **detect / download / install(UAC) / login
  > 四步的流程这一次已实机跑过**，**覆盖起点前移到第一步**（`WINDOWS_VERIFIED_FROM = "detect"` ⇒ 未验清单为空
  > ⇒ `windowsVerified = true`，前端黄标撤下）。
  > **证据性质 = 当事人陈述，不是机器可复核的产物**：依据是用户本人口述（原话「走的是 MAM 向导」「反正我感觉是
  > 足以指导没做过的用户一步一步点下去了」），**没有截图/日志/留痕产物**，当时的一次性探测任务书也已删除
  > （`9acf727`，rebase 前旧哈希 `6040ba6`）。逐条登记见 **`docs/release-notes/windows-wizard-acceptance-2026-10-07.md`**。
  > **未覆盖 / 待真机复核**：新加的 `tailscale login` 主动取链接、`--timeout 15s` 的实际退出形态、kill 等待者
  > 对 `AuthURL` 的影响——**这几条尚未在真机复核**（该记录 §七逐条登记）。
  > **纪律保留**：将来若又发现某步没实测，**必须同样在提交与本文档里写明依据**（不得为让提示消失而翻验证位）。
- **Funnel 首次开通的批准步是「可能不出现」的分支（2026-10-07 实测）**：Windows 上 `funnel --bg` **0.1 秒直接成功**、
  **无任何批准链接与浏览器弹窗**；而 macOS 实测首开**确有**一次浏览器批准。故代码**不得等批准**——

### C3 · 配置完成后的强制可达性校验——一等要求

> **2026-10-22 用户裁决更新**：普通校验与刷新改为只读，等待公网 DNS 不触发 reset，也不给重复重试。重置重开仅属于用户明确确认的「重新开通」修复入口。当前等待文案、折叠及 Cloudflare 引导契约以 [两套向导收尾方案](2026-10-22-remote-wizard-completion.md) 为准；下文旧实测时长及事故记录保留为历史证据，不再作为界面承诺。

> **实测事故（2026-10-06）**：首次开启 Funnel 后，**本地信号全部正常**——Funnel 状态显示已开启、开关为真、证书域已启用、`tailscale cert` 甚至真的签下了 Let's Encrypt 证书——**但公网地址打不开**：公网 DNS 的地址记录当时尚未发布。手机侧表现为"域名无法解析"。**任何本机自检都发现不了**，因为本机是尾网成员，该名字被 MagicDNS 接管（解析到尾网地址），压根不走公网路径。
> **恢复动作**：重置 Funnel 后重新开启 → 触发记录重新发布 → 解析随即恢复正常。

- **需求**：**把"配置成功"与"地址可用"当成两件事。**
- **六条要求**：
  1. 配置完成后必须显式执行一次**尾网之外**的可达性校验：确认该地址能**解析出公网地址**且能**接通**；
  2. **校验不通过就不许把地址当可用呈现**——界面明确报"固定地址尚未生效"，保留其他通道兜底并给出重试，**不能把一个打不开的地址摆在界面上让用户干等**；
  3. 失败时**如实报告并继续只读复验**；等待期间不重置 Funnel。用户明确选择「重新开通」并确认后，才复用原有重置重开修复内核（2026-10-22 用户裁决）；
  4. **校验不能在本机做**，两个原因各自都足以致命：① 本机是尾网成员，该名字被 MagicDNS 接管，压根不走公网路径；② 本机可能装有网络加速/代理工具（本次实测机器上就有——它用自签 CA 做本地 MITM，把该域名的 HTTPS 请求拦下并返回错误页）。**校验必须在尾网之外发起**；
  5. **主次必须写对（2026-10-06 修正）**：机制以**外部解析 / 探测为主**——从尾网之外查该域名的**公网地址记录是否存在**并尝试接通。**手机端回传不能作为主机制**：手机若解析不出来，就**根本打不开页面、也就无从回传**——这个机制恰恰测不到它要测的那个故障（这正是本次事故的形态）。手机端的回传**只能确认成功**（作为"真实路径确实通了"的加分证据），**无法报告失败**；
  6. **上游是 beta，此校验是长期件而非一次性**（**2026-10-07 已实装**：轮询间隔带退避、流式校验安装包哈希避免整包入内存）：地址失效时自动重试 + 保持其他通道可用（宪法原则 2「通道无关」正好兜住）。
     > **2026-10-07 评审实测更正（用户裁决）**：初版实现把重验条件写成"当前态已是 Verified 才每 60 秒重验"，导致两个后果：① 一旦翻 Failed，条件恒假 → **再无自动重试**，只能用户手点；② 每次 MAM 重启校验态复位为"未验证"，而恢复路径不触发校验 → **地址恒不显示**，与 §C1「设置页常驻固定地址」「重启后地址不变」**直接冲突**。已裁决改为：**只要通道在运行就按窗口校验（不分当前态）**，事件判据为「**从可用跌落**」：`Verified → Failed`、`Verified → RecordPending`（记录被撤）**或** `Verified → Recovering`（已可用地址被暂时撤下）；持续失败与未验证态不发（自存上一轮态防刷屏）。
  7. **自愈与任何「判配置是否存在」的动作，都必须先确认 `BackendState=Running`（2026-10-07 实测）**：真机重启后 **T+58s** 时服务已 Running 但 **`BackendState=NoState`**、**`funnel status --json` 短暂为 `{}`**，**T+73s** tailscaled 自己就把 Funnel 配置**逐字段恢复**了。窗口内若按 `{}` 判「配置丢失」→ 会**不必要地重开**；更重的是**自愈会 `funnel reset` 把 tailscaled 正在恢复的完好配置清掉**（旧行为经测试实证）。故：**初始化中一律 Deferred**——不读 funnel status、不写 shields-up、不发 `funnel --bg`、不 reset；只有「后端连续 Running + 归属确认 Absent」才补开通（一次缺失期只试一次）。撤销路径**不设此门**（用户显式撤销时"撤不掉"是更糟失败模式）。
     **tailscaled 状态写恰好六处**，门覆盖如下（2026-10-08 由"五处"更正为六处——新增第 4 行的 `tailscale login`）：

     | 写命令                                                                                                                                                                                                                           | 唯一实现点            | 门                                                             |
     | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------- | -------------------------------------------------------------- |
     | `set --shields-up=false`                                                                                                                                                                                                         | `disable_shields_up`  | 两个调用方各自过门：`enable_funnel`⓪、`run_step("shields_up")` |
     | `funnel --bg`                                                                                                                                                                                                                    | `enable_funnel`       | ⓪                                                              |
     | `funnel reset`                                                                                                                                                                                                                   | `disable_funnel`      | 调用方：撤销路径**有意不设门**；`heal_and_reverify` 过后端门   |
     | `login --timeout 15s`（**登录步主动取链接**，2026-10-08 补）                                                                                                                                                                     | `spawn_login_attempt` | **有意不过 W-A 初始化门**（理由见下）                          |
     | **初始化态有界降级**：`NoState`/`Starting` 持续超 **180 秒** → 不再说"恢复中"，改为如实点名「后端持续未就绪（NoState，已 X 分钟）」+ 写快照 error + 向导重试入口；就绪即交回未验证态。「恢复中」**不得成为掩盖真故障的挡箭牌**。 |
     | **退避判据须包含后端相位跃迁**（否则补开通最坏等约 2 个轮询窗 ≈ 2 分钟）。                                                                                                                                                       |

     > **第六处为什么有意不过门（2026-10-08 登记）**：该命令**不写任何设置**（argv 零旗标，只有
     > `login --timeout 15s` 三条，白名单常量 + **实际 argv** 守卫双重锁死），且**上游 CLI 自带 Running 门**
     > ——`tailscale login` 在后端尚未就绪时由 CLI 自己处理/等待，**等价于把 W-A 的 Deferred 语义下沉给 CLI 自己**；
     > 在恢复窗口里再加一道 MAM 侧的门，只会给登录步多一个"读不到状态"的失败面，而不减少任何写入。
     > ⚠️ **残余（待裁决，如实登记）**：恢复窗口内（后端在重连、其实已登录的机器）登录步会呈现「待做」+
     > 「获取登录链接」按钮——对这类机器是**假待做**。危害有界（点下去只是一次有界等待、不改配置），
     > 但**待控制方在两条路里裁决**：**① 补门**（初始化中把登录步也 Deferred / 呈现"后端正在重连"），
     > 或 **② 呈现 amber**（照本文档 §C3 要求 7 的中间态档位，不涂红、不说假话）。

  8. **校验态必须随生命周期失效**（**2026-10-07 已实装**：`start`/`stop` 入口直接作废并清零重验时钟，`stop` 与快照复位在同一临界区）：`stop` / `reset` / 重新 `start` 之后，旧的"已验证"不得继续被当作有效——`funnel reset` 恰恰是本次事故里"记录未发布"的触发动作，若校验态跨它存活，界面就会把一个**刚被自己 reset 掉**的地址报成可用。
- **输出与效果**：用户不会拿到一个打不开的地址；配置失败时可自愈或明确降级。
- **实测补充（2026-10-07，Windows 真机）**：① **公网 DNS 记录约需 5–6 分钟才发布**——期间本机直连立刻 HTTP 200
  （走 100.x 本地路径），DoH 却连续 NODATA，直到 5–6 分钟后才出现 A 记录；**AAAA 始终不发布**。
  故 UI 文案须给出**预期时长**，且**按场景分三档**（2026-10-07 实测三档时间差异巨大，单档会说错成因）：

  | 档           | 时长         | 成因                                         | 判据（可证）                                                                                                                                                                                                                                                                           |
  | ------------ | ------------ | -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | **首次开通** | 5–6 分钟     | 公网 DNS 记录首次发布                        | 默认档（**不可证边界**：MAM 关着时被手动 reset → 只能落此档，故文案两界都给「首次 5–6 分钟 / 此前开通过通常 1 分钟内」）                                                                                                                                                               |
  | **重新开通** | 30 秒–1 分钟 | 记录重新发布                                 | **本进程内执行过 `funnel reset`**——`disable_funnel` 是 reset 的**唯一**调用点，且有**源码锁** `funnel_reset_has_exactly_one_call_site` 把这句话变成可执行约束（自愈路径也已收口到它，此前绕过记账的缺口已修）。若 reset 失败则如实 `Failed`，**不发** `set --shields-up` 也不发 `--bg` |
  | **开机恢复** | 1–2 分钟     | **后端重连**（不是域名发布，DNS 记录不撤销） | `BackendState` 非 Running，或「见过初始化窗口 ∧ 首个 Running 后 3 分钟宽限内解析得到但连不通」；**宽限窗有界**，超窗交回如实 `Failed`                                                                                                                                                  |

  ② **本机 DNS 劫持连"指定公共解析器"都骗得过**：`Resolve-DnsName -Server 223.5.5.5` 恒返回 MagicDNS 值（Tailscale 的 WFP 规则接管 53 端口）⇒ **任何走系统 DNS 栈的检查在本机都永远显示"通"**，验证**只能**走 DoH（443）或带 IP 钉住的强制连通性测试。
  ③ 本网络下 `8.8.8.8`/`119.29.29.29`/`180.76.76.76` 的 DoH **均不可达**，故 DoH 源表须为**实测可达的 IP 字面量**多源（不可只押一个）。

- **残余风险（2026-10-07 评审登记，如实申报）**：本机制的探测**仍从本机发起**，只是钉住 IP 并禁用系统代理。这能破**本机 DNS 接管**与**代理式 MITM**（本次事故的两个已列成因），但**破不了 TUN / 透明重定向式 MITM**——若用户把自签 CA 装进系统信任库，请求会被解成错误页，而"拿到任意 HTTP 响应即算通"会把错误页读成"已验证"。**已于 2026-10-07 加一道廉价判据**：探针改请求看板地址、要求 **HTTP 200 ＋ 响应带 MAM 特征头 `x-mam-reach: board-1`**（该头只在看板入口成功分支写入，产物缺失的 404 分支不带）；代理拦截页 / 门户页 / 自签 CA 错误页都不满足 → 如实判"尚未生效"。**诚实边界**：这不是鉴权或密码学证明——知道特征值的 MITM 仍可伪造；它只把"任意响应即算通"这个过宽口径收紧到"必须像 MAM 的看板"。
- **边界**：本机制**只覆盖"解析记录尚未发布"这一类失败**（用户 2026-10-06 确认：新增通道时解析记录需要一段时间才生效，故"暂时连不上"只应出现在这种情况）——它**不**覆盖其他故障（证书错误、上游限流、本机进程崩溃）。机制依赖一个**外部解析服务**（选型在实施计划里定，须满足"可降级"）；**外部服务不可用时不得据此判定地址可用**——宁可报"尚未验证"，也不谎报"已生效"。

### C4 · 通道区重排为 4 张卡

- **需求**：新通道加入后，**对外通道恰好 4 张卡**；**本机不再显示地址、也不再占卡片位**。
- **现状问题**：通道区现有 4 张卡「本机 / 局域网 / 临时通道 / 固定网址」，其中本机默认开启且不对外，却与三条对外通道并列；新通道再加一张会到 5 张，既拥挤又语义不齐。**而且现有卡片与宪法口径本就不一致**——宪法四模式是「直连域名 / named tunnel / quick tunnel / Tailscale」，而 UI 把「本机」当成一张卡、却**完全没有 Tailscale**。
- **目标形态（用户 2026-10-06 指定）**——注意 **(3) 是把现有「命名隧道」卡**改名为「自有域名」**，不是新增**：

  | #   | 卡片                         | 说明（UI 文案方向）                                  | 要自有域名? |
  | --- | ---------------------------- | ---------------------------------------------------- | ----------- |
  | 1   | **局域网连接**               | 同一 WiFi / 网线接入；**本机访问也走这张**（见下条） | ❌          |
  | 2   | **临时隧道**                 | 零配置即用，地址每次重启会变                         | ❌          |
  | 3   | **自有域名**                 | 永久地址，需你自己的域名                             | ✅          |
  | 4   | **外部域名（免域名）**〔新〕 | 永久地址，不需要域名                                 | ❌          |

- **恰好对上宪法四模式**：局域网连接 = 直连域名 / 临时隧道 = quick tunnel / 自有域名 = named tunnel / 外部域名（免域名）= Tailscale。**补齐了长期缺失的 Tailscale，也移出了本来不是通道的「本机」**——这是本次重排的额外收益，不只是视觉腾地方。
- **本机访问怎么走（用户裁决）**：**不再单独显示本机地址**。要从本机访问，就用**「局域网连接」那张卡显示的地址**——**前提是该开关已打开**（服务只在回环监听时，局域网地址不可达，故卡片必须显式呈现开关状态）。「本机」在界面上降为一个开关状态说明，**不是一张卡**。
- **命名要解决的一个误导**：(3) 与 (4) 都是"永久地址"，差别只在**要不要你自己有域名**。副标题必须把这点写死（「永久地址，需你自己的域名」/「永久地址，不需要域名」），否则用户会困惑两者区别。
- **新卡片的三种状态**：**未安装**（一句价值主张 + 「一键配置」按钮 → 进入 §C2 向导）；**配置中**（向导进度，**每步都能看出卡在哪**）；**已配置**（固定地址 + 二维码 + 复制 + 运行态）。
- **线稿是硬契约，必须同步改（2026-10-06 用户确认可改）**：项目声明「UI 唯一契约 = `docs/engineering/architecture/wireframes/2026-09-17-remote-settings-redesign.html`，**实现与线稿不一致即缺陷**」。线稿现在画的是**旧 4 卡**（本机 / 局域网 / 临时隧道 / 命名隧道），因此**本项的前置是同步更新线稿**：卡片改名、**本机地址整行删除**、卡片三态、以及文件区的带宽提示与进度条，都要先在线稿上落地并**在浏览器直接打开该文件预览**（自包含单文件，`file://` 即可；项目里「localhost 8940 可预览」的说法**经查无脚本支撑**——全库仅 M5 计划一处孤证、`scripts/` 与 `package.json` 无 HTML 预览命令、实测该端口连接被拒）。**顺序是先改线稿、再改实现**（反向做会产生一段"实现与线稿不一致"的窗口）。
- **边界**：带宽与进度提示**不属于通道卡片**，属于文件面板 / 附件区（§C5）——"慢"只在用户真去传文件时才痛。

### C5 · 带宽如实告知、进度可见与满速升级路径——一等需求

> **用户原话（带宽）**：「在现在的设计阶段，就需要探测一下它的带宽问题……如果带宽不满足，那么在传文件的地方，需要加上一个备注，说明是以什么样的形式受限。」
> **用户原话（进度）**：「如果比较慢的话，用户上传文件的时候应该知道进度吧。比如上传图片或者 10 兆左右的 PDF 大文件，是不是应该有一个上传的进度条，让用户能看见？」

- **需求侧（已实测）**：

  | 交互             | 单次字节                              | 方向 | 出处                                    |
  | ---------------- | ------------------------------------- | ---- | --------------------------------------- |
  | 移动端首屏       | 263 KB（gzip 后）                     | 下行 | 实测构建产物                            |
  | 看板 / 会话刷新  | KB 级                                 | 下行 | —                                       |
  | 文本 / 代码预览  | ≤ 500 KB                              | 下行 | 单文件上限                              |
  | **图片预览**     | **≤ 5 MB / 张**                       | 下行 | 单文件上限                              |
  | **手机上传附件** | **≤ 20 MB / 个**                      | 上行 | 单文件上限                              |
  | 视频             | **无专门通道**——最多作为 ≤20MB 的附件 | 上行 | 移动端预览仅支持图片/HTML/Markdown/代码 |

- **供给侧（已实测，2026-10-06，手机蜂窝 → Funnel → 本机）**：

  | 方向     | 实测            | 备注                                          |
  | -------- | --------------- | --------------------------------------------- |
  | **下行** | **≈ 1.8 Mbps**  | 6 秒持续下载，客户端实收 1.33 MB              |
  | **上行** | **≈ 0.8 Mbps**  | 手机上传，服务端实收 0.98 MB / 10.2 秒        |
  | 并行两路 | 合计 ≈ 1.1 Mbps | **低于单路** → **总容量受限，不是按连接限速** |

  调研对照：官方从不公布数字（只写"不可配置的带宽限制"）；2023 年有一例轶事实测约 1 Mbps；Tailscale 自家博客（2026-01）实测其托管中继约 2.2 Mbit/s，官方措辞 "severely throttled"。**本次实测落在同一量级，"Funnel 约 1–2 Mbps"由此从推测升级为实测。**

- **影响量化**：

  | 交互               | 需求    | 实测下耗时    | 判断                    |
  | ------------------ | ------- | ------------- | ----------------------- |
  | 移动端首屏         | 263 KB  | **~1.2 秒**   | ✅ 可接受（之后有缓存） |
  | 看板 / 会话刷新    | KB 级   | 瞬时          | ✅                      |
  | 文本 / 代码预览    | ≤500 KB | ~2.3 秒       | ✅ 可接受               |
  | **图片预览**       | ≤5 MB   | **~23 秒**    | ❌ **不可接受**         |
  | **附件下载**       | ≤20 MB  | **~1.5 分钟** | ❌ **不可接受**         |
  | **10 MB 文件上传** | 10 MB   | **~100 秒**   | ❌ **不可接受**         |
  | **手机上传附件**   | ≤20 MB  | **~3.3 分钟** | ❌ **最差**（上行更慢） |

  **结论：Funnel 撑得起 MAM 的主用途（看板 / 文本 / 审批 / 通知），撑不起文件能力；且上行比下行更差——手机发附件是最痛的场景。**

- **四层对策**：
  1. **主用途不受影响**：看板、会话内容、审批、问答都是 KB 级，1.8 Mbps 充裕（首屏 1.2 秒）；
  2. **文件区就地备注（用户点名要求）**：MAM 检测当前访问是否走受限通道，若是，则在文件面板与附件区显示提示，并**按文件大小预估耗时**（例：「当前通道带宽受限：20 MB 附件约需 1.5 分钟，手机上传约 3.3 分钟」），同时说明**这是通道限制、不是故障**；
  3. **进度可见（用户点名要求）**：**上传与下载都必须有进度反馈**——已传字节、百分比、预估剩余时间；受限通道下的预估按本通道实测速率计算。**理由**：本通道下 5 MB 图片要 ~23 秒、10 MB 上传要 ~100 秒，**没有进度用户会以为卡死**（本条即来自实测过程中的真实反馈：探针当时没有进度，用户无法判断是否在传、传到哪里）；
  4. **满速升级路径（比静态备注更有用）**：手机装上 Tailscale 后走**尾网直连**，带宽高出 1–2 个数量级且全程私密。文件区提供就地指引，把"慢"变成"可以更快"。**该路径不占卡片位**（仍维持 §C4 的 4 张卡），只在用户真正遇到大文件时就地出现。
- **方法论教训（写下来以免后人重踩）**：

  > **不能用"服务端发出量 ÷ 耗时"测这条链路的带宽。** 中间链路有 MB 级缓冲，服务端把数据写进缓冲区就"完成"了，而数据还在路上。本次实测中服务端口径 2.93 Mbps、客户端实收 1.76 Mbps——**服务端口径高估 66%**。更早一次用"固定体积 + 长度声明"的测法甚至量出 **24.32 Mbps**，是纯伪影。
  > **正确口径只有两个**：下行用**客户端实收**÷时间；上行用**服务端实收**÷时间。
  > 另：并行两路合计**低于**单路，说明是**总容量封顶**，加连接不会变快。

- **边界**：文件能力在本通道上不可用是**既定事实**（非待验项）；进度条是**如实反映**，速率未知时显示已传字节而非假百分比；测法上**必须用蜂窝数据**——同网访问会绕近路，测出来是假数字。

### C6 · 与第一部分的衔接：外部设备体验零变化

- **配对来源记录的语义（2026-10-07）**：`origin_ip` 列 = **最近一次配对时该设备的真实公网出口来源**（花名册与审计用，§G5 要求）；而**去重指纹**改用**原始 TCP 对端**（稳定、不可伪造）。二者刻意分离（`persist_device_with_fingerprint`）——**同一浏览器换网络重配仍是"覆盖原行"，不新增设备、不占名额**；这是对 §G5 改造中"指纹含真实 IP 导致换网络就新建行、很快占满设备名额（默认上限 10，见 `max_devices_from`）"的修正。
- **载荷契约（2026-10-07 补）**：`tailscale.reach` 与 `error` 一样**受 `enabled` 门约束**（未启用一律写 `unverified`）——否则竞态下会把**刚被用户关掉的通道**渲染成「恢复中」且滞留。`store_tick` 的后端相位写入必须与快照在**同一把 `DESIRED` 临界区**内。
- **托盘口径（2026-10-07 补）**：判据是 `matches!(Verified)`——**非 `Verified` 一律不上托盘**（含 `record_pending` / `recovering` / `failed`）。
- **需求**：本次接入新通道，**外部访问设备的体验一字不改**——首次连接需输入一次访问密码，此后在有效期内免密码。
- **对齐结果**：这正是现有设计，本设计不改动：

  | 场景                 | 现在                     | 本设计之后                     |
  | -------------------- | ------------------------ | ------------------------------ |
  | 外部设备**首次**连接 | 输入访问密码             | 输入访问密码（不变）           |
  | 外部设备**后续**连接 | 凭设备凭据免密（180 天） | 凭设备凭据免密（180 天，不变） |
  | 设备满员 / 吊销      | 桌面端手动腾位           | 不变                           |

- **唯一被改的是本机**：从「免密」变为「需输入一次访问密码」。**这正是用户的本意**（不论本机还是远端都应输入密码），故不构成体验落差；本机访问走 §C4 的局域网地址。
- **边界**：本通道**不引入任何新的鉴权语义**；新增通道在门禁侧**零接线**（§G1 推论②）——**这正是先做第一部分（前置）的收益**。

## 5. 非功能需求

- **安全**：不变量 §G1 为最高约束；新增通道**零门禁接线**；403 不泄露凭据状态；配对入口保持既有防预言机与滑动限速语义；**来源信息只进限速与审计，永不进放行判定**（§G5 要求 4）。
- **地址稳定性**：**核心承诺**——机器重启、MAM 重启、断网恢复后地址不变。
- **首次配置**：**一等需求**——人工确认数 **macOS ≤4 次 / Windows ≤3 次**；全程无命令行、无文档查阅（§C2）。
- **隐私**：中继不可解密（TLS 终止在本机）；项目方不经手任何流量。
- **兼容**：已配对设备凭据继续有效；历史展示数据保留可读；**通道配置、隧道指向、端口全部不变**（这是选零豁免而非双监听器的关键收益之一）。
- **性能**：删除每请求的系统连接表扫描，回环请求路径变短。
- **可维护**：净删代码大于净增；三平台鉴权逻辑完全同构，消除平台落差这一类缺陷。
- **可用性依赖**：Tailscale 服务与用户 tailnet 账号；**不作为唯一通道**（宪法原则 2）。
- **合规**：只从官方源按需下载；**不打包、不再分发**第三方安装包（§C2）。
- **诚实**：受限通道下必须**如实提示**，不得让用户误判为故障（§C5）；地址未验证通过不得自称可用（§C3）。

## 8. 已知限制与待验项（如实申报）

1. **本机免密被撤销**（§1.5 ②）：推翻 M5 A3 的一条裁决。代价是本机首次访问需输入一次访问密码——**用户本意即"不论本机还是远端都应输入密码"**，故不构成体验落差。
2. **同机反代免密洞在本设计前真实存在**：已实测证实，随 §G1 结构性消失；实施时须把该实测用例转为**长期回归锚点**（由红转绿）。
3. **来源标注精度下降**：失去连接归属实锤后按域名推断。纯装饰用途，可接受。
4. **带宽已实测：下行 ≈1.8 / 上行 ≈0.8 Mbps**，解决方案是 §C5 的三层对策。**文件能力在本通道上不可用是既定事实，不是待验项**。
5. **四步物理上无法自动化**（§C2）：安装授权、macOS 系统扩展批准（**Windows 无此步**）、浏览器登录、首次 Funnel 批准。目标是压到 **macOS 四次 / Windows 三次**确认，**不是消除它们**。
6. **国内可达性：本次实测通过，但仍不承诺**。实测环境为中国移动蜂窝 + 家用宽带：控制面登录、DERP 中继（最近东京 49 ms）、公网 DNS、端到端 HTTPS 全部正常，**"国内被墙"在这次没有成立**。但各省各运营商表现不一，且首次开启后公网 DNS 记录可能未发布（§C3）——故仍**不能作为唯一通道**。
7. **Tailscale 官方文档自相矛盾**：其 macOS 变体对比表称 Funnel 在 App Store / Standalone 版不可用，而源码显示该限制**只针对文件/目录伺服，端口伺服可用**（本设计的用法是端口伺服）。已依源码与社区实证判定可用，但**实施时须实机复验**。
8. **「阻止传入连接」的写入方式待实测**：**读取已实测**（偏好项 `shields-up`，本次实机读到其当前值为关）；但**写入**（程序化关闭它）**尚未实测**——实施时须先实机验证再接线。
9. **Funnel 仍为 beta**：上游可能变更；卡片文案不得承诺 SLA。
10. **一次性登录无法省略**：受"永久地址必须由持有域名的机构签发"这一物理约束，任何免域名方案都要求用户在某个服务商处有一次身份。这是本设计**不可能消除**的代价，只能压到一次。
11. **限速分桶的 Host 信任只对「真过 CF 边缘」的流量成立（2026-10-07 复核补记）**：规则②把「Host 命中已登记域名」当作"确实经该通道进来"的证据，该等价**只对真过 Cloudflare 边缘的流量**成立——**同机转发**（同机反代或任何能触达回环端口的转发）可**同时**伪造 `Host` 与 `CF-Connecting-IP`，从而**自选限速分桶**。影响**有界且只限限速**（放行判定只看设备凭据 §G1，请求头进不了鉴权）：每次失败仍记全局桶 ⇒ 单攻击者额度从「每来源 5 次/窗口」退化为「全局 50 次/窗口」；4 位 PIN 全量 10⁴ 组合最坏耗时 **≈2×10⁴ 分钟 → ≈2×10³ 分钟**（10 倍）；且单伪造者可填满全局桶 ⇒ `/pair/pin` 对所有人锁 10 分钟（可按窗口循环重放）——**配对入口的有界可用性代价**，已配对设备读写不受影响。**威胁模型缓和**：利用它必须先能触达回环端口（即已在机器上，而那时配对 PIN 就显示在应用里）。**本批不加固的理由**：隧道流量到达本地端口时 TCP 对端**恒为回环地址**（cloudflared/tailscaled 都是本机进程），"回环来源一律不信 Host"会让真隧道流量也全落全局桶，**正好退回 §G5 要修的桶塌缩**；真修法需更强的来源证据（如连接器注入只有它知道的共享密钥头——**能力待核实**），列为后续可选、**不在本批**。
