## 1. 目标与需求来源

### 1.1 要解决的问题

1. Desktop 更新频繁，不能依靠维护者对每个完整 build 手工验证所有能力，才能让手机继续处理问答和审批。
2. “兼容/已验证”会话徽标过于粗糙：消息可发不代表计划模式、审批、答题、权限切换全部可用。
3. 当前详情页将能力横幅、队列提示、模式、权限、不可用错误及发送回执堆成多行，挤占手机正文空间。
4. 用户用普通正文回答后，Desktop 原生 Question 仍挂着；正文继续生成不能证明原问题已正式解决。
5. 各工具已有部分内容展示、终端应答和降级机制，但缺少统一的交互分类、回退语义与卡片生命周期。

### 1.2 用户已确认的方向

- 保持控制原来的 Desktop 会话，按功能自动适配；未知 build 不长期被整体限制为只能发消息。
- **本次明确不采用 Happy 式 app-server 托管方案，不由 Tuvis 启动/托管用于对话执行的独立 Codex 运行时，也不自动迁移或接管到另一宿主。** Happy 仅提供 UI、交互生命周期和协议经验参考。Desktop 自身内部使用 app-server 不属于 Tuvis 新增托管路线。
- F01—F08 为本批必做；F09—F11 先评估可得性与难度，难度过高则放第二批或 tracking 待办，不阻塞首批交付。
- F12—F14 的多工具架构与治理改造本批不做，后续归口 #174；已有 Codex 动作安全、最小诊断与本批回归验收不因此取消。
- 不支持的操作不常驻显示；支持的正常显示；自动适配提醒集中、轻量、可查看详情。
- “内容可见＋有可靠处理出口”作为多工具通用回退方向；普通文字不代替正式审批。
- 先由用户确认本说明书，确认后再编写执行计划。

功能中的细化选择属于本稿提出的默认设计，随本稿一起待确认；不将作者补充写成用户已经逐条拍板。

## 3. 共用设计原则

### 3.1 能力与证据分开

操作能力至少拆分为：消息发送、命令审批、文件审批、阻塞问答、异步问答、请求取消、回合打断、计划模式读取/设置、权限状态读取/设置。权限请求应答与整个线程权限切换也分别建模。

每项同时表达三类事实：

| 维度 | 表达内容 |
| --- | --- |
| 是否已接入 | Tuvis 是否具备该操作的适配器和响应构造器 |
| 当前能否操作 | 当前契约、设备授权、目标、状态及能力策略是否允许 |
| 证据来源 | 随包已核验、当前契约匹配、本机真实操作成功，或尚无证据 |

“没有实现”“上游不支持”“尚待识别”“临时断链”“被当前审批状态拦截”不能合并为一个不可用值。某次操作成功不能提升其他能力；某次网络故障不能抹掉历史成功。

### 3.2 当前契约识别，减少逐 build 手工登记

版本号保留为身份、缓存和诊断依据，不再单独承担所有操作的总准入门。

未登记 build 的非普通消息操作，必须先取得**当前能力的契约匹配证据**：

1. 当前实际运行目标及完整指纹可归因，目标线程和 owner 唯一。
2. 适配器存在已核验的契约分支；当前方法及版本可由当前运行包或协议声明确认，与该分支匹配。
3. 请求、响应及必要状态字段可按当前 schema/已核验解析器校验；枚举、选择数量和作用域不靠猜测。
4. 操作关键约束可以满足，例如 requestId 原样回送、问题身份绑定、expectedTurnId 安全阀、权限不扩大。

方法名存在、build 数字相近、只有 CLI schema 成功或其他用户的报告，均不单独足以开放未证明的 Desktop 写路径。协议没有声明的信息，不假造“能力协商成功”；可只读解析当前安装包的契约证据。

全部条件成立时，自动适配可以开放**对应已实现操作的用户主动尝试**；首次真实操作承担效果验证，不额外创建测试消息、审批或权限请求。界面仍标自动适配，不把契约匹配写成该 build 已全部真机验证。

约定不匹配时只降级受影响能力。能力语义发生未知变化时暂停该能力，保留消息和其他已支持操作；不得为追求“自动”绕过上游权限体系。

### 3.3 缓存、触发和关闭

- 复用既有完整身份指纹、能力账本、连接代际隔离和成功证据持久化；再按能力与契约规则版本区分记录。
- 新 build 自动进行所需只读识别，能匹配已实现契约即可继续工作，不要求用户安装历史版本。
- 旧指纹成功不能直接装入新身份；同契约复用也须重新建立当前身份与该契约的匹配关系。
- 相同身份、相同能力成功后不重复完整探测；实时目标、卡片和权限核对仍执行。
- 暂时失败沿用既有退避和下一次用户触发，不用持续后台重探或重复写入试探恢复。
- 关闭自动适配立即阻止新的未知版本适配操作；已发动作仍可有界收尾和只读核对。重开复用有效证据，不自动发送草稿、批准请求或恢复暂停队列。

### 3.4 事实来源

Desktop 以原生请求、结构化消息、RPC 回执及同目标新鲜投影为依据；终端继续遵守宪法和项目已有屏读权威纪律。只读历史正文不单独证明当前仍有未决请求。

原生阻塞请求与异步 Question 都可呈现为卡片，但不得合并成相同底层答题接口。统一的是产品状态与动作语义，响应仍由各适配器负责。

## 4. 逐功能需求与验收

### F01 · 逐操作能力识别与放行

**用户行为：** 打开一个新版本会话，不需手动找实验开关。可安全识别的能力正常出现，其余进入自动适配详情。

**要求：** 后端输出有效操作集合，详情区分未接入、未识别、不支持和临时异常；前端不能按工具名字自行生成一排操作。所有直接 HTTP 写入口与按钮使用同一策略。高风险功能不因消息可发送而连带开放。

**验收：** 未知 build 命令审批可用、问答未识别、权限未接入时，三个状态独立；只读识别不执行会话、发消息、批准或变更权限。新连接旧异步证据不能解锁新卡；断链不消除持久成功。协议漂移只影响对应操作。

### F02 · 原生阻塞选择题正式作答

**用户行为：** 手机显示当前真实问题和选项；按上游支持的单选、多选、自由回答规则输入，一次正式提交。

**要求：** 答案绑定原 requestId、题目 ID 和内容上下文；禁止多答、漏处理必答项、未知题目、非法选项或不允许的自由文本。多题同属一个请求时按其响应契约统一提交，不擅自拆成多个普通消息。提交走原请求响应路径，不进入普通消息忙态 FIFO。

**验收：** 选择答案后原 Desktop 请求真实解决，手机与桌面收敛；两端同时作答只产生一个有效结果；重现同题文或复用 requestId 不能复活旧 token。上游未结束时不能仅凭点击就把卡标已答。

### F03 · 异步 Question 正式作答

**用户行为：** 类似本轮图 3 的 Question 在手机可正式选答；回答后原 Desktop 卡不继续作为未答问题挂着。

**要求：** 从 `AgentMessage.questions[]` 等已核验结构提取问题、所属回合、消息/题目身份。复用官方客户端实际使用的结构化回答语义；`questionItemId` 等字段只能取自当前有效结构，不能从题干猜 ID。当前包中的结构化答复标记只是候选契约，实施时仍须完成同线程闭环验证。

若原生客户端通过普通输入或 steering 封套承载正式答案，Tuvis 建立窄化的“正式答题”动作：只携带该题目的合法回答，绑定原线程/回合，不变成任意正文的审批绕行口。存在另一个阻塞审批时，除非上游契约明确允许并已核验，两条路径不能混用；优先处理阻塞请求。

**验收：** 使用当前目标 macOS build，在隔离会话回答选项、自由回答，均关联正确题目并让原卡得到真实处理。普通“去旅游”与正式答题的状态区别可复现；同名题、多题、多回合不串答；消息继续生成不单独作为已答证据。仅有正文回退不能宣称本功能完成。

### F04 · 命令与文件审批自动适配

**用户行为：** 当前请求可处理时，看到具体操作摘要与真实可用决策；主动点击允许或拒绝。

**要求：** 复用现有 schema 和 pending 决策词交集，不退回“空交集开放全部”。只提交原请求允许且适配器已实现的决策。首批只提供单次允许、拒绝及上游明确支持的取消，不自动增加会话级允许、策略修订或额外权限。

`decline` 与 `cancel` 含义不同：只有结束回合的取消可用时，必须标明“拒绝并中止本轮”，不能统一包装成普通拒绝。请求展示为问题形式但实际承载 MCP/系统批准时，也保留审批语义。

**验收：** 未知 build 同契约下允许、拒绝闭环成立；显式空列表、对象扩权词、过期 token、换 owner 均不能写出。回执不确定时保持待确认，不能重发批准或假报完成。

### F05 · 卡片生命周期、清理与多端同步

**用户行为：** 活动区只显示仍需处理的卡；已结束卡进入历史，不长期顶在输入区。

**要求：** 最少区分待处理、提交中、结果待确认、已回答、已拒绝、已取消、已由上游结束、状态无法确认。原因未知的请求消失写“请求已结束”，不能擅自写“已回答”。

正式解决、取消事件、同代新鲜请求列表和异步题目关联结果共同驱动状态。异步答案至少要看到原线程中正式结构化答复的准确关联，且符合上游的已处理判据；不使用文字相同、消息数增加、模型说收到或任意 revision 增加代替。

回合终结使未答异步题失去活动资格时，标“回合已结束，未记录正式答复”。若上游带 `autoResolutionMs`，展示上游时限；本地到点不能直接假定请求已解决，更不能自行批准或打断。没有时限时不创造定时清卡副作用。

多请求按阻塞审批优先、其余按上游稳定顺序提供切换；同一请求的多题保留一个完整表单。活动区不把所有只读旧卡无限堆叠，历史仍可回看。

**验收：** 桌面处理、另一手机处理、上游取消、回合中断/结束后当前卡准确收敛。断链/stale 只撤回操作资格，不假装解决。重连、回到详情与已提交结果丢回执均能只读纠偏，不因历史重放复活旧卡。

### F06 · 安全摘要与普通意见回退

**用户行为：** 不能正式操作时仍能读懂在等什么，并能选择真实可用的下一步。

**要求：** 能解析的题干、选项、命令或文件摘要可见；不能安全解释的字段不整份 dump。缺失内容如实占位，不让模型补猜。历史摘要标明来源和是否仍待处理。

正文回复只表示普通意见；非阻塞提问可按正常输入规则发送，但未取得正式关联时不能宣称原卡已答。真正阻塞审批在场时继续拦普通消息并保留草稿；可正式应答则用卡片，否则用户可选择可靠取消/中止，再表达意见。通用回退不提供“输入允许就批准”的猜测规则。

**没有可靠远程处理动作时：** 明确显示“此请求需在原 Desktop/终端处理”，提供“刷新状态”（只读）并保留摘要、待处理入口和草稿。摘要可以折叠，未决状态不能被清掉；不能为了提供出口而临时拼接取消、按键、无头或自动中止。这里承诺不被前端错误状态困住，不承诺上游未开放的请求一定能远程解决。

**验收：** 未支持交互有摘要与真实处置指引，正常正文不变成批准；阻塞 pending＋idle 仍零普通投递，unsupported pending 同样生效。正式回应/取消/中止均不可用时，回原端指引和只读刷新可用、待处理标记持续保留。未知 kind 不泄露凭据或原始敏感对象，不伪造可取消动作。

### F07 · 取消请求与打断回合

**用户行为：** 优先使用上游确实支持的单请求跳过/取消；只能结束回合时明确选择“中止本轮”。

**要求：** “收起”只改变本地显示，不影响执行，不得冒充取消。请求取消能力与回合打断能力分开识别。未知 build 可在当前打断契约匹配后开放显式打断，不要求完整 build 手工登记，但 `expectedTurnId`、owner 及版本安全阀不减弱。

打断先建立可靠暂停保护；完成、拒绝、未知结果准确区分。旧队列保持暂停，仅用户明确恢复或授权本条先发；不自动续跑或重发被中断工作。只读识别不得实际发送测试打断。

**验收：** 取消不影响无关请求；打断只作用目标回合，缺安全阀零指令。终态先于回执、并发打断一成一败、数据库失败、结果未知均不放出旧队列。两个有效设备看到暂停变化，无 Desktop 新帧也能收到通知；不存在调度广播自激。

### F08 · 一行工具栏与能力详情

**用户行为：** 无异常时，输入区上方只有一行紧凑工具栏；不再常驻多行不支持说明。

**要求：** 常驻行只放有效的模式/权限入口和轻量“自动适配”入口；不支持的组整组隐藏。没有可显示模式/权限时，只保留轻量状态入口，不留空白容器。不按整个工具名显示不可用按钮。

正常首次提示一次即可；能力详情包含版本、逐项状态、证据来源、当前限制和排障入口。当前部分可用时不显示暗示“所有功能已验证”的总徽标。未接入控件的理由放详情，不把点一次必报错的按钮当入口。

支持但暂时异常时，入口保留并就近提示；同一原因不在横幅、模式、权限、队列重复打印。发送待确认和真实待处理请求仍保留一条醒目可展开入口，不能为了收纳掩盖结果。问答/审批表单按需展开，不受“一行”限制。

移动端窄屏保持一行，次要入口收入“更多”；不缩小文字/触控目标来硬挤，不横向撑破正文。错误只在相关位置显示，修复后撤下；文案中英文同步。

**验收：** 以 360/390 CSS px 宽度及中英文检查：无异常常驻栏一行；仅模式、仅权限、都不支持、暂时断链、结果待确认分别有正确呈现。旧 TUI 模式/权限按钮不再误出现在未接入的 Desktop 操作上。

### F09 · 进入和退出计划模式

**范围状态：候选，先完成只读与隔离闭环评估，再决定本批或第二批。**

**用户行为：** 读取真实模式，主动切“计划/操作”；切换后知道何时生效。

**要求：** 使用已识别原生模式枚举和线程设置，不发送一句“请先计划”或聊天 `/plan` 来假装切档。退出计划不等于批准实施计划，不顺带扩大权限。

默认设计：忙态只允许设置下一回合模式，标明“下次生效”，不暗中打断当前工作；空闲时可更新下一次执行使用的实际设置。原生协议不能明确表达生效范围时，保持只读而不是猜。读取当前回合模式与下次模式不同值时分别表达，不能用一个已选按钮混淆。

**验收：** 计划→操作和操作→计划均可只读核对，下一次执行使用所选模式；没有为核对偷偷发测试消息。失败或 Unknown 不假装切换成功；换会话、两端竞争和重连不串档。

### F10 · 计划实施确认（候选）

**范围状态：先评估；其他 MCP 表单、URL 等扩展仅保留设计边界，不在本批统一接入。**

**用户行为：** 计划正文与“是否实施”请求可关联阅读，明白自己是在切模式还是批准执行。

**要求：** 根据真实 kind 保留语义，不能把计划批准自动归为普通选择题；答“开始实施”可能触发执行，须用该请求的正式动作。MCP 表单/URL 等扩展同理，按明确契约提供操作，未接入时安全摘要＋可靠出口。

**验收：** 计划退出、批准实施、拒绝实施、普通正文表达意见是可区分的行为；无受支持契约时不出猜测按钮，不用普通答题封套绕过审批。

### F11 · 权限状态与显式切换（后置）

**范围状态：先评估，默认倾向第二批/待办；是否纳入本批须用户另行确认。**

**用户行为：** 能读取时看真实权限；接入正式切换后，先看清授权范围再确认。

**要求：** 线程权限设置和单次权限请求分别适配。仅显示上游确实支持、当前设备有权选择的档位；展示本次变化的网络/文件访问范围、生效线程与回合，不强行套用别家“只读/默认/自动审批/完全信任”枚举。

自动适配只发现和恢复能力，不替用户授权。权限增加必须明确确认，不默认选择最宽权限。首个权限切换版本默认仅作用下一回合/明确线程范围，不在活动回合中静默扩权；组织策略禁止的档位不可选。不能证明范围时隐藏切换，详情解释。

**验收：** 读取、缩权、明确扩权、组织策略限制、取消确认、拒绝/未知结果分别可验证；不影响其他线程，不修改全局配置冒充单线程切换，不把批准一个命令升级成会话全信任。

### F12 · 多工具统一回退框架

**范围状态：本批不实施；以下为 #174 体系后续承接要求。**

**用户行为：** 不同工具的交互呈现和“未支持时怎么办”一致，同时尊重各自实际能力。

**要求：** 共用交互类别、状态、摘要和动作集合；各适配器分别提供原生请求响应、已验证终端应答或只读回退。必须分别声明能展示、能正式回应、能取消请求、能打断回合；不把其中一项推导成全部支持。

本批仅落地 Codex Desktop 所需的呈现和操作语义，不增加多工具统一框架或改造其他适配器。后续按 #174 逐项收编其他工具，分别登记已实现、未接入与验收范围；Happy 的托管能力和 amux 的终端按键机制不直接算作 Tuvis 已有能力。

**验收：** 至少覆盖原生请求、终端已核验卡片、只读未支持三类来源；未实现工具如实显示边界。终端继续服从屏读权威；正式扩展 Windows 注入/屏读时使用项目专属探测技能，不拿本稿替代活体取证。

### F13 · 动作确认、超时、幂等与草稿

**范围状态：不做跨工具抽象改造；以下是本批必须复用和保持的既有安全契约，不是另一个通用框架项目。**

**要求：** 复用既有动作账本和稳定操作身份。普通发送仍按 30 秒前台、120 秒有界主动收尾、10 秒只读核对；本稿新增交互写操作的前台等待也不得超过 30 秒，连接、必要识别和回执核对共用剩余预算。上游请求过期不通过重新提交规避。

写出结果未知时保留原动作和卡片的待确认状态，不自动重发批准、答题、模式或权限变化。新鲜同目标证据才能收敛，旧 owner/epoch 迟到结果只能归原动作，不能修改新卡或新模式。

同一交互的重复点击/多端竞争最多一个有效处理；不同答案不共用同一操作身份。草稿和交互草稿随真实提交版本关联；响应、切会话、卡片更新不清后来编辑的新内容。人工继续的后继五分类、唯一后继、旧写出权边界保留，不假报已发或已完成。

**验收：** 模拟回执丢失、30 秒到期、部分写入、旧 promise 迟到、重启、两设备提交和改稿；均不自动双投、不错题、不越权、不丢新稿。关键并发验收启动真实 scheduler/写出路径，不仅手工替换前端 props。

### F14 · 诊断、回归与能力记录

**范围状态：统一多工具体系归口 #174，本批只保留实现与探测所需的最小记录和回归，不新增通用采集/上报服务。**

**要求：** 本地记录工具/版本指纹、契约版本、能力、请求类别、失败阶段、耗时和确认结果，复用现有诊断接缝。用户报告和类似 issue 不能自动成为能力放行证据。

日志不默认记录整份问题答案、消息正文、命令、路径、凭据或数据库。用户实际阅读的卡片内容不等于允许外传；上报仍沿既有“本地记录、用户主动预览上传”设计，未部署服务不能宣称可提交。

**验收：** 用捕获并脱敏的结构化样本覆盖契约变化、缺字段、新枚举；当前 macOS 与可安排 Windows 分别实机验收。未测平台、未接入种类、失败和 Unknown 分开记录，不能把方法存在或合成输入写成真实操作通过。

## 5. 统一交互事实与生命周期

### 5.1 最小事实

交互身份应能定位工具、原会话、原回合、原请求/消息/题目；包含来源类别、内容上下文版本、owner/连接代际和当前状态。持久来源 ID 与本次连接 token 分开，断链重连不会因显示 ID 相同而复活旧写权限。

当前有效动作由后端统一给出。前端可维护本地输入和提交中样式，但不能持有另一套能力白名单、把本地已发送状态当上游真值。

### 5.2 状态转换与确认

| 事件 | 活动区行为 | 事实约束 |
| --- | --- | --- |
| 新鲜有效请求到达 | 展示可操作卡或摘要回退 | 当前身份与内容上下文明确 |
| 用户提交 | 提交中，抑制重复动作 | 不预先标已回答/已批准 |
| 写结果未知 | 保留待确认，提供只读核对 | 不自动重发、不按超时写未送达 |
| 准确关联的答复被上游确认 | 收敛为已处理并归入历史 | 不以模型正文或相同文字证明 |
| 另一端/上游清除 | 撤下活动卡并写真实或通用结束原因 | 不知道具体原因时不猜 |
| 断链/换代/内容改变 | 原操作资格失效，保留输入待刷新 | 新 token/新身份重新判断 |
| 用户收起 | 可折叠本地展示，保留待处理入口 | 不改变上游状态 |
| 用户取消/中止 | 等待目标请求或回合真实终态 | 不取消其他目标、不自动恢复队列 |

## 6. 模块职责与兼容边界

| 层 | 设计职责 |
| --- | --- |
| 能力协调器 | 当前指纹与契约匹配、成功证据、运行健康、逐操作有效集合 |
| 交互投影器 | 区分原生请求/异步 Question/计划确认，输出安全内容、身份、状态和合法动作 |
| 目标工具适配器 | 构造原协议响应、核验作用域和身份、解包回执及解决/取消事件 |
| 动作编排 | 预算、稳定身份、写出资格、幂等、结果核对、队列和草稿归属 |
| 移动端共用 UI | 一行工具栏、卡片、摘要、详情与风险提示；不自己决定权限或补猜协议 |

本表是 Codex Desktop 本批内部职责，不是多工具架构重构任务。复用现有 `codex_desktop_ipc`、控制 router/queue、探测与动作账本、`useCodexThread`、`PendingRequestCard`、`CodexQueuePanel`、`MessageComposer` 和 `ModeBar` 的对接基础；不把详细新函数签名、表结构或任务分派提前当成执行计划。

发布、GET 首快照和提交守卫必须同源；内容版本和传输顺序保持分离，不给旧内容盖更新序号。只在有效状态变化时推送，不产生“收到通知→结算→重发相同通知”的自激；手机也不能依赖桌面偶然再发一帧才能刷新本地控制状态。

### 6.1 与既有文档的关系

- 保留 2026-10-23 设计的默认自动适配、Desktop 不转无头、审批硬门、30/120/10 秒、Unknown 恢复、成功证据持久化和隐私边界。
- 本稿批准后，取代下层旧文档中“所有新增交互仅精确 build 手工登记后开放”的总闸、异步 Question 永远不接入、以及无能力时仍显示旧 Desktop/TUI 按钮的口径；不是取消版本门控与证据要求。
- 计划/权限原先不在已审工作包 A 范围，本稿是明确的后续增量，不把旧代码复审记录改写为已经实现。
- 提及三期控制功能不改变宪法的分期归属；不扩展任意 shell、绕过 harness 权限或修改宪法。

## 7. 需求确认与交付验收

### 7.1 用户本轮需要核对的产品选择

| 项 | 本稿默认设计 |
| --- | --- |
| 接入路线 | 原 Desktop 原线程，**明确不使用 Happy 式 app-server 托管**；逐能力建立当前契约匹配 |
| 首批重点 | **F01—F08 必做**；缺闭环证据先验证，不拿只读回退充当必做功能完成 |
| 模式与权限 | **F09—F11 先评估**；可控项经用户确认纳入，否则第二批/待办。忙态只设置下回合模式，权限切换首版不在线扩权 |
| 未支持回退 | 安全摘要＋明确下一步，普通意见不假装正式处理 |
| 清卡 | 上游状态驱动；不靠定时批准/中止，收起与取消分开 |
| 视觉收纳 | 无异常一行；未支持组隐藏；真实待决/未知结果保留一条行动入口 |
| 跨工具范围 | **F12—F14 的统一改造本批不做，后续归口 #174**；本批既有 Codex 保障和必要验收保持 |

用户确认本稿无误后再写执行计划；对表中选择的修改直接更新本文。当前没有任务承包、开发步骤或自动启动授权。

### 7.2 必须保留的整体验收场景

1. 新 build 无需维护者新增完整白名单，当前已实现且契约匹配的能力可用；不匹配能力单独降级。
2. 当前目标 macOS build 上分别完成阻塞问答、异步 Question、命令/文件审批的真实原请求处理；未具备触发条件的种类如实待验。
3. 图 3 类旧 Question 能通过正式答题结束；普通正文继续、收起、取消、中止有不同且准确的状态。
4. 图 1 类无异常界面一行；未支持按钮不出现；发送待确认和真实 pending 不被藏掉。
5. 请求消失/重现、题干修改、跨设备先答、断链重连、回合结束和超时均不答错题、不复活旧卡。
6. 打断终态早于回执、并发打断、同值恢复、无 Desktop 新帧的暂停/恢复都能正确收敛；队列不自动放行、不自激。
7. 初始等待期编辑、人工继续在途编辑、多层 Unknown 和附件改动均不清新稿，未编辑的实际提交稿可正常清理。
8. F09—F11 仅在确认纳入的阶段完成双向切换、范围与读回核对；未纳入的功能不作为首批验收阻塞，也不显示假能力。
9. 所有真实写动作使用隔离会话并按授权执行；只读探测不能作为隐藏写测试。

## 10. 可得性、难度与设计前置验证

### 10.1 证据等级

- **已有实现/真实闭环**：仓内生产路径或历史真实 wire 证明了方向；不同平台/build 仍须核对，不能宣称当前增量已验收。
- **静态可行方向**：当前安装包或外部参考源码存在相关结构/处理逻辑，但未完成目标 Desktop 的正式回应与状态回读。
- **未闭合**：关键路由、作用域或生效语义未确定，需要探测后再承诺实现范围。

难度是本次设计评估，不是工期报价或已有测试结论。这里不编写开发任务和执行步骤，也不自动运行写探针。

| 功能 | 当前可依靠的证据/实现 | 还缺什么 | 难度与判断 |
| --- | --- | --- | --- |
