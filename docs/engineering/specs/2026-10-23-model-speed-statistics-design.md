# 模型速度统计：统一口径与接入证据

> 日期：2026-10-23
> 状态：前序口径记录；已由 [2026-10-24 正式设计](2026-10-24-model-speed-statistics-design.md)及其逐源探测证据接续。本文旧样本仅作历史记录，不作为当前覆盖率或实施依据。
> 上位依据：`docs/MASTER-PLAN.md`；沿用既有用量及费用统计设计，本文不修改其 Token 记账语义。

## 1. 用户已明确的需求

在现有时间区间、工具与模型组合的费用统计基础上，一起展示：

1. 模型用时。
2. 工具调用用时。
3. 首 token 平均等待时间。
4. 流式输出速度（TPS），排除首 token 等待时间。

速度由「平均首 token 等待 + 流式 TPS」共同表达，不合成为单一评分。工具调用时间已有统计，应复用其采集能力。用户接受轻量 Hook 配置，不希望为此引入模型网关或要求安装插件。

## 2. 指标定义

对具有可靠计时的一次请求尝试，记请求开始为 S、首个有效输出到达为 F、请求完成为 E、对应输出 Token 为 O：

| 展示项            | 定义                                     | 单位             |
| ----------------- | ---------------------------------------- | ---------------- |
| 模型用时          | 有效模型请求处理时长之和；不包含工具执行 | 秒 / 分钟 / 小时 |
| 工具调用用时      | 已关联工具调用的有效耗时之和             | 秒 / 分钟 / 小时 |
| 首 token 平均等待 | Σ(F − S) / 有效首 token 样本数           | 毫秒 / 秒        |
| 流式输出速度      | ΣO / [Σ(E − F) / 1000]，时间戳以毫秒计   | tok/s            |

- 每次模型请求均有自己的首 token 等待；不是每个回合只取第一次。
- TPS 的分子、分母必须来自同一批有效样本；不可用全量输出除以部分样本的生成时间。
- 区间 TPS 按总 Token / 总生成时间计算，不直接平均各请求 TPS；首 token 等待则按有效请求样本数平均。
- 「排除首 token」指排除等待阶段，不是从输出计数中机械减去一个 Token。
- 完整、单次、无重试且时钟一致的请求，模型用时 = 首 token 等待 + 首输出后至请求完成的耗时。
- 工具参数的生成属于模型输出阶段；工具真正执行归工具阶段，不重复记为模型用时。

用户举例：累计总用时 40 分钟，其中工具调用 25 分钟，则模型用时为 15 分钟。这 15 分钟在计时完整时可进一步拆成等待与生成。显示名称不能把「模型 + 工具」之和也叫「模型用时」。

## 3. 技术建议与待验证边界

以下为实现侧建议，不冒充用户已经裁定的产品细节。

### 3.1 累计用时与回合实际经过时间

建议上述两项「用时」采用累计工作时长，与 DSH 累计模型 / 工具计时一致。并行请求分别累计，工具调用分别累计。其和不保证等于回合开始至结束的实际经过时间。

若另行展示回合阶段占比，必须保留每个事件的起止时间，在回合边界内计算时间区间并集、重叠与未覆盖时间。父级工具等待子代理时，其耗时可能包含子代理的模型、工具耗时，禁止父子阶段简单相加后声称完整拆分了实际经过时间。

不以「回合总长 − 工具累计耗时」估算模型用时。剩余时间可能包括调度、审批、Hook、重试退避与未观测阶段；没有对应事件时保留未归因，不命名为思考时间。

### 3.2 首输出与重试

- 首个协议事件不一定携带 Token。应验证原生首 token 字段或首个有效非空输出的语义，不能使用连接建立或空事件代替。
- 思考输出、工具参数与正文的边界因工具而异；输出计数与计时必须语义一致。无法分离思考时，不额外承诺纯正文 TPS。
- 重试应保留逻辑请求与尝试身份。总请求耗时可能跨越失败尝试、退避和成功尝试，禁止不核实就用总耗时减成功尝试的 TTFT。
- 一次性返回、缺失首输出时间、计时无效或疑似缓冲突发的样本，不应直接作为可信流式速度；具体判据需逐源验证。

### 3.3 缺失、区间与身份

- 不可得显示 `—`，不填 0。各指标保留自己的有效样本数、来源和覆盖情况。
- 模型用时与首 token / TPS 的覆盖可能不同，部分计时缺失时不强行声称全部时长已经拆完。
- 明细至少保留工具、模型、供应商证据、会话、回合、请求、尝试、开始 / 首输出 / 完成时间、输出计数及计时来源。
- 复用现有费用身份解析，不能把不同原始模型或测量口径悄悄混合。
- 区间边界、跨区间请求、进行中请求及父子代理包含规则，须在完整设计中对齐既有查询契约；不得按 Token 比例猜分跨界请求。
- 日志、数据库与遥测对同一请求的观测要去重或补全；性能采集不得重复增加费用账本 Token。

## 4. 本轮只读取证

### 4.1 ZCode

本机 `model_usage` 已有 `started_at`、`first_token_at`、`completed_at`、`duration_ms`、`time_to_first_token_ms`、`output_tokens`、`reasoning_tokens` 及逻辑请求 / 尝试 / 回合关联字段。

本次快照中，15,981 条已完成且输出大于 0 的请求，有 10,854 条具备首 token 等待和正的生成窗口，覆盖约 68%。该比例仅为本机当时的历史样本，不是产品兼容性承诺。

示例回合实际经过 14.463 秒，两次请求均标记 `GLM-5.3`、`max`：等待分别 5.032 / 2.629 秒，首输出后耗时分别 2.315 / 4.418 秒，输出分别 247 / 296 Token，合并 TPS 为 543 / 6.733 ≈ 80.6。此值不是 DSH 会话的速度，不能用于跨工具性能结论。

### 4.2 DSH

本地会话缓存 `sessionStats` 已有 `llmMs`、`toolMs`、`ttftMs`、`ttftSteps`、`decodeMs`、`decodeTokens`。

最近一份缓存的最近模型为 `glm-5.3-flash`：`decodeTokens = 86741`、`decodeMs = 1715530`，生成速度约 50.6 tok/s；含等待的模型步骤吞吐约 44.8 tok/s。最近模型不保证整份会话从未切换模型。

会话缓存的累计值不足以恢复任意区间、逐模型、逐回合明细，应从持久事件提取步骤与流时序。原生累计公式跨重试、取消与突发返回的边界也需要验证，不能直接将缓存当作统一明细契约。

### 4.3 原生遥测候选

- Claude Code：官方增强追踪的模型请求 span 提供请求耗时、`ttft_ms`、`first_content_ms`、输出 Token 与重试身份。需版本探测及本机实测，不以跨尝试字段直接相减。[官方说明](https://code.claude.com/docs/en/monitoring-usage)
- Codex：官方 OTel 支持请求、流事件、工具与回合计时。仍需验证目标版本是否提供足够关联与首输出证据；流事件自身的处理耗时不能当成生成耗时。[官方说明](https://learn.chatgpt.com/docs/config-file/config-advanced#observability-and-telemetry)
- 其他采集源尚未完成本轮计时字段与样本覆盖核查，不提前承诺四项全部可得。

## 5. 后续完整设计必须解决的事项

1. 逐源探测、样本覆盖、重试与流式判据；与既有工具耗时是否具有同一阶段边界。
2. 请求性能记录的存储、去重、缓存、水位版本、保留与迁移。
3. 时间区间、模型 / 渠道分组、子代理包含规则与现有查询的一致性。
4. 四项指标在原费用行的具体布局、有效样本提示与中英文字段。
5. 需要遥测时的本机接收器、轻量启用 / 关闭及启动生效规则；不改 API 路由、不要求插件。
6. 在影子数据目录验证；修改 `services/usage/**` 前先停止开发应用或隔离数据根，禁止实验采集写真实账本。
