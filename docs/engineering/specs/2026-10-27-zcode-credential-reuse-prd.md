# ZCode 记住授权与自动恢复连接 PRD

日期：2026-10-27。需求确认依据：用户已选择方案 A，并要求自动恢复连接、尽可能减少重复点击授权。阶段：用户已确认需求；设计与执行计划已编制，尚未开始产品实现。

本文件沿用项目现有文档目录；上位依据为 `docs/MASTER-PLAN.md`，协议与现有实现依据为 ZCode 统一远控 spec 和官方桥接合同。配套[技术设计](2026-10-27-zcode-credential-reuse-design.md)与[执行计划](../plans/2026-10-27-zcode-credential-reuse-implementation.md)据本 PRD 制定；不修改 MASTER-PLAN。

## 1. 目标

用户通过官方 OAuth 授权一次后，Tuvis 安全记住自己获得的账号 JWT；在 JWT 仍有效、远程接入开启且用户未主动暂停连接时，授权成功或 App 重启后自动恢复 ZCode 官方远控连接。

用户不需要每次启动都重新点“授权”，也不需要授权成功后再点一次“连接”。只有账号凭据确实失效，或用户主动忘记授权时，才需要再次授权。

## 2. 已确定的范围

- **只采用方案 A**：macOS Keychain、Windows Credential Manager、Linux Secret Service 保存 Tuvis 自己通过官方 OAuth 取得的账号 JWT。
- 复用现有链路：持久 JWT → Rust 内存授权态 → 每次连接现取 terminal token → 官方 relay → bridge／command／SSE。
- 改动集中在凭据生命周期、自动连接编排、授权状态展示及必要测试；不重写 relay 协议或现有消息控制能力。
- 首版沿用本机当前一个 ZCode 账号／一条设备链接，不扩展多账号管理、凭据导入导出或新的设置一级页面。

## 4. 功能需求

### R1 授权并记住

- 设置卡保留官方授权入口，清楚说明“授权后保存在本机系统凭据存储，下次自动恢复”；无需另加一套登录管理流程。
- 官方授权成功后，将账号 JWT 保存到当前系统用户的凭据存储；短期 terminal token 不持久化。
- 安全存储写入成功才显示“已记住授权”。写入失败时明确提示“本次可用，但未记住，下次可能需要重新授权”，不能假报成功。
- 凭据存储不可用时不写入普通配置文件或 SQLite。已有本次内存授权可以继续使用。

### R2 自动恢复连接

- 官方授权成功后，远程接入已开启且链接有效时，直接沿用现有 connect 流程连接。
- App 启动时恢复有效授权；远程接入已开启、链接有效且连接意图允许时，自动连接。
- 重新开启远程接入时，同样复用有效授权和既有连接意图。
- 网络暂时不可用时保留授权；可恢复故障采用有界退避重试，具体次数／间隔由技术设计确定，不重新打开 OAuth 页面。
- 全过程只保留一个连接尝试／一个上游连接；自动恢复只恢复连接和读取订阅，不重发历史消息或动作。

### R3 尊重用户的断开与接管状态

- 用户主动“断开”后暂停自动连接，记住该意图；重启 App 不擅自重新连接。用户显式“连接”后恢复自动连接意图。
- 普通退出程序、升级退出或远程停服清理，只释放运行时连接，不等同于用户主动断开。
- 远程总开关关闭时不自动连接；再次开启时按既有连接意图恢复。
- 收到 KICKED 时保持“连接被接管”，停止自动重连并记住暂停意图，直到用户显式恢复连接，避免与官方网页互抢。

### R4 换链接不重复授权

- 同一官方服务／账号下更新 sid／mid 时，作废旧连接、会话投影和在途动作，保留账号 JWT；允许自动连接时改连新目标。
- 删除链接后停止连接并显示“请配置链接”，保留账号授权，方便重新配置。
- 若目标设备不属于当前账号，显示相应错误；不把所有设备或连接错误都当成 JWT 失效。

### R5 失效与忘记授权

- JWT 已过期或申请 terminal token 时收到401：清除对应代的内存和持久凭据，显示“授权已失效，请重新授权”；不自动弹出浏览器。
- 断网、5xx、保险箱锁定或访问被拒，不作为账号撤销处理；保留仍可能有效的记录，显示真实原因。
- 设置卡提供“忘记授权”：断开连接、停止自动恢复、清内存并删除系统凭据，保留设备链接。
- 删除失败时先禁用恢复，明确提示删除未完成；迟到的旧请求、旧401或旧保存不得覆盖／删除／复活新授权。
- 普通退出程序保留已保存的授权。

### R6 状态清楚可理解

- 区分授权与连接：未授权、已授权未连接、连接中、已连接、暂时离线、被接管、授权失效。
- 安全存储锁定／不可用、保存／删除失败在原 ZCode 设置卡就地提示，不误写成“必须重新授权”。
- 不向前端或手机返回 JWT；手机只获得所需状态和现有控制能力。
- 正文、文件预览继续可用；持久化与自动连接不改变逐能力开放规则。

## 5. 最小技术边界

只增加一个凭据存储适配口及所需的生命周期协调，不做独立凭据平台。

主要落点：`services/zcode_control/auth.rs`、`hub.rs`、新增凭据存储文件、启动／远程开关接线、相关 DTO／IPC、`ZcodeRemoteSettingsCard.tsx` 和中英文案。必要时为既有构造函数注入适配口。

保留官方 OAuth 参数、terminal token 请求方式、relay／bridge／command／SSE 协议和既有目标、代际、pending、幂等、审计守卫。OS 存储操作放在状态锁外；沿用并扩展已有 epoch／取消纪律，自动化测试通过假存储注入，不能访问真实保险箱。

用户意图所需的非敏感偏好可进 settings；JWT 只能进入系统凭据存储和受控 Rust 内存。开发版与正式版使用分离的凭据命名空间；正常升级使用稳定标识。

## 7. 设计、计划与验证顺序

**无需重新进行官方协议探测。** 现有授权、JWT换terminal token、relay与控制合同继续作为依据，直接进入本功能的技术设计定稿，再写 TDD 执行计划。

设计阶段仅需核对所选系统凭据 API／Rust 适配库的版本、容量、平台支持及构建要求，不扩成一轮新的 ZCode 探针项目。Windows单条 CredentialBlob上限2,560 bytes，不能截断或假报保存成功；超限和存储不可用必须进入明确失败路径。

系统权限提示、真实重启恢复、锁定、签名升级、JWT有效期和实际容量属于实现后的集成／实机验收，不宣称已被现有协议探针证明。持久化不承诺一个月有效，也不延长 JWT 寿命。

待最终规划确认后，同步统一设计 spec、合同中的“仅内存”阶段约定及用户手册中英文。PRD只定义行为和验收；具体函数签名、依赖版本、重试参数、测试步骤放到设计／执行计划，不在此展开。
